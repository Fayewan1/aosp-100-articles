1. TL;DR

开机不是一件事，是一条链：bootloader 交棒后，一阶段 init 挂载分区，二阶段 init 解析 init.rc，属性系统起来，Zygote 预热，system_server 起服务，最后 sys.boot_completed 落下、桌面可交互。这条链上任何一环卡住，现象都表现为「开机慢」或「停在动画」，但根因位置完全不同。本卷 9 篇按链条顺序切开，每篇负责一段，能定位到具体文件与符号。导读只给地图和读法，不重复各篇论证。

3. 问题背景

现场常听到三种说法：「开机慢」「卡在开机动画」「进桌面后要等很久才能点」。这三种现象在日志里往往混在一起，因为从内核交棒到桌面可交互是一整条同步依赖链，任何一段慢了都会被用户归为同一句话。想拆开它，必须知道链条上有哪几段、每段的入口文件是什么、交接点由谁置位。本卷就是给这条链做分段编号。

4. 核心机制

4.1 概念与关系

链条的主干是串行的：bootloader 把控制权交出去，之后每一段都要等上一段完成某件事。有一处容易被读成「并列分支」，其实是派生关系——class_start main（把 zygote 这一类服务整体拉起）写在 on nonencrypted（init.rc:1227-1229）里，它的排入者不是 rc 里某条 trigger，而是 fs_mgr 的挂载返回码：设备侧 rc 调 mount_all 时，do_mount_all 内部的 queue_fs_event（builtins.cpp:583/:601）按返回码把 nonencrypted 排进队列（:583 对应 DEV_NOT_ENCRYPTABLE，:601 覆盖 FILE_ENCRYPTED/IS_METADATA_ENCRYPTED/NEEDS_METADATA_ENCRYPTION 三种加密情形——加密设备上这条分支必然被排入）。mount_all 通常挂在 on late-init 的 fs 段之后（本树 rootdir 的 rc 里没有这条命令，故本树不可达），所以这一支实际发生在 trigger post-fs-data（:537）与 trigger load-bpf-programs（:540）之后、trigger zygote-start（:543）之前——是先后关系，不是并列关系。

关键概念四个：一阶段 init 负责「盘有了」；二阶段 init 负责「规则有了」；属性系统负责「配置可查」；Zygote 与 system_server 负责「进程有了、服务有了」。前两段在 C++，后两段在 Java。

这一支的落点要记清：class_start main 不在 late-init 的 trigger 序列里，它在 on nonencrypted；而 zygote 自己那条路是 on zygote-start（init.rc:1091）里的 start zygote（:1094）单独点名的。两者不对称，不能当成可互换的两条路：on nonencrypted 没有属性门控，进队就执行 class_start；on zygote-start 段内第一行是 wait_for_prop odsign.verification.done 1（:1092），:1094 的 start zygote 要等这个属性到位才执行——所以「zygote-start 被触发」与「zygote 真的起来」是两个时点，中间可能隔着一段等待。

4.3 一个具体例子

以「属性从哪来」追一遍可以看清分段。二阶段 init 由 system/core/init/init.cpp 承载（共 1346 行），它解析 system/core/rootdir/init.rc（共 1320 行；本文件内 8 个 import、7 条以 service 开头的定义，被 import 引入的服务不在这个计数里）。里面 on late-init（init.rc:518）内先 trigger zygote-start（init.rc:543）拉起 zygote 与 zygote_secondary，之后还依次 trigger firmware_mounts_complete（:546）与 trigger early-boot（:548），最后才 trigger boot（init.rc:549）；被触发的 on zygote-start（init.rc:1091）里 start zygote 与 start zygote_secondary 在 :1094–:1095；这之前还有 trigger load-bpf-programs（:540），夹在 post-fs-data（:537）与 zygote-start（:543）之间。也就是说：late-init 先触发 zygote-start 拉起 Java 世界的入口，再发 boot 触发。这里要防一个误读——zygote 的起点是 on zygote-start 里的 start zygote（:1094，服务自身还带 class main），不是 trigger boot；on nonencrypted 那条 class_start main（:1228）是另一条能起同一类的路径。再往后，ZygoteInit.java（共 1009 行）跑完，SystemServer.java（共 3862 行）编排服务，最后由 ActivityManagerService.finishBooting() 设置 sys.boot_completed（ActivityManagerService.java:5991）与 dev.bootcomplete（:5992）。一条属性，跨了四个文件、三个语言边界。

7. 常见问题与误区

7.1 误区

  • 「开机慢就是 init.rc 写太多」：错。init.rc 只是规则文件，真正耗时在分区挂载、服务启动顺序与 Java 侧预加载。先量化，再定位。
  • 「Zygote 起来就等于系统起来了」：错。Zygote 只完成了 Java 运行时与预加载的准备工作，服务编排在 system_server 里才发生。
  • 「`sys.boot_completed` 置位就全部完成了」：看起来对，其实只表示开机广播阶段结束。桌面可交互还涉及后续的服务就绪与窗口动画退出。
  • 「一阶段和二阶段 init 是同一份代码」：错。两者同在一个目录，但入口文件与职责不同，一阶段只管把必须分区挂上。
  • 「`trigger boot` 就是 zygote 的起点」：错，这是把派生关系当成了起点。zygote 由 on zygote-start（init.rc:1091）里的 start zygote（:1094）拉起，而该段首行 wait_for_prop odsign.verification.done 1（:1092）会先卡一道属性门控，trigger zygote-start（:543）排在 trigger boot（:549）之前；on nonencrypted 里的 class_start main（:1228）是另一条按类批量启动的路径。看日志时若只盯 boot，会漏掉前面这条。
