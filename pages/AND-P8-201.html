1. TL;DR

init.rc 不是脚本，是声明。它只声明三样东西：服务（service）、动作（on）、导入（import）；什么时候执行由触发器决定，不由文件顺序决定。

init 做两件事：解析全部 rc 并登记，然后按触发器把动作排队、逐条执行。trigger 命令不执行任何东西，只是把另一个触发器名塞进队列尾。

开机主链是一条自排队的触发器链，但入口是二选一的：二阶段 init 在 init.cpp:1279-1283 按 BootMode 分流——charger 模式下只排 charger，其余模式排 late-init（init.cpp:698 还有 RECOVERY_MODE 分支）。late-init 动作里依次 trigger 出 early-fs → fs → post-fs → late-fs → post-fs-data → load-bpf-programs → zygote-start → firmware_mounts_complete → early-boot → boot。

服务靠 class 分类，start 只启动一个服务，class_start 启动一整类。zygote 属 class main，ueventd 与 console 属 class core。但 class_start main 不在 late-init 链上，而在 on nonencrypted（init.rc:1227）里。把该触发器排入队列的是 C++ 侧的 queue_fs_event（builtins.cpp:583/:601），由 do_mount_all（:617）在 queue_event 门控（:622/:625）下调用；本树 rootdir 的 rc 里没有任何可执行的 mount_all 命令（:521/:528/:530 三处都只是注释），也没有 on fs 段，所以这条链在本树不可达——它的实际排入依赖设备侧 rc。

3. 问题背景

你在 init.rc 里加了一个 on boot 段，写了 start myservice，重启后服务没起来，logcat 里也没有任何报错。改成 on late-init 也没用。

另一个常见困惑：明明 init.rc 里 on boot 写在 on zygote-start 后面，为什么 zygote 先起？还有人以为 rc 文件是从上往下当脚本读的，把 start 放在文件末尾就以为它最后执行。

这些都指向同一个误解：把 rc 当命令行脚本。它不是。弄清 rc 的四种语法元素和 init 的排队模型，这类问题就不用猜。

4. 核心机制

4.1 概念与关系

四个概念：

  • section：rc 文件的顶层块，只有三种——import、on、service。
  • action：一个 on <trigger> 块，内含若干命令。它登记在 ActionManager 里，等触发器来叫。
  • service：一个 service <name> <path> <args> 块，内含 class、socket、critical 等选项。它登记在 ServiceList 里，等 start 或 class_start 来叫。
  • trigger：触发器名。两种来源——trigger 内建命令主动排队，或属性变化 property:<key>=<value> 被动匹配。

关系一句话：触发器选中动作，动作里的命令去动服务。动作自己从不主动跑。

QueueEventTrigger 只在队尾追加一个名字（action_manager.cpp:48），属性变化走 QueuePropertyChange（:53），真正逐条跑是 ExecuteOneCommand（:72）。这条「先排队、后执行」的分界，是理解全部时序的钥匙。

4.2 关键内容

解析阶段登记了什么

init.rc 是 1320 行、8 个 import、7 个顶层 service 定义。zygote 服务不在 init.rc 里，而在被导入的文件里——具体是哪个文件由 :12 的 import /system/etc/init/hw/init.${ro.zygote}.rc 间接决定：ro.zygote 取值不同，导入的就是 init.zygote64.rc、init.zygote32.rc 或 init.zygote64_32.rc（后两者 class main 分别在 :2 与 :4）。写成「固定导入 init.zygote64.rc」会漏掉另外两种布局。

两个 parser 各管一半：action_parser.cpp（183 行）解析 on 段，service_parser.cpp（735 行）解析 service 段。服务没写 class 时取默认值 {"default"}（service.cpp:172）——这条默认值解释了为什么很多服务能被一个 class_start default 带起来。

服务的 class 分类

ServiceParser::ParseClass（service_parser.cpp:94）把 class 关键字收进服务的 classnames 集合。本篇涉及的三类：

名称含义出处
class core核心服务类，ueventd 与 console 属此类；启动落点是 init.rc:1221 的 class_start core，位于 on boot（:1112-1221）段内，本树可达init.rc:1266（service ueventd）、init.rc:1285（service console）
class main主服务类，zygote 属此类；class_start main 在 on nonencrypted（:1228），本树不可达（见下）init.zygote64.rc:2、init.zygote32.rc:2、init.zygote64_32.rc:4
class default未写 class 时的默认归类service.cpp:172

注意 zygote 不在 core 也不在 default，它是 main。而 class_start main 写在 on nonencrypted（init.rc:1227）里（:1228 class_start main、:1229 class_start late_start），不在 late-init 链上。这个段的触发器名没有对应的 trigger nonencrypted 文本命令，而是 C++ 侧排入：builtins.cpp:580 的 queue_fs_event 在四种 fs_mgr 返回码（DEV_NOT_ENCRYPTABLE、FILE_ENCRYPTED、IS_METADATA_ENCRYPTED、NEEDS_METADATA_ENCRYPTION）下都调 QueueEventTrigger("nonencrypted")（:583/:601），另有一条 NEEDS_RECOVERY 分支（:585）走 reboot 不入列。

这里有一条必须说清的边界：queue_fs_event 的唯一调用者是 do_mount_all（builtins.cpp:617，内建表注册在 :1337），且受 queue_event 门控（:622 初值 true、:625 在 MOUNT_MODE_EARLY 下置 false）。而本树 system/core/rootdir/ 下的 rc（init.rc、init.zygote64.rc 等）里没有任何可执行的 mount_all 命令——:521/:528/:530 三处命中全是注释；grep -n '^on ' 列出的段里也没有 on fs，只有 on early-fs（:551，仅 start vold）与 on post-fs（:555，仅 checkpoint 标记与 bind/remount）。也就是说 on nonencrypted 在本树不可达，它靠设备侧 rc 的 mount_all 调用才会被排入。所以「开机没起 zygote」时，该查的是设备侧 rc 里有没有 mount_all、fs_mgr 走到哪个返回码，而不是在 late-init 链或本树 rc 里找 class_start main。

trigger 内建命令只是排队

init.rc 里那串 trigger early-fs、trigger fs、trigger post-fs 全部由 do_trigger（builtins.cpp:769）执行，实现就是一句 QueueEventTrigger(args[1])。builtins.cpp 共 1369 行，trigger 在其中的「内建命令表」里，不是 shell 语法。

含义很清楚：执行到这一行时什么也没发生，只是名字进了队列。等当前动作的命令全部跑完，init 才会取出队首触发器，去执行它匹配的动作。

动作的执行边界

单个动作的执行由 Action::ExecuteOneCommand（action.cpp:146）逐条推进，ExecuteAllCommands（action.cpp:153）跑到没有剩余命令。action.cpp 共 248 行。这意味着一个动作内部是严格串行的；跨动作的顺序才由队列决定。

二阶段触发序列

二阶段 init 在 init.cpp 里排的前两个触发器是无条件的：early-init（:1239）、init（:1261）。第三个是二选一的分支，不是序列上的又一环：

// init.cpp:1278
// Don't mount filesystems or start core system services in charger mode.
if (bootmode == BootMode::CHARGER_MODE) {
    am.QueueEventTrigger("charger");   // :1280
} else {
    am.QueueEventTrigger("late-init"); // :1282
}

bootmode 由 GetBootMode()（init.cpp:694）给出，除 CHARGER_MODE 外还有 RECOVERY_MODE（:699）。充电模式下整条开机主链不执行——不挂文件系统、不起核心服务，本篇与 §4.3 的 late-init 叙述只在非 charger 分支成立。最后 queue_property_triggers_action（:1286）把属性匹配动作挂到队列尾。

关键在最后一步：属性触发器整体排在事件触发器之后，而且它本身分两步——先 QueueBuiltinAction(property_enable_triggers_action)（init.cpp:687-688）把属性触发门控打开，再 QueueAllPropertyActions()（:689）经 QueuePropertyChange("", "")（action_manager.cpp:58-59）把全部属性动作入队。门控初值为 0（init.cpp:125）、在这里置 1（:682）。这就是为什么 on property:sys.boot_completed=1（init.rc:1237）不可能早于 boot 执行——不是因为它「不在候选范围里」（QueuePropertyChange 与 QueueEventTrigger 共用同一个 event_queue_，它一直在候选范围），而是因为在门控打开之前它压根不会入队。

4.3 一个具体例子

把 late-init 到 zygote 启动这一路走一遍。

init.cpp:1282 排入 late-init（非 charger 模式）。该触发器命中 init.rc:518 的动作，ExecuteAllCommands 开始逐条跑，共 10 次 trigger：

  • init.rc:519 trigger early-fs → 名字入队
  • init.rc:525 trigger fs → 名字入队（fs 段在本树没有对应的 on fs，其挂载动作由设备侧 rc 承担；但这一环在排队骨架上不能漏）
  • init.rc:526 trigger post-fs → 名字入队
  • init.rc:533 trigger late-fs → 名字入队
  • init.rc:537 trigger post-fs-data → 名字入队
  • init.rc:540 trigger load-bpf-programs → 名字入队
  • init.rc:543 trigger zygote-start → 名字入队
  • init.rc:546 trigger firmware_mounts_complete → 名字入队
  • init.rc:548 trigger early-boot → 名字入队
  • init.rc:549 trigger boot → 名字入队

这些 trigger 执行时全是空动作，但队列里已经依次躺好了后续触发器。late-init 的命令跑完后，init 取出 zygote-start，命中 init.rc:1091 的动作：

  • wait_for_prop odsign.verification.done 1（会阻塞，直到属性到位）
  • start statsd
  • start zygote
  • start zygote_secondary

start zygote 找到 init.zygote64.rc:1 定义的服务：service zygote /system/bin/app_process64 -Xzygote /system/bin --zygote --start-system-server --socket-name=zygote。它的 socket 由 init 预先创建：socket zygote stream 660 root system（init.zygote64.rc:6）；critical window=${zygote.critical_window.minute:-off} target=zygote-fatal（:20）声明了它挂掉的重启窗口。

这里要补一条容易漏的路径：zygote 在这里是被 start 点名拉起的，而 class_start main 这条更通用的机制在 on nonencrypted（init.rc:1227），由 do_mount_all → queue_fs_event（builtins.cpp:617/:580）排入，与上面 10 次 trigger 是两条不同的入队来源。但如前所述，后一条在本树不可达：本树 rc 只覆盖开机主链的排队骨架，挂载动作与 on fs 段都不在这里，读的时候不能把本树 rc 当成主链的全部。

之后轮到 boot，命中 init.rc:1112 的动作：ifup lo、设主机名、调 /proc/sys/vm 参数、给 zram writeback 节点改属主与权限。这些都发生在 zygote 之后，不是之前。

7. 常见问题与误区

7.1 误区

误区一：rc 文件从上往下当脚本执行。 不是。解析阶段只做登记，执行阶段由触发器驱动。你在文件末尾写的 start，只有它所在的 on 段被触发时才跑。

误区二：`trigger` 命令会立刻执行目标动作。 不会。do_trigger 只是 QueueEventTrigger(args[1])，把名字放到队列尾。目标动作要等当前动作的命令跑完、init 取队首时才执行。

误区三：`on boot` 里 `start` 的服务一定在全部早期服务之后起。 看起来对，其实不完整。boot 是靠 late-init 里 trigger boot（init.rc:549）排进队列的，而队列里排在它前面的还有 zygote-start 等。更关键的是，boot 动作内部一旦有阻塞命令，后面的命令全等它；反之某个 class_start 失败也不影响它后面的命令继续跑。

误区四：服务不写 `class` 就是「没有 class」，必须单独 `start`。 默认是 {"default"}（service.cpp:172），会被 class_start default 带走。

7.2 高频提问

问：为什么 zygote 比 on boot 里写的服务先起？ 答：on boot 的触发名是 late-init 里 trigger boot（init.rc:549）排进队列的，而 trigger zygote-start（:543）排在它前面。队列是先进先出，zygote-start 先被取出。 追问：那两个 trigger 之间写别的命令会怎样？ 答：插入的命令先于两个 trigger 执行，但不改变两个触发器的相对次序。 追问：取出队首时只执行一个动作吗？ 答：不止一个。action_manager.cpp:78-89 的 while 循环会把队头事件一路弹出，每弹一次就遍历 actions_ 把所有 CheckEvent 命中的动作压进 current_executing_actions_，直到队列空或队头换成新事件。所以「取出 zygote-start」实际是把所有监听该触发名的动作一次性排上，FIFO 指的是事件出队次序，不是「一次只出一个动作」。

问：on property:sys.boot_completed=1 和 on boot 谁先跑？ 答：boot 一定先。属性匹配动作由 queue_property_triggers_action（init.cpp:1286）整体挂到队列尾，排在事件触发器之后；而且这一步本身是两步——先 property_enable_triggers_action（init.cpp:687-688）开门控，再 QueueAllPropertyActions()（:689）才真正入队。门控不开，属性动作连队列都进不去。 追问：那开机期间属性变化能被 on property: 即时捕获吗？ 答：能，但执行时机是入队后按队列顺序，不是属性写入的瞬间。属性机制细节归 AND-P8-202。
