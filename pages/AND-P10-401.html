1. TL;DR

logcat 不带 -b 时的默认订阅不是「全部日志」，而是 LOG_ID_MAIN、LOG_ID_SYSTEM、LOG_ID_CRASH、LOG_ID_KERNEL 四个缓冲区，由 if (id_mask == 0) 分支一次性赋值；注意显式写 -b default 只得到前三个，KERNEL 不会加入。LOG_ID_EVENTS、LOG_ID_STATS、LOG_ID_SECURITY 走特殊分支，不在默认集合里；LOG_ID_RADIO 同样不在默认集合（log_id_t 全集 8 个，android/log.h :105-:119），要用得显式 -b radio。默认输出格式是 threadtime，不是 brief。dumpsys 慢，多半不是「服务实现烂」，而是它对每个服务逐个发一次 dump 事务，默认单次超时 10000 毫秒，服务多了就逐项累加。dumpsys 的 -t 按秒解析再乘 1000（毫秒用 -T），--priority 既过滤服务清单，又向服务端注入 --dump-priority/-a 参数从而改变服务的 dump 分派——但这两件事都只在未显式指定服务名（dump 全部服务或 -l）时发生（dumpsys.cpp :257-:259：setServiceArgs 的调用点在 if (services.empty() || showListOnly) 分支内）；-a 与 --dump-priority 按 priorityFlags 分支注入，并非总是同时。上面这些都是源码常量口径，本篇不断言任何真机输出。

3. 问题背景

你打开终端敲 logcat，日志刷得飞快，但某条 Log.i 死活不出现——要么 tag 拼错，要么它根本没进你订阅的缓冲区。你敲 dumpsys 想看某个服务状态，终端卡了十几秒才出结果，你以为机器卡死了，其实是它在一项一项地问服务。两条命令天天用，但缓冲区有几个、默认格式是什么、超时是谁的、-t 的单位是什么，多数人答不上来。本篇只回答这些问题，不教你怎么定位卡顿和崩溃。

4. 核心机制

4.1 概念与关系

dumpsys 走 Binder 事务（经 ServiceManager 拿每个服务的代理，逐个发 dump），logcat 走 logd 的 socket 与日志缓冲区——底层路径并不相同；相同的只是「客户端只做选取与格式化」这一层。

图 1：logcat 与 dumpsys 的客户端—服务端分层

logcat                       dumpsys
  |                            |
  |-- logd socket ---------    |-- servicemanager 查询 ---
  |                    |       |                          |
  +-- 日志缓冲区 <-- logd       +-- 逐服务 dump 事务 --> 各系统服务

两个命令的共同点是：客户端本身不做业务，只做选取与格式化。差别在选取维度——logcat 按缓冲区 id 选，dumpsys 按服务名与优先级选。

4.2 关键内容

logcat 的缓冲区选择由 id_mask 位掩码表达，有两条互不相干的路：显式 -b 解析臂在 logcat.cpp :827–:830，-b default 拼出 LOG_ID_MAIN、LOG_ID_SYSTEM、LOG_ID_CRASH；隐式默认在 :916 的 if (id_mask == 0)，:917–:918 用一条语句赋值 MAIN|SYSTEM|CRASH|KERNEL。因此 -b default 只有 3 个缓冲，不带 -b 才是 4 个。LOG_ID_EVENTS 等特殊 id 由 :222 的 is_binary 分支处理；另有一个遍历 LOG_ID_MIN 到 LOG_ID_MAX 的循环在 :1047，那是 clear/set-size/get-size 三个动作共用的，与前面两处不是同一机制。

dumpsys 侧，用法文本自 dumpsys.cpp :68 起，形如 dumpsys [-t TIMEOUT] [--priority LEVEL] [--clients] [--dump] [--pid] [--thread]。--priority LEVEL 的说明是「filter services based on specified priority」（:81），--skip SERVICES 则「dumps all services but SERVICES (comma-separated list)」（:83）。

4.3 一个具体例子

以 meminfo 服务为例，看一次 dumpsys meminfo 的服务端落点。

ActivityManagerService.java :2132 有 ServiceManager.addService("meminfo", new MemBinder(this), false, ...)。MemBinder 自己并不直接打印：它的 dump（:2304）先把请求交给 PriorityDump.dump(mPriorityDumper, fd, pw, args)（:2310），由分派层按优先级选路——dumpHigh（:2287）以 {"-a"} 回调（:2289）、dump（:2293）直传参数，两条路最终都落到 dumpApplicationMemoryUsage（调用点 :2294；实现在 :13016，随后经 :13104 转到私有重载 :13109，表头在 :13138 与 :13190 打印），表头由 dumpApplicationMemoryUsageHeader（:12932）产出（这是文本 dump 路径；--proto 走另一重载，落点同为 dumpApplicationMemoryUsage，本篇断言不依赖文本还是 proto 分支）。

于是整条链是：客户端按名字查到 meminfo 的 Binder 代理 → 发 dump 事务 → MemBinder 接住 → 落到 dumpApplicationMemoryUsage → 先输出表头再输出逐进程数据。你看到的每一行都来自这一段 Java 代码，而不是 dumpsys 客户端自己拼的。客户端只负责服务枚举、超时控制与输出重定向。

7. 常见问题与误区

7.1 误区

误区一：logcat 默认输出全部日志。 错。隐式默认（:916–:918）含 LOG_ID_MAIN、LOG_ID_SYSTEM、LOG_ID_CRASH、LOG_ID_KERNEL；LOG_ID_EVENTS、LOG_ID_STATS、LOG_ID_SECURITY 走 :222 的特殊分支，不在默认集合里；LOG_ID_RADIO（android/log.h :107）也不在，需 -b radio 显式订阅。

误区二：dumpsys 卡住说明某个服务挂了。 多数情况不是每个服务都慢——10000 毫秒（:139）是单个服务的静默无输出上限：dumpsys.cpp :508-509 设 deadline、:524 用 poll 等可读、:532-534 在超时或返回 0 时判 TIMED_OUT。正常服务毫秒级返回，只有卡死或长时间不发字符的才会吃满这个上限，因此不能按「服务数 × 10000ms」累加来估算总耗时。

误区三：`-t` 的单位是毫秒。 错。-t 按秒解析再乘 1000（:193–:194），毫秒要用 -T（:205–:207）。给 -t 10000 会被当成一万秒。

误区四：`--priority` 只筛清单。 它还改输出：过滤之后 setServiceArgs 按分支注入 -a（:338–:341，仅 ALL/NORMAL/DEFAULT）与 --dump-priority 及优先级串（:345–:350，仅 CRITICAL/HIGH/NORMAL），服务端按此分派不同 dump 路径，故内容会变。但前提同样是未显式指定服务名（dumpsys.cpp :257-:259），指定了服务名时过滤与注入都不发生。

7.2 高频提问

问：logcat -g 和 logcat -G 差在哪？ 答：-g, --buffer-size 只查看当前缓冲区大小（:414），-G, --buffer-size=SIZE 是设置（:416）。大小写不同，行为相反。 追问：那 -b 呢？ 答：-b 选缓冲区，改变的是 id_mask 里的位，与 -g/-G 属于两个维度；注意 -b default 只给三缓冲，不带 -b 才是四缓冲。

问：为什么 dumpsys --skip 能提速，--priority 也能，但体感不同？ 答：--skip 不改清单本身——被跳过的服务仍在清单里打印并标注 (skipped)（:272），真正跳过发生在 dump 循环（:285 if (IsSkipped(...)) continue;）；--priority 按优先级阈值筛选（仅在未显式指定服务名时，dumpsys.cpp :257-:259），保留哪些取决于服务的优先级声明。 追问：两个一起用会冲突吗？ 答：不冲突，都是对同一份服务清单做集合运算，最终被 dump 的集合是两者叠加的结果。
