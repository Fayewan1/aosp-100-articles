1. TL;DR

VINTF（Vendor Interface）是这套互相声明的总名。manifest 声明「这台设备/这套框架有什么」；compatibility matrix（兼容性矩阵，FCM）声明「某个级别要求什么」。校验就是拿设备的 target-level 挑出对应 FCM，再用清单与矩阵做双向匹配。四类取数口都挂在 VintfObject 上：设备清单、框架清单、设备矩阵、框架矩阵。设备清单有固定的组装次序与旧路径兜底，框架清单则要聚合多分区并再做一次级别过滤。匹配失败的表现形式是 check_vintf 报缺 HAL、或开机时 vendor 镜像与 system 镜像对不上。

3. 问题背景

换了一份 vendor 镜像，或者把 system 分区升到一个新版本，开机后 check_vintf 判失败，日志里只说某个 HAL 缺失，或者某个版本区间不被接受。打开 /vendor/etc/vintf/ 看到 manifest，再看 hardware/interfaces/compatibility_matrices/ 里一堆 compatibility_matrix.*.xml，不知道设备到底该按哪一份对账。

另一类困惑是方向搞反了：以为框架侧的要求写在设备清单 里，或者以为改 manifest 多加一个 HAL 就能通过。实际是 manifest 与 matrix 分属两侧，各管一件事。本篇把这套关系的语义、加载次序、匹配算法和失败形态讲清。

4. 核心机制

4.1 概念与关系

四个对象、两组对账：

  • 设备清单（device manifest）：设备侧声明自己提供哪些 HAL、版本区间是多少、target-level 是多少。
  • 框架清单（framework manifest）：框架侧声明它提供哪些 HAL，供 vendor 侧取用。
  • 兼容性矩阵（FCM，compatibility matrix）：按 level 命名的一族文件，规定该级别下必备的 HAL 与可接受版本区间。
  • target-level：设备清单里的字段，决定这台设备被哪一份 FCM 校验。

图 1：两端清单与矩阵的对账关系

 device manifest ---> 挑 target-level ---> 对应 FCM
      |                                      |
      |  声明提供了什么                        |  要求必须有什么
      +------------> 匹配 <------------------+
 framework manifest --过滤--> 与设备级别相符的部分

框架清单不是原样参与对账：取数后按设备清单 的 target-level 过滤掉级别不相交的 HAL，再进入匹配。

按级别过滤。fetchFrameworkHalManifest 取数后调用 filterHalsByDeviceManifestLevel（调用点在 VintfObject.cpp:513，函数体在 :534）。判定依据是设备清单 的 target-level：框架清单 中 minLevel/maxLevel 与设备级别不相交的 HAL 被剔除，没有标 level 的条目按「无穷旧」处理。所以同一份框架清单，在不同 target-level 的设备上看到的可见 HAL 集合不同。

合并与冲突判定。多来源清单并入同一个对象时要判冲突：HalManifest::add(ManifestHal&&, std::string*)（system/libvintf/HalManifest.cpp:219），冲突判定在 shouldAdd（:45）与 addingConflictingMajorVersion（:64）。同一 HAL 同主版本、区间重叠但内容不一致，属于冲突而非合并。

矩阵侧：CompatibilityMatrix::add（system/libvintf/CompatibilityMatrix.cpp:35）负责并入，fetchAllInformation（:122）负责取数；合并入口在 CompatibilityMatrix::combine 与 combineDeviceMatrices（system/libvintf/AssembleVintf.cpp:745/:706）。

FCM 实文件。hardware/interfaces/compatibility_matrices/ 下带 level 的矩阵共 6 份，另有 1 份空白模板：

文件level条目构成（<hal format 计数）
compatibility_matrix.7.xml799 条：format="hidl" 49 条、format="aidl" 50 条
compatibility_matrix.8.xml886 条：format="hidl" 11 条、format="aidl" 74 条
compatibility_matrix.202404.xml202404年度快照，两种格式混存
compatibility_matrix.202504.xml202504同上
compatibility_matrix.202604.xml202604同上
compatibility_matrix.202704.xml20270492 条：format="hidl" 0 条、format="aidl" 91 条（另 1 条带 updatable-via-apex="true"），出现版本区间 <version>1-4</version>

表里最该记住的一条：格式不是按 level 二分的。level 7 里 AIDL 条目（50）已经多于 HIDL（49），因为低级别设备要兼容存量 HIDL HAL，两种写法都得留；到 202704 才彻底没有 HIDL 条目。所以「老 level 就是 HIDL、新 level 才是 AIDL」这个判断看起来顺，实际是反的。同目录的 compatibility_matrix.empty.xml 与 manifest.empty.xml 是空白模板，没有 level 属性；文件编号与 level 属性一致，这是两者能对上的依据。

内核条件。矩阵 schema 允许写内核条件：<xs:element name="kernel" ... minOccurs="0" maxOccurs="unbounded"/>（system/libvintf/xsd/compatibilityMatrix/compatibility_matrix.xsd:25），并有 kernel-sepolicy-version（:87）。解析出的条件序列由 MatrixKernel::conditions() 暴露（system/libvintf/include/vintf/MatrixKernel.h:57）。本树框架 FCM 两份实文件里没有 <kernel> 条目，内核侧的兼容面不属于本篇，见 AND-P5-101。

4.3 一个具体例子

设某设备清单为 device/generic/goldfish/manifest.xml，内容只有一行根元素 <manifest version="1.0" type="device" target-level="8">。target-level 就是设备声明的 FCM 级别。

对账流程：

  1. GetDeviceHalManifest 命中上面这份，得 target-level 8。
  2. 框架清单经 filterHalsByDeviceManifestLevel，把 minLevel/maxLevel 与 8 不相交的 HAL 去掉。
  3. 级别 8 对应 compatibility_matrix.8.xml，作为要求面。
  4. 清单与矩阵逐 HAL 比对：矩阵要求的存在于清单、版本区间落在矩阵允许范围内，即通过。
  5. 不通过时，check_vintf --check-compat（system/libvintf/check_vintf.cpp:201）输出缺 HAL 提示。

图 3：一次校验的判定链

device manifest（target-level=8）
   |
   +--> 过滤框架清单（minLevel/maxLevel 与 8 相交才保留）
   |
   +--> 按 8 选 FCM：compatibility_matrix.8.xml
   |
   +--> 逐 HAL / 接口 / 实例比对
          |--> 全部命中：判定通过
          +--> 有缺项：check_vintf --check-compat 报缺，给两条出路

缺 HAL 的提示文本在 gCheckMissingHalsSuggestion（system/libvintf/check_vintf.cpp:387），给两条出路：新包加入最新 FCM，或 types-only 包加入 libvintf_fcm_exclude 豁免表（目录在 hardware/interfaces/compatibility_matrices/exclude/）。注意「最新 FCM」不是「当前 level 的 FCM」，两者在升版本场景下不是同一个文件。

同一份 Goldfish 清单若被手工改成 target-level 7，第 2 步过滤结果会变，第 3 步换成 compatibility_matrix.7.xml，要求面从「86 条、11 HIDL＋74 AIDL」变成「99 条、49 HIDL＋50 AIDL」——条目集合与格式配比同时变。同一套 vendor 镜像在两个 target-level 下的判定结论可以完全不同，变的不是「用哪种写法」，而是「要求哪些条目、允许哪些版本」。

4.4 与相邻篇的关系

AND-P4-101 讲 HAL 契约怎么写、怎么注册——manifest 里一条 <hal> 的字段语义归它。本篇讲这条 <hal> 被谁、按什么规则校验。

7. 常见问题与误区

7.1 误区

误区一：改设备清单 多加一条 HAL 就能通过校验。 方向反了。manifest 声明「有什么」，矩阵声明「要什么」。清单里多一条不满足的 HAL，只会在框架清单匹配、冲突判定里引入新问题；缺 HAL 报错的解要么补实现、要么按 gCheckMissingHalsSuggestion 走 FCM 或豁免表。

误区二：框架清单就是 `/system/etc/vintf/manifest.xml` 一份文件。 实际是多源聚合：/system 的清单与片段、product 与 system_ext 的清单与片段一起并；合并时按 shouldAdd 判冲突。只看一份文件会漏掉实际生效的条目。

误区三：设备上所有 FCM 都会参与校验。 只有与 target-level 对应的那一份是要求面。compatibility_matrix.7.xml 与 compatibility_matrix.202704.xml 同时在树里，不代表同时生效。

误区四（看起来对其实是错的）：框架清单 里写了某个 HAL，设备就应该能用。 中间还有 filterHalsByDeviceManifestLevel。框架清单 里 minLevel/maxLevel 与设备 target-level 不相交的条目会被剔除，声明存在不等于对这台设备可见。

误区五：`check_vintf` 报缺 HAL 说明代码没编译进去。 也可能只是清单没声明，或声明了但级别不匹配。三种原因输出相似，不能只看一行报错下结论。

7.2 高频提问

问：换 vendor 镜像后 system 侧没变，为什么兼容性会挂？ 答：vendor 镜像带来的设备清单 决定了 target-level，target-level 一变，框架清单的过滤结果与所对账的 FCM 文件同时变。 追问：那 system 侧完全无关吗？ 答：相关。system 侧的框架清单 与 FCM 是要求面和供给面的另一半，两侧任一侧变都可能让匹配失败。

问：--check-compat 和 --check-one 有什么区别？ 答：前者做清单与矩阵的兼容性对账，后者做单文件检查。日常排「缺 HAL」用 --check-compat。 追问：两者都会读设备 FCM 吗？ 答：--check-compat 会按 target-level 取对应 FCM；单文件检查不建立完整对账关系。

问：FCM 文件名里的数字就是 level 吗？ 答：本树实测一致：文件 compatibility_matrix.7.xml 的 level="7"，compatibility_matrix.202704.xml 的 level="202704"。 追问：能靠文件名推断校验行为吗？ 答：能对上是哪一份，但对不上校验细节；条目写法（HIDL 还是 AIDL）、版本区间要不要写，必须看文件内容。
