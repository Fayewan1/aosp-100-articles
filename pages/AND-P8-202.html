1. TL;DR

一条属性从设置到被读到，路径是：调用方经 libbinder 之外的专用 socket 把 name=value 发给 init 的 property_service，init 在 CheckPermissions 里按 SELinux source context 和调用方凭据决定放不放行，放行后写进属性内存区，读侧直接读这块内存，不经过 init——getprop 用 __system_property_foreach 加回调遍历，应用查单键才用 __system_property_get。

StartPropertyService 起两个线程、两个 socket：PROP_SERVICE_NAME 权限 0666，PROP_SERVICE_FOR_SYSTEM_NAME 权限 0660 且属主 AID_SYSTEM。

ro. 类属性写一次就锁死——PropertySet（:378）在 :399-402 判 StartsWith(name, "ro.") 后直接返回 PROP_ERROR_READ_ONLY_PROPERTY；persist. 前缀会落到 /data/property/persistent_properties。

内核来源有两条：cmdline 里的 androidboot.* 在 ProcessKernelCmdline 里映射成 ro.boot.*，bootconfig 走 ProcessBootconfig。

读侧极快的原因是属性区是共享只读内存，getprop 只是遍历这块区域。

3. 问题背景

你写了个 native 服务，启动时 __system_property_set("persist.demo.flag", "1") 返回 0，没有任何报错，但下次开机这个值又变回默认。换一条 ro.demo.flag 设置，直接失败，日志里只有一行 permission denied。

另一头，getprop 一秒钟能刷出几百条属性，而 setprop 每条都要等 init 回应。同是属性接口，读和写的代价差出两个数量级。

这两个现象指向同一件事：属性不是「一个全局变量」，而是一套由 init 独占写入、所有进程只读的通道。搞清楚谁在写、谁能写、写进去之后存在哪，才能解释上面两件事。本篇只走这条链路。

4. 核心机制

4.1 概念与关系

四个概念：

  • 属性区：一块进程间共享的只读内存，所有进程都映射同一份，读侧无系统调用。
  • property_service：init 里的一组分发线程，是唯一写入口。
  • CheckPermissions：init 侧的准入判定，输入是属性名、值、调用方 SELinux 上下文与凭据。
  • property_contexts：system/sepolicy/private/property_contexts 里的「属性名前缀 → SELinux 类型」映射表，共 1959 行。

设置是「跨进程 + 判定」，读取是「本地内存拷贝」，这就是两者代价差异的根。

4.2 关键内容

写侧的完整链路，以 property_service.cpp（1575 行）为轴：

  1. StartPropertyService（:1551）在 init 启动时调用，先 InitPropertySet("ro.property_service.version", "2")（:1552），标记协议版本。
  2. 建立 socketpair 连接 init 与 property_service，随后起两个线程：StartThread(PROP_SERVICE_FOR_SYSTEM_NAME, 0660, AID_SYSTEM, property_service_for_system_thread, true)（:1562）与 StartThread(PROP_SERVICE_NAME, 0666, 0, property_service_thread, false)（:1564）。
  3. 设置请求进入 HandlePropertySet（:541），先调 CheckPermissions(name, value, source_context, cr, error)（:498）判定。
  4. 判定依据是 SELinux source context 加调用方凭据，规则来自 property_contexts 的前缀匹配。
  5. 通过后写入属性内存区。落盘不是「前缀对上就写」，而是要同时满足三个条件——判断在 static PropertySet（:378 起）里：先算 need_persist = StartsWith(name, "persist.") || StartsWith(name, "next_boot.")（:416），再由 :417 一行判 if (socket && persistent_properties_loaded && need_persist)，:418-421 则是命中后的异步分支。条件本身是三条：前缀命中、socket 非空、且持久属性已回载完成。persistent_properties_loaded 是静态标志，:106 初值为 false，:1463 在回载结束时置 true。三者齐了才写 /data/property/persistent_properties。这里还有一条分支要分清：若 ro.property_service.async_persist_writes 为真（:1566-1569 读取该属性后才创建 PersistWriteThread），:418-421 会把写入交给写盘线程并立刻返回——真正的 WritePersistentProperty（:1518）与回包 socket.SendUint32(PROP_SUCCESS)（:1522）是线程侧异步完成的。所以开了这个开关时，「返回 0」的语义是「已排队」，不是「已落盘」。这也正是 §3 那个「返回 0 却没持久化」场景的成因之一：早期进程在 load_persist_props 之前 set，前缀对了也照样不落盘。

补一句父子关系：判定与写入虽都在 PropertySet 里，但入口是 HandlePropertySet（:541）——它在 :544 调 CheckPermissions 做权限判定，全部通过后在 :581 才 return PropertySet(name, value, socket, error) 完成内存写入与落盘。所以「权限不过」与「写不进」是两个函数、两个阶段。

两个 socket 的区分就是「谁能写」的第一道闸，见表 1。

读侧和工具侧：

  • bionic/libc/bionic/system_property_set.cpp（332 行）提供 __system_property_set 入口，负责连 socket 并发送。
  • bionic/libc/bionic/system_property_api.cpp（137 行）提供 __system_property_get（:86），在本地属性区查名字取值。
  • system/core/toolbox/getprop.cpp（162 行）是 getprop 命令：PrintAllProperties（:39）里先 __system_property_foreach（:41）拿到每个 prop_info，再在回调里 __system_property_read_callback（:43）取值。注意它用的不是 __system_property_get——那是应用侧单键查询的入口，getprop 要的是全量遍历。
  • system/core/init/property_type.cpp（86 行）做 init 侧的类型解析。

内核来源两条，都在 property_service.cpp：ProcessKernelCmdline（:1388）把 cmdline 里的 androidboot.* 转成 ro.boot.*；ProcessBootconfig（:1397）处理 bootconfig 来源。两者都在开机早期执行，早于大部分 service 起来。

开机早期的默认值装配按 PropertyInit（:1405）里的固定次序执行：ProcessKernelDt → ProcessBootconfig → ProcessKernelCmdline → ExportKernelBootProps（定义 :1338，把内核变量导出成 init 内部与对外属性）→ PropertyLoadBootDefaults（:1148）→ PropertyLoadDerivedDefaults。也就是说 cmdline/bootconfig 的映射先于默认属性文件装载，后者可以覆盖前者。

persist. 落盘值不在 PropertyLoadBootDefaults 里合并：该函数只读 /prop.default 等默认属性文件。持久值的回载由 init 主线程在 rc 的 on post-fs-data 段调 load_persist_props 内建命令（system/core/rootdir/init.rc:722）触发（该分支里还会调 load_override_properties()（:1448，定义在 :870）处理覆盖值，并在 :1462 置 ro.persistent_properties.ready=true 作为「回载完成」的对外观测点）——它经 SendLoadPersistentPropertiesMessage（init.cpp:933）把消息发给 property_service，由 HandleInitSocket 的 kLoadPersistentProperties 分支（property_service.cpp:1447-1464）调 LoadPersistentProperties() 后逐条 InitPropertySet。时序上这在 PropertyLoadBootDefaults 之后，因此持久值能覆盖默认值。

4.3 一个具体例子

以写一条 persist.demo.flag=1 为例，按上面的链路走一遍：

  1. 进程调 __system_property_set（system_property_set.cpp）。
  2. 请求经 socket 到 init 的 property_service_thread（对应 PROP_SERVICE_NAME，:1564）。
  3. HandlePropertySet（:541）接住，调 CheckPermissions（:498）。
  4. CheckPermissions 拿调用方 SELinux source context 去 property_contexts 里按前缀匹配，判定该域是否被允许写这类属性。
  5. 通过则写入属性区。落盘再看三条件（:416 的 need_persist、:417 的 socket 与 persistent_properties_loaded）：本例前缀命中 persist.，若此刻 persistent_properties_loaded 仍为 false（:106 初值），写入成功但不落盘；只有等 :1463 把它置 true 之后，同类写入才会落 /data/property/persistent_properties。
  6. 下次开机按三步装配（下面给的是 PropertyInit 内的调用点行号，与 §4.2 引用 :1148 这类定义行不是一套口径）：先 ProcessKernelDt/ProcessBootconfig/ProcessKernelCmdline（:1421-1423）映射 bootconfig 与 cmdline，ExportKernelBootProps（:1427）导出内核变量；再 PropertyLoadBootDefaults（:1148）装载默认属性文件；最后 on post-fs-data 段的 load_persist_props（system/core/rootdir/init.rc:722）经 kLoadPersistentProperties 分支（:1447-1464）把 /data/property/persistent_properties 里的持久值读回来——分支内还会 load_override_properties()（:1448，定义 :870）应用覆盖值，末尾 :1462 置 ro.persistent_properties.ready=true。此时 persist.demo.flag=1 才重新可见，且能覆盖同名的默认值。

对照第 3 节的场景：返回 0 却没有持久化，说明 socket 通信成功但持久化环节另有条件；而 ro. 设置失败要走另一条判据：CheckPermissions 放行之后，PropertySet（:378）在 :399-402 发现前缀是 ro. 且已存在，返回 PROP_ERROR_READ_ONLY_PROPERTY——这是「写一次」的语义，不是权限问题，也不是 I/O 错误。顺便把 CheckPermissions（:498-537）自己的组成拆清：先 IsLegalPropertyName（:500），ctl. 开头走 CheckControlPropertyPerms 特判（:505-513），其余先 GetPropertyInfo（:517）取目标上下文，再 CheckMacPerms（:519）判 SELinux，最后 CheckType（:530）判值类型。

7. 常见问题与误区

7.1 误区

误区一：以为 `__system_property_set` 返回 0 就是写成功了。 返回 0 只代表请求送达并得到 init 回应；ro. 前缀的属性一旦设定即锁死——第二次设置走 PropertySet 的 :399-402，返回 PROP_ERROR_READ_ONLY_PROPERTY，与权限判定无关。而部分调用路径的失败不体现在这个返回值上。判断是否真正生效应该回读。

误区二：以为所有进程通过同一个 socket 写属性。 实际有两个：PROP_SERVICE_NAME 权限 0666，PROP_SERVICE_FOR_SYSTEM_NAME 权限 0660 且属主 AID_SYSTEM（:1562、:1564）。系统进程与普通进程走的入口不同。一个例外是 sys.powerctl：system_property_set.cpp:64-73 里，只要调用方对该高权限 socket 有写权限（access(..., W_OK) 为真），就改走 property_service_for_system_socket——所以同一个属性对不同进程会落到不同 socket，权限结论不能只按属性名推。

误区三：以为读属性也要问 init。 读侧只访问本地映射的属性区，不产生跨进程调用。具体入口要分清：应用查单个键走 __system_property_get（system_property_api.cpp :86），getprop 命令走的是 __system_property_foreach（getprop.cpp:41）加回调里的 __system_property_read_callback（:43），frameworks 侧单键查询则走 android::base::GetProperty。三者都不经过 init。这正是 getprop 能瞬时刷出几百条的原因。

误区四（看起来对其实是错的）：以为属性权限写在 `property_contexts` 里就够了。 property_contexts 只给出「这个名字属于哪个 SELinux 类型」，真正放不放行要 CheckPermissions（:498）结合调用方的 source context 和凭据一起算。上下文类型对、调用方域不对，依然拒绝。

7.2 高频提问

问：ro.boot.* 是谁写进去的？ 答：ProcessKernelCmdline（:1388）在开机早期把 kernel cmdline 里的 androidboot.* 映射成 ro.boot.*，ProcessBootconfig（:1397）处理 bootconfig 来源。 追问：两者冲突时谁说了算？ 答：DT 优先。property_service.cpp:1419-1420 的注释写明「properties set in DT always have priority over the command-line ones」，紧接着 :1421 处理 DT、:1423 才处理 cmdline——所以同名属性同时在两处出现时，以 DT 里的值为准。这条结论在本树是源码注释直接声明的设计意图，不需要真机验证；换版本时注释与次序要重新核。

问：persist. 属性的落盘时机是每次 set 都写吗？ 答：persist. 前缀的属性落在 /data/property/persistent_properties，写盘动作发生在 HandlePropertySet 通过 CheckPermissions 判定、且满足「前缀 + socket 非空 + 已回载」三条件之后（:416-418）；若开了 ro.property_service.async_persist_writes，返回值只表示「已交给写盘线程」。回载不在 PropertyLoadBootDefaults（:1148）里，而是 on post-fs-data 段的 load_persist_props（system/core/rootdir/init.rc:722）经 kLoadPersistentProperties 分支（:1447-1464）完成，期间 load_override_properties()（:1448）应用覆盖值，:1462 置 ro.persistent_properties.ready=true。 追问：落盘失败会怎样？ 答：表现为值在本次开机内可见、重启后丢失。先查 /data/property/ 的挂载与权限，再查 CheckPermissions 是否放行。
