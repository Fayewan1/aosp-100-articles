1. TL;DR

boot 镜像不是一个整体，而是「头 + 若干字节段」的结构化容器，各段边界由头里的 kernel_size、ramdisk_size、second_size 等字段共同定义。头格式的定义处是 bootimg.h：BOOT_MAGIC 为 "ANDROID!"，VENDOR_BOOT_MAGIC 为 "VNDRBOOT"，boot_img_hdr 是 boot_img_hdr_v0 的别名，即设备侧解析必须认历史布局。注意字段归属的版本差：boot_img_hdr_v0（:80-127）只有 magic、kernel/ramdisk/second 三组 size 加 page_size、header_version，recovery_dtbo_size（:170）与 header_size（:172）是 boot_img_hdr_v1（:169 起）才追加的字段——按最新版头解释 v0 镜像必然错位。宿主侧 mkbootimg.py 负责按该契约打包，fastboot.cpp 负责按同一契约分片下发。fastboot flash 一条命令背后是「解析命令 → do_flash（读镜像进缓冲、必要时先下发 .sig、repack_ramdisk）→ flash_buf（copy_avb_footer → 仅在 --disable-verity/--disable-verification 置位时 rewrite_vbmeta_buffer）→ 分片下发」的序列，链路上任何一环失败都不会启动。

3. 问题背景

手里拿到一个 boot.img，unpack_bootimg 拆出一堆 kernel、ramdisk、second，再加一个 DTB（device tree blob），但没人说得清这些段的先后顺序由谁决定。想做一条自动化刷机脚本，发现 fastboot flash boot 与 fastboot flashall 行为不一样：前者只写分区，后者还会动 vbmeta 和 slot。设备变砖后进 fastbootd，getvar 能看到 is-userspace 为真，但不知道自己此刻到底在 bootloader 还是 fastbootd 里、哪些命令在两侧语义不同。这些都是同一个问题的不同侧面：镜像的字节布局契约与刷机链路的分层契约。

4. 核心机制

4.1 概念与关系

四层：头格式（bootimg.h 定义结构体与魔数）、打包器（mkbootimg.py 按结构体写出字节）、下发链路（fastboot 宿主工具把镜像切片发给设备）、设备侧接收（bootloader 或 fastbootd）。四层共用同一份结构体定义，任何一层自行解释字段都会出现「能刷进去、起不来」。

关键概念：

  • boot 镜像：boot_img_hdr_v0 打头的容器，承载 kernel 与 ramdisk。
  • vendor_boot 镜像：以 VENDOR_BOOT_MAGIC 打头的另一类容器，承载厂商侧内容。
  • vbmeta 镜像：AVB 的签名元数据，avb_vbmeta_image.c 负责其结构处理。
  • BCB（bootloader control block）：bootloader 与系统互递状态的持久块，定义在 bootloader_message.cpp。

4.2 关键内容

4.3 一个具体例子

以下按 2026-10-19 于本地 android17-release 树的实测口径走一遍 fastboot flash boot boot.img：

  1. main.cpp:31 的入口接收参数，交给 fastboot.cpp 分派。
  2. 命令被识别为 flash，但关键点在于：flash 不直接进 do_flash，中间还有一层任务对象。fastboot.cpp 先 CollectTasks 建出 FlashTask（task.h:49，Run() 在 task.cpp:156），由 FlashTask::Run 决定走哪条路：fastbootd 会话（task.cpp:157 的 is_userspace_fastboot）直接 do_flash（:165）；静态分区或带 --force 也 do_flash（:169）；动态分区且非 force 则改走 FetchAndParseMetadata（:175）→ SparseForSuper（:205）→ flash_partition(fp_, "super", ...)（:213），这条路径不经 do_flash/flash_buf。走 do_flash（fastboot.cpp:1509）的那些情况，函数体（:1509-1538）才展开成四步。这个函数体（:1509-1538）主体是四步：经 fp->source 或 load_buf 把镜像读进 fastboot_buffer；对逻辑分区先 ResizePartition；repack_ramdisk 重打包 ramdisk；最后转 flash_buf（:1254）真正下发。第一步还有一条旁支：读镜像时若同目录存在同名 .sig 文件（:1524），会先 Download/RawCommand 把签名单独下发（:1526-1527），这一步与主流程并行存在，不属于四步主体。
  3. flash_buf（:1254）内部先 copy_avb_footer（:1171）拷贝并处理 AVB footer。随后只有 g_disable_verity || g_disable_verification 为真（即带了 --disable-verity/--disable-verification）时，才调 rewrite_vbmeta_buffer（:1079）按实际分区状态重算 vbmeta。若 apply_vbmeta 为假、设备又没有独立 vbmeta 分区、目标又是 boot/boot_a/boot_b，这一步走 vbmeta_in_boot 变体。次序不能反：footer 先就位，vbmeta 重算才有输入。
  4. 数据切片下发，设备侧按 bootimg.h 的布局解释头部，并按 --page-size 对齐写入。默认 2048（fastboot.cpp:618 的用法文本给出默认值，实际取值约束在 mkbootimg.py:537）。
  5. 以上是 flash（单分区）路径的完整函数面。is_userspace_fastboot（:1555）、reboot_to_userspace_fastboot（:1560）、set_active（:1542）都不在这条路径上：前两者在 fastboot.cpp 全文没有除定义与内部互调（:1574）之外的调用点——注意范围限定：跨文件还有 task.cpp:157 的 FlashTask::Run 会调 is_userspace_fastboot，而它正是 flashall 逐分区路径的必经点；set_active 的写入动作至少在三处：FlashAllTool::Flash（:1799/:1801）、FastBootTool::Main 的 update 收尾（:2633-2634 的 fb->SetActive(next_active)），以及 FB_CMD_SET_ACTIVE 命令分支（:2549-2551，即 fastboot set-active <slot> 这条用户命令：:2550 先 verify_slot，:2551 直接 fb->SetActive(slot)）。而 :2407-2421 那段（if (fp->wants_set_active) 的完整闭合块）只是 wants_set_active 标志的判定与 next_active 取值，不是写入动作本身。
  6. 若换 flashall：FlashAllTool::Flash（:1792）先按 slot_override 调 set_active（内部先 supports_AB（:1543）判 A/B，再 get_current_slot（:1548）取当前槽），再 DetermineSlot、CollectTasks，最后才逐任务执行 FlashTask::Run（task.cpp:156）——注意不是直接 do_flash：FlashTask::Run 内部按分区类型分派，只有 fastbootd、静态分区或 --force 这三种情况才落到 do_flash（:165/:169），动态分区走 super 元数据那条路（:175-213）。也就是说 slot 动作发生在逐分区刷写之前，do_flash 也不是 flashall 的必经函数。
  7. BCB（bootloader_message.cpp 的 read_bootloader_message/write_bootloader_message，:155/:169）是 recovery/bootloader 之间的独立状态接口：宿主 fastboot.cpp 全文不读写 BCB，刷写流程的状态推进不经过它。

4.4 与相邻篇的关系

  • AND-P8-101 给 bootloader 交棒时序，本篇给交棒前的镜像字节契约，两者是前置与承接。
  • 镜像的构建产出（怎么生成、怎么打包进目标文件）归 AND-P5-101 与 AND-P11，本篇不重复。
  • A/B 与虚拟分区的策略层（何时切、如何回滚）归 P11；本篇只描述 fastboot 用哪些函数读这些状态。
  • 系统服务编排（Zygote、SystemServer）属本卷后续篇（卷纲未立项编号前称「后续篇」），不在本篇范围。
  • 厂商 bootloader 内部实现不在本树，本篇只能到 bootloader_message.cpp 的接口边界；BCB 属 recovery/bootloader 侧接口，宿主 flash 链路不读写。

7. 常见问题与误区

7.1 误区

误区一：`boot_img_hdr` 是最新版本的头结构。 错。bootimg.h:133 写的是 typedef struct boot_img_hdr_v0 boot_img_hdr，即别名指向 v0。v0（:80-127）里没有 recovery_dtbo_size 与 header_size，这两个字段要到 boot_img_hdr_v1（:169-173）才出现；按「最新字段」写解析代码必然错位。

误区二：`fastboot flash` 和 `fastboot flashall` 只是刷的分区数量不同。 不完全对。flashall 由 FlashAllTool::Flash（:1792）驱动，会在逐分区刷写之前先 set_active（:1542，内部先 supports_AB 判 A/B、再 get_current_slot 取当前槽）。单分区 flash 走 do_flash（:1509-1538）→ flash_buf（:1254），不碰 slot。vbmeta 重算（rewrite_vbmeta_buffer，:1079）也不在 flash 的常规路径上自动发生——只有 --disable-verity/--disable-verification 置位时才触发。触发时它始终排在 copy_avb_footer（:1171）之后。

误区三：设备上只有一个 fastboot。 错。宿主侧 fastboot.cpp 与设备侧 bootable/recovery/fastboot/fastboot.cpp（107 行）是两套代码，后者是 fastbootd 在 recovery 侧的 UI 集成件（菜单胶水），fastbootd 守护进程主体不在本树。用 is_userspace_fastboot（:1555）才能区分当前在哪一侧。

误区四（看起来对其实是错的）：`--page-size` 只是个性能参数。 它同时是镜像布局参数。默认 2048（fastboot.cpp:618 的用法文本给出该默认值，取值约束在 mkbootimg.py:537），打包与下发两侧必须一致，否则设备按错位解释头部。

7.2 高频提问

问：boot 与 flash 都下发镜像，差别在哪？ 答：boot 下载后直接启动，不落盘；flash 走 do_flash（:1509）写入具名分区。 追问：那调试时为什么不都用 boot？ 答：boot 不验证「写盘后的实际布局」，落盘路径的问题只能靠 flash 复现。

问：getvar is-userspace 返回真，说明设备已经在 fastbootd 里了吗？ 答：是。is_userspace_fastboot（:1555）就是这一判断的代码落点：它向设备 GetVar("is-userspace") 并比对返回值。返回真表示当前会话走的是用户态 fastboot；设备侧对应 bootable/recovery/fastboot/fastboot.cpp 那套 recovery UI 集成件（fastbootd 守护进程主体不在本树）。 追问：此时 flashing unlock 还能用吗？ 答：取决于当前执行体。命令是否被接受由当前执行的一侧决定，不能只看命令名。
