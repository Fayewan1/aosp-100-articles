1. TL;DR

Android 的安全不是一道门，是若干道门串成的一条链：bootloader 验镜像、内核与 SELinux 限权、HAL 与 TEE 守住密钥、框架层管权限与签名、应用侧靠沙箱隔离。每一层只负责「挡住什么」，不负责「兜住全部」；任何一层的价值都在于失守后下一层仍在。理解这套架构的关键不是记住有多少机制，而是记住每层边界的划定物：neverallow 规则、protectionLevel、SecurityLevel 枚举、签名白名单。本篇只讲分层的组织方式与威胁模型，不拆任何一层的实现细节。

3. 问题背景

一个应用进程为什么只能读自己的 /data/data/<pkg>，为什么读不了别的应用的私有目录，为什么即使拿到 root 也未必能改某个分区？这三个问题常被当成同一个问题，其实答案分布在不同层。反过来，碰到「某个文件明明有权限却打不开」「某个系统属性读不到」「某个 HAL 服务连不上」时，很多人的排查路径是从报错往回猜，而不是先判断这件事该由哪一层裁决。分层认不清，排查就只能靠试。本篇先把层的顺序与每层的裁决点摆出来。

4. 核心机制

4.1 概念与关系

四个关键概念：

  • 强制访问控制（Mandatory Access Control，MAC）：SELinux 在自主权限（DAC）之外再加一道判定，主体类型与客体类型不匹配就拒绝，root 也不例外。
  • 自主访问控制（Discretionary Access Control，DAC）：传统 Unix 的 uid/gid/权限位，由属主自行决定。
  • 信任根（Root of Trust）：一段不可被上层修改的代码或密钥，作为验证的起点；本树内只能看到它向下的接口（KeyMint 的 SecurityLevel），不包含它自身。
  • 攻击面分层：按「谁能被谁触达」切层，而不是按代码模块切；同一模块可以横跨两层。

关系不是「串成一条链、上一层失守由下一层兜住」。层与层之间是依赖加独立信任边界两种关系，混着看才会判断错：某一层失守，哪些机制跟着一起失效、哪些仍能独立成立，才是威胁模型要回答的问题。

这张图的读法有三条。第一，上游依赖不可自证：bootloader/AVB 不成立，后面关于「镜像可信」的一切推断都不成立，而不是「由内核兜住」。第二，同一执行环境里的机制会一起失效：内核被攻破，SELinux、seccomp、DAC、卷加密密钥的保护同时崩塌，它们之间不存在互相兜底；此时仍成立的只有 TEE/StrongBox 里的密钥材料不可导出这一条。第三，标了「依赖框架」的机制，其强度止于框架进程：权限授予状态、app op 状态都存在 system_server 里，能改这些状态就改了判定结果，SELinux 只能约束「哪个进程能改」，不能保证「改不了」。

4.2 关键内容

威胁模型按攻击面分层组织，顺序固定：bootloader（不在本树）→ TEE/StrongBox → 内核 → HAL → 框架 → 应用。每层要回答三个问题：边界用什么划定、越过边界需要什么、越过后下一层是什么。

内核层的划定物是 `.te` 策略文件。 平台策略源在 system/sepolicy/private 与 system/sepolicy/public 两个目录下，共 501 个 .te（private 356 ＋ public 145）；若把 vendor 89 个、microdroid 61 个也数进来，全树非 prebuilt 是 652 个——本篇后续所有计数都按前一口径，换口径要连数一起换。策略不是靠数量取胜，而是靠三类语句的分工：

名称含义出处
allow放行某类型主体对某类型客体的操作，共 4591 条private＋public 的 .te，行首锚定
neverallow编译期断言，任何 allow 与它冲突即构建失败，共 1172 条同上
type定义 SELinux 类型，共 1594 个同上

这三个数只在「只数 .te、行首锚定」的口径下成立；同一批文件里还有 148 条 allowx 一类的变体，放宽或不放宽差出几百条，所以引用时必须带命令（见 §6）。

neverallow 的作用方式值得强调：它不是运行时判定，而是构建期把「不该存在的放行」变成编译错误。这意味着策略的防线有一部分前移到了构建环节。

public 与 private 的目录切分本身就是架构边界。 system/sepolicy/public 是 vendor 可见面，system/sepolicy/private 是平台自有面。vendor 只能依赖 public 里的类型与属性；平台想在 private 里改动，不必担心破坏 vendor 的编译。system/sepolicy/compat/ 下的 plat_sepolicy_genfs_202504.cil、_202604.cil、_202704.cil 三个文件不是「让不同 target API 的模块共存」的映射表，而是 genfs 标签的版本化产物：system/sepolicy/Android.bp:580-594 按 BOARD_GENFS_LABELS_VERSION 生成版本号文件，:673-676 按同一个变量把对应的 .cil 选进 device_first_srcs；运行时由 system/core/init/selinux.cpp:333-347 读 /system/etc/selinux/plat_sepolicy_genfs_<版本>.cil，读不到就记日志跳过（202504 及以上才报错）。也就是说，选哪个文件由板级变量决定，与应用的 target SDK 无关。

API 分层同样有版本快照。 system/sepolicy/prebuilts/api/202604/ 保存 private 349 ＋ public 145 个 .te 的快照。快照存在的原因与 neverallow 同源：策略是跨版本契约，得有一个「当时长什么样」的基准。

框架层的划定物是权限等级。 frameworks/base/core/res/AndroidManifest.xml 里有 1160 个 <permission> 元素、19 个 <permission-group> 元素（按行 grep -c '<permission ' 只得 1116，漏掉 44 个属性换行书写的标签；grep -o 'protectionLevel=' | wc -l 得 1160，可交叉印证）。protectionLevel 按完整串计：normal 87、dangerous 42、signature 298、signature|privileged 298、internal|role 114、signature|role 48；若按首个 flag 分族，则是 signature 864、internal 133、normal 108、dangerous 51，两种口径差在几十种带附加 flag 的组合上（如 signature|privileged|role 34、signature|privileged|development 24、dangerous|instant 8、normal|instant 18）。

等级越高，授出条件越苛刻，但苛刻的方式不是「并且」而是「或」。signature 一档要求申请方与声明方签名一致；signature|privileged 的判定在 AppIdPermissionPolicy.kt:1143-1160 写得清楚：先算 mayGrantByPrivileged（不在特权档，或过了特权白名单检查），再算 shouldGrantBySignature 与 shouldGrantByProtectionFlags，最后取 mayGrantByPrivileged && (shouldGrantBySignature || shouldGrantByProtectionFlags)。也就是说签名与 protection flags 是两条并列通道，特权白名单是与它们相乘的门控；把 signature|privileged 读成「签名一致并且还得在特权分区」会把其中一条通道漏掉。

签名白名单把「谁签的」接进 SELinux。 system/sepolicy/private/mac_permissions.xml 共 77 行，做的是 MMAC：把 seinfo 与签名证书对应起来。于是「同一签名」这件事不只影响权限授予，也影响进程落在哪个 SELinux 域。

数这份白名单要小心注释：grep -c '<signer' 得 10，但文件开头 :4-47 是一整块注释，里面放了 4 个示例 <signer>；真正生效的只有 6 个，分别在 :50（@PLATFORM）、:55（@SDK_SANDBOX）、:60（@BLUETOOTH）、:65（@MEDIA）、:69（@NETWORK_STACK）、:74（@NFC）。本篇后续提到条数时按 6 个计，并给出排除注释的取法（见 §6）。

init 负责把策略装上并决定是否强制。 system/core/init/selinux.cpp 共 844 行；EnforcingStatus 枚举在 :101（SELINUX_PERMISSIVE/SELINUX_ENFORCING），IsEnforcing() 在 :114，kernel_enforcing 判定在 :433（security_getenforce() == 1）。这一步发生在任何应用进程被拉起之前。

seccomp 是 SELinux 之内再收一层系统调用面。 bionic/libc/seccomp/seccomp_policy.cpp 共 319 行，install_filter 在 :193。SELinux 管「能不能对某类型客体做某操作」，seccomp 管「这个系统调用能不能进内核」，粒度不同。

密钥安全等级不是「密钥放在哪」这一个刻度，而是两种用法。 hardware/interfaces/security/keymint/aidl/android/hardware/security/keymint/SecurityLevel.aidl:20-29 写明了：一是由 IKeyMintDevice::getHardwareInfo 返回，刻画实现本身跑在什么环境里；二是与单个授权 Tag 关联，刻画强制这个 Tag 的最弱环境——即攻击者要攻破哪一层才能破坏该 Tag 的强制。枚举值仍是 SOFTWARE=0、TRUSTED_ENVIRONMENT=1、STRONGBOX=2、KEYSTORE=100，注释引 CDD 9.11.1 [C-1-2] 与 CDD 9.11.2 作为合规依据。

KEYSTORE 这一档是两种用法分家的证据：:67-75 明确「KeyMint 实现永远不得从 getHardwareInfo 返回 KEYSTORE」，它只用于那些不由 IKeyMintDevice 强制、而由 Keystore 自己强制的 Tag，并且注释直说「能攻破 keystore 进程、拿到 root 或攻破内核的人，就能阻止这些 Tag 被正确强制」。所以这一档不代表更强的硬件，反而代表保护强度止于 Keystore 进程——它是 §4.1 里「依赖框架」那一条的现成例子。框架层能问的只有「这把密钥/这个 Tag 落在哪一级」，问不到它具体在哪块硬件里。

4.3 一个具体例子

假设一个应用要存一把用于签名的私钥。

它调用 Keystore 2，请求生成的密钥带强绑定要求。这条链的关键在于：安全等级不是 KeyMint 事后「回答」的，而是调用方选定、Keystore 2 在构造期就备好的。顺序如下：

第一步，Keystore 2 服务启动时就构造两级实例——service.rs:70-90 先建必选的 TRUSTED_ENVIRONMENT 实例（建不出来整个服务直接返回错误，日志会问「Does the device have a /default Keymaster or KeyMint instance?」），再可选地建 STRONGBOX（失败就忽略）。第二步，service.rs:402-407 的 IKeystoreService::getSecurityLevel(security_level) 按调用方请求的等级，把对应的 IKeystoreSecurityLevel 实例交出去。第三步，主路径 generate_key（security_level.rs:684 起）的三个出口（:750/:766/:805）都不直接碰 HAL，而是交给重试助手 generate_key_and_retry_on_att_id_mismatch（:623）——常规调用落在 :633 的 self.keymint.generateKey(params, attest_key)，只有报 CANNOT_ATTEST_IDS 一类错误且版本与 IMEI 标签俱备时，才在 :680 用交换过 IMEI 的参数再试一次；返回的 KeyMetadata 在 :229-235 里把 keySecurityLevel 填成这个实例自己的等级——所以元数据里的等级是实例的既定属性，不是验算出来的结论。第四步，密钥材料始终不进入应用进程地址空间，应用拿到的是句柄；若应用进程被攻破，攻击者能拿到句柄但不能导出材料。

至于「谁能连上 Keystore」：普通应用域是在策略里显式放行的——system/sepolicy/private/app.te:186-190 给出 keystore:keystore2_key 的一组操作与 use_keystore(...)，system/sepolicy/public/te_macros:680-688 把这个宏展开成 apc_service/keystore_service/legacykeystore_service 三个 service_manager find 与双向 binder_call（宏体 :683-687）。真正的 uid、SID 与 key permission 检查发生在 Keystore 进程内部，不在这几条 allow 里。

把这些层拆开看：没有框架层判定，任意应用都能请求；没有 TEE 实例，密钥材料会由软件实现落地；没有 SELinux，被攻破的进程连不到服务（但反过来说，SELinux 只管「连得上连不上」，管不了「连上之后 Keystore 自己怎么判」）。这正是 §4.1 那张依赖图的实际含义——每一层管的事不一样，失守的后果也不一样。

4.4 与相邻篇的关系

  • AND-P9-102 承接 bootloader 与验证启动，本篇只把它列为攻击面的第一层。
  • AND-P9-201 展开权限模型，本篇只用 protectionLevel 分布说明框架层裁决点的形态。
  • AND-P9-202 展开应用沙箱，本篇的「uid + SELinux 域」只作为链条末端一句。
  • AND-P9-301 展开 APK 签名验证，本篇只用 mac_permissions.xml 的 6 个生效 <signer> 说明签名如何接入 SELinux。
  • AND-P9-401 展开密钥存储，本篇只用 SecurityLevel 枚举说明 TEE 层的抽象粒度。

分工原则：本篇给顺序与边界，后续篇给每层内部的机制与失败形态。

7. 常见问题与误区

7.1 误区

误区 1：以为开了 SELinux 就等于应用被隔开了。 纠正：SELinux 管的是类型之间的操作许可，应用之间的隔离首先由 uid 决定。两层判定顺序不同、粒度不同，缺一层都会留下空档。

误区 2：以为 `neverallow` 是运行时拦截。 纠正：它在构建期让冲突的 allow 直接编译失败。策略的一部分防线前移到了构建环节，所以「线上没报错」不能证明策略没问题。

误区 3：以为 KeyMint 的 `SecurityLevel` 是在描述密钥有多强。 纠正两层。第一层，它刻画的不是「强度」而是「环境」：SecurityLevel.aidl:20-29 明说它有两种用法——getHardwareInfo 返回的是实现所在的执行环境，与单个 Tag 关联时表示的是强制该 Tag 的最弱环境。第二层，KEYSTORE=100 不是更强的硬件：:67-75 规定它永不由 getHardwareInfo 返回，只用于由 Keystore 自己强制的 Tag，注释直承「攻破 keystore 进程或内核即可阻止这些 Tag 被正确强制」。所以这四个值既不是强度排序，也不都是位置；KEYSTORE 是保护边界止于进程的那一档。

误区 4（看起来对其实是错的）：以为 public 与 private 只是目录整理习惯。 纠正：public 是 vendor 可见面、private 是平台自有面，这个切分是跨分区契约的物理载体。把平台内部类型挪进 public 会扩大 vendor 的依赖面，改动成本随之锁定。

7.2 高频提问

问：signature 与 signature|privileged 数量都是 298，是不是统计重复了？ 答：不是重复，是两个不同的 protectionLevel 取值碰巧同为 298 条。但不能反过来推断「它们是同一批权限的两种版本」——signature|privileged 的判定是 mayGrantByPrivileged && (签名一致 ‖ protection flags)（AppIdPermissionPolicy.kt:1143-1160），与纯 signature 走的是不同分支；而且带附加 flag 的组合另有几十种（如 signature|privileged|role 34 条），不在两个 298 里。 追问：那应用该申请哪一档？ 答：本篇只解释等级语义，具体申请策略属于权限模型的边界，见 AND-P9-201。

问：system/sepolicy/compat/ 下三个 .cil 是不是对应三次发版？ 答：不是按发版轮次准备的。它们是 genfs 标签的版本化产物，选哪个由板级变量 BOARD_GENFS_LABELS_VERSION 决定（Android.bp:580-594 生成版本号、:673-676 选文件），运行时 selinux.cpp:333-347 读 /system/etc/selinux/plat_sepolicy_genfs_<版本>.cil，读不到就记日志跳过。与应用 target SDK 无关。 追问：为什么不直接改策略源？ 答：策略源是跨版本契约，快照与版本化产物的存在就是为了让旧基准不被改写。
