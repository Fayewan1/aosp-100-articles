1. TL;DR

/sys/power/state 写 mem 就挂起，写之前必须先回写 /sys/power/wakeup_count。这个「先回写计数、再写状态」的顺序不是仪式，而是消除竞争的唯一手段：计数写失败说明这段时间里已经出现新的唤醒事件，本轮必须放弃。libsuspend 的自动挂起循环把这两步包在 sem_wait(&suspend_lockout) 之后，失败后睡眠时间翻倍，上限一分钟。想判断「谁阻止了睡眠」看 /sys/power/wakeup_count 与内核 wakeup 源计数；想判断「谁把它唤醒」只能靠事后计数对比与 wakeup 源统计，/sys/power/state 本身不告诉你答案。

3. 问题背景

设备放在桌上，屏幕灭了，电池却在一夜之间掉了两成。或者反过来：抓到的日志里系统明明已经进入挂起，几分钟后又自己醒了，却找不到是谁按的键。这两种现象在同一个路口分岔——内核到底有没有真的睡下去，以及是谁在最后一刻把计数改掉了。

多数人第一步会去翻 /sys/power/state 和框架的唤醒锁记录，然后卡住：前者只有一个状态字符串，后者只能证明「某个进程持有锁」，不能证明「内核拒绝了挂起」。真正决定成败的是 /sys/power/wakeup_count 的读写顺序。

本篇只走内核侧这条通路。上层省电策略归 P9/P10，唤醒锁在框架层的表达归 P2。

4. 核心机制

4.1 概念与关系

三个概念构成一个闭环：系统睡眠状态（system sleep state，mem 这一类字符串）是写入 /sys/power/state 的目标；唤醒计数（wakeup count，/sys/power/wakeup_count）是可读可写的整数，任何唤醒事件发生都会让内核侧的计数增长；唤醒源（wakeup source）是内核里被标记为可唤醒系统的设备节点，它的 active 状态决定挂起请求会不会被拒。

图 1：写状态与回写计数的先后关系

userspace                       kernel
  |                               |
  |-- read wakeup_count --------->|  snapshot N
  |<-- "N" -----------------------|
  |                               |  (期间若有唤醒事件，计数变 N+k)
  |-- write "N" to wakeup_count ->|
  |<-- 成功: 挂起请求入队 ---------|
  |<-- 失败: EINVAL/短写 ---------|  N != 当前计数
  |                               |
  |-- write "mem" to state ------>|  进入 suspend

先回写计数，成功才写状态。回写是「我认领 N 这个时刻」，内核在挂起流程末尾再比对一次；不一致就拒绝。

4.2 关键内容

libsuspend 对外只有四个入口，见 system/core/libsuspend/include/suspend/autosuspend.h。

名称含义出处
autosuspend_enable()启动自动挂起循环线程autosuspend.h
autosuspend_disable()停止循环并退出挂起模式autosuspend.h
autosuspend_force_suspend(int timeout_ms)绕开循环，立即强制挂起一次autosuspend.h
autosuspend_set_wakeup_callback(void (*func)(bool success))注册唤醒回调，参数是上一次挂起是否成功autosuspend.h

初始化路径唯一：autosuspend_init() 内 autosuspend_ops = autosuspend_wakeup_count_init();，拿不到即 ALOGE("failed to initialize autosuspend") 并返回 -1。也就是说 wakeup_count 方案不是多选项之一，而是唯一实现源。

挂起循环的核心是顺序。suspend_thread_func() 先 update_sleep_time(success) 再 usleep(sleep_time)，然后 lseek(wakeup_count_fd, 0, SEEK_SET) 并 ReadFdToString(wakeup_count_fd, &wakeup_count) 取快照。真正落笔前 sem_wait(&suspend_lockout) 占住锁，随后先 WriteStringToFd(wakeup_count, wakeup_count_fd)，成功才 WriteStringToFd(sleep_state, state_fd)。

写 wakeup_count 失败就是本轮放弃的信号：这段时间内出现了新唤醒事件，认领的时刻已经过期。失败分支不向调用方报错、也不重试，仅在用户态记一条 PLOG(ERROR) << "error writing to " << sys_power_wakeup_count（autosuspend_wakeup_count.cpp:103），随后回到循环顶部重新取快照——所以从 API 返回值上看不出这次失败，日志里才有。

退避策略在 update_sleep_time() 里，注释原句 "double sleep time after each failure up to one minute"，BASE_SLEEP_TIME 100000、MAX_SLEEP_TIME 60000000，单位微秒。首次等待 0.1 秒，每失败一次翻倍，封顶 60 秒。

force_suspend(int timeout_ms) 走另一条路：先 init_state_fd() 再直接写 sleep_state，不经过唤醒计数比对。init_state_fd() 用 TEMP_FAILURE_RETRY(open(sys_power_state, O_CLOEXEC | O_RDWR)) 打开状态节点。

4.3 一个具体例子

假设某个后台任务每隔几秒唤醒一次。循环第一次：读计数得 N，回写 N 成功，写 mem。挂起流程末尾比对时计数已变成 N+1，挂起被拒，回调收到 success=false。update_sleep_time 把 100000 微秒翻成 200000。

第二轮读计数得 N+1，回写失败（写进去的是 N+1，内核侧已是 N+2），本轮直接放弃，连 mem 都没写。再翻倍到 400000。如此下去，等到后台任务停下来，某轮回写终于成功，且比对时没有新增事件，系统真正睡下去。

这解释了为什么「看起来系统一直在尝试挂起」但电没省下来：失败次数越多，重试间隔越长，日志里两次尝试之间的空档会拉大到一分钟。

7. 常见问题与误区

7.1 误区

误区一：写 `/sys/power/state` 成功就等于系统睡着了。 写进去只是发出请求，内核在挂起流程末尾还要比对唤醒计数与唤醒源状态，任何一处不满足都会中止。用户态看到的写成功不代表进入 mem。

误区二：`/sys/power/wakeup_count` 只能读。 它必须可写，回写是消除竞争的关键动作。只读不写的挂起实现存在时间窗：取快照到真正挂起之间出现的唤醒事件会被吞掉。

误区三：`autosuspend_force_suspend()` 是「更可靠的挂起」。 它跳过计数比对直接写状态，恰恰放弃了竞争保护。看起来对其实是错的——它适合的是有明确超时约束的一次性场景，不是日常通路的加速版。

7.2 高频提问

问：自动挂起循环失败后为什么要翻倍等待，而不是立刻重试？ 答：立刻重试在一段持续有事件的时间里只会反复写失败，白耗 CPU；翻倍把重试频率压下去，上限一分钟，等事件潮过去。 追问：那怎么知道是「事件潮」还是「某个唤醒源一直 active」？ 答：这两者用户态可观测现象不同。前者计数在涨但最终会停；后者计数稳定，挂起请求每次都卡在唤醒源检查上，需要去看具体唤醒源的 active 计数。

问：SNAPSHOT_S2RAM 和写 mem 是一回事吗？ 答：不是。suspend_ioctls.h 里的这组 ioctl 走快照/休眠通道，与 /sys/power/state 不同层，语义是冻结进程加内存快照，不是本文讲的系统睡眠。 追问：那为什么两者都叫 suspend？ 答：命名撞车，实现路径完全不同。排查问题时先确认是哪条通道，再谈现象。
