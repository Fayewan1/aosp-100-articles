1. TL;DR

dumpsys meminfo 打出来的 PSS 族四类口径（USS、SwapPss、Rss、memtrack）的每个数字都来自 Debug.java → android_os_Debug.cpp，但底部分两条：前三类经 ProcMemInfo.SmapsOrRollup 读 /proc/pid/smaps_rollup（rollup 不可用时回退解析 smaps）的 pss/rss 字段（android_os_Debug.cpp :293、procmeminfo.cpp :334-337；这是简要分支——同一套 ProcMemInfo 另有详细分支，Android 堆 stats 走 system/memory/libmeminfo/androidprocheaps.cpp :25-29 直读全量 /proc/pid/smaps），memtrack 一类走 memtrack HAL；注意 android_os_Debug.cpp :288 的预置关系——read_memtrack_memory 成功时 pss、uss、rss 同时被赋成 memtrack 三项之和，随后 :293-296 才在之上累加 SmapsOrRollup 的结果，所以 memtrack 已折进返回的 pss/uss/rss，四类口径不互斥（android_os_Debug.cpp :142-174，取 smaps 未计入的图形/显存类分配，:176-177 注释明示）；App Summary 段的 native/dalvik 堆与对象/binder 计数不走这条链（由目标进程经 thread.dumpMemInfo 自行取数，见 §7.1 误区三）。RSS 是「页在不在这个进程的页表里」，PSS 是「按共享页分摊后的份额」，USS 是「独占」，三者对同一进程单调递减。整机汇总另走 MemInfoReader，LMKD 只看 oom_score_adj 槽位与 PSI 压力，不看 PSS。native 泄漏的定位不是看某个数字变大，而是看同一口径在多次采样间的斜率，再用 memtrack 与调用栈产物把归因收到具体分配点。

3. 问题背景

线上反馈「这个进程内存一直涨」。你 adb shell dumpsys meminfo <pid> 一看，TOTAL PSS 比昨天大了 30 MB，于是判断泄漏。但如果涨的是 RSS、PSS 没动，那只是共享页被算进了页表；如果 PSS 涨而 USS 没涨，那是共享库或 dma-buf 被动增长。三种情况的归因路径完全不同，而 dumpsys meminfo 把四类口径并排打印，恰恰是为了让你能区分它们。分辨不清口径，后面的 native 泄漏排查一定会走错方向。

4. 核心机制

4.1 概念与关系

四类口径是同一个进程内存的不同切法，不是四个不同的东西。

图 1：四类内存口径的包含关系（自外向内收窄）

RSS  ── 该进程页表里映射的物理页总量
 └ PSS ── 共享页按映射进程数分摊后的份额
    └ USS ── 只被本进程映射的独占页
SwapPss  ── 已被换出/压缩的页，按 PSS 同样规则分摊
  • RSS（Resident Set Size）看的是「页在不在」，不区分共享。
  • PSS（Proportional Set Size）把每个共享页除以映射它的进程数，避免整机求和时重复计数，所以整机 PSS 相加才有意义。
  • USS（Unique Set Size）只统计独占页，进程被杀后能实际还给系统的量。
  • SwapPss 与 PSS 同构，但对象是已被换出或被 zram 压缩的页。

这四类口径由 android_os_Debug_getPssPid 一次读齐。Java 侧的 getPss(int pid, long[] outUssSwapPssRss, long[] outMemtrack) 就是它的包装：两个出参数组分别装前三类口径与 memtrack 口径。

4.2 关键内容

取数链路分三段：Java 入口、JNI 实现、内核与 /proc。

第一段在 Debug.java，三条入口语义各不相同，最容易记混。getMemoryInfo(MemoryInfo) 取的是本进程 dalvik/native/other 的 PSS 分项，JNI 落 android_os_Debug_getDirtyPages（:820-823 注册），内部以 getpid() 转调 android_os_Debug_getDirtyPagesPid（:272/:274）；getMemoryInfo(int pid, MemoryInfo) 是按 pid 取同一套分项，返回 boolean 表示读取是否成功；两者都只填单进程堆分项，与整机、与「类型」无关。真正把 USS、SwapPss、Rss、memtrack 四类口径一起带回来的是 getPss(int pid, long[] outUssSwapPssRss, long[] outMemtrack)。

第二段在 android_os_Debug.cpp。android_os_Debug_getPss 内部以 getpid() 转调 android_os_Debug_getPssPid；android_os_Debug_getDirtyPagesPid（:192）经 ExtractAndroidHeapStats（:200）填 dalvik/native/graphics/gl/other 的 pss/privateDirty/rss 分项；android_os_Debug_getMemInfo（:428，注册 :828）绑的是 Java 侧 Debug.getMemInfo(long[] outSizes)（Debug.java :2118，注释写明读 /proc/meminfo），即 MemInfoReader 的底层，不是 MemoryInfo。以上几段语义不同，不要混看。

第三段是 MEMINFO_* 下标常量。它们寻址的对象是 getMemInfo 的出参 long[]（Debug.java :2118，MEMINFO_COUNT=29 于 :2110），错一个下标就会把 Cached 当成 Slab 读。

4.3 一个具体例子

假设某进程 dumpsys meminfo 里 TOTAL PSS 连续三次采样为 A、A+10、A+20（单位省略，本篇不断言任何设备上的实测内存占用数值）。判断顺序如下。

先看 RSS 有没有同步上涨。RSS 涨、PSS 不动，说明共享映射变多，比如多加载了一个被别的进程也在用的库，这不是泄漏。

再看 USS。PSS 涨而 USS 平，说明涨的部分是共享口径，可能是 dma-buf 或共享库被反复映射。USS 与 PSS 同步涨，才落在「本进程独占内存增长」这个分支上。

最后看 memtrack 出参。getPss(int pid, long[] outUssSwapPssRss, long[] outMemtrack) 一并带回的 memtrack 数组，就是用来区分「图形/显存类分配」和「普通 native 堆」的开关。memtrack 涨得多，就不要去翻 malloc 调用栈，去查图形缓冲的生命周期。

7. 常见问题与误区

7.1 误区

误区一：PSS 涨了就是泄漏。 错。PSS 是按共享页分摊的份额，共享库、dma-buf 的映射变化都会推高它，进程自身并没有多持有内存。只有 USS 同向上涨，才落在「本进程独占内存增长」分支。

误区二：RSS 可以直接跨进程相加当整机占用。 错。共享页在每个进程的 RSS 里都计一次，相加会重复。整机求和要用 PSS，这也是 PSS 存在的原因。

误区三（看起来对其实是错的）：`dumpsys meminfo` 的数字是客户端 dumpsys 进程算出来的。 错。"meminfo" 是 ActivityManagerService 注册的服务；PSS 汇总由 system_server 侧 Debug.getMemoryInfo(pid) 读 /proc 得出（ActivityManagerService.java :13016 入口、:13903），app 进程的详细段与 App Summary 则由目标进程经 thread.dumpMemInfo → ActivityThread.dumpMemInfo 排版回写——但数据归属要分清：App Summary 里 Java Heap:/Native Heap:/Code:/Stack: 各行的 PSS 全部取自入参 memInfo，而该 memInfo 是 system_server 在 ActivityManagerService.java :13245 用 Debug.getMemoryInfo(pid, mi) 取到、经 :13281-13284 跨 binder 传进来的；目标进程本地只取 Heap Size/Alloc/Free（:1859-1867）与 Objects/SQL/binder 段（:1869-1890）（ActivityManagerService.java :13281 委派；ActivityThread.java :1803/:1856，native 堆经 Debug.getNativeHeapSize 系列（JNI 内走 mallinfo，android_os_Debug.cpp :114/:120/:126），dalvik 堆经 Runtime.totalMemory/freeMemory，两段分别落在 :1859-1861 与 :1863-1867）。客户端始终不算数，核心结论不变。

误区四：LMKD 是按 PSS 挑进程杀的。 错。LMKD 扫描的是 oom_score_adj，从 OOM_SCORE_ADJ_MAX=1000 向下扫；killcnt[] 也按 ADJTOSLOT(adj) 槽位计数，这套结构里没有 PSS 的位置。唯一沾到 Pss 的是同一 adj 槽位内挑「最重」那个进程时的 tasksize 计量——proc_get_heaviest（:2294）把 dmabuf_pss 折进页数累加（:2307/:2310-:2312），且只用于槽位内排序，不决定杀不杀。另有一处易混：kill_one_process 在 :2479 声明 dmabuf_pss_bytes、:2509-2512 读 dmabuf_pss，但只进 kill 统计与 desc/statslog 上报，同样不参与决策——参与杀进程决策的 PSS 计量只有 proc_get_heaviest 的 tasksize 一条。

7.2 高频提问

问：为什么 getPss() 和 getPss(int pid, ...) 结果不一样？ 答：前者只取本进程，且只带回 PSS 一个量；后者收一个 pid、带回四个数组口径。实现上前者走 getpid() 转调 android_os_Debug_getPssPid，后者给的是同一个底层取数函数的完整出参。追问：那我要看 USS 该用谁？答：只能用带出参数组的那一个，USS 在 outUssSwapPssRss 里，单返回值接口拿不到。

问：整机内存为什么不能从 Debug.getMemoryInfo 和 MemInfoReader 拼？ 答：getMemoryInfo 填的是单进程堆分项，跟整机无关；整机那一路是 MemInfoReader.readMemInfo() 内部调 Debug.getMemInfo(long[] outSizes)（Debug.java :2118）读 /proc/meminfo，MEMINFO_* 下标寻址的正是这个 long[]，不是 MemoryInfo。切片用 getTotalSize()、getFreeSize()、getCachedSize()、getKernelUsedSize()。追问：swap 和 zram 看哪个？答：getSwapTotalSizeKb() 与 getZramTotalSizeKb()，两个都读，不要互相替代。
