1. TL;DR

「AOSP 到产品」不是一条单向流水线，而是一组可核入口的串联：lunch() 定产品与变体，make() 把 Android.bp 交给 Soong，releasetools 生成 target files 与 OTA，update_engine 消费 payload。

本篇不做机制复述，只做清单式收口：每个阶段给出一个树内可核的入口、一个产物路径、一条判据。判据都是静态可核的，不含实测耗时与体积。

一次交付是否「做完了」，可以用五步判据串起来查：版本锚点 → 构建 → 测试 → 发布配置 → 更新资产。

本篇是 P11 卷收卷篇，逐条指向 P0–P11 的承接篇，本身不引入新机制。

3. 问题背景

产品线交付到第三次，团队开始问同一个问题：这次改动到底经过了哪几道门？

有人拿出 out/ 目录说构建过了，有人拿出 CTS 报告说测过了，有人说 OTA 包在别人的机器上。三份证据互相对不上，因为没有共同的判据。

更麻烦的是版本锚点。manifest 的默认 revision 是 android17-release（.repo/manifests/default.xml :7），只有 platform/superproject（:11）另标 android-latest-release——镜像到底出自哪个 release config、哪一次同步，事后查不清。

本篇要解决的就是这个：把「做没做」从口头确认变成树内可核的路径与入口。

4. 核心机制

4.1 概念与关系

五个概念。版本锚点：manifest 的默认 revision（android17-release），决定所有仓的基线。构建入口：lunch() 按 <product>-<release>-<variant> 三元组选产品、release config 与变体（三者独立：TARGET_RELEASE 决定取哪份 release config，TARGET_BUILD_VARIANT 决定 user/userdebug/eng），make() 转 Soong。测试门：CTS 与 VTS 各自的目录与套件。发布配置：build/release/release_configs/ 下的 textproto。更新资产：releasetools 的产物与 update_engine 的 payload。

4.3 一个具体例子

拿一次「只改一个模块」的交付走一遍判据链。

版本锚点：查 manifest，确认在 android17-release 组内，树内 1087 个项目。构建：lunch() :535 选产品与变体，再用 tapas() :674 指定模块组，不触发整包。测试：改动落在 frameworks 侧则跑 cts/tests，落在 HAL 侧则跑 test/vts。发布配置：若变体是 user，对应 release_configs/ 里的 user textproto。更新资产：build/make/tools/releasetools/ 生成 target files，system/update_engine/ 侧消费 payload。

每一步的产物都是文件系统上的一条路径，不是一句口头结论。任一环缺路径，这次交付就不成立。

7. 常见问题与误区

7.1 误区

「out/ 目录有产物就等于构建通过」。产物存在只说明某次 make() 跑到了收尾，不说明对应哪个锚点、哪个变体。判据要落到 manifest revision 与 lunch() 的产品变体上。

「CTS 和 VTS 都在跑测试，随便报一份即可」。两者分属 cts/ 与 test/vts 两个顶层位置，覆盖面向不同。报错目录，等于报错门。

「`lunch()` 只是设环境变量，选错不影响产物」。lunch() :535 同时定产品与变体，变体直接决定 release_configs/ 里取哪份 textproto。看起来只是环境变量，实际改了发布配置的输入。

7.2 高频提问

问：一次交付最少要核几个入口？答：五步各一个：manifest revision、lunch()+make()、cts/ 或 test/vts、release_configs/ 的 textproto、releasetools 与 update_engine 的产物路径。追问：能少核吗？答：能少核，但要明说欠哪一步，不要用别的步骤的结论顶上。

问：tapas()/banchan() 和 make() 什么关系？答：同一文件内的两档粒度，:674/:747 构模块组，:1033 转 soong_ui.bash --make-mode 走整包。追问：只改一个模块可以不走整包吗？答：可以，走模块组入口，但测试门的判据不变。
