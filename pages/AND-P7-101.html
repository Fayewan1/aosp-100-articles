1. TL;DR

MediaCodec 是 Android 媒体框架的编解码中枢：它给应用一套「塞入压缩数据、取出解码结果」的同步/异步 API。跨进程边界不在 `MediaCodec` 这一层——Java 门面经 JNI（android_media_MediaCodec.cpp:271/:276 调 MediaCodec::CreateByType/CreateByComponentName）落到 libstagefright 的 native MediaCodec，而后者就在应用进程里：它是个库，不是服务。真正的「出口」在更下游：MediaCodec::GetCodecBase（MediaCodec.cpp:2565）按名字前缀与 owner 决定后端——c2. 走 CreateCCodec()（Codec2），omx. 走 new ACodec（OMX）；这一步之后才跨界。组件的落脚进程分三种：平台软编随 com.android.media.swcodec APEX 跑在 `media.swcodec` 进程（main_swcodecservice.cpp 把 argv[0] 写成 media.swcodec，并把这批组件注册成名为 software 的 component store，见 CodecServiceRegistrant.cpp:827），遗留 OMX 主机在 `media.codec` 进程（main_codecservice.cpp），硬编则由厂商 HAL 服务承载。应用侧持有的是状态机与 buffer 槽位，设备与耗时全在 codec 服务那一侧。理解这条链路，相机预览、录音、视频播放三类场景都共用同一套心智模型。

顺带清一个常见误会：mediaserver 跟 MediaCodec 没关系——main_mediaserver.cpp:49-50 只 instantiate() 了 MediaPlayerService 与 ResourceManagerService。

3. 问题背景

开发者常把卡顿、花屏、首帧慢归咎于「解码太慢」，但定位时往往发现：应用侧的 dequeueOutputBuffer 只是从 native 层的 BufferChannel 取结果，真正的耗时发生在另一个进程——平台软解在 media.swcodec，硬解在厂商 HAL 服务——的组件里。如果不先建立「JNI → 进程内 native 调度 → 进程外组件」的分层心智，就会在错误的地方加日志、在错误的进程里抓 trace。本文的目标，就是把这条链路在代码层面钉死。

4. 核心机制

4.1 数据结构与状态定义

MediaCodec 在 Java 侧是一个状态机门面，核心字段是 mCodecInfo（来自 MediaCodecList 的编解码器描述）与一组 buffer 槽位索引。契约里的生命周期是三大状态 + 子状态（MediaCodec.java:289-292）：Stopped（含 Uninitialized/Configured/Error）、Executing（含 Flushed/Running/End-of-Stream）、Released。configure 把它从 Uninitialized 带到 Configured；start 带到 Executing——落点是 Executing 的第一个子状态 `Flushed`（:304-306，此时 buffer 全在框架手里），一旦第一个输入 buffer 被取出就迁入 Running（大多数人认知里的「运行中」其实是这一子状态）；队列里收到带 BUFFER_FLAG_END_OF_STREAM 标记的输入 buffer 后迁到 End-of-Stream，此时不再收输入但仍吐输出。把 Running 与 Configured 并列成「四态」等于把子状态抬成顶层态，写状态判断时最容易漏掉的是独立旁支 Error。配置阶段通过 MediaFormat 约定输入/输出格式（如 KEY_MIME、KEY_WIDTH）。

图 1：MediaCodec 的三态生命周期与子状态（顶层 Stopped/Executing/Released）

Stopped ── Uninitialized --configure--> Configured
        └─ (任意状态出错) --------------> Error

Configured --start--> Executing ── Flushed(持有全部 buffer)
                                      │ 取出第一个输入 buffer
                                      ↓
                                   Running(生命周期的主体)
                                      │ 送入带 EOS 标记的输入 buffer
                                      ↓
                                 End-of-Stream(不再收输入,仍吐输出)

Stopped / Executing --release--> Released（终态）

4.2 关键流程（含失败路径）

同步模式下，应用主动轮询 buffer；异步模式由回调驱动。两条路径殊途同归，都经过「取空输入槽 → 填数据 → 提交 → 等输出 → 取结果」五步。失败路径主要有三类：配置阶段格式不被支持（configure 抛 IllegalArgumentException/MediaCodec.CodecException）、运行中组件死亡（Binder/HwBinder 断连或 codec 服务进程崩溃），以及资源侧问题——后者要分两层看：init 阶段与 ResourceManagerService 建链失败（调用方权限被拒或服务不可达）时，MediaCodec::init 直接把 mCodec 置空并返回错误；而多客户端争用发生在运行期，组件分配完成后在 kWhatComponentAllocated 分支（MediaCodec.cpp:4826）里经 addResource(MediaResource::CodecResource(...))（:4878）向 ResourceManagerService 登记编解码器资源，争用时由服务端 reclaim、客户端按回调释放——这与 init 失败不是同一处因果，排查时要先分清楚卡在哪一层。注意别把 :2377/:2455 两处 addResource(MediaResource::VideoBatteryResource(...)) 当成资源登记入口：那两处挂在 mBatteryChecker->onCodecActivity 回调里，登记的是电池耗电资源，与编解码器名额无关。

图 2：同步模式 buffer 往返

app --queueInputBuffer(idx)--> MediaCodec(填输入槽)
app <--dequeueOutputBuffer-- MediaCodec(取输出槽)
app --releaseOutputBuffer---> 归还给框架

4.3 关键代码逐段剖析

门面的入口是 createByCodecName（MediaCodec.java:2133），它按名字（如 "c2.android.avc.decoder"）向 MediaCodecList 解析出编解码器信息并构造实例。配置由两个公开重载完成：configure 在 :2411 与 :2441，内部收敛到私有 configure（MediaCodec.java:2453）——这两个重载的声明是 public void configure(，没有 `final`；而 start（:2769）、stop（:2781）、flush（:2825）、release（:2223）与后面几个 buffer 方法都是 public final。写 grep 核对时别漏掉这一处差异。

buffer 提交与回收是高频路径：queueInputBuffer（:3143）把输入槽交还框架，dequeueInputBuffer（:3582）申请一个空输入槽，dequeueOutputBuffer（:4265）取解码结果，releaseOutputBuffer（:4310）归还输出槽。

native 侧 MediaCodec.cpp 是真正的调度员，而它运行在调用方进程里：libstagefright 是被链接进来的库，JNI（frameworks/base/media/jni/android_media_MediaCodec.cpp:271/:276）直接在本地 new 出这个对象。MediaCodec::configure 有两组定义（:2923、:2997，分别对应不同重载/路径），start（:3683）拉起组件，queueInputBuffer（:3831）与 dequeueInputBuffer（:4065）在 native 队列上移动 buffer，flush（:4335）清空缓冲队列。异步路径通过 BufferCallback::onInputBufferAvailable（:1063）与 BufferCallback::onOutputBufferAvailable（:1072）把槽位可用性回推到应用。

跨进程发生在选后端这一步（MediaCodec::GetCodecBase，MediaCodec.cpp:2565）：owner 为 default 或名字以 omx. 开头 ⇒ new ACodec；owner 以 codec2 开头或名字以 c2. 开头 ⇒ CreateCCodec()。选完之后，跨进程通信由 ACodec/CCodec 承担 —— 它们才是站在进程边界另一侧的那一半。

Codec2 组件是编解码的最终执行体。frameworks/av/media/codec2/components/ 下按格式分目录存放 Codec2 组件——软编与软解都有，解码实现如 avc/C2SoftAvcDec.h、aac/C2SoftAacDec.h；这批组件由 media.swcodec 进程注册成一个名为 software 的 component store（main_swcodecservice.cpp:41 设进程名，CodecServiceRegistrant.cpp:827 完成注册；该进程的服务入口位于 com.android.media.swcodec APEX 内，见 main_swcodecservice.cpp 中 /apex/com.android.media.swcodec/... 的 seccomp 策略路径），框架侧经 Codec2 接口与它通信；硬件路径则同样表示为另一个 component store，落在厂商 HAL 服务里。

4.4 与相邻机制的关系

  • 与 MediaCodecList（MediaCodecList.java:225 的 findDecoderForFormat、:249 的 findEncoderForFormat）的关系：MediaCodec 不负责「选哪个编解码器」，那一步由 MediaCodecList 完成。
  • 与相机/录音的关系：相机预览流、录音流都复用 MediaCodec 完成编码（如视频录制），因此本篇是 301/201 的上游。
  • 与图形卷的关系：解码产出的 Surface 直接交给 BufferQueue（见 AND-P6-102），消费侧在图形卷。

7. 常见问题与误区

7.1 误区

  • 「MediaCodec 在应用进程里解码」。这只对了一半：调度确实在应用进程（JNI 直接 new 出 native MediaCodec 对象），真正干活的是进程外的组件——平台软解跑在 media.swcodec，硬解由厂商 HAL 服务承担。应用进程只持状态机与 buffer 槽。
  • 「dequeueOutputBuffer 卡住就是解码慢」。它可能只是在等 codec 服务进程投递输出；耗时既可能在远端组件，也可能只是本地队列空转，两端要分开看。
  • 「看起来对其实是错的」：以为 configure 抛异常一定是参数写错。也可能是该编解码器在当前设备不被 MediaCodecList 选到（能力不匹配），属于选型失败而非格式错误。
  • 「同步比异步更可靠」。两者底层走同一套 native 队列，差异只在谁来轮询；异步只是把轮询交给回调线程。

7.2 高频提问

问：首帧慢该往哪看？ 答：先看 configure/start 是否完成，再看 codec 服务进程那侧的组件初始化耗时（平台软解在 media.swcodec、硬解在厂商 HAL 服务），最后才是 buffer 链路；应用侧 dequeueOutputBuffer 只是末端。 追问：怎么确认问题在远端？ 答：dumpsys media.codec 是观察这条链路的入口（输出内容随实现与版本变化，本树静态不可核验，请以实机输出为准），用它区分本地轮询与远端组件。

问：为什么同一段代码在 A 设备快、B 设备慢？ 答：MediaCodecList 在两设备选到的编解码器不同（软解 vs 硬解），硬解能力由厂商 HAL 决定，框架层不可控。
