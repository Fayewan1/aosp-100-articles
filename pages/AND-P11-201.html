1. TL;DR

产品不是「一个目录 + 一个 makefile」，而是一条 inherit-product 展开链的终值：链上每层只往 PRODUCT_* 变量里叠加——单值变量本地显式赋值优先，列表变量追加——BOARD_* 走板级配置另一条求值路径，最后由构建系统一次性做一致性校验。变体（user/userdebug/eng）在 main.mk 只做合法性与默认值收敛，真正差异落在各模块自己的 TARGET_BUILD_VARIANT 判断上。A/B 由 AB_OTA_UPDATER := true 这一开关整体切换产物形态，动态分区由 PRODUCT_USE_DYNAMIC_PARTITIONS := true 触发超级分区布局生成。goldfish（本树参考设备）把 AB_OTA_UPDATER 显式设为 none——该开关在 board_config.mk :973–:974 的默认值是 true——是读反例的好样本。分区布局的实际落地在 system/fs/fs_mgr/liblp，本篇只到配置层，镜像与 OTA 产物交给 202。

3. 问题背景

你在 lunch 列表里挑了一个产品，加了自己的板子目录，改完 PRODUCT_NAME，构建却报产品重名或 PRODUCT_* 冲突。换到另一台机器上同步同一棵树，同一个产品又变成 A/B 了，因为另一块板子的 BoardConfigCommon.mk 里多了一行。再往下走，PRODUCT_USE_DYNAMIC_PARTITIONS 打开后 super 分区镜像报和 PRODUCT_BUILD_SUPER_EMPTY_IMAGE 互相矛盾。这些现象的共性是：产品配置分散在 device 目录与 build 目录两侧，改一处看不出全貌。本篇把这条链的求值顺序、校验点和开关边界摆出来。

4. 核心机制

4.1 概念与关系

四个概念，一条求值方向。

产品（product）：由 AndroidProducts.mk 声明、被 lunch 选中的那份 makefile，它通过 inherit-product 把上游片段收进来。板级配置（board config）：BoardConfig*.mk 里的 BOARD_* 变量，与产品变量并行求值，两者不是继承关系。变体（variant）：TARGET_BUILD_VARIANT 的三档取值。分区形态：A/B 与动态分区两个正交开关，前者决定更新方式，后者决定分区容纳方式。

图 1：产品配置从声明到校验的求值方向

AndroidProducts.mk 声明产品列表
        |
        v
lunch 选定 -> 产品 makefile 入口（PRODUCT_NAME）
        |  inherit-product 逐层展开
        v
product_config.mk 汇总 PRODUCT_*
board_config.mk 汇总 BOARD_*，交叉校验
        |
        v
main.mk 收敛 TARGET_BUILD_VARIANT
        |
        v
Makefile 按 AB_OTA_UPDATER 等开关切产物分支

关系要点：PRODUCT_* 分两类——单值变量（如 PRODUCT_NAME，product.mk :25 列入 _product_single_value_vars）本地显式赋值优先于继承值，列表变量（如 PRODUCT_PACKAGES）按继承链追加；BOARD_* 不参与 inherit-product 的继承展开，但「只在板级文件里累积」是错的：产品 makefile 先于板级文件被求值（envsetup.mk :351 → product_config.mk :234 → node_fns.mk :190，而 board_config.mk :254 才 include BoardConfig.mk），产品侧写下的 BOARD_ 赋值会先落地，板级文件里的 ?= 兜底反而覆盖不了它。两个域的交叉校验集中在 board_config.mk，这也是绝大多数「配置矛盾」报错的出处。

配置规模先给个量级感：product_config.mk 共 764 行，PRODUCT_ 赋值行 54 处；board_config.mk 共 1119 行，BOARD_ 赋值行 36 处；product.mk 共 683 行。计数口径为按单前缀分别统计——grep -cP '^\s*PRODUCT_[A-Z_]+\s*:?(\+|\?)?=' product_config.mk 与 grep -cP '^\s*BOARD_[A-Z_]+\s*:?(\+|\?)?=' board_config.mk，可原样复现；若把两个前缀并成一条正则去跑 board_config.mk，会连它的 7 处 PRODUCT_ 行一起计入，得 43。函数落点：inherit-product 定义在 build/make/core/product.mk 的 532 行，inherit-product-if-exists 定义在 579 行。后者的语义差一层——文件不存在时不报错，这让不同分支的树可以共用同一份上游产品文件。

变体的收敛做三件事。main.mk 102 行定义 INTERNAL_VALID_VARIANTS := user userdebug eng；103 行起的过滤分支对非法值直接 $(error stopping)（:110）；:131-147 还有一层集中分派——tags_to_install 在 :131 置空后按变体累加（userdebug 得 debug（:135）、eng 得 debug eng（:139）），:146-147 在 SANITIZE_TARGET 含 address 且已含 debug 时再加 asan；它决定带标签模块是否被装上。此外 :151-157 的 java_coverage 与 :174 的 sdk 还有两个分支。变体的其余行为仍在各模块自己的 TARGET_BUILD_VARIANT 判断里。另有两处更早的拦截：envsetup.mk :83-84 在变体为空时回落到 eng，:350-356 对非法值先报 bad TARGET_BUILD_VARIANT。这意味着「userdebug 和 user 差在哪」不是某一份文件能回答的，要靠 grep TARGET_BUILD_VARIANT 去看具体模块。

A/B 是整体切换。build/make/core/Makefile 6246 行 ifeq ($(AB_OTA_UPDATER),true) 是首个产物组织分支，:6358 另有非 A/B 分支，:6370/:6395/:6977 还有多处消费——但都只在 A/B 树上走，非 A/B 走另一套产物组织。这个开关的取值不止两档。board_config.mk :988 只判 ifneq ($(AB_OTA_UPDATER),true)：none 与其他非 true 取值一律落到非 A/B（空值到不了这里，:973-:974 已先置 true），goldfish 取的 none 就是 false 之外的第三档。

它在 Makefile 里的消费点全集是 :6246、:6358、:6370、:6395、:6404-:6405（AB_OTA_PARTITIONS 守卫 error）、:6977、:7599；其中 :6358 单独判 false 才构建静态 updater。

系统留的共存口在 board_config.mk：:973–:974 在未设置时默认取 true，:976 把它列入 .KATI_READONLY（此后不可再改，故赋值须早于板级配置求值）；:985-992 的 TARGET_OTA_ALLOW_NON_AB 在开关非 true 或 PRODUCT_OTA_FORCE_NON_AB_PACKAGE 为 true 时置真，允许 A/B 与非 A/B 配置并存。

动态分区的校验是一棵小树，不是双向报错。外层守卫在 board_config.mk :663 ifeq (true,$(PRODUCT_BUILD_SUPER_PARTITION))——未显式设这个开关时，它回落成 PRODUCT_USE_DYNAMIC_PARTITIONS 的值（product_config.mk :519-521）。:664–:669 是一支：动态分区打开且 BOARD_SUPER_PARTITION_SIZE 非空时，:667 置 BUILDING_SUPER_EMPTY_IMAGE := true；容量为空时不报错，只是不置位。:670–:678 是另一支：只有显式设了 PRODUCT_BUILD_SUPER_EMPTY_IMAGE=true，才要求动态分区必须同开（:672）且容量必须非空（:675），两条各一条 $(error ...)。:679–:680 还有一层：外层守卫不成立而空镜像开关为真同样报错。

BOARD_VNDK_VERSION 的校验点在 board_config.mk 1019 行，注释即 # Check BOARD_VNDK_VERSION。链接期支撑在 system/core/libvndksupport/linker.cpp，共 85 行。

设备侧声明落在 device/generic/goldfish/manifest.xml，首行为 <manifest version="1.0" type="device" target-level="8">。这是 VINTF 设备侧声明的位置，与产品配置是两套东西：产品配置决定构建什么，manifest 声明运行时接口契约。

分区布局的实际实现已经不在 system/core。本树 system/fs/fs_mgr/（manifest 项目 platform/system/fs/fs_mgr）是 fs_mgr 的新家，system/core/fs_mgr 未检出。规模：liblp/builder.cpp 1277 行、images.cpp 534 行、super_layout_builder.cpp 246 行、reader.cpp 499 行、writer.cpp 411 行；libsnapshot/snapshot.cpp 4923 行、snapshotctl.cpp 1146 行；fs_mgr.cpp 2513 行。libsnapshot 的体量说明虚拟 A/B 与快照逻辑本身是重活，配置层那两行开关只是入口。

4.3 一个具体例子

走 goldfish 的 64 位 x86_64 产品。device/generic/goldfish/AndroidProducts.mk 声明 12 个产品，sdk_phone64_x86_64 是其中之一。

它的入口文件是 device/generic/goldfish/64bitonly/product/sdk_phone64_x86_64.mk。三处继承按行序发生：

21 行 $(call inherit-product, $(SRC_TARGET_DIR)/product/core_64_bit_only.mk)，从 build 树拿 64 位基础；31 行 $(call inherit-product, device/generic/goldfish/board/emu64x/details.mk)，接板级细节；32 行 $(call inherit-product, device/generic/goldfish/product/phone.mk)，接手机形态的上游片段。随后 35 行 PRODUCT_NAME := sdk_phone64_x86_64，37 行 PRODUCT_MODEL := Android SDK built for x86_64。

图 2：sdk_phone64_x86_64 的继承展开

core_64_bit_only.mk  (build 树)
        |
        +-- emu64x/details.mk  (板级细节)
        |
        +-- phone.mk  (产品形态)
                |
                v
   PRODUCT_NAME / PRODUCT_MODEL 收口

位置是惯例而非机制：PRODUCT_NAME 是单值变量（product.mk :25），node_fns.mk :150-165 的继承展开对单值变量执行「本地显式优先」——本层显式设了值，继承来的同名列就不再生效，放前放后都能覆盖上游。goldfish 把四个 PRODUCT_ 赋值（PRODUCT_BRAND :34、PRODUCT_NAME :35、PRODUCT_DEVICE :36、PRODUCT_MODEL :37）连续放在继承之后，与产品配置的阅读顺序一致。「改了产品名却仍是旧名」要查的是 lunch 选中的产品与 AndroidProducts.mk 的指向，不是赋值行序。

配套目录规模：device/generic/goldfish/product/ 有 11 个文件（base_phone.mk、phone.mk、tablet.mk、generic.mk、versions.mk 等），device/generic/goldfish/board/ 有 12 个条目（BoardConfigCommon.mk、emu64x、emu64a、fstab、kernel 等）。产品形态与板级形态各占一侧，互不继承。

再看这台设备的两个分区开关，它们不在同一个文件里：AB_OTA_UPDATER := none 在 device/generic/goldfish/board/BoardConfigCommon.mk 39 行，是显式关 A/B（系统默认值是 true）；PRODUCT_USE_DYNAMIC_PARTITIONS := true 在产品文件 16 行（64bitonly/product/sdk_phone64_x86_64.mk），与 BoardConfigCommon.mk 51 行的 BOARD_EMULATOR_DYNAMIC_PARTITIONS_PARTITION_LIST、73 行默认 8 GiB 的 BOARD_EMULATOR_DYNAMIC_PARTITIONS_SIZE 是同一套开关下的参数化——产品文件 :18 用 ?= 先把容量置成 1800 MiB，变量从此非空，BoardConfigCommon.mk :73 的 ?= 8589934592（8 GiB）兜底随即失效（属弱赋值先占，不是强覆盖）；同一文件 :48 的 BOARD_SUPER_PARTITION_SIZE ?= 8598323200（8 GiB + 8 MiB）同理被 :19 的 := 抢先。:19 据此推出 BOARD_SUPER_PARTITION_SIZE（再 +8 MiB）。模拟器变量不是另一条路径。

7. 常见问题与误区

7.1 误区

误区一：改 `PRODUCT_NAME` 就能重命名产品。 名字要落在对的文件里。sdk_phone64_x86_64.mk 把 PRODUCT_NAME 放在三处继承之后（35 行）是惯例写法；单值变量的本地显式赋值本来就更优先（product.mk :25 列入单值表，node_fns.mk :150-165 的展开规则），不是「不放后面就会被盖掉」。改了没生效，先查 lunch 选中的产品是不是这一份。

误区二：`inherit-product-if-exists` 只是容错写法，等价于先判断文件存在。 它的实际效果是让同一份上游产品文件在不同分支的树上共用——分支没有那个文件时不中断求值。这属于契约差异，不是风格选择：用 inherit-product 引用可能缺失的文件，配置阶段就会失败。

误区三：`user` 与 `userdebug` 的差异写在某个配置中心文件里。 main.mk 确实做了一层集中分派：:131 起用 tags_to_install 按变体累加标签（userdebug 得 debug（:135）、eng 得 debug eng（:139），SANITIZE_TARGET 含 address 时再加 asan（:146-147））。但这层只决定带标签的模块是否被装上，变体的其余行为仍是各模块自己对 TARGET_BUILD_VARIANT 的判断叠加出来的，所以没有任何一处能完整列出差异。

误区四（看起来对其实是错的）：goldfish 既然支持动态分区，那它就是 A/B 设备。 两个开关正交。BoardConfigCommon.mk 39 行是 AB_OTA_UPDATER := none，参考设备显式关 A/B；它的动态分区由产品文件 16 行的 PRODUCT_USE_DYNAMIC_PARTITIONS := true 打开，BOARD_EMULATOR_DYNAMIC_PARTITIONS_* 是同一开关下的容量与列表参数，不是互斥的另一支。

7.2 高频提问

问：为什么我把 AB_OTA_UPDATER := true 加到产品 makefile 里没生效？ 答：BOARD_* 与 PRODUCT_* 是两个域，但这个开关两侧都能赋：aosp_arm64.mk :58、aosp_x86_64.mk :60 就是在产品 makefile 里写 AB_OTA_UPDATER := true 的。容易踩空的是未赋值时的默认方向——board_config.mk :973–:974 只在值为空时置 true，:976 随即把它列入 .KATI_READONLY，所以赋值必须发生在板级配置求值之前；产品侧写了，板级那句默认就不会生效。它不参与 inherit-product 的继承展开，这点是真的。 追问：那放 BoardConfigCommon.mk 就够了吗？ 答：取值到位之后仍要过 board_config.mk 的交叉校验。开关本身通过不代表分区布局能生成，super 分区容量与列表还各有约束。

问：打开 PRODUCT_USE_DYNAMIC_PARTITIONS 为什么报错说 BOARD_SUPER_PARTITION_SIZE 未定义？ 答：那条报错在 board_config.mk :675，前提是显式设了 PRODUCT_BUILD_SUPER_EMPTY_IMAGE=true——此时容量必须给出。没设这个开关时，容量为空不报错，只是 BUILDING_SUPER_EMPTY_IMAGE 不置位（:666–:667）。 追问：那「设了空镜像开关却没开动态分区」呢？ 答：那是 :672 的另一条 $(error ...)。两条报错文案不同，按行号即可定位。
