1. TL;DR

View 画完不出图，真正落笔的是 RenderThread：UI 线程只把 DisplayList 同步进 RenderNode，RenderThread 把它转成 Skia 记录并提交给 GL 或 Vulkan 后端。RenderThread::getInstance() 是进程内单例，后端上下文分两个入口创建：GL 走 requireGlContext()（内部 GrDirectContexts::MakeGL），Vulkan 走 requireVkContext()（内部 mVkManager->createContext(options)），两者由 requireGrContext() 按后端类型分派。CanvasContext 持有一条 IRenderPipeline，具体是 SkiaOpenGLPipeline 还是 SkiaVulkanPipeline 由上下文创建时的选择决定。首帧慢的主要原因是上下文初始化、gralloc 缓冲与首帧绘制串在同一条线程上，而不是渲染指令本身慢。

3. 问题背景

onDraw 里加了一行日志，发现它只被调用一次；可界面明明每帧都在动，日志却不涨。反过来，清掉一个自定义 View 的绘制代码，掉帧也没好转。于是有人怀疑「绘制在别的线程」，但说不清那个线程是谁、什么时候被唤醒、Canvas 里的指令最后交给了谁。还有人第一次把后端切到 Vulkan，发现首帧明显变慢，却找不到慢在哪一步。这些问题的共性是：缺一张从 ThreadedRenderer 到 IRenderPipeline 的调用链地图。

4. 核心机制

4.1 概念与关系

四个角色。ThreadedRenderer 是 Java 侧入口，extends HardwareRenderer，由它把 Surface 交给 native。RenderThread 是进程内唯一渲染线程，管理 EGL 与 Vulkan 上下文。CanvasContext 是「一块画布」的 native 表示，持有一条 IRenderPipeline。RenderNode 持有 DisplayList，是 UI 线程与渲染线程之间传递绘制内容的载体。

图 1：一次绘制从 Java 到后端的角色链

ThreadedRenderer (Java)
   |
   v
RenderThread (进程内单例, 持上下文)
   |
   v
CanvasContext (持 IRenderPipeline)
   |
   +--> SkiaOpenGLPipeline
   +--> SkiaVulkanPipeline

RenderThread 与 CanvasContext 是一对多：一个渲染线程服务同一进程内多个窗口，每个窗口一份 CanvasContext。CanvasContext 与 pipeline 是一对一：mRenderPipeline 字段是 std::unique_ptr<IRenderPipeline>，只在构造时确定。

4.2 关键内容

单例与上下文创建。 RenderThread::getInstance() 返回进程级单例，内部是文件作用域的 static sp<RenderThread> sInstance。上下文不随线程创建而创建，而是延后到首次使用时。GL 与 Vulkan 各有一个创建函数：requireGlContext（RenderThread.cpp:235-252）先调 mEglManager->initialize() 把 EGL 初始化好（:239），再用 GrDirectContexts::MakeGL 建出 Skia 的 GL 后端上下文（:249）；requireVkContext（:254-270）则先 mVkManager->initialize()（:262），再 mVkManager->createContext(options)（:267）。两者都通过 setGrContext（:344）落位，对外统一由 requireGrContext（:356-363）给出——它按 Properties::getRenderPipelineType() 是否为 RenderPipelineType::SkiaGL 分派到上述两个函数之一。

这里的名称容易误导：requireGlContext 这个名字容易让人以为它是统一入口，实际它只建 GL；Vulkan 走独立的 requireVkContext。读代码时不能凭名字判断后端，要看 requireGrContext 的分派。

树同步。 UI 线程一侧的核心动作在 RenderNode：prepareTreeImpl（:228）沿树遍历并做属性更新，遍历末尾调 pushStagingDisplayListChanges（:268）把 staging 状态提交，后者内部（:563）再调 syncDisplayList（:569）把新的 DisplayList 挂到渲染侧的 RenderNode 上。这一步只搬运描述，不做栅格化。

绘制与呈现。 RenderThread 的 threadLoop 是取任务的主循环。绘制落到 CanvasContext::draw，返回值类型是 IRenderPipeline::DrawResult。SkiaPipeline 负责组织图层，renderLayersImpl 在构造后的两个位置被调用，分别对应常规渲染与需要额外处理的分支。具体后端里，SkiaOpenGLPipeline::makeCurrent 切换 EGL 上下文，draw 提交绘制，SkSurfaces::WrapBackendRenderTarget 把 ANativeWindow 的缓冲包装成 Skia 的渲染目标，最后由 swapBuffers 呈现。Vulkan 侧入口更薄，构造函数完成初始化，vulkanManager() 暴露管理器。

Surface 绑定。 CanvasContext::setSurface 与 setSurfaceControl 是两条绑窗路径，前者直接挂 ANativeWindow* 并可带超时开关，后者走 SurfaceControl。Java 侧 ThreadedRenderer.setSurface 把 Surface 传下来，destroyHardwareResources 在视图树销毁时释放 GPU 资源。

帧信息。 FrameInfo 类的 importUiThreadInfo 把 UI 线程侧的帧耗时并入渲染线程的记录，这是跨线程对账一帧的接口。

4.3 一个具体例子

以打开一个普通的硬件加速窗口为例。

  1. Java 侧 ThreadedRenderer 拿到 Surface，调 setSurface，native 侧进入 CanvasContext::setSurface。
  2. 首次绘制经 requireGrContext 分派：选 GL 后端进 requireGlContext，mEglManager->initialize() 建立 EGL 后走 GrDirectContexts::MakeGL；选 Vulkan 后端进 requireVkContext，先 mVkManager->initialize() 再 mVkManager->createContext(options)。
  3. setGrContext 把上下文交给 CanvasContext；mRenderPipeline 中的 SkiaOpenGLPipeline 或 SkiaVulkanPipeline 后续都用它。
  4. UI 线程 prepareTreeImpl → pushStagingDisplayListChanges（其内部调 syncDisplayList）把 DisplayList 同步过去并提交。
  5. threadLoop 取到绘制任务，进入 CanvasContext::draw。GL 后端在此走 makeCurrent、SkSurfaces::WrapBackendRenderTarget、draw、swapBuffers。
  6. FrameInfo::importUiThreadInfo 把 UI 线程耗时并入本帧记录。

第 2 步落在渲染线程上，且必须完成后才能出首帧。这就是首帧比之后每帧更慢的原因：初始化与第一笔绘制串行。

7. 常见问题与误区

7.1 误区

误区一：`onDraw` 每帧都会执行。 只有内容失效时 syncDisplayList 才有新东西同步；内容不变时渲染线程可以复用已有 DisplayList 重绘，UI 线程不参与。

误区二：`requireGlContext` 是所有后端的统一入口。 名字是历史遗留，容易误读。它只建 GL 上下文；Vulkan 走独立的 requireVkContext，两者的分派在 requireGrContext。读代码时不能凭名字判断后端。

误区三：每个窗口一个 `RenderThread`。 getInstance() 返回进程级单例，CanvasContext 才是一窗一份。因此多个窗口共享同一渲染线程，一个窗口的初始化会挤占另一个窗口的绘制时间。

误区四：首帧慢是因为 DisplayList 太大。 首帧相比后续帧多出的是上下文初始化与首帧缓冲准备，这部分在 requireGrContext 分派的上下文创建路径（requireGlContext／requireVkContext）上，与 DisplayList 体量关系不大。

7.2 高频提问

问：切到 Vulkan 后端后，代码里要改什么？ 答：Java 侧入口仍是 ThreadedRenderer，其父类 HardwareRenderer 暴露后端选择；native 侧由 CanvasContext 持有的 mRenderPipeline 实例区分，业务绘制代码不感知。 追问：那自定义 View 的 Canvas 调用会变吗？ 答：不会。DisplayList 记录的是绘制语义，SkiaOpenGLPipeline 与 SkiaVulkanPipeline 都从同一份记录出发，差异在下游。

问：怎么知道某一帧是渲染线程还是 UI 线程慢？ 答：看 FrameInfo，importUiThreadInfo 会把 UI 线程侧的耗时并入渲染线程的帧记录，两段可分开看。 追问：FrameInfo 能覆盖上下文创建阶段吗？ 答：覆盖到的是帧记录口径，上下文初始化本身是否计入需按具体采集点确认，本篇不断言。
