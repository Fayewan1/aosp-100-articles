1. TL;DR

Android 上的 Vulkan 不是「桌面 Vulkan 编译过来跑」，而是 libvulkan loader 把驱动当作可替换插件、按属性在两套加载路径里选一个，再把 VkSurfaceKHR 桥接到 SurfaceFlinger 能消费的 BufferQueue 上。桌面 loader 假设驱动是 .so 由 libvulkan.so.1 按 ICD 清单枚举；Android loader 直接读属性走 APEX 或 updatable gfx driver，没有 ICD JSON 那一层。swapchain 在 Android 上不是「窗口系统的可选后端」，vkCreateSwapchainKHR 必须拿到一个 ANativeWindow 句柄，否则创建失败。HWUI 有一条走 VkPipeline 的渲染路径，它与 Skia 的 GL 路径并列存在。没有驱动时还有 nulldrv 兜底，让 API 调用不崩、画面不出。

3. 问题背景

你写了一个 Vulkan 应用，桌面上好好的，搬到 Android 上第一件事就是 vkCreateInstance 之后 vkCreateSwapchainKHR 直接返回 VK_ERROR_SURFACE_LOST_KHR，或者 vkGetPhysicalDeviceSurfaceCapabilitiesKHR 返回的尺寸和 Surface 实际尺寸对不上。第二个困惑是：adb shell 里 ro.vulkan.apex 是什么、为什么换个设备值就不一样。第三个困惑是 HWUI 明明有 GL 后端，为什么还会有 SkiaVulkanPipeline。这三件事都不在 Vulkan 规范里，全是 Android 落地时加的那层。

4. 核心机制

4.1 概念与关系

四个概念：loader（应用链接的 libvulkan）、驱动（builtin 与 updated 两条加载路径）、swapchain 桥（把 VkSwapchainKHR 和 ANativeWindow 互转）、HWUI 后端（SkiaVulkanPipeline）。

图 1：Vulkan 在 Android 的加载与桥接层次

应用
  |  vkXxx
libvulkan (loader: api.cpp)
  |  GetInstanceProcAddr 链尾 = driver
  |--- LoadBuiltinDriver  <- ro.vulkan.apex
  |--- LoadUpdatedDriver   <- updatable gfx driver
  v
驱动 .so
  |
  +--> swapchain.cpp <--> ANativeWindow / BufferQueue
  |
  +--> SkiaVulkanPipeline (HWUI 侧)

loader 的职责是「把调用转发到驱动」，但它在 create_instance 时要把自己的装载数据注入进去，后面 swapchain 才知道用哪个 loader 的 ANativeWindow 包装。

4.2 关键内容

loader 的分层。 api.cpp 共 1545 行，vkGetInstanceProcAddr 的最终落点是 get_instance_proc_addr_ = driver::GetInstanceProcAddr（:597），也就是 loader 链的最后一段直接指向驱动表，loader 本身不实现图形命令。实例创建由 PFN_vkCreateInstance create_instance 承接（:854-856）。装载数据注入有两个点：SetInstanceLoaderData（:509）与 SetDeviceLoaderData（:511），swapchain 与内存相关扩展靠这两个函数拿到 loader 私有上下文。vkEnumerateInstanceLayerProperties 的实现注释在 :1315，原文口径是：所有 explicit 层都会返回给应用；为兼容 LunarG loader，所有 implicit 层也同样返回；只有 platform 与 OEM 层不返回——它们在应用不知情的前提下被启用。所以 layer 枚举并非整体留空，留空的只是 platform/OEM 那一类。

驱动加载双路径。 driver.cpp 共 2102 行，路径选择在 Hal::Open()（:241），底层加载器是 LoadDriver（:153），两条路径如下：

名称含义出处

LoadBuiltinDriver从 APEX 加载 builtin 驱动，读 ro.vulkan.apexdriver.cpp:202，属性读取 :208-211

driver.h 共 337 行，声明了这两条路径共用的驱动句柄与函数表结构。两条路径的差别是更新粒度：builtin 随系统分区走，updated 可以脱离系统版本单独更新，代价是加载时要多做一层校验。选择次序在 Hal::Open()（:241）：先调 LoadUpdatedDriver（:259），拿到 -ENOENT（没有可更新驱动）才回退 LoadBuiltinDriver（:261）；两条都失败时用 stub HAL（nulldrv）兜底（:263-267）。底层 LoadDriver（:153-200）遍历 HAL_SUBNAME_KEY_PROPERTIES（:141-144，即 ro.hardware.vulkan 与 ro.board.platform）拼出 vulkan.<值>.so（:164），有 linker namespace 走 android_dlopen_ext（:171，updated 路径），没有则走 android_load_sphal_library（:178，builtin 路径）。

swapchain 桥接。 swapchain.cpp 共 3529 行，核心是两个互逆的转换：HandleFromSwapchain（:440）把 loader 侧的 VkSwapchainKHR 转成 64 位句柄，SwapchainFromHandle（:444）转回来——它们只做句柄与对象互转，不负责取窗口。创建入口 CreateSwapchainKHR 在 :1900，它经 SurfaceFromHandle（:1951）从 create_info->surface 拿到 ANativeWindow；BufferQueue 由该 ANativeWindow／Surface 层持有，swapchain 只是连上去，不是自己创建一份。oldSwapchain 的处理分两段：:1953-1961 校验 surface.swapchain_handle 与传入句柄是否一致，不一致直接返回 VK_ERROR_NATIVE_WINDOW_IN_USE_KHR；一致则走 :1962-1963 的 OrphanSwapchain 把旧链孤儿化。重建 swapchain 时必须由应用把旧句柄传进来，否则旧 BufferQueue 的 slot 不会被释放。VkSwapchainImageUsageFlagsANDROID 在 :2116，这是 Android 独有的 usage 位，用来告诉合成器这张图是不是被当作共享纹理使用。

HWUI 侧。 SkiaVulkanPipeline.cpp 共 226 行，构造函数在 :45，vulkanManager() 在 :54。它很薄，因为真正干活的是 Skia 的 GrVulkanManager，HWUI 只负责把 VkDevice/VkQueue 与 Surface 生命周期对上。版本口径：SkMilestone.h:8 是 #define SK_MILESTONE 148。

兜底。 null_driver.cpp 共 1841 行，#include <hardware/hwvulkan.h>（:23）。它实现一套能返回成功但不出图的 Vulkan 接口，好处是图形栈初始化不会因缺驱动整条链崩掉。

4.3 一个具体例子

假设设备上 ro.vulkan.apex 有值。Hal::Open()（:241）先调 LoadUpdatedDriver（:259）；设备没有可更新驱动时它返回 -ENOENT，于是回退 LoadBuiltinDriver（:261）——后者读 ro.vulkan.apex（:208-209）拿到 APEX 名，从该 APEX 的导出 namespace 里 dlopen 驱动。驱动加载成功后，create_instance 指向驱动的 vkCreateInstance（:854-856）。应用 vkCreateSwapchainKHR 进来，CreateSwapchainKHR（:1900）先经 SurfaceFromHandle（:1951）由 create_info->surface 取到 ANativeWindow（HandleFromSwapchain（:440）只是 swapchain 句柄与对象互转的工具，不参与取窗口），读 VkSwapchainImageUsageFlagsANDROID（:2116）判断 usage，最后经 ANativeWindow 连到 Surface 层持有的 BufferQueue。应用若在这个窗口上重建，必须在 oldSwapchain 字段（:1953）填旧句柄——swapchain.cpp:1953-1961 校验 surface.swapchain_handle 与传入句柄是否一致，不一致直接返回 VK_ERROR_NATIVE_WINDOW_IN_USE_KHR；一致则走 :1962-1963 的 OrphanSwapchain 把旧链孤儿化，其 buffer 才能被回收。

7. 常见问题与误区

7.1 误区

误区一：Android 的 Vulkan loader 也走 ICD JSON 枚举。 不对。桌面 loader 读 /usr/share/vulkan/icd.d/*.json，Android 没有这一层。driver.cpp 里只有 LoadBuiltinDriver 与 LoadUpdatedDriver 两条路径，前者读 ro.vulkan.apex，后者走 updatable gfx driver。

误区二：`vkCreateSwapchainKHR` 拿到的 surface 是「窗口句柄的包装」，和桌面 `VkSurfaceKHR` 同一语义。 看起来对其实是错的。桌面 surface 绑定的是窗口系统（X11/Wayland）的窗口；Android 的 surface 必须落到一个 ANativeWindow 上，HandleFromSwapchain（:440）/SwapchainFromHandle（:444）这一对转换就是为此存在。没有 ANativeWindow 就没有 surface，这与桌面「surface 可以脱离某个具体窗口存活」不同。

误区三：HWUI 只有 GL 一条路。 不对，SkiaVulkanPipeline.cpp 存在且独立编译，SkiaVulkanPipeline 与 GL 后端并列，由运行时决定启用哪条。

7.2 高频提问

问：ro.vulkan.apex 没设值怎么办？ 答：加载次序在 Hal::Open()（driver.cpp:241）：先 LoadUpdatedDriver（:259），返回 -ENOENT 才回退 LoadBuiltinDriver（:261）。ro.vulkan.apex 只影响 LoadBuiltinDriver 内部——设了就从该 APEX 的导出 namespace 加载（:208-215），没设则走系统 HAL 搜索路径（LoadDriver 以空 namespace 调 android_load_sphal_library，:178）。两条都失败才由 stub HAL（nulldrv）顶上（:263-267）。 追问：nulldrv 顶上以后应用会怎样？ 答：实例和 device 能建出来，绘制命令返回成功但不出图。这是「不崩」而不是「能用」，属于兜底而非功能。

问：重建 swapchain 一定要传 oldSwapchain 吗？ 答：swapchain.cpp:1953-1961 校验这个字段（不一致返回 VK_ERROR_NATIVE_WINDOW_IN_USE_KHR），:1962-1963 的 OrphanSwapchain 负责把旧链孤儿化。传了，旧 BufferQueue 的 slot 才能在创建新链时被回收；不传，旧链资源取决于驱动与 loader 的协作，容易留下未释放的 buffer。 追问：VkSwapchainImageUsageFlagsANDROID（:2116）是做什么的？ 答：给合成器声明这张图的使用方式，影响 BufferQueue 分配时选的 gralloc usage 位，不是应用侧可见的语义。
