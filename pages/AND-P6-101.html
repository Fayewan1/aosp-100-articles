1. TL;DR

Android 的图形栈分两条互不重叠的入口链：OpenGL ES 走 EGL，Vulkan 走 loader，两者在 frameworks/native 之下才汇到驱动。EGL 的实质工作是维护两张全局钩子表 gHooks[2] 与 gHooksNoContext，当前上下文由 TLS 槽位 TLS_SLOT_OPENGL_API 决定。Vulkan 的 loader 不做钩子表，它把入口链直接改写为驱动函数指针，例如 get_instance_proc_addr_ = driver::GetInstanceProcAddr。渲染侧，SurfaceFlinger 与 HWUI 都通过 RenderEngine 抽象，Skia 后端是 SkiaRenderEngine.cpp，另有 GL 与 Vulkan 数个变体并存。本篇只给分层与契约文件，BufferQueue 归 AND-P6-102，合成归 AND-P6-201。

3. 问题背景

应用里一行 GLES20.glDrawArrays，或者一句 vkCmdDraw，从 Java 到 GPU 中间要跨多少层？最常出现的困惑是两类。一类是「我明明调的是 GL，为什么崩溃栈里出现 libvulkan.so」——原因是 RenderEngine 的 Skia 后端可以由 Vulkan 承载，但那是 SurfaceFlinger 自己的绘制，与应用调用的 GL 无关。另一类是「编译进系统的驱动到底什么时候被 dlopen」——EGL 与 Vulkan 的答案完全不同：EGL 在初始化时一次性填表，Vulkan 在 loader 引导期改写函数指针。把这两条链摊开看，才能判断某一行日志属于哪一层。

4. 核心机制

4.1 概念与关系

四个概念。EGL：GL 与本地窗口系统的粘合层，负责上下文、表面与当前绑定。Vulkan loader：代替 GL 的「钩子表」模式，用函数指针链把应用调用导到驱动。驱动：厂商提供的 libGLES_*.so 或 Vulkan ICD，由属性与目录扫描决定加载哪一个。RenderEngine：SurfaceFlinger 侧的绘制抽象，屏蔽 Skia / GL / Vulkan 后端差异。

图 1：应用绘制到驱动的两条入口链

应用(Java/Kotlin)
   |
HardwareRenderer.setSurface   -> HWUI (libhwui)
   |
   +-- GL 路径 --> EGL (eglApi/egl.cpp) --> 驱动
   +-- Vk 路径 --> libvulkan loader    --> 驱动

SurfaceFlinger --> RenderEngine --> Skia (GL 或 Vk 后端)

两条链在驱动处合流，但上面的契约完全不同：GL 侧应用直接调 EGL，Vulkan 侧应用只认识 loader。

4.2 关键内容

EGL 侧：钩子表 + TLS。 egl.cpp 全文 223 行，核心资产是两张表：gl_hooks_t gHooks[2]（:34）与 gl_hooks_t gHooksNoContext（:35）。gHooks 的长度 2 对应两套 API 变体，gHooksNoContext 供无当前上下文时调用兜底。当前上下文绑定后，EGL 把选中的钩子表地址写进 TLS 槽位 TLS_SLOT_OPENGL_API（:188）。之后应用每一次 glXxx 都是「读 TLS → 取函数指针 → 跳转」，不经过 libEGL 的符号查找。这是 GL 侧性能与隔离的关键设计：分叉点在这一行，不在 eglApi.cpp。

EGL 侧：三段生命周期。 egl_display_t 在 egl_display.cpp（共 560 行）里管显示设备：initialize（:240）通过已就绪的驱动入口完成 EGL 初始化并在 :270 把 TLS 兜底为 gHooksNoContext，terminate（:401）释放，makeCurrent（:496）切换当前上下文并更新 TLS。要注意的是，驱动连接与 gHooks 的填充并不在 initialize 内：实际发生在 egl_init_drivers_locked（egl.cpp:125）——它在 :136-137 把 cnx->hooks[GLESv1/2_INDEX] 指向 &gHooks[...]，并在 :138 调 loader.open(cnx)，由 Loader::open 内部把驱动函数指针填进 gHooks。eglApi.cpp 共 659 行，是 eglGetDisplay、eglCreateContext、eglMakeCurrent 等入口的分发面，它本身不含策略。

Vulkan 侧：loader 改写而非填表。 frameworks/native/vulkan/libvulkan/api.cpp 共 1545 行。loader 在拿到驱动后做的是函数指针赋值，get_instance_proc_addr_ = driver::GetInstanceProcAddr（:597）；vkCreateInstance 则经 get_instance_proc_addr_(VK_NULL_HANDLE, "vkCreateInstance") 取到 PFN_vkCreateInstance create_instance，位置在 :854-858。两者差别在于：GL 的钩子表是按签名预先声明好的数组，Vulkan 的入口是在运行期查询出来的指针，驱动可以有自己的一套实现，loader 只看签名是否匹配。

图 2：两条链上的关键契约符号

EGL:    gHooks[2] / gHooksNoContext  (表, 静态)
        TLS_SLOT_OPENGL_API          (槽, 每线程)

Vulkan: get_instance_proc_addr_      (指针, 运行期赋值)
        create_instance              (查询得到的入口)

驱动加载。 driver.cpp（共 2102 行）分三条路径：LoadDriver（:153）是总入口，LoadBuiltinDriver（:202）走系统内置驱动，LoadUpdatedDriver（:224）走可更新驱动。内置驱动的目录从属性 ro.vulkan.apex 读得（:208-211），也就是说 Vulkan 驱动的选择不是在编译期写死的，而是由这一属性指向的 APEX 决定。

RenderEngine 的后端族。 SkiaRenderEngine.cpp 共 1907 行，构造函数 SkiaRenderEngine::SkiaRenderEngine(Threaded threaded, ...) 在 :328，主绘制入口 drawLayersInternal 在 :885。同目录并存 SkiaGLRenderEngine.cpp（571 行）、SkiaVkRenderEngine.cpp（182 行）、GaneshVkRenderEngine.cpp（131 行）、GraphiteVkRenderEngine.cpp（312 行）。行数差异本身就是信息：GL 后端比 Vulkan 后端厚，而 Graphite 后端比 Ganesh 后端厚，说明迁移尚未收敛到单一实现。

构建切分。 frameworks/native/libs/renderengine/Android.bp 中 librenderengine_skia_sources 在 :82，librenderengine 模块在 :145。源集合与模块名分开定义，意味着后端文件通过源集合拼装，而不是各自成立一个模块。

4.3 一个具体例子

假设应用某次绘制崩在 libGLES_*.so 里。按图 1 回溯：Java 侧 HardwareRenderer.setSurface 交付 Surface，HWUI 建上下文时进 egl_display_t::initialize（:240）——此时驱动连接与 gHooks 填充已在更早的 egl_init_drivers_locked（egl.cpp:125，由 Loader::open 执行）完成，initialize 调通驱动入口后在 :270 把 TLS 兜底为 gHooksNoContext；egl_display_t::makeCurrent（:496）把选中的表写进 TLS_SLOT_OPENGL_API（:188）；应用调用 glDrawArrays 时读 TLS 跳转。崩溃点落在驱动，说明分叉早已完成、入口链正确，问题在驱动或传参——而不是 EGL。反过来说，若崩溃栈里出现 libvulkan.so 但应用只调 GL，则要查 SurfaceFlinger 的 RenderEngine 是否选了 Vulkan 后端（SkiaVkRenderEngine.cpp 一族），与本应用的 GL 调用无关。

7. 常见问题与误区

7.1 误区

错误认知：EGL 是 GL 的「包装库」，所有 `glXxx` 都经过它。 纠正：glXxx 不经过 libEGL 的符号解析，它读 TLS_SLOT_OPENGL_API 拿到钩子表后直接跳驱动函数指针。EGL 只在 initialize 与 makeCurrent 时介入。

错误认知：Vulkan 也有一张像 `gHooks` 那样的钩子表。 纠正：没有。Vulkan loader 走的是 get_instance_proc_addr_ = driver::GetInstanceProcAddr（:597）这样的指针改写，加上运行期查询 vkCreateInstance，机制是「查询」而非「预声明数组」。

错误认知：`libvulkan.so` 出现在栈里就说明应用在用 Vulkan。 看起对，其实错：SurfaceFlinger 的 RenderEngine 可能选了 Vulkan 后端（SkiaVkRenderEngine.cpp 一族），而应用同时只调 GL。判定依据是两条链互不重叠——应用 GL 走 EGL，合成侧 Vulkan 走 loader。

错误认知：Vulkan 驱动路径在编译期固定。 纠正：LoadBuiltinDriver（:202）从属性 ro.vulkan.apex（:208-211）读得 APEX 位置，LoadUpdatedDriver（:224）另有路径，加载位置是运行期决定的。

7.2 高频提问

问：两张钩子表 gHooks[2] 与 gHooksNoContext 各管什么？ 答：gHooks 在下标 0/1 上分别指向两套 API 变体的钩子；gHooksNoContext 在没有当前上下文时兜底，避免空指针跳转。追问：谁决定当前用哪张？ 答：egl_display_t::makeCurrent（:496）在绑定上下文时选表，并把地址写进 TLS_SLOT_OPENGL_API（:188）——每线程一份。

问：为什么 RenderEngine 要保留 SkiaGLRenderEngine.cpp、SkiaVkRenderEngine.cpp、GaneshVkRenderEngine.cpp、GraphiteVkRenderEngine.cpp 四个变体？ 答：GL 与 Vulkan 是不同后端，Vulkan 后端内部又分 Ganesh 与 Graphite 两代渲染抽象，Android.bp 用 librenderengine_skia_sources（:82）拼装源集合而不是各自成模块，因此可以并存。追问：迁移完成了吗？ 答：从行数看（GL 571 行 vs Vulkan 两代 131 与 312 行）尚无单一收敛实现，本篇不断言具体默认选谁。
