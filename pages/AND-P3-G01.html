1. TL;DR

Java 代码之下还有一层：对象由 ART 管理、线程跑在 bionic 之上、跨语言调用走 JNI、跨进程调用走 libbinder。本卷 9 篇就讲这一层的静态结构。读顺序有讲究：先建立 Native 世界的地图，再分三条支线（运行时、桥、守护与分区），最后在 libbinder 那篇合流。本卷不承诺运行时性能数字，全部结论来自源码静态分析。读完你应能说清一个 Activity 启动时，Native 侧到底被谁、被什么顺序拉起。

3. 问题背景

你在 Java 层写下 new Thread(...).start()，线程真的就在你以为的地方跑起来了。应用崩溃日志里出现 libc.so 的帧，你不知道它属于谁。给应用加一个通过 JNI 调用的 .so，加载失败时提示只有一行 UnsatisfiedLinkError。这些现象都在同一个地方：Java 世界之下那一层。它不是黑盒，只是一直没人带你走一遍。

4. 核心机制

4.1 概念与关系

本卷只讲四个位置：运行时（ART）、C 库（bionic）、跨语言入口（JNI）、跨进程通道（libbinder）。四者不是并列的层级，而是同一进程里四个不同的职责面。

图 1：本卷四个职责面与 Java 层的关系

        Java 代码 / 框架 Java 类
                 |
     +-----------+-----------+
     |           |           |
    ART         JNI       libbinder
  (对象/线程)  (跨语言)    (跨进程)
     |           |           |
     +----- bionic (libc) ---+
                 |
            Linux 内核

ART 管对象与线程，JNI 是 Java 与 Native 的调用桥，libbinder 让 Native 侧也能发起和接收进程间调用，三者都站在 bionic 之上。P3 讲的是这张图的内部；P5 讲最下面那格。

7. 常见问题与误区

7.1 误区

误区一：Native 层是一个独立进程。 不是。ART、bionic、libbinder 都在你的应用进程地址空间里，与 Java 代码同生共死。所谓「Native 世界」是代码层次，不是进程边界。

误区二：JNI 只是给 Java 调 C 用的。 看起来对，其实是错的。JNI 是双向的：Native 侧也能通过 JNIEnv 回调 Java，也能主动把线程挂到 VM 上。只当单向桥用，很多回调崩溃的现场就解释不通。

误区三：ART 只管 Java 内存，与 Native 内存无关。 不是。Java 堆与 Native 堆是两套账，但同一个进程的地址空间是共享的，垃圾回收（GC）与 Native 分配会互相挤压。202 与 401 分别从两侧讲这件事。
