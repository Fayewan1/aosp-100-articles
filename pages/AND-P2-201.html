1. TL;DR

startActivity() 不是「把界面调起来」，而是一次跨进程异步请求。请求经 Binder 送进 system_server 的 ActivityTaskManagerService（ATMS，就是老 AMS 里被拆出来的那一半），在那里生成一条 ActivityRecord、塞进目标任务栈；随后 ATMS 反手用 Binder 回调应用进程，后者才在主线程上把 Activity 建出来。

整条链是 Activity.startActivity(Activity.java:6496) → Instrumentation.execStartActivity(Instrumentation.java:1973) → ATMS.startActivityAsUser(ActivityTaskManagerService.java:1302) → ActivityStarter.execute(ActivityStarter.java:837) → resumeFocusedTasksTopActivities(ActivityStarter.java:2247) → ClientLifecycleManager.scheduleTransaction(ClientLifecycleManager.java:73) → 应用侧 TransactionExecutor.execute(TransactionExecutor.java:72) → ActivityThread.handleLaunchActivity(ActivityThread.java:4733)。

有两个后果必须记住。其一，startActivity 返回 START_SUCCESS 只表示「system_server 收下了这个意图」，此刻目标 Activity 对象可能还没 new 出来。其二，Android 10 起后台启动被拦时，这个调用照样「成功」返回，只是没有任何界面——静默失败是这一层最坑的形态。

3. 问题背景

先看一个真实抱怨：「代码里明明 startActivity 成功返回了，界面却没起来，logcat 还什么错都没有。」

把调用方的返回值打出来是 START_SUCCESS（0）。这不是 bug，是语义误读。startActivity 的返回值来自 ATMS，含义只有「意图已被受理」；而「界面起来」发生在那之后的一次反向跨进程回调里。两件事之间隔着：目标栈的处理、可能的重定向（ActivityStarter.executeRequest 里那几十个 return START_* 分支）、以及应用进程主线程的执行机会。

在 Android 10 引入后台启动限制之后，这个误读的破坏力被放大了：当调用方进程处于后台、又没有豁免条件时，ATMS 会在 ActivityStarter 里拦下这次启动，日志里只留一条告警（下面是一例，措辞随版本略有差异）：

要点：Activity 实例活在客户端，ActivityRecord 活在服务端，两者靠 token 对应——服务端是 ActivityRecord.Token（一个 Binder 对象，ActivityRecord.java:1787），客户端 ActivityThread.ActivityClientRecord.token 持有同一个 IBinder（ActivityThread.java:658）。你在代码里 getSystemService 拿到的多是服务端的代理，this（Activity）才是客户端实体。理解这条「双份记账」是读后面流程的前提。

四条最容易踩的失败/分支路径：

  1. 后台启动限制（§3 那种静默失败）：executeRequest 里对 BackgroundActivityStartController 的判定不放行 ⇒ 直接返回某个 START_*/START_CANCELED，不生成 AR、不下发事务。调用方只看到返回值。
  2. 缺少 `FLAG_ACTIVITY_NEW_TASK`：App 上下文（Application/Service）启动 Activity 必须带这个标志，否则抛 AndroidRuntimeException: Calling startActivity() from outside of an Activity context requires the FLAG_ACTIVITY_NEW_TASK flag。这一条发生在客户端、Instrumentation 之前，很好定位。
  3. 组件不可达：目标未导出、未在 manifest 声明、或 Intent 无匹配 resolver ⇒ 服务端 executeRequest 返回 START_CLASS_NOT_FOUND/START_NOT_ACTIVITY，同样不产生界面。
  4. 重定向/复用：singleTop/singleTask、ALWAYS_FINISH、launchMode 命中时，ActivityStarter 可能不新建 AR，而是 deliverNewIntent 复用旧实例——表现为「界面切了，但没走 onCreate」，这是被误判为「启动丢失」的高频来源。

注意执行顺序：先 `attach` 再 `onCreate`。attach(Activity.java:9201/9214) 里才把 mWindow、mMainThread、mToken 等注入进来——所以 onCreate 里能安全调 getWindow()，而从 onCreate 里再反查「谁启动了我」是可用的。反过来，任何在 attach 之前想碰 Activity 实例的代码（比如某些 hook 框架）都会踩空。

4.4 与相邻机制的关系

  • 与 Binder（AND-P2-101）：本篇的两次跨进程——客户端 startActivity 上行、ATMS scheduleTransaction 下行——都是普通同步 Binder 事务。上行会阻塞调用方线程直到 ATMS 返回；下行是 ATMS 主动发起（IApplicationThread 是 ATMS 持有的、指向应用进程的代理），所以它不占用调用方线程。
  • 与 WMS（AND-P2-202）：ATMS 只管「决定启动哪个 Activity、进哪个 Task」；真正的窗口创建、客户端 addView 的落地、层级与动画归 WMS。两者在 system_server 里同属窗口管理大模块，边界在 ActivityRecord/WindowToken 的分工。
  • 与 PMS（AND-P2-203）：Intent 解析（找目标组件）、导出性校验依赖 PMS 的包信息。
  • 与主线程/Looper（AND-P2-301）：handleLaunchActivity 及其后续回调全部在应用主线程上跑，由 Looper 驱动。这就是「Activity 启动慢」会拖垮整个 App 主线程的直接原因。

7. 常见问题与误区

`startActivity` 返回 `START_SUCCESS` 不等于界面起来了。 返回值只代表 ATMS 受理，界面在那之后的反向回调（scheduleTransaction）里才创建。若要等待界面起来，不要轮询返回值，可用 ActivityLifecycleCallbacks 或 onResume 等回调。

后台启动被拦不会报错。 Android 10+ 后台启动限制触发时，日志只有一条告警（措辞随版本略有差异，不宜按字符串硬匹配），调用方拿到的仍是「成功」码。这是最典型的静默失败；排查时先确认进程是否处于前台、有无前台服务或 SYSTEM_ALERT_WINDOW 等豁免。

`singleTop` 下再启动同一个 Activity，不一定走 `onCreate`。 若栈顶已是该 Activity，ActivityStarter 走 deliverNewIntent 复用实例，只回调 onNewIntent，不 new 也不 onCreate。把「没走 onCreate」当成启动失败是常见误判。

`attach` 严格早于 `onCreate`。 attach(4528) 先把 mWindow、mToken 等注入，onCreate(4557) 里才拿得到。任何想在 onCreate 之前访问 Activity 内部成员的代码都会空指针。

面试高频：为什么 App 上下文启动 Activity 必须加 `FLAG_ACTIVITY_NEW_TASK`？ 答：因为非 Activity 上下文没有所属 Task，Activity 是「长在」Task 上的；不给目标指定/新建 Task，服务端无法决定它进哪个返回栈。追问「加了之后 onNewIntent 会被调用吗」：取决于目标是否已有实例与 launchMode，NEW_TASK 本身不保证新建。

面试高频：ATMS 和 AMS 是什么关系？ 答：Android 10（Q）把原 ActivityManagerService 里"管 Activity/Task"的部分拆成 ActivityTaskManagerService，AMS 保留进程/服务/内存管理，两者在 system_server 内互相持有引用（历史沿革，据官方资料，本树无法回溯验证）。今天你说「AMS 启动 Activity」多半指的是 ATMS。追问「为什么拆」：职责与线程模型解耦，ATMS 的部分路径可减少与 AMS 大锁的争用。
