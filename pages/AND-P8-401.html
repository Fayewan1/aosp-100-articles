1. TL;DR

system_server 进程里的服务不是「按需启动」，而是由 SystemServer.run() 分三阶段顺序编排：Bootstrap、Core、Other。顺序的硬约束来自服务间依赖：后段服务构造时要拿前段服务的实例，前段没起完，后段直接抛异常。每段每个服务都被 TimingsTraceAndSlog 打上 trace 并写入 SystemServerTiming 标签，开机耗时分析就靠这条 trace 加 sys.system_server.start_* 三个属性。三阶段之后 run() 仍在同一个 try 块里往下走：startApexServices(t)（:1050，定义在 :3685，收尾处 :3709 调 sealStartedServices() 封口服务注册面）、updateWatchdogTimeout(t)（:1053）、CriticalEventLog.getInstance().logSystemServerStarted()（:1054）。所以「三阶段」是服务编排的主干，不是 run() 的全部。sys.boot_completed 并不在 SystemServer 里设置，也不由编排触发：它写在 ActivityManagerService 的 finishBooting() 内，该方法有两道门控——mBootAnimationComplete（:5915-5921）与低层工厂测试（:5984-5986）。

3. 问题背景

开机 log 里 services 一条条刷过去，服务多到看不过来。真出问题时，现象往往是「某个服务没起来，另一个服务抛 NPE」——比如 ActivityTaskManagerService 构造时为 null，或者某个 ServiceManager 查询拿不到实例。想看 trace 定位慢在哪，打开 SystemServerTiming 却发现几百个小段，不知道哪些是可砍的。这篇要回答的就是：这三阶段边界怎么划、哪个服务被谁依赖、trace 埋点在哪、开机完成到底由谁宣布。

4. 核心机制

4.1 概念与关系

三个概念：

  • SystemServer：run() 是三阶段编排的唯一入口，逐段调用三个 start*Services 方法。
  • SystemServiceManager：负责 startService 的注册与生命周期回调，服务实例被它持有，供后段查询。
  • TimingsTraceAndSlog：在 SystemServerTiming 标签下逐服务打 trace，把「谁慢」变成可量化的段。

但 finishBooting() 不是编排的自然收尾，它被两道门控挡着。方法体在 :5910，进来先建 TimingsTraceAndSlog 并 t.traceBegin("FinishBooting")（:5911-5913），紧接着的第一段逻辑（:5915-5921）是 synchronized (mGlobalLock) { if (!mBootAnimationComplete) { mCallFinishBooting = true; return; } }——开机动画没结束，它直接返回并记账，sys.boot_completed 一个字节都不写。第二道门控在更靠后的 :5984-5986：if (mFactoryTest == FactoryTest.FACTORY_TEST_LOW_LEVEL) { return; }，位置在 :5991 写属性之前。低层工厂测试模式下 sys.boot_completed 恒不写入，这与开机动画无关，是另一条独立的早退。真正把 mBootAnimationComplete 置真的是 bootAnimationComplete()（:6089），而它的调用方在窗口侧：WindowManagerService.java:4412 的 mActivityManager.bootAnimationComplete()。但这一条也不是无条件执行的。该调用点位于 performEnableScreen 收尾，上游前置返回不止三处：:4342-4343 的 mDisplayEnabled、:4345-4346 的 !mSystemBooted && !mShowingBootMessages、:4349-4350 的 !mShowingBootMessages && !mPolicy.canDismissBootAnimation()、:4356-4359 等 checkpoint 就绪（Flags.syncBeforeEnablingScreen() 为真时），再往后才是 :4362-4375 等全部已有窗口绘制完毕（mForceDisplayEnabled 为假时）、:4392-4395 的 !checkBootAnimationCompleteLocked()、:4397-4400 的 !SurfaceControl.bootFinished()。其中 :4388 紧接着把 service.bootanim.exit 置 1。无开机动画的场景（headless、service.bootanim.exit 预置）或 bootFinished() 失败时，这条路径可能长时间不到达，此时放行落在 ensureBootCompleted 链上。所以准确口径是：sys.boot_completed 的时点由「开机动画何时结束」与上述前置条件共同决定，与 startOtherServices 没有固定先后关系。进程内另有几条入口，都不在 SystemServer.run() 里：

  • ensureBootCompleted()（:6186），:6197 在 booting 为真时调 finishBooting。
  • 三处 mHandler 错误弹窗分支（:1831/:1835/:1858）。
  • ActivityTaskManagerService.java:7444 的工厂测试路径。
  • ActivityTaskManagerService.postFinishBooting()（:5980-5989），:5983 调 mAmInternal.finishBooting()，调用方是 ActivityTaskSupervisor.java:1564，参数由 booting 与 enableScreen 两个布尔控制。

4.3 一个具体例子

按顺序走一遍 run() 的时间线：

  1. 进程入口先过构造器 SystemServer()：:736/:737 在这里用 SystemClock.elapsedRealtime() 与 uptimeMillis() 捕获 mRuntimeStartElapsedTime/mRuntimeStartUptime，并经 Process.setStartTimes 下沉——这是一次启动真正的时间原点。
  2. :859 建 TimingsTraceAndSlog t，此后每段服务调用都记在 SystemServerTiming 下。
  3. :868–:870 把构造器已捕获的两个时刻与启动计数写进 sys.system_server.start_count、start_elapsed、start_uptime。想算「system_server 从启动到某服务可用」的耗时，用 start_elapsed 与该服务 SystemServerTiming trace 段的起点作差；若手上的时刻来自另一个时钟源，就换 start_uptime。start_count 只记启动次数，不参与作差。
  4. 进 Bootstrap :1192：:1203 先给 ART 模块服务装 manager，:1209 取 Watchdog.getInstance()，:1245 建 Installer，:1292 起 ActivityTaskManagerService，:1294 起 ActivityManagerService 的 Lifecycle。
  5. 进 Core :1467：SystemConfigService、BatteryService、UsageStatsService、WebViewUpdateService、RollbackManagerService、GpuService。
  6. 进 Other :1550：KeyChainSystemService、AccountManagerService、ContentService、DropBoxManagerService、TelecomLoaderService、RoleManagerService 等。注意 AccountManager 必须在 ContentService 之前（:1651 的注释明示了这条依赖），段内平铺的列表不等于无序。
  7. startOtherServices 返回后，run() 在同一 try 块内还依次调 startApexServices(t)（:1050，定义在 :3685，收尾 :3709 调 sealStartedServices() 封口注册面）、updateWatchdogTimeout(t)（:1053）与 CriticalEventLog.getInstance().logSystemServerStarted()（:1054）。编排主干到此结束。sys.boot_completed=1 不在这一步写：AMS 的 finishBooting()（ActivityManagerService.java:5910）被 :5915-5921 的 mBootAnimationComplete 门控，动画没结束就直接返回；属性写入 :5991/:5992 要等 WindowManagerService.java:4412 触发 bootAnimationComplete()（:6089）之后才发生。

7. 常见问题与误区

7.1 误区

  • 误区：服务顺序可以随意调，只要都在 `run()` 里起。 纠正：Core 与 Other 的服务构造参数里有 Bootstrap 阶段的实例（如 AMS/ATMS），提前或挪后会在构造期直接拿到 null 或抛异常，顺序是依赖驱动的，不是风格问题。
  • 误区：`sys.boot_completed` 是 `SystemServer` 在编排末尾设的。 纠正：它在 ActivityManagerService.java:5991 的 finishBooting() 内设置，SystemServer 只负责把服务按序拉起。更要紧的是它不由编排触发：finishBooting() 有两道早退，第一道是 :5915-5921 的 mBootAnimationComplete（放行者是 WindowManagerService.java:4412 的 bootAnimationComplete()），第二道是 :5984-5986 的 mFactoryTest == FACTORY_TEST_LOW_LEVEL。低层工厂测试设备上属性永远不置 1，与动画无关。
  • 误区：三阶段各跑一个线程，所以能看到交错。 纠正：三阶段都是 run() 内的同步调用（:1192、:1467、:1550），顺序推进；并发出现在各服务自身的内部线程里，不改变编排顺序。

7.2 高频提问

问：为什么计时器和三个启动属性要放在 run() 最前面？ 答：时刻本身在构造器 SystemServer() 的 :736/:737 就已捕获（mRuntimeStartElapsedTime/mRuntimeStartUptime），run() 前段把这两个字段写进系统属性只是落盘动作；放在 run() 最前面是为了让后续 trace 段与耗时统计都能对齐到同一时刻，晚写就会漏掉前段开销的记录口径（不是漏掉时刻本身）。追问：三个属性口径有什么区别？答：start_count 是启动次数，start_elapsed 与 start_uptime 是两个不同时钟口径的启动时刻，取哪个取决于你比较的对象是什么时钟。

问：SystemServerTiming 这个标签下几百个段，怎么下手？ 答：先按段名前缀归到三个阶段，再看每段时长；编排级问题通常出现在段与段之间的空档，也就是某服务构造期阻塞。追问：段名和 start*Services 的边界一定一一对应吗？答：不一定，段是按服务调用粒度铺的，一个 start*Services 方法里有很多段；对应关系要看 trace 层级而非段名。
