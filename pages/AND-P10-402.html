1. TL;DR

atrace 是采集器，perfetto 是采集框架加产物格式，两者不是二选一。atrace 沿 ATRACE_TAG_* 标签在 trace_marker 上打点，并把内核侧的调度、中断、频率等通过 ftrace 事件并入同一份 trace。perfetto 的 traced_probes 侧加载配置、调用 atrace 的类别开关，把结果写成 perfetto 格式；perfetto_cmd 只负责传配置与设定产物。产物统一用 trace processor 的 shell 做查询入口。

3. 问题背景

你已经知道要抓 trace，于是在命令行敲下 atrace 的时长参数，抓回来一份文件，打开看到一屏彩色条块，却不知道哪个类别是自己要的。换 perfetto 抓，配置模板一大堆，data_sources 里又冒出 linux.ftrace、track_event 这些名字，不确定和 atrace 的 gfx、input 是不是一回事。

更常见的是抓完发现想要的区间没覆盖到：不知道打点默认是关的，也不知道内核侧事件需要额外的 rc 权限。本篇只解决一件事：trace 从打点到落盘这一段，各方分别负责什么。

4. 核心机制

4.1 概念与关系

四个概念：打点标签、采集类别、采集后端、产物格式。

打点标签决定「有没有这条记录」，采集类别决定「这次抓不抓这一类记录」，采集后端决定「记录往哪写」，产物格式决定「下游怎么读」。打点标签在进程内，采集类别与采集后端在系统侧，产物格式由消费侧工具约定。

图 1：打点、类别、后端、产物的关系

  ATRACE_END    ->  trace_marker

                                        |
                                    产物 trace
                                        |

关键点在于两条路径上都存在「开关」，且它们是前置门禁而非 trace_marker 的下游处理环节：进程内的 ATRACE_TAG 编译期/运行期开关（门禁一）决定打点写不写，采集侧的类别开关（门禁二，图 1 中 atrace 类别开关与 perfetto 配置那一列）决定记录抓不抓。任一为关，区间就不出现。

4.2 关键内容

Java 侧打点在 Trace.java，beginSection 在 :511、endSection 在 :527，isEnabled() 在 :495。TRACE_TAG_* 自 :52 起，TRACE_TAG_NEVER=0、TRACE_TAG_ALWAYS=1L << 0、TRACE_TAG_GRAPHICS=1L << 1、TRACE_TAG_INPUT=1L << 2、TRACE_TAG_VIEW=1L << 3、TRACE_TAG_WEBVIEW=1L << 4。isEnabled() 是廉价判断，可以在热路径前做一次门禁。

Native 侧在 cutils/trace.h，共 325 行，位定义与 Java 侧对齐：

名称含义出处
ATRACE_TAG_NEVER值 0，永不上报system/core/libcutils/include/cutils/trace.h:50
ATRACE_TAG_ALWAYS(1<<0)，始终上报同上 :51
ATRACE_TAG_GRAPHICS(1<<1)，对应 atrace 的 gfx同上 :52

未定义 ATRACE_TAG 时默认 ATRACE_TAG_NEVER（:86–:87）；定义值越界则 #error（:88–:89）。这条是编译期契约：漏定义等于静默关闭，不会报错。

atrace 侧，atrace.cpp 共 1481 行，k_categories[] 自 :102 起共 46 个类别（:253 收尾），g_categoryEnables[arraysize(k_categories)] 在 :296。帮助文本 --list_categories 在 :1112，长选项表自 :1280 起（:1285 为表内 list_categories 条目），处理分支 :1362。

46 个类别按启用通道分四类，不是二分：

  • **仅带 ATRACE_TAG_* 标签（24 个）**：input :106、view :107、webview :108、wm :109、am :110、sm :111、audio :112、video :113、camera :114、hal :115、res :116、dalvik :117、rs :118、bionic :119、power :120、pm :121、ss :122、database :123、network :124、adb :125、vibrator :126、aidl :127、nnapi :128、rro :129。
  • 标签与 sysfs 兼有（2 个）：gfx（:103，ATRACE_TAG_GRAPHICS，另带唯一 sysfile events/gpu_mem/gpu_mem_total/enable（:104））、thermal（:249，ATRACE_TAG_THERMAL，另带 thermal_temperature 与 cdev_update）。这两类必须两侧都开才完整。
  • 标签为 0、纯走 sysfs（19 个）：sched :131、irq :144、irqoff :148、preemptoff :152、i2c :156、freq :167、membus :181、idle :184、disk :187、mmc :202、load :205、sync :208、workq :216、memreclaim :219、regulators :226、binder_driver :229、binder_lock :235、pagecache :240、memory :243。
  • 属性特判（1 个）：core_services :130——标签为 0、sysfile 表为空 { }，既不走 ATRACE_TAG 也不走 sysfs；它的启用通道是 ro.atrace.core.services 属性（isCategorySupported 在 atrace.cpp :447-448 对它单独返回属性非空判定），启用时把属性值并入 app 包名列表（:818）。所以「core_services 是 sysfs 类」不成立，选它看不到内核事件，它管的是应用侧 core service 打点。

前三类合计 24+2+19 = 45，再加上属性特判的 core_services 一项，共 46。--list_categories 里它们并列显示，但启用机制不同，这也是「选了 sched 却看不到调度事件」「只开了 gfx 却缺 GPU 内存项」的常见原因。另外，设备上 --list_categories 还会附加 VENDOR/HAL 条目（atrace.cpp :1080–:1085），且只打印 isCategorySupported 为真的项，因此不同设备的列表可能多于本树的 46 项；本篇的 46 是编译期表项数口径。

权限与缓冲在 atrace.rc（共 573 行）：on late-init（:3）里执行 chmod 0222 /sys/kernel/debug/tracing/trace_marker（:6）与 /sys/kernel/tracing/ 下同名文件（:7），write /proc/sys/kernel/sched_schedstats 1（:10），buffer_size_kb 的权限放开在 :18–:19。trace_marker 的 0222 是写权限，意味着采集侧只管写，读走 ftrace 的 trace 节点。

实际执行 exec /system/bin/atrace 的是 external/perfetto/src/traced/probes/ftrace/atrace_wrapper.cc:94 的 execv（唯一 exec 点）；:126 那处 /system/bin/atrace 位于 20s 超时分支（:114）内，只用于拼错误消息（:130），不是执行点。ftrace_data_source.cc:39 另以 Subprocess 调 --list_categories；perfetto_cmd 侧只传配置。

后端选择在 tracing_muxer_impl.cc（共 2825 行）。BackendTypePriority（:145）区分 kSystemBackend（:147）与 kInProcessBackend（:149）。数据源注册入口是 TracingMuxerImpl::RegisterDataSource（:1101）。同一进程里的多个客户端共享一个 muxer，由它决定这次采集落到系统后端还是进程内后端。

4.3 一个具体例子

想看一次界面操作的区间是否落进 trace。Java 侧在操作前后调 beginSection/endSection（Trace.java:511、:527），它们走的是 TRACE_TAG_APP = 1L << 12（Trace.java:80；门禁判断 :512、native 写出 :516），不是 TRACE_TAG_GRAPHICS。抓应用自写区间要用 atrace -a <包名>（atrace.cpp:1303 收进 g_debugAppCmdLine，经 :813 并入包名列表，再写 debug.atrace.app_N 系列属性，:70/:71）或 perfetto --app（perfetto_cmd.cc:186）；gfx 类别（atrace.cpp:103，ATRACE_TAG_GRAPHICS）管的是图形管线那条轨，与应用自写区间不是同一回事。内核对 trace_marker 的写权限已由 atrace.rc:6 放开。

任一条件不满足，区间或 GPU 内存项就会缺失。注意这里没有任何实测数字：标签位、类别名、权限模式都是源码常量与文件内容，不构成对某台设备行为的断言。

7. 常见问题与误区

7.1 误区

误区一：atrace 和 perfetto 是两代工具，新版本只用后者。 纠正：atrace 是 perfetto 之前就存在的采集器，perfetto 的 traced_probes 会 exec 它并复用它的类别开关（atrace_wrapper.cc:94）。本树里 atrace.cpp 仍在维护，k_categories[] 有 46 个类别。

误区二：`gfx` 和 `sched` 是同一类开关。 纠正：sched（:131）标签为 0、纯走 sysfs；gfx（:103）是双通道，既靠 ATRACE_TAG_GRAPHICS（trace.h:52）的进程内标签位，也带自己的 sysfile 项，两侧都要开。所以「开了 gfx 就全都有」和「gfx 与 sched 同机制」都不成立。

误区三（看着对其实不对）：打点代码写进函数里，trace 里就一定有区间。 纠正：未定义 ATRACE_TAG 时默认是 ATRACE_TAG_NEVER（trace.h:86–:87），编译通过、运行不报错、产物为空。这是静默失败，靠读代码发现不了，要看编译宏。

误区四：`--txt` 既然能用就用于生产脚本。 纠正：该选项在 perfetto_cmd.cc:170 的注释里明确标了 Not for production use。

7.2 高频提问

问：抓 trace 时长默认多少？ 答：perfetto_cmd 的 --time/-t（:182）默认 10s。这是源码常量值，不是任何设备上的实测。 追问：后台采集会让命令一直阻塞吗？ 答：--background/-d（:143）直接返回，--background-wait/-D（:147）等待，说明里写明等待上限 30s。

问：perfetto 的数据源和我写的 ATRACE_BEGIN 是什么关系？ 答：数据源由 TracingMuxerImpl::RegisterDataSource（:1101）注册，后端由 BackendTypePriority（:145）在系统后端与进程内后端间分流；打点标签决定记录是否产生，数据源决定记录被谁收走。 追问：分不清该看哪一层怎么办？ 答：先确认类别是否启用、标签是否定义；两层都通再看后端选择。
