1. TL;DR

NSC（Network Security Config，网络安全配置）不是一个静态文件，而是被装配成 Provider 插到 JCA 信任工厂的第 1 位，之后所有 TrustManagerFactory 的默认信任锚均由此装配而来。CT（Certificate Transparency，证书透明度）校验挂在 TrustManagerImpl 里，先由策略判定「这个主机名是否要求 CT」，再交给 CertificateTransparency 执行，并读取 log store 状态。log store 不可用时按 fail-open 处理：上报后返回，不抛异常——这就是「CT 失败不一定断连」的根源。理解这条链的关键，是把「配置装配」「信任锚裁剪」「CT 门控」「log store 状态」四件事分开看。

3. 问题背景

应用侧最容易撞上的两个现象：一是 cleartextTrafficPermitted="false" 明明写了却仍能发出明文请求，或者反过来写了自定义 CA 却没生效；二是 CT 相关的日志里报了错，连接却照样成功。第三个常见困惑是「我到底改了哪个文件才换掉信任锚」——答案不在 manifest，而在 Provider 被插到 JCA 的第 1 位这件事上。三个现象指向同一个问题：这套机制的装配顺序与失败语义一直缺乏交代。

4. 核心机制

4.1 概念与关系

四个概念：配置源（config source）负责把 manifest 属性与 XML 读成策略对象；Provider 负责把策略装进 JCA；TrustManagerImpl 负责在握手时按主机名查策略；CertificateTransparency 负责按 log store 状态决定是否继续。

关系要点：Provider 是唯一的装配入口；TrustManagerImpl 是信任链校验路径上的判定点（SSLSocket 侧另有 SSLParametersImpl.java:877 的同名门控）；CertificateTransparency 只做校验执行与失败上报，不做「要不要查 CT」的决定。

4.2 关键内容

装配。NetworkSecurityConfigProvider 继承的 Provider 身份由 super("AndroidNSSP", 1.0, "Android Network Security Policy Provider") 给定，并注册 TrustManagerFactory.PKIX 与别名 Alg.Alias.TrustManagerFactory.X509。install(Context) 调用 Security.insertProviderAt(new NetworkSecurityConfigProvider(), 1)，插到位置 1——这是「默认信任工厂来自 NSC」的全部来源。handleNewApplication(Context) 处理共享进程下多个应用 usesCleartextTraffic 冲突。

信任锚裁剪。策略对象决定哪些源进入信任锚集合；UserCertificateSource 与 SystemCertificateSource 是可被策略增删的两类。裁剪发生在装配期，不在握手期。

CT 门控与 fail-open。TrustManagerImpl 里 policy.isCertificateTransparencyVerificationRequired(host) 决定该主机名是否走 CT。走 CT 时进入 CertificateTransparency，其中 logStore.getState() != LogStore.State.COMPLIANT 的分支在上报后直接返回，不抛异常。log store 不可用（没有 log list 或 log list 过旧）落在这一支。

log store 位置与刷新。LogStoreImplv3 从 ANDROID_DATA 拼接路径，末段为 current/log_list.ctfb；中间那段是版本号目录，由 getPathForCompatVersion(COMPAT_VERSION)（:121）按 COMPAT_VERSION = 3（:60）生成 v3，所以完整路径口径是 /data/misc/keychain/ct/v3/current/log_list.ctfb；LOG_LIST_CHECK_INTERVAL_IN_MS = 10L * 60 * 1_000 即 10 分钟检查一次。Platform.newDefaultCertificateTransparency 里先 new PolicyImpl()，再按版本选 new LogStoreImplv3(policy) 或 new LogStoreImplv2(policy)。

4.3 一个具体例子

某应用配置 cleartextTrafficPermitted="false"，同时在某域上加了一个自定义信任锚。进程启动时 NetworkSecurityConfigProvider.install 把 AndroidNSSP 插到第 1 位；ManifestConfigSource 读到 manifest 里的属性值，XmlConfigSource 解析成策略；策略里该域的可信锚集合被改写，SystemCertificateSource 被裁剪。握手时 TrustManagerImpl 按主机名查策略拿到该域条目，判定不需要 CT，于是不进 CertificateTransparency。若该域需要 CT 而 /data/misc/keychain/ct/v3/current/log_list.ctfb 缺失，logStore.getState() 不是 COMPLIANT，上报后返回，连接仍成功——这就是日志报错但请求通过的原因。

7. 常见问题与误区

7.1 误区

误区一：NSC 是框架在握手时读文件。 错。配置在装配期被读成策略对象并装进 Provider，握手期只查策略。

误区二：CT 校验失败必然导致连接失败。 错。log store 不可用时走 fail-open，这条分支不抛异常。

误区三：在 manifest 里写了自定义 CA 就等于系统信任锚全部失效。 这个说法以偏概全：是否裁剪系统锚由策略里的信任锚集合决定，SystemCertificateSource 只是可被增删的一类来源——写了自定义 CA 不代表策略一定裁掉系统锚。

7.2 高频提问

问：为什么把 Provider 插到位置 1 这么关键？ 答：位置 1 意味着它是 TrustManagerFactory 的默认解析结果，应用不显式指定 provider 时拿到的就是 NSC 的信任工厂。 追问：应用显式指定别的 provider 呢？ 答：那就绕过了 NSC 的策略，信任锚与明文策略都不再生效。

问：LogStoreImplv3 和 LogStoreImplv2 怎么选？ 答：由 Platform.newDefaultCertificateTransparency 按运行环境选择，两者都吃同一个 PolicyImpl。 追问：log list 多久刷新一次？ 答：LOG_LIST_CHECK_INTERVAL_IN_MS 是 10 分钟，即 10L * 60 * 1_000。
