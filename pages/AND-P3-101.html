1. TL;DR

应用崩溃日志里出现 dlopen failed: library "libxxx.so" not found，或者 setprop 返回失败，问题往往已经落在 Java 之下的 native 层。bionic 同时提供 C 库和链接器：libc 与 linker 是同一目录下的两个 Soong 模块，模块名就是安装后的 .so 名。.so 的装载由 linker 按命名空间配置解析，配置来自 /system/etc/ld.config.txt 与 /linkerconfig/ld.config.txt。属性的读取在进程内完成，写入却必须交给 init：__system_property_set 只把控制消息发给属性服务，具体落盘由 init 的 PropertyServiceThread 执行。记住三条硬边界：属性名 32 字节、属性值 92 字节、写入要过 SELinux 检查。

3. 问题背景

一个应用调 System.loadLibrary("foo")，抛 UnsatisfiedLinkError；同一台机器上 adb shell 里用 pm 装的另一个应用加载同名库却正常。换个场景：脚本里循环 setprop 写一个自定义属性，前几次成功，后面开始失败，日志里只有 SELinux 拒绝。再换一个场景：getprop ro.build.type 立刻返回，但写一个 persist. 前缀属性后，另一进程读到的仍是旧值。

这三个现象分别指向 native 世界的三个基础件：.so 从哪来、由谁装载；属性谁能写、写到哪里去；读和写为什么路径完全不同。把这三件事拆开看，后面的 JNI、libbinder、init.rc 才有立足点。

4. 核心机制

4.1 概念与关系

四个概念：

  • bionic：Android 的 C 库与加载器集合。它不是一个 .so，而是 libc、linker、libm、libdl、libc++ 等一组模块的统称，目录层面各自独立。
  • linker：动态链接器，负责把 .so 映射进进程并按命名空间配置解析依赖。它本身也是一个模块，名叫 linker。
  • 属性系统（property system）：键值存储。读侧在进程内查内存，写侧必须经过 init 的属性服务。
  • 命名空间（namespace）：linker 的库搜索隔离单元，用 android_namespace_t 表示，配置来自 ld.config.txt 等配置文件。

读侧完全在进程内完成：属性区由 bionic 按 context 分区映射，__system_property_find 直接命中。写侧是一条 socket 控制消息，终点是 init 的 PropertyServiceThread；init 收到后先做 selinux_check_access，再落进属性区，persist. 前缀的再异步交给持久化写线程。

4.2 关键内容

bionic 的模块构成。 libc 模块定义在 bionic/libc/Android.bp:1726，linker 模块定义在 bionic/linker/Android.bp:440。Soong 的 cc_library 默认让模块名等于安装的 .so 名，所以 bp 里的名字就是设备上看到的名字。目录层面还存在 bionic/libm、bionic/libdl、libc++ 等，它们是不同的模块，各有自己的 bp。

两个硬上限。 属性值上限 PROP_VALUE_MAX = 92，属性名上限 PROP_NAME_MAX = 32，都在 bionic/libc/include/sys/system_properties.h（分别在第 50 行与第 116 行）。这两个数字是 buffer 尺寸，不是「建议长度」，超了就是截断或失败。

属性读写 API。 同族符号集中如下：

名称含义出处
__system_property_find按名字在属性区中定位属性节点system_properties.h:66
__system_property_read_callback读属性并回调出值，避免拷贝到定长 buffersystem_properties.h:75
__system_property_wait等待属性区版本号变化，实现监听system_properties.h:108
__system_property_set写属性，实际是向 init 发控制消息bionic/libc/bionic/system_property_set.cpp:274

写路径的完整链。 __system_property_set 不直接改共享属性区，它把控制消息发给 init。init 侧由 PropertyServiceThread（system/core/init/property_service.cpp:1471）接收；StartPropertyService（:1551）内以 StartThread(PROP_SERVICE_NAME, 0666, 0, property_service_thread, false)（:1564）启动线程，socket 名是 PROP_SERVICE_NAME "property_service"（system_properties.h:179）。消息进入 HandlePropertySet（property_service.cpp:541），再交给 PropertySet（:378）；persist. 前缀的属性由 persist_write_thread（:417-419）异步落盘。

属性区按 context 分区。 bionic 侧通过 contexts_->GetSerialPropArea() 与 GetPropAreaForName(name)（bionic/libc/system_properties/system_properties.cpp:159/190）取到对应的属性区，这就是为什么「同一份属性」实际分布在不同的映射区里。

属性文件加载顺序。 property_service.cpp 中按序加载：/system/build.prop（:1207）→ /system_dlkm/etc/build.prop（:1213）→ /vendor/default.prop（:1217）→ /vendor/build.prop（:1219）→ /vendor_dlkm/etc/build.prop（:1220）→ /odm_dlkm/etc/build.prop（:1221）。

SELinux 约束属性类型。 system/sepolicy/private/property_contexts 把属性名前缀逐条映射到类型，例如 ril. → u:object_r:radio_prop:s0、net.rmnet → u:object_r:net_radio_prop:s0。init 侧调用 selinux_check_access(..., "property_service", "set", ...)（property_service.cpp:174）做判定。

命名空间配置的来源。 linker 侧读取三份主要候选配置：/system/etc/ld.config.txt（bionic/linker/linker.cpp:102）、/system/etc/ld.config.vndk_lite.txt（:103）、/linkerconfig/ld.config.txt（:105，由 system/linkerconfig 生成）。候选实际更多——还有 arch 专属路径（:100，/system/etc/ld.config.<ABI>.txt）、APEX 专用路径与 vndk 版本化路径，完整查找顺序见 AND-P3-402。命名空间对象类型是 android_namespace_t，定义在 linker_namespaces.h。

装载入口。 dlopen 系列经 bionic/libdl 进入 linker。应用进程里，类加载器按 BaseDexClassLoader 的 librarySearchPath 找 native 库（libcore 侧，细节归后续篇）。

4.3 一个具体例子

假设某进程调用 __system_property_set("persist.vendor.foo", "bar")，走一遍：

  1. 调用落进 system_property_set.cpp:274，此处不做内存写，只组一条控制消息，发往名为 property_service 的 socket。
  2. init 的 PropertyServiceThread（property_service.cpp:1471）收到消息，进入 HandlePropertySet（:541）。
  3. 先做 selinux_check_access(..., "property_service", "set", ...)（:174）。persist.vendor.foo 需要能匹配 property_contexts 里某个前缀以及域规则；匹配不上直接拒绝。
  4. 通过后进入 PropertySet（:378）。名字长度必须不超过 PROP_NAME_MAX = 32，值不超过 PROP_VALUE_MAX = 92。
  5. 因为带 persist. 前缀，值交给 persist_write_thread（:417-419）异步持久化。
  6. 读侧任何进程调 __system_property_find 时，bionic 经 GetPropAreaForName(name)（system_properties.cpp:190）找到对应属性区，直接读到新值。

反方向的例子：getprop ro.build.type 不经过 init，一次函数调用就返回，因为它只有 __system_property_find 这一步。

7. 常见问题与误区

7.1 误区

误区一：bionic 就是一个叫 `libbionic.so` 的库。 实际上 bionic 是仓库与一组模块的集合名。设备上并不存在 libbionic.so；你能看到的是 libc.so、linker、libm.so、libdl.so 等。

误区二：`__system_property_set` 直接把值写进共享属性区。 这个理解看起来对，因为读侧确实是进程内直接查内存。但写侧不是对称的：system_property_set.cpp:274 只发控制消息给 init，所有权在 init 一侧。之所以这样设计，就是为了让每次写入都能过一遍 selinux_check_access 与命名规则。

误区三：属性写完立即对所有进程可见且已落盘。 内存可见性通常是即时的，但 persist. 前缀的值是由 persist_write_thread 异步持久化的，重启后能否读到取决于那一步是否完成。

误区四：属性名可以随便长。 PROP_NAME_MAX = 32 是硬上限，超长的名字会被拒绝或截断，且不同层的截断行为可能不一致。

7.2 高频提问

问：为什么应用里 dlopen 一个 /vendor/lib64 下的库失败，shell 里 ldd 却能看到？ 答：应用进程的 linker 按自己的命名空间配置搜索，配置由 ld.config.txt 系列决定；shell 进程的配置不同，搜索结果自然不同。 追问：那怎么确认应用进程用的是哪份配置？ 答：看进程对应的 linker 配置来源：/system/etc/ld.config.txt、/system/etc/ld.config.vndk_lite.txt、/linkerconfig/ld.config.txt 三者中生效的那份（选择逻辑属 VNDK 命名空间细节，见 AND-P3-402）。

问：setprop 失败但没有任何 Java 异常，怎么定位？ 答：先看是不是 SELinux 拒绝：init 侧在 property_service.cpp:174 调 selinux_check_access，拒绝会留下审计日志；再看名字/值是否超过 32/92 的上限。 追问：属性名合法、SELinux 也放行，还是失败？ 答：检查该前缀是否在 property_contexts 里有映射，以及调用域是否被授予对应类型；两条任一缺失都会在判定阶段被挡住。
