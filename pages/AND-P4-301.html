1. TL;DR

应用的播放请求最终落到一个 IModule 远端代理上，中间隔着 AudioFlinger、一层 HAL（硬件抽象层）封装（libaudiohal）和一次跨进程调用。判断「请求在哪一层被丢掉」，关键是认清三段：AudioFlinger 的 Binder 方法表入口、FactoryHal 选出的 HAL 版本与实现、DeviceHalAidl／IModule 的打开与读写。真正被固化的是绑定关系——mDevicesFactoryHal 是 const 成员，初始化时（onFirstRef）选定 HIDL 还是 AIDL 实现，之后不再改；getHalVersion() 本身是每次调用都向 HAL 现查，返回值稳定只因为绑定没变。HAL 服务进程重启会连带重启 audioserver，所以你看到的「无声」可能是 HAL 进程退出而非音频通路阻塞。

3. 问题背景

用户报「播放无声」，但你拿到的是 audioserver 的日志：没有报错，createTrack 返回成功，写入也没有返回负值。这时继续在应用侧找是徒劳的——请求已经交出去了，问题在 HAL 及其以下。另一种常见困惑：某台设备上 mDevicesFactoryHal 打开模块失败，换一台同版本 Android 却正常。两台机器的差别往往不在代码，而在 VINTF 里声明了哪个 HAL，以及 audioserver 有没有权限拿到那个服务。本篇只讲「AudioPolicy 决定之后到设备」这一段，把中间每一层的名字和失败形态摊开。

4. 核心机制

4.1 概念与关系

四个概念。AudioFlinger 是 media.audio_flinger 服务的实现者，对外暴露 Binder 方法表。mDevicesFactoryHal 是 AudioFlinger 持有的 HAL 工厂抽象，实际类型是 DevicesFactoryHalAidl 或 DevicesFactoryHalHidl，由 FactoryHal.cpp 按可用性挑选。DeviceHalAidl 是 AIDL 实现下的设备封装，由工厂的 openDevice 产出（调用点在 AudioFlinger.cpp:2636），把 AudioFlinger 的调用翻译成对 IModule 的调用。IModule 是 vendor 侧真正干活的接口。

4.2 关键内容

AudioFlinger 对外的入口是方法表，不是某个函数。BINDER_METHOD_ENTRY(createTrack)（AudioFlinger.cpp:175）与 BINDER_METHOD_ENTRY(loadHwModule)（:212）是两个关键项；createTrack 的实现体在 :1048。这意味着「应用能不能创建轨道」这件事，在 Binder 派发阶段就已定型，之后才走到 HAL 层。

HAL 抽象入口是 mDevicesFactoryHal，它第一次被用是在 onFirstRef()（:343 起）里：:350-351 挂设备可用性回调，:353 读 getHalVersion() 决定 AAudio 的 burst 参数；此外 :405（getMmapPolicyInfos）、:810、:2709 也各读一次。所以「版本不变」不等于「只读一次」：getHalVersion() 每次调用都经 mConfig->getInterfaceVersion() 向 HAL 现查（DevicesFactoryHalAidl.cpp:199-206）。真正被固化的是绑定关系——mDevicesFactoryHal 是 const 成员，由 DevicesFactoryHalInterface::create() 在初始化时定下（AudioFlinger.h:683-684），之后同一进程内不会再换成另一种实现。

工厂选择看接口名与包名：HIDL 接口名为 <"android.hardware.audio", "IDevicesFactory">（FactoryHal.cpp:43/63），AIDL 侧包名为 android.hardware.audio.core（:43 同段注释）。createHalService（:73）用 createIDevicesFactory／createIEffectsFactory（:76）取实现；可用性判定分别为 hasAidlHalService（:103）与 hasHidlHalService（:114），最终由 createPreferredImpl（:151）决定优先项。

4.3 一个具体例子

一次无声排查。先在 android.hardware.audio.service-aidl.xml 里确认该 HAL 声明的实例是 IModule/default 与 IConfig/default，版本号 <version>4</version>。如果 VINTF 完全匹配不上，createPreferredImpl 拿不到实现、返回 nullptr（FactoryHal.cpp:183），mDevicesFactoryHal 于是为空；后来 onFirstRef() 在 :351 直接调 mDevicesFactoryHal->setCallbackOnce(...)，没有判空，结果是 audioserver 启动即崩溃——这时的现象是日志里的 crash 与重启循环，而不是「createTrack 成功但无声」。走不到「成功但无声」的通常是另一种情况：工厂拿到了、模块也打开了，但 initCheck 或 openOutputStream 失败。

再看 initCheck（DeviceHalAidl.cpp:183）。它返回失败时，AudioFlinger 会记录模块不可用并保留其他已成功打开的模块；落到失败模块上的写入再也进不了 IModule::openOutputStream，应用侧只看到写入不再被消费。

最后看 HAL 进程。若 HAL 崩溃，onrestart restart audioserver 会重启 audioserver；应用侧的 AudioTrack 随之失效，表现为播放中断后重连。此时日志里没有音频错误，只有服务重启记录。

7. 常见问题与误区

7.1 误区

误区一：HAL 版本可以在运行期切换。 纠正：getHalVersion() 本身是活查询，每次调用都问 HAL；不能切换的是绑定——mDevicesFactoryHal 是 const 成员，初始化时定下 HIDL 还是 AIDL 实现，同一进程内不再变。要换实现只能重启 audioserver。

误区二：`createTrack` 返回成功就代表能出声。 纠正：createTrack（AudioFlinger.cpp:1048）只保证轨道对象建立，HAL 侧 openOutputStream 与 initCheck 是另外两道关。轨道成功而无声完全正常。

误区三（看起来对其实是错的）：AIDL 和 HIDL 会同时被使用。 纠正：createPreferredImpl 在可用实现中选一个优先项，最终只走一条路径。两者同时存在时是择一，不是双跑。

误区四：应用无声时先看 AudioTrack 的 state。 纠正：若 HAL 进程崩溃过，onrestart restart audioserver 会让 audioserver 重启，AudioTrack 的失败是结果而非原因。先查服务重启记录。

7.2 高频提问

问：mDevicesFactoryHal 为空时，日志里能看到什么？ 答：先是 FactoryHal.cpp:177 那句 Found no HAL version, main(Device) ...，紧接着就是崩溃——onFirstRef() 在 :351 对该空指针直接调方法，没有判空。所以这个状态下不存在「运行期静默」，audioserver 根本起不来。 追问：那怎么确认是这一步？ 答：检查 VINTF manifest 里是否声明了 IModule/default 与 IConfig/default，版本号是否匹配 <version>4</version>。

问：initCheck 失败会被重试吗？ 答：不会。失败即放弃该模块，AudioFlinger 保留其他已成功打开的模块；若没有可替代的，表现为无输出。 追问：怎么定位是 initCheck？ 答：在 DeviceHalAidl.cpp 的 initCheck（:183）处加日志，或比对模块打开前后的可用模块列表。
