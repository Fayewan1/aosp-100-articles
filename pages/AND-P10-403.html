1. TL;DR

ANR 与崩溃是两条完全不同的链路：ANR 是「有人在等」，由 TimeoutRecord 记录超时种类、AnrHelper 排队、ProcessErrorStateRecord 落状态；崩溃是「有人死了」，由 debuggerd 抓现场、tombstone.cpp 刻盘、NativeCrashListener 回传 Java 侧。

判断 ANR 的第一步不是看 Java 调用栈，而是看这次 ANR 的 mReason 是哪种超时记录——它决定了「谁在等谁」的初始拓扑。

输入分发的超时常量是 5000 毫秒（AIDL 字面值，Java 侧 InputConstants 再乘 Build.HW_TIMEOUT_MULTIPLIER），广播前台 10 秒、后台 60 秒，Service 默认 20 秒、后台放大 10 倍，ContentProvider 发布 10 秒——这些都是源码常量的口径，不是某台机器的实测值。注意 instrumentation / wrapper 场景另有一条 60 秒的取值，不经过这个 5000。

simpleperf 与 lldb 在这条链上的作用是取证据：前者按 -e cpu-cycles -f 4000 的默认速率采样热点，后者接 debuggerd 交出的现场。

3. 问题背景

手上有一份额外的 anr_ 文件，打开是几百行线程栈；另有一具 tombstone，第一行是一串信号名和地址。两份产物的共同点是「信息很多，但看不出起点」。

常见的错法是直接跳到最长的那个线程栈里找可疑函数。ANR 的答案往往不在栈里，而在「这次判定的超时由谁设定、用的是哪个常量」；崩溃的答案往往不在最后一帧，而在信号是谁发的、ptrace 是在哪一步接管的。

本篇只讲判定链路与产物解读：超时由谁记录、ANR 怎么产生、tombstone 怎么生成、采样与调试器的命令契约是什么。

4. 核心机制

4.1 概念与关系

四个概念要分清。超时记录（TimeoutRecord）是「这次判定的理由书」，回答是哪种超时、等了多久。ANR 记录（AnrRecord）是排队单元，每条待处理 ANR 占一行。错误状态（ProcessErrorStateRecord）是进程对象的持久标记，isNotResponding() 读它。tombstone 是崩溃现场的落盘产物，与 ANR 链路在 DropBoxManagerService 之前互不相干。

图 1：ANR 与崩溃两条链路的汇合点

超时发生
  -> TimeoutRecord (mReason)
    -> AnrHelper.mAnrRecords 排队
      -> AnrConsumerThread 消费
        -> ProcessErrorStateRecord.setNotResponding
          -> DropBoxManagerService.isTagEnabled

native 崩溃
  -> debuggerd 接管 (ptrace)
    -> crash_dump 回溯
      -> tombstone.cpp 刻盘
        -> NativeCrashListener 读 socket
          -> DropBoxManagerService.isTagEnabled

两条链路在归档处汇合，但前面每一步的责任主体完全不同。判读时先确定产物属于哪条链路，再看该链路的第一个分叉点。

注：图 1 的崩溃分支里，crash_dump 的两路输出是并行的——tombstone 刻盘（tombstone.cpp :861/:865）与回传 Java 侧的 AM socket（NativeCrashListener，crash_dump.cpp :875）同源并行，并非严格的「先落盘再回传」；上图按责任主体先后简化绘制。

4.2 关键内容

ANR 侧：从超时种类到排队消费

AnrHelper 是统一入口，全文 336 行。待处理队列是 ArrayList<AnrRecord> mAnrRecords（:81）。入口方法 appNotResponding(ProcessRecord, TimeoutRecord)（:117）与带组件名的重载（:123）。消费线程 AnrConsumerThread（:205）由 startAnrConsumerIfNeeded()（:178/:185）按需拉起——没有 ANR 时不占线程。

输入分发：5000 毫秒的来路

InputConstants.java :24–:26 的 DEFAULT_DISPATCHING_TIMEOUT_MILLIS 取 IInputConstants.UNMULTIPLIED_DEFAULT_DISPATCHING_TIMEOUT_MILLIS（后者定义在 frameworks/native/libs/input/android/os/IInputConstants.aidl :26，字面值 5000，注释写 // 5 seconds）再乘 Build.HW_TIMEOUT_MULTIPLIER——Java 侧不是裸 5000，普通进程口径同样带硬件倍率。

消费侧在 ActivityRecord.java（全文 9918 行）：mInputDispatchingTimeoutMillis 初始化于 :674，在 :4087 重置，超时回调 inputDispatchingTimedOut(TimeoutRecord, int) 在 :6819。

但这不只有初始化这一条赋值。setProcess 路径在 ActivityRecord.java :2184 把 mInputDispatchingTimeoutMillis 重新赋值为 getInputDispatchingTimeoutMillisLocked(this)；该函数在 ActivityTaskManagerService.java :5586（有进程则转 :5590 → :5593），最终落到 WindowProcessController.java :1487 的 getInputDispatchingTimeoutMillis()，其返回

isInstrumenting() || isUsingWrapper()
    ? INSTRUMENTATION_KEY_DISPATCHING_TIMEOUT_MILLIS
    : DEFAULT_DISPATCHING_TIMEOUT_MILLIS

前者定义于 ActivityTaskManagerService.java :345，值为 60 * 1000。也就是说，带 instrumentation 或 wrapper 的进程，输入分发判定阈值是 60 秒，这个值不再由 IInputConstants.aidl 决定；只有普通情况才回到 5000。

再者，「判定对象是 Activity」这个说法要收窄。按 frameworks/base/services/core/java/com/android/server/wm/AnrController.java :304–:306（注意 core/java/android/app/ 下另有同名类，内容吻合的是 wm 侧这个），activity 为空或为 embedded 时直接按 pid 归因，aboveSystem 另判；ActivityRecord.java :6835–:6847 里 blameActivityProcess 为 false 时同样转 pid 路径。即便走 Activity 分支，最终仍是以 ProcessRecord 进入 AnrHelper（ActivityManagerService.java :19354）——Activity 只用于定组件与归因，不构成独立判定对象。pid 归因的具体取值点是 ActivityManagerService.java :19314 取出 ProcessRecord 的 pid（ProcessRecord.java :1861–:1862 的 pid 字段，经 WindowProcessController.java :1487 同函数回写），再交给 AnrHelper；而 ActivityTaskManagerService.java :5587–:5588／:5594–:5595 在 r == null、无进程或 WPC 为 null 时直接返回 DEFAULT_DISPATCHING_TIMEOUT_MILLIS，60 秒分支此时不生效。

4.3 一个具体例子

假设一份 ANR 的 mReason 指向 forInputDispatchWindowUnresponsive。链路走一遍：

输入分发器等待超过 DEFAULT_DISPATCHING_TIMEOUT_MILLIS（AIDL 字面值 5000 乘 Build.HW_TIMEOUT_MULTIPLIER；instrumentation / wrapper 场景为 60 秒）→ 构造该 TimeoutRecord → 交给 AnrHelper :123 的 8 参重载 appNotResponding(...)（输入分发由 ActivityManagerService.java :19354 调用，末位 isContinuousAnr=true；:117 的两参版只作内部转调、传 isContinuousAnr=false，供 AMS :7791/:7805 等非输入类 ANR 使用）→ 入队 mAnrRecords（:81）→ startAnrConsumerIfNeeded()（:185）拉起 AnrConsumerThread（:205）→ 消费时写 setNotResponding(true)（:212）并联动窗口侧 → 归档时经 DropBoxManagerService，先判 isTagEnabled（:201/:593），未启用则直接返回（if (!isTagEnabled(tag)) return; :544）。

这里每个箭头都有明确的代码落点，所以「5 秒」不是猜的，是 IInputConstants.aidl :26 的字面值。若日志显示的时间明显大于 5 秒，差额一般来自 dump 与队列等待，也可能是 instrumentation 分支取到了 60 秒，而不是判定阈值本身。

对比 Service 场景：DEFAULT_SERVICE_TIMEOUT 是 20 秒，DEFAULT_SERVICE_BACKGROUND_TIMEOUT 是它的 10 倍。同样一次「主线程卡住」，前台 Service 和后台 Service 的判定时刻差一个数量级——只看调用栈不看种类，很容易误判「为什么这次这么久才报」。

7. 常见问题与误区

7.1 误区

误区一：ANR 的 5 秒是全局统一的。 错。5 秒只对应普通进程的输入分发这一条链路（IInputConstants.aidl :26）。带 instrumentation 或 wrapper 的进程走 ActivityRecord.java :2184 → ActivityTaskManagerService.java :5586/:5593 → WindowProcessController.java :1487，取 INSTRUMENTATION_KEY_DISPATCHING_TIMEOUT_MILLIS（ActivityTaskManagerService.java :345）即 60 秒，且不再由 IInputConstants.aidl 决定。广播前台是 10 秒、后台 60 秒，Service 默认 20 秒、后台放大 10 倍。先看 mReason 再谈时间。

误区二：ANR 处理在调用方线程同步完成。 看起来对，其实是错的。AnrHelper 把记录塞进 mAnrRecords（:81），由 AnrConsumerThread（:205）异步消费。所以日志里 dump 的时间点晚于超时时刻是正常的，这个差值不代表系统卡住。

误区三：tombstone 是崩溃进程自己写的。 错。崩溃进程已被信号挂起，写盘由 crash_dump 完成：先 ptrace(PTRACE_SEIZE, ...)（:112）接管，回溯用 AndroidRemoteUnwinder（:826），再由 tombstone.cpp 落盘——现场编码由 engrave_tombstone_ucontext（:55 定义）完成，主体在 engrave_tombstone（:134 处被调用），proto 版由 tombstone_proto.cpp :902 的 engrave_tombstone_proto 产出。严格说法是「主链路由 crash_dump 代写」，因为存在一条例外：debuggerd_fallback.cpp :342 在崩溃进程自身内（先 tombstoned_connect(getpid(), …)）直接调用 engrave_tombstone_ucontext 落盘，这是 intercept 或不可 fork 场景下的兜底路径。

误区四：Java 侧能看到崩溃就一定读了文件。 错。NativeCrashListener 走的是 DEBUGGERD_SOCKET_PATH（:51）这个 socket，先读 9 字节定长头（:221）。文件与 socket 是两条并行通道。

7.2 高频提问

问：一份 ANR 文件里时间对不上，先怀疑什么？ 答：先怀疑 Build.HW_TIMEOUT_MULTIPLIER。多数超时常量都乘了它，实际阈值可能不是字面值；输入分发另要排除 instrumentation / wrapper 分支。 追问：哪条没乘？ 答：短时前台服务的 DEFAULT_SHORT_FGS_TIMEOUT_DURATION 是 3 * 60_000，字面值即 3 分钟；媒体处理与数据同步两类 FGS 均为 6 * 60 * 60_000。

问：simpleperf 默认采什么？ 答：default_measured_event_type = "cpu-cycles"（:85），帮助文本写明默认 -e cpu-cycles -f 4000 -o perf.data（:158）。 追问：不设时长会怎样？ 答：duration_in_sec_ 初值 0（:363），非零时才设定时器退出（:782–:784）；为 0 表示一直采到你手动停。

问：报告侧默认给完整调用栈吗？ 答：不给。brief_callgraph_ = !options.PullBoolValue("--full-callgraph")（:627），默认是精简栈，要全栈得显式加 --full-callgraph（:575）。
