1. TL;DR

gralloc 负责「缓冲从哪来」。到 gralloc 5，它的映射接口 IMapper 已经不是 HIDL/AIDL，而是 stable C API：经 dlsym 从 mapper.<suffix>.so 里取一张函数表。分配动作由 AIDL 的 IAllocator 承担，GraphicBufferAllocator 是统一入口。三种载体分工明确：ion 在本树已全桩化，dma-buf heap 是当前用户态分配与缓存同步的正路，memfd 提供匿名文件的 fd 语义。读完后你应能判断：一个缓冲该找 IAllocator 还是 IMapper，以及为什么手里还调得动 ion_alloc 却一定拿不到 fd。

3. 问题背景

你在写一个相机或视频后处理链路，需要把一块 YUV 缓冲从 HAL 进程送到另一个进程。第一个问题是：这块内存谁分配、用什么接口分配。第二个问题是：拿到 fd 之后，另一半代码还在调 ion_alloc，编译通过、运行返回 -1，而错误日志里没有任何解释。第三个问题是：升级到新版本后，原来按 HIDL 写的 IMapper 客户端整段编译不过。

这三个问题其实指向同一件事：图形缓冲的「分配契约」在近几个版本被拆成了几层，而且载体从 ion 迁到了 dma-buf heap。下面按「谁来分配、谁来映射、fd 怎么传」三层拆开。

4. 核心机制

4.1 概念与关系

三个角色，别混：

  • `IAllocator`：AIDL 接口，回答「给我分配一块满足这些描述符要求的缓冲」。
  • `IMapper`：stable C API，回答「把这块缓冲映射进我的地址空间」「这块缓冲的布局是什么」。
  • 载体：分配出来的东西在用户态表现为一个 fd，底层可能是 dma-buf heap、memfd 或（历史上）ion。

关键点：分配走 AIDL，映射走 stable C。两条链的加载方式不同，失败形态也不同。

4.2 关键内容

IMapper 为什么是 C API

hardware/interfaces/graphics/mapper/stable-c/README.md 首段直接写明：Starting with gralloc version 5, IMapper is now exposed as a C API instead of through HIDL or AIDL. 这一句是整篇的地基。C API 意味着没有 Binder 事务、没有版本化接口描述，只有一张函数表加一套结构体。

库的落点与后缀

实现库放在 /vendor/lib[64]/hw/mapper.<imapper_suffix>.so。<imapper_suffix> 不是编译期定死的，而是由 VINTF manifest 的 <instance> 指定。同一份 README 给的示例是 <name>mapper</name>、<version>5.0</version>、<instance>minigbm</instance>——于是加载的就是 mapper.minigbm.so。

这是本篇最容易被忽略的契约：换一个 `<instance>` 值，框架加载的就是另一个 so。多套 gralloc 实现共存靠的是 manifest，不是链接期符号。

加载入口

frameworks/native/libs/ui/Gralloc5.cpp 里这条链是：

名称含义出处

这里还有一层版本分叉：loadIMapperLibrary() 在 __builtin_available(android __ANDROID_API_V__) 成立时改走 AServiceManager_openDeclaredPassthroughHal("mapper", mapperSuffix, ...)（Gralloc5.cpp:103-105），只有老分支才拼 android_load_sphal_library("mapper.<suffix>.so")（:107-108）。所以 V 之后加载失败要先去查 servicemanager 的 declared 声明与 service_contexts，而不是查 dlsym。

分配入口

框架侧的单一入口是 GraphicBufferAllocator::allocate(const AllocationRequest&)（GraphicBufferAllocator.cpp:119），内部走 mAllocator->allocate(request)（:140）。旧签名还有一条回落分支在 :149——这意味着同一进程里可能存在两条分配路径，排查时要确认走的是哪条。

IAllocator 本身在 hardware/interfaces/graphics/allocator/aidl/android/hardware/graphics/allocator/IAllocator.aidl:23 声明为 interface IAllocator，文件 :71 的注释明确交代了它与 IMapper stable-C 的分工关系。

dma-buf heap 用户态分配器

system/memory/libdmabufheap/include/BufferAllocator/BufferAllocator.h:33 定义 class BufferAllocator。核心方法：

名称含义出处

配置文件按设备节点组织，键直接写成 /dev/dma_heap/system（configs/example.json）。也就是说 heap 名与设备节点是两套命名，配置里认节点，代码里认常量。

ion 的现状

system/memory/libion/ion.c 在本树已经全桩化：分配类入口 ion_open（:22）、ion_alloc（:28）、ion_alloc_fd（:32）、ion_share（:46）一律 return -1；只有 ion_is_legacy（:62）与 ion_is_using_modular_heaps（:65）这两个语义查询桩返回 0。头文件 system/memory/libion/include/ion/ion.h 仍然导出同名声明（:32 / :42 / :56）。

这是一个典型的「编译通过、运行必失败」形态：符号在，语义没了。任何仍走 ion 的旧代码路径都不会有编译告警，只会在运行期拿到 -1。

4.3 一个具体例子

假设设备 manifest 里写 <instance>minigbm</instance>，那么：

  1. 框架启动后首次映射缓冲，Gralloc5.cpp:92 的 loadIMapperLibrary() 拼出 /vendor/lib64/hw/mapper.minigbm.so。
  2. :128 用 dlsym(so, "AIMapper_loadIMapper") 取符号，:130 调用，得到 IMapper 函数表。
  3. 分配侧走另一条路：GraphicBufferAllocator::allocate（GraphicBufferAllocator.cpp:119）→ mAllocator->allocate(request)（:140）→ IAllocator 的 Binder 调用。
  4. vendor 侧实现用 dma-buf heap 落地：BufferAllocator::Alloc("system", len, flags)（BufferAllocator.h:50），带缓存选 "system"，不需要 CPU 读选 "system-uncached"。
  5. CPU 要读这块缓冲，先 CpuSyncStart（:75），读完 CpuSyncEnd（:85）。
  6. 如果这一路上有人改调 ion_alloc（ion.c:29），得到的是 -1，链路断在分配这一步，而不是映射。

7. 常见问题与误区

7.1 误区

误区一：以为 gralloc 5 的 `IMapper` 还是 AIDL，照旧写 AIDL 客户端。 纠正：IMapper 自 gralloc 5 起是 stable C API（stable-c/README.md 首段）。AIDL 那一侧只剩 IAllocator（IAllocator.aidl:23）。两者不是同一个接口的两个版本，是两件事：一个负责分配，一个负责映射。

误区二：以为 `extract()` 出来的 fd 就是「分配器里那块内存」，只是同一个对象的两个名字。 纠正：这是看起来对、其实需要限定的说法。fd 是传递载体，跨进程传的是 fd 不是指针；持有 fd 的进程要访问，仍然要经 IMapper 做映射并拿到布局描述。把 fd 当成共享内存起始地址，是跨进程图形链路最常见的翻车点。

误区三：以为 `libion` 还能用，因为头文件和符号都在。 纠正：system/memory/libion/ion.c 的 ion_open（:22）、ion_alloc（:28）、ion_alloc_fd（:32）、ion_share（:46）全部 return -1。声明还在（ion.h:32/42/56）只说明源码兼容，不说明语义存在。任何依赖返回值的旧路径都会在运行期断掉。

误区四：以为 heap 名就是设备节点名。 纠正：代码里认的是 "system" 与 "system-uncached" 两个常量（dmabufheap-defs.h:22/23），配置文件里认的是 /dev/dma_heap/system 这样的节点键（configs/example.json）。字符串写错不会编译报错，只会分配失败。

7.2 高频提问

问：我要新加一种 gralloc 实现，框架怎么知道加载哪一个？ 答：由 VINTF manifest 里的 <instance> 决定，框架拼出 /vendor/lib[64]/hw/mapper.<instance>.so 去 dlsym。示例中 <instance>minigbm</instance> 对应 mapper.minigbm.so。 追问：那能不能只改 so 不放 manifest？ 答：不行。后缀来自 manifest 的 <instance>，so 文件名必须与之对齐，否则 loadIMapperLibrary() 拼出来的路径根本不存在。

问：分配一块带 CPU 缓存的缓冲，我该写哪个名字？ 答：kDmabufSystemHeapName[]，值为 "system"（dmabufheap-defs.h:22）。不需要 CPU 读写的场景用 kDmabufSystemUncachedHeapName[]，值为 "system-uncached"。 追问：我选错了会怎样？ 答：不会编译失败。要么多付缓存维护开销，要么在 CPU 访问时撞上一致性问题——所以 CPU 访问前后要配 CpuSyncStart（BufferAllocator.h:75）与 CpuSyncEnd（:85）。

问：为什么 GraphicBufferAllocator 里有一条旧签名回落分支？ 答：GraphicBufferAllocator.cpp:149 的回落分支用于兼容旧调用形态，主路径是 :140 的 mAllocator->allocate(request)。排查分配行为时先确认实际走的是哪条。
