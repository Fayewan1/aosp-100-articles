1. TL;DR

Android.bp 不是给 make 读的，它由 Soong 自己解析。Soong 是一个 Go 程序，其 Android.bp 解析内核来自 blueprint。整条主线的执行者是 soong_ui：它先跑 soong_build 把 Android.bp 翻成 ninja 片段并产出 soong 变量，再跑 kati 把 Android.mk 世界叠加这些变量翻成另一段 ninja 片段，最后把两段合并成一个 build.ninja 交给 ninja 执行。模块类型名（如 cc_binary）不是语法关键字，而是 RegisterModuleType 在运行时注册的字符串。能否走增量分析取决于 config cache：incrementalValid（cmd/soong_build/main.go :201）比对的是配置层——env 哈希、product 变量文件时间戳与 soong_build 二进制时间戳（:213–:215），并不看 .bp 内容；且该路径只在 soong-only 下启用——SetIncrementalEnabled(IncrementalBuildActions && !KatiEnabled) 在 :354 无条件置位（注释在 :353），置位后才在 :356 调用 incrementalValid。真正解析全树 .bp 的是 soong_build 进程自己的那次 bootstrap.RunBlueprint（cmd/soong_build/main.go :271，:284-285 的注释直述 build.ninja 就是它写的）；ui/build/soong.go :416 那次是另一层——它在 bootstrapBlueprint（:289，由 runSoong :603 无条件调用）里，产出的是引导构建 soong_build 自身的 bootstrap.ninja。两层都与 config cache 的判定无关。

3. 问题背景

你在 Android.bp 里加了一个 cc_binary 模块，敲 make，然后看到屏幕上先跑了一段 Make 风格的输出、又跑了一段 Go 程序的日志、最后是 ninja 的进度条。三个引擎接力跑同一件事，谁在读你的 Android.bp？改一个 .cpp 文件重跑，为什么有时几秒结束、有时像是从头扫了一遍全树？build.ninja 到底在哪、里面长什么样？搞不清这些接力点，构建变慢、改了不生效、Android.bp 写错却报了个看不懂的错，就只能盲试。

4. 核心机制

4.1 概念与关系

四个概念：入口（soong_ui，被 soong_ui.bash 拉起）、两个前端（kati 读 Android.mk 世界，soong_build 读 Android.bp 世界）、中间产物（各自的 ninja 片段）、执行器（ninja）。soong_ui 是唯一的编排者，它决定跑谁、按什么顺序、合并成什么。

4.2 关键内容

入口链

soong_ui.bash 只有 44 行，是 shell 到 Go 的薄垫片。build/make/envsetup.sh 里 get_make_command() 在树顶检测到它时，把 make 转成 build/soong/soong_ui.bash --make-mode。所以「make 不再是 Make」，本树里的 make 命令只是历史入口名。

进 Go 后，cmd/soong_ui/main.go 的 main() 在 :130。真正干活的是 ui/build/build.go：SetupOutDir :34 定输出目录，buildUUID :83（调用点 :76）生成本次构建标识，SetupTempDir :96（调用点 :300）备临时目录，checkRAM :204（调用点 :297）做内存门槛检查，createCombinedBuildNinjaFile :118 负责把两个前端的片段合一个。

两个前端与后缀常量

kati 这一路在 ui/build/kati.go（421 行）。产物后缀是一组常量，集中在 :32–:35：

名称含义出处
katiBuildSuffix空串，主构建片段build/soong/ui/build/kati.go :32–:35
-cleanspec 后缀Android.mk 的 clean 规格片段同上
-package 后缀打包阶段片段同上
-soong-only-package 后缀仅 Soong 侧的打包片段同上

同文件里 genKatiSuffix :44、runKati :99、runKatiBuild :239、runKatiPackage :351 把「哪次调用、产物叫什么」串起来。

kati 不是从源码树构建出来的：build/make/kati 本树未收录。实际使用的是预编译二进制 prebuilts/build-tools/linux-x86/bin/ 下的 ckati、rkati、make；选哪个由 runKati（:99）经 config.KatiBin()（config.go :2035–2043）决定——useRkati 在 dumpvars.go :386 置位，release flag RELEASE_USE_RKATI 或环境变量 SOONG_USE_RKATI 任一为真即用 rkati，ABFS 构建再加 -wrap 后缀。build/soong/scripts/run-ckati.sh（91 行）在 :52 直接调用 prebuilts/build-tools/linux-x86/bin/ckati。

soong_build 这一路在 cmd/soong_build/main.go（445 行）。newContext :107 建立 android 包的上下文，needToWriteNinjaHint :115 与 writeNinjaHint :127 处理写 ninja 的提示路径，incrementalValid :201 与 writeConfigCache :246 决定复用或重建 config cache。

模块类型是注册出来的

Android.bp 里写的 cc_binary、java_library 不是语法。cc/binary.go :73 有 ctx.RegisterModuleType("cc_binary", BinaryFactory)，java/java.go :53 有 ctx.RegisterModuleType("java_library", LibraryFactory)。解析器拿到字符串后查注册表找工厂函数，工厂函数再返回模块对象。

图 2：从 bp 字符串到模块对象

Android.bp 文本
   |
blueprint 解析（语法层，只认 property 结构）
   |
模块类型名字符串 "cc_binary"
   |
RegisterModuleType 注册表 -> BinaryFactory
   |
模块对象 + 变体 + mutator 展开

这解释了两件事：写错模块类型名的报错是「不认识的模块类型」而不是语法错误；新增一类模块要动 Go 代码、重新构建 soong_build，在 .bp 里加声明无效。

源文件收集与配置推导

android/paths.go :71 是 func Glob(...)，配合 :81 GlobFiles、:95 GlobFilesOutsideModuleDir，是 .bp 里 srcs: ["*.cpp"] 这类写法的落点。glob 在解析期展开成文件列表，进 ninja 后就是一组确定的输入路径。

defaults 模块的作用是把公共属性抽出来供其他模块继承，合并发生在 mutator 阶段（实现在 android/defaults.go），不是文本预处理。android/module.go :3099 是另一件事：EvaluateConfiguration 里的时序护栏——if !ctx.HasMutatorFinished("defaults") 时直接报 Cannot evaluate configurable property before the defaults mutator has run。

自身形态

build/soong/Android.bp 共 359 行。subdirs 共 9 项（:10–:18）：androidmk、bpfix、cmd/*、fs、finder、jar、zip、third_party/zip、ui/*。:21 的 bootstrap_go_package name 为 soong，:23 的 pkgPath 为 android/soong，deps 为 ["blueprint"]。也就是说 Soong 解析 Android.bp 的能力来自 blueprint 这个 Go 包，Soong 自身也是被这套构建系统构建的 Go 包。

4.3 一个具体例子

从树顶敲 make，走到 ninja 之前的顺序：

  1. envsetup.sh 的 get_make_command() 检测到 build/soong/soong_ui.bash，改道 --make-mode。
  2. soong_ui 的 main()（cmd/soong_ui/main.go :130）起来，先过 preProductConfigSetup :293。需要看配置变量时走 dumpVar :358。这一阶段还有一趟独立的 kati 调用：build.go :344 的 if what&RunProductConfig != 0 门控着 :345 的 runMakeProductConfig，它在产品配置就绪后重跑 kati 取回产品变量——所以 soong 与 kati 之间不是单向消费，产品变量这一路是 kati → soong。
  3. 输出与临时目录就位：只有 SetupOutDir 是从 cmd/soong_ui/main.go :296 调的（preProductConfigSetup 体内，实现在 build.go :34）；SetupTempDir（定义 :96、调用 :300）、checkRAM（定义 :204、调用 :297）与 buildUUID（定义 :83、调用 :76）的调用点都在 build.go 自己里面。
  4. soong_build 先跑（build.go :381 runSoong，实现落在 ui/build/soong.go）：incrementalValid :201 先判断 config cache 能不能用——它比对的是配置层三项（env 哈希、product 变量文件时间戳、soong_build 二进制时间戳，:213–:215），不含 `.bp` 内容；而增量路径的开关在 :354 就已按 IncrementalBuildActions && !KatiEnabled 无条件置位（注释在 :353），置位通过才在 :356 调 incrementalValid 比对配置层三项。真正解析全树 .bp 的是 soong_build 进程内的 bootstrap.RunBlueprint（cmd/soong_build/main.go :271），它不受这个判定影响（soong.go :289 的 bootstrapBlueprint 才是引导层，其 :416 产出 bootstrap.ninja；它在 runSoong（定义 :588）的 :603 处被调用）；判定不通过则重解析并 writeConfigCache :246 落盘。产出 out/soong/build.ninja 与供 kati 消费的 soong 变量/mk。
  5. kati 随后（build.go :385–:387 三个调用）：runKatiCleanSpec、runKatiBuild :239（build 阶段）、runKatiPackage :351（package 阶段）依次执行，把 Android.mk 世界叠加第 4 步产出的 soong 变量翻成 ninja 片段。runKati :99 用 genKatiSuffix :44 生成的产物名，二进制经 config.KatiBin()（config.go :2035–2043）选取——默认 ckati，RELEASE_USE_RKATI 或 SOONG_USE_RKATI 为真时 rkati。
  6. createCombinedBuildNinjaFile :118 把两段合成一个 build.ninja。
  7. runNinjaForBuild :40 调到 runNinja :47 执行。卡住时 ninjaStucknessChecker 的 check :434 出手诊断。

第 4 步的分水岭在于 soong_build 是否被 ninja 判定为需要重跑——需要重跑就由 soong_build 走 cmd/soong_build/main.go :271 的 RunBlueprint 重扫全树；config cache 只在 soong-only 且增量分析置位时参与，常规 make 不进这条路径。另需注意第 4、5 步并非无条件依次接力：build.go :380 与 :384 分别以 what&RunSoong、what&RunKati 位掩码门控，:389 另有 else if what&RunKatiNinja 分支——它只读回上次的 kati suffix，不重跑 kati。上面描述的是机制路径；实际耗时与产物内容未在本树构建验证。

7. 常见问题与误区

7.1 误区

误区一：`Android.bp` 是 Make 的一种方言，所以 `make` 直接读它。 错。Android.bp 由 blueprint 解析，blueprint 是 Go 包（bootstrap_go_package 的 deps 明确写着 ["blueprint"]）。make 命令只是入口名，实际已被 soong_ui.bash 接管。

误区二：`cc_binary` 是语法关键字，解析器认得。 错。它只是 RegisterModuleType("cc_binary", BinaryFactory) 注册进表里的字符串。同一个名字在没注册它的上下文里就是非法模块类型。

误区三：改了 `.bp` 里的注释或空白，重建应该秒过。 看起来对，其实是错的——但错因常被说反。incrementalValid（cmd/soong_build/main.go :201）比对的不是 .bp 的内容，而是配置层三项：env 哈希、product 变量文件时间戳、soong_build 二进制时间戳（:213–:215）。改 `.bp` 本身不会让这个缓存失效，它失效只因配置层变了。而且这个判定只在增量路径被打开后才发生：:354 先按 IncrementalBuildActions && !KatiEnabled 置位（注释在 :353），:356 才调它——带 kati 的常规构建根本不走这条路。真正解析全树 .bp 的是 soong_build 进程内的 bootstrap.RunBlueprint（cmd/soong_build/main.go :271），不是引导层的 soong.go :416。

误区四：kati 是本树源码构建出来的，所以本树可以改 kati 行为。 错。build/make/kati 本树未收录，实际二进制在 prebuilts/build-tools/linux-x86/bin/ 下。

7.2 高频提问

问：build.ninja 是怎么来的，只有一个吗？ 答：由 createCombinedBuildNinjaFile（ui/build/build.go :118）合并两个前端片段而来：一个是 kati 给的，一个是 soong_build 给的。产物位置由 SetupOutDir :34 定。是否还有别的辅助 ninja 文件，本篇不断言。 追问：那两个前端怎么保证产物名对得上？ 答：靠约定而非共享结构。kati 侧用 genKatiSuffix（kati.go :44）生成产物名，常量在 :32–:35；soong_build 侧要产出同名规则的模块。对不上时表现为 ninja 报「无规则可生成该文件」，不是 .bp 语法错误。

问：Android.mk 和 Android.bp 混着的树，谁先跑？ 答：soong_build 先、kati 后。编排在 build.go：:381 先 runSoong，:385–:387 才依次 runKatiCleanSpec/runKatiBuild/runKatiPackage。两者都是 soong_ui 的子步骤，不是两个并行进程互相等待。 追问：那为什么报错时 Make 风格与 Go 风格的输出交替出现？ 答：因为两个前端各自往标准输出写。它反映的是步骤边界，不是同一引擎的两种日志格式。
