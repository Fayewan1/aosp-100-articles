1. TL;DR

Sensors HAL 2.x 之后，事件不再靠 poll() 拉取，而是 HAL 单向写入 Event Fast Message Queue（FMQ），再用 EventFlag 把读端叫醒。另一条 Wake Lock FMQ 方向相反：框架把已处理的唤醒事件数写进去，HAL 读。hardware/interfaces/sensors/ 下 1.0、2.0、2.1 三个 HIDL 目录与 aidl 目录并存，AIDL 侧 ISensors 里根本没有 poll()。框架侧由 AidlSensorHalWrapper 与 HidlSensorHalWrapper 两条实现撑起统一接口 ISensorHalWrapper.h，SensorDevice 只认包装层。Context Hub 是另一组接口（IContextHub），它解决的是「低功耗协处理器上的感知」，与传感器事件搬运不是同一条队列。判断一件事能不能通过 HAL 做到，先看它落在 Event FMQ 这条单向契约里，还是落在 sendMessageToHub 这条消息通道里。

3. 问题背景

你在写一个计步或抬腕唤醒类的功能，采样率很低，要求熄屏也不断。翻 AOSP 时发现传感器服务里没有「读一次」这种调用：HAL 不给你数据，是 HAL 把数据塞进一个队列，再拍一下你的门。继续翻，hardware/interfaces/sensors/ 底下同时躺着 1.0、2.0、2.1 和 aidl 四个目录，不知道设备上到底走哪条。再往低功耗方向找，又冒出 IContextHub 和 system/chre/，看起来也是「传感器」，但接口完全不一样。三个问题叠在一起：事件谁在搬、版本怎么选、协处理器算不算传感器 HAL。

4. 核心机制

4.1 概念与关系

四个概念：接口版本目录（HIDL 的 1.0/2.0/2.1 与 aidl，是同一能力的多份契约）、HAL 包装层（ISensorHalWrapper.h 下的两套实现，把版本差异吸收掉）、Event FMQ（事件唯一出口，HAL 只写不读）、Context Hub（独立接口面，管的是 hub 上的消息与 app，不管 Event FMQ）。

图 1：事件从 HAL 到 SensorService 的搬运路径

  HAL 进程                     SensorService
  ----------                   --------------
  Event FMQ  --写-->  [队列]  --读-->  mEventQueue
       |                                    ^
       +-- EventFlag 唤醒 -----------------+

这四者的关系是：版本目录决定「用哪份接口」，包装层决定「代码里怎么写一份」，Event FMQ 决定「数据怎么流动」，Context Hub 是并列的另一条线，不进这张图。

4.2 关键内容

AIDL 接口面。interface ISensors（ISensors.aidl:27）只暴露少量方法：activate(sensorHandle, enabled)（:41）、getSensorsList()（:110）、initialize(MQDescriptor<Event>, MQDescriptor<int>, ISensorsCallback)（:193-195）。没有 poll()。这一点是 HIDL 1.0 与之后版本的分水岭：老的 poll() 是拉模型，新的是推模型。

两条队列，方向相反。initialize 的两个 MQDescriptor 参数分别对应 Event FMQ 与 Wake Lock FMQ（ISensors.aidl:113-153）。Event FMQ 是 HAL 写、框架读，装传感器事件；Wake Lock FMQ 反过来，框架把「已处理的 WAKE_UP 事件数」写进去、HAL 读出来，据此判断唤醒锁能不能释放（:138-149）。两者共同点是没有请求-应答语义，不同点是数据流方向。

写侧纪律。HAL 只能写 Event FMQ、不能读；写完调 EventFlag 唤醒读端（ISensors.aidl:119-128）。这条单向约束决定了 HAL 不可能「等框架来取」，也决定了背压只能在队列满时表现为丢事件，而不是阻塞 HAL。

读侧实现。框架侧持有 mEventQueue（AidlSensorHalWrapper.cpp:131），用 EventFlag::createEventFlag（:143）建标志，initialize(dupeDesc, dupeDesc, callback)（:153）把描述符交进去，循环里靠 availableToRead()（:174）判断有没有新事件。

包装层双轨。AidlSensorHalWrapper.cpp 与 HidlSensorHalWrapper.cpp 并存，统一接口在 ISensorHalWrapper.h（均在 frameworks/native/services/sensorservice/）。上层调用点只认 ISensorHalWrapper，因此一台设备走 AIDL 还是 HIDL，对上层的形状是一样的。

图 2：版本差异在三层被吸收

hardware/interfaces/sensors/   1.0 / 2.0 / 2.1 / aidl
              |
      ISensorHalWrapper.h（统一接口）
         |                    |
HidlSensorHalWrapper   AidlSensorHalWrapper
         \                  /
            SensorDevice（只认包装层）

列表初始化。SensorDevice::initializeSensorList（SensorDevice.cpp:82）先调 mHalWrapper->getSensorsList()（:87）。逐项 activate(handle, 0)（:135）确实存在，但被条件门住：只有 if (!mHalWrapper->supportsMessageQueues()) 成立才走（:132-136 的注释写明「HAL 1.0 才需要逐个关断，2.0 在 initialize 里自己处理」）。AIDL 侧 supportsMessageQueues() 返回真，这一步跳过；2.x 与 AIDL 的清理由 initialize 契约承担（ISensors.aidl:166-178：调用 initialize 时所有已激活请求与直连通道必须关闭并清理）。

Context Hub 侧。interface IContextHub（IContextHub.aidl:34）的关键方法是 sendMessageToHub(contextHubId, message)（:179）与 getHubs()（:265）；目录同样 1.0/1.1/1.2 ＋ aidl 并存。运行时实现树在 system/chre/（api_parser、apps、chpp 等子目录）。

4.3 一个具体例子

以抬腕唤醒为例，走一遍 AIDL 路径。SensorDevice 构造时先 connectHalService()（SensorDevice.cpp:73），AidlSensorHalWrapper::connect() 里依次建 mEventQueue（AidlSensorHalWrapper.cpp:131）、EventFlag::createEventFlag（:143）、调 mSensors->initialize(mEventQueue->dupeDesc(), mWakeLockQueue->dupeDesc(), mCallback)（:153），把两条队列与回调交下去。这一步在取清单之前——先有队列，才有地方收事件。构造完成后才调 initializeSensorList()（SensorDevice.cpp:77），里面取 getSensorsList()（:87）；因为 supportsMessageQueues() 为真（AidlSensorHalWrapper.cpp:101），逐项 activate(handle, 0) 被跳过。

HAL 侧从此按 ISensors.aidl:119-131 的约定干活：有事件就写 Event FMQ，写完拍 EventFlag。框架侧在循环里判 availableToRead()（AidlSensorHalWrapper.cpp:174），有数据就读出来分发；处理完再把「已处理的 WAKE_UP 数」写进 Wake Lock FMQ（writeWakeLockHandled，:347-350）。应用真正打开抬腕唤醒时，走的是 activate(sensorHandle, enabled)（ISensors.aidl:41），enabled 置 1。整条路上没有一次 poll()。

如果这个唤醒判断要在 hub 上做，那是另一条路：走 sendMessageToHub(contextHubId, message)（IContextHub.aidl:179），消息进 hub，system/chre/ 里的运行时负责在协处理器上跑逻辑。能力边界不同，不是同一个队列的两种用法。

4.4 与相邻篇的关系

本篇只讲事件搬运的契约：接口面、两条队列、写侧纪律、包装层。传感器融合算法与功耗策略归 P10，本篇不碰。器件驱动归 P5，Event FMQ 上游怎么采到数据不在本篇范围。这类「多版本目录并存 + 包装层吸收差异」的通用形态，P4-101 已经讲过，本篇是它在传感器域的具体样本。P4-402 提供小 HAL 的另一组样本，可作对照。

7. 常见问题与误区

7.1 误区

误区一：Sensors HAL 2.x 是「更快的 poll」。 不是。AIDL 的 ISensors 里没有 poll()，事件全部走 Event FMQ ＋ 回调（ISensors.aidl:113-128）。这不是同一模型调参，是换模型。

误区二：`initialize` 的两个 `MQDescriptor` 一个是请求、一个是应答。 不是。它们分别对应 Event FMQ 与 Wake Lock FMQ，方向相反：Event FMQ 是 HAL 写、框架读；Wake Lock FMQ 是框架写、HAL 读（ISensors.aidl:138-149）。两条都没有请求-应答语义，但也不是同向的两条。

误区三：HAL 写完队列可以顺便读一下做自检。 看起来合理，实际违反契约。约定是 HAL 只能写 Event FMQ、不能读，写完调 EventFlag 唤醒读端（ISensors.aidl:119-128）。读端只有一个。

误区四：Context Hub 就是低功耗版传感器 HAL。 不是同一层。IContextHub 的接口面是 sendMessageToHub 与 getHubs，处理的是 hub 上的消息与 app；传感器事件走 Event FMQ，两条路互不替代。

7.2 高频提问

问：一台设备上四个版本目录都在，实际用哪个？ 答：由设备侧声明的接口版本决定，运行时选定后由包装层落到 AidlSensorHalWrapper 或 HidlSensorHalWrapper 之一。目录并存本身不代表同时启用。 追问：那写代码时要两套都写吗？ 答：不需要。上层对着 ISensorHalWrapper.h 写，版本差异在包装层内部消化。

问：初始化时为什么要对每个传感器 activate(handle, 0)？ 答：那句话只对 HAL 1.0 成立。SensorDevice::initializeSensorList（SensorDevice.cpp:82）在取完 getSensorsList()（:87）之后确实有这个循环，但它在 if (!mHalWrapper->supportsMessageQueues()) 里（:132-136），只有拉模型路径才执行；2.x 与 AIDL 的清理由 initialize 的契约负责。 追问：那 AIDL 路径下谁来保证没有残留使能状态？ 答：HAL 自己。ISensors.aidl:166-178 规定 initialize 被调用时，所有已激活请求与直连通道都必须关闭并清理，这是交付队列描述符的附带义务。
