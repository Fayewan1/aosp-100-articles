1. TL;DR

开机耗时不是一个数字，而是一串被分散埋在三个进程域里的时间戳：init 侧属性、Zygote 侧 logtag 与 trace、SystemServer 侧 trace 与 logtag。要把「慢在哪一段」问清楚，第一步不是优化，而是确认这几处埋点各自的写法与采集口径。

init 阶段留下 ro.boottime.init 系列属性：RecordStageBoottimes 内最多四个（一个时刻＋三个时长），函数外另有 cold_boot_wait，mount_all 内建还会写三个 mount_all.* 时长——粒度都到阶段级；Zygote 的 preload 区间靠 LOG_BOOT_PROGRESS_PRELOAD_START/END 与 Zygote64Timing trace tag 双通道记录；SystemServer 的区间由 TimingsTraceAndSlog 统一承担，tag 固定为 SystemServerTiming。

跨进程的对齐基准来自 boot_progress_* 事件族，ID 分布在 3000–3100 区间：3000 的 boot_progress_start 由主 zygote 自身启动时写（AndroidRuntime.cpp:1252-1253，位置在 AndroidRuntime::start 入口的 options 循环内，早于 startVm 完成与 forkSystemServer），3011 的 system_server_start 与三个 sys.system_server.start_* 属性同源、属双通道，最后以 sys.boot_completed 与 dev.bootcomplete 收尾。单应用首帧则用 am start -W 读 WaitResult，不在开机时间线内。

3. 问题背景

有人报「开机慢了两秒」，你打开日志，看到 boot_progress_enable_screen 比基线晚了 2 秒，但 boot_progress_system_run 只晚了 0.1 秒。剩下 1.9 秒落在哪个区间？如果不知道 SystemServer 侧每个 phase 由 TimingsTraceAndSlog 自动打点，就只能靠猜。

另一类困惑是口径问题：同一台机器，logcat -b events 算出的一段耗时与 dumpsys 或 trace 里读出的对不上。原因常是两个埋点覆盖的区间本就不同——比如 boot_progress 是事件时刻，而 ro.boottime.init.selinux 是一段区间长度。

本篇只解决这两件事：埋点在哪、口径怎么对。怎么把时间压下去，不在这里。

4. 核心机制

4.1 概念与关系

四个概念构成开机时间线的坐标系。

  • 阶段属性：init 把某段耗时写成 ro.boottime.* 属性，开机后只读，粒度是阶段。
  • 进程内区间：进程内部用 trace tag 划分区间。Zygote 在非 lazy-preload 模式下用 Zygote64Timing/Zygote32Timing（带 --enable-lazy-preload 的 zygote_secondary 另起 ZygoteInitTiming_lazy），SystemServer 的主线程用 SystemServerTiming，异步操作另有 SystemServerTimingAsync（TimingsTraceAndSlog.java:37 定义，:50-53 由 newAsyncLog() 生产）。
  • 全局事件：boot_progress_* 事件（ID 3000–3100 段）是跨进程的共同基准，仅记录「时刻」，不记录时长。
  • 完成标志：sys.boot_completed 与 dev.bootcomplete 标记时间线终点。

四者的关系是：事件给「什么时候」，trace 与属性给「花了多久」。两者不能互相替代，只能互相校验。

4.2 关键内容

同类符号必须成组看，否则容易把「时刻」当成「时长」。

这些属性的口径要分开记：ro.boottime.init 是时刻（setenv(kEnvFirstStageStartedAt, ...) 带下来的那一下，写点 :908）；.first_stage（:922-923）是 selinux_start_time_ns − first_stage_start_time_ns，.selinux（:924-926）是 second_stage_start − selinux_start，两者都是纳秒；.modules 与 mount_all.* 是毫秒。把它们混成一类、或跨量纲相减，是「事件差值对不上属性值」最常见的根因。还有一条容易忽略的守卫：init.cpp:919-920 在两个环境变量任一缺失（值为 -1）时直接 return，此时 .first_stage/.selinux/.modules 三个属性根本不会写出，只有 :908 的时刻已落。

Zygote 走双通道。LOG_BOOT_PROGRESS_PRELOAD_START = 3020 与 LOG_BOOT_PROGRESS_PRELOAD_END = 3030（ZygoteInit.java:100/:101），写点在 :890/:893；trace tag 为 Zygote64Timing/Zygote32Timing（:845）——这个 tag 只属于非 lazy-preload 路径，zygote_secondary 带 --enable-lazy-preload 时（init.zygote64_32.rc:3）换成 ZygoteInitTiming_lazy（:182），且 :890/:893 两个事件不写。事件告诉你 preload 区间在整条线上的位置，trace 告诉你区间内各步骤怎么分。

SystemServer 侧由 TimingsTraceAndSlog 统一承担，但 tag 不止一个。该文件 108 行，主 tag SYSTEM_SERVER_TIMING_TAG = "SystemServerTiming" 定义在 :32，异步 tag SYSTEM_SERVER_TIMING_ASYNC_TAG（值即 SystemServerTimingAsync）定义在 :37，由 newAsyncLog()（:50-53）生产；实例在 frameworks/base/services/java/com/android/server/SystemServer.java:859 用 new TimingsTraceAndSlog() 创建，此后每个 traceBegin/traceEnd 都自动落 trace，同时把 phase 耗时汇进日志。

重启计数另有一套属性：sys.system_server.start_count/.start_elapsed/.start_uptime（frameworks/base/services/java/com/android/server/SystemServer.java:548-550，写入点 :868-870）。这三个值在系统反复重启时是判断「是不是每次都重来一遍」的直接证据。同一份数据还走了事件通道：EventLog.writeEvent(EventLogTags.SYSTEM_SERVER_START, mStartCount, mRuntimeStartUptime, mRuntimeStartElapsedTime) 在 :872-873，对应 logtags 里的 3011 system_server_start——属性与事件是双通道，别只认一边。

Zygote 还会把起点上报给统计：FrameworkStatsLog.write(BOOT_TIME_EVENT_ELAPSED_TIME_REPORTED, BOOT_TIME_EVENT_ELAPSED_TIME__EVENT__ZYGOTE_INIT_START, startTime)（ZygoteInit.java:872-874）。这条通道的数据不出现在 logcat，别在设备日志里找。

4.3 一个具体例子

假设基线机与问题机的 events buffer 对齐后读到：

  • boot_progress_system_run（3010）差值 +0.1 秒
  • boot_progress_pms_ready（3100）差值 +0.4 秒
  • boot_progress_enable_screen（3050）差值 +2.0 秒

3010–3100 段与 3050–3100 段都无法解释剩下的 1.5 秒。此时切到 SystemServerTiming trace：按 phase 名排序取各自 traceEnd - traceBegin，逐项与基线比对，差值集中在哪个 phase 就很清楚。要注意别只看主 tag——newAsyncLog() 打的段落在 SystemServerTimingAsync 下，主要出现在 SystemServerInitThreadPool（:116）、SensorService（:74）、UserController（:4723）与 SystemServer 自身的若干并行初始化点（:1595/:1775/:1782）。只过滤主 tag 会把并行初始化那部分耗时整个漏掉，与 AND-P8-401 的三阶段编排衔接时正好落在盲区。

若怀疑 preload 段，则取 Zygote64Timing trace 看 3020–3030 区间内部，而不是看这两个事件本身的差值——它们只界定时长，不切分内容。

若怀疑 init 段，先确认属性存在（init.cpp:919-920 的守卫会让三个时长属性在环境变量缺失时根本不写），再读 ro.boottime.init.first_stage/.selinux/.modules 三个时长属性与基线相减——但必须先统一量纲：前两个是纳秒、.modules 是毫秒，跨量纲相减得到的数没有意义；mount_all.* 三个同为毫秒，可互相比。ro.boottime.init 本身是时刻，只能用于对齐起点，不能当时长相减。

7. 常见问题与误区

7.1 误区

**误区一：ro.boottime.init* 属性都是时长。** 错。ro.boottime.init 是时刻（第一阶段起始，相对内核启动的偏移，init.cpp:908），不是「首阶段总时长」；同族另外三个才是时长（:922/:924/:928）。拿它去和 boot_progress_system_run 做减法，得到的数没有意义——两个口径相差一个起点。

误区二：所有 `boot_progress` 标签都在一个文件里。 听起来合理，实际错在三个文件各占一份。3000 与 3020/3030 的标签名声明在 system/logging/logcat/event.logtags（:64/:66/:68），3010 与 3060–3100 在 server/EventLogTags.logtags，3040 与 3050 在 am/EventLogTags.logtags。只 grep frameworks/base 会漏掉 preload 那一对，只 grep 一个模块目录会漏掉一半。

误区三：events buffer 里的时间是绝对时刻。 它是设备开机以来的相对时刻，跨设备或跨重启比对必须先对齐起点，否则差值全来自起算点不同。还有一层更容易踩：这一族事件不是同一时钟源，共三种口径。3000 来自 native 侧 LOG_EVENT_LONG(LOG_BOOT_PROGRESS_START, ns2ms(systemTime(SYSTEM_TIME_MONOTONIC)))（AndroidRuntime.cpp:1252-1253），取的是内核 CLOCK_MONOTONIC；3010/3011 取 SystemClock.elapsedRealtime()（SystemServer.java:908，变量名虽叫 uptimeMillis），含深睡；3020/3030 取 SystemClock.uptimeMillis()（ZygoteInit.java:890-891/893-894），不含深睡。跨这三个点直接相减，差值里混着时钟口径差。

7.2 高频提问

问：Zygote64Timing 和 3020/3030 事件是什么关系？ 答：事件只标记 preload 起止两端的时刻，trace 把这两个时刻之间的内容切细。查区间位置用事件，查区间内部怎么分用 trace。 追问：带 --enable-lazy-preload 时这两个事件还在吗？ 答：不在。ZygoteInit.java:888 的 if (!enableLazyPreload) 把 :889-895 整段包住，3020/3030 的写点就在这段里；该参数由 :859 置真，本树 init.zygote64_32.rc:3 对 zygote_secondary 就是带参启动（init.rc:1095 会 start zygote_secondary）。这种配置下预加载被推到首次 fork 之前，trace tag 也换成 ZygoteInitTiming_lazy（ZygoteInit.java:182），要看这一段耗时只能抓 trace，事件里没有。

问：system_server_start（3011）和那三个 sys.system_server.start_* 属性是什么关系？ 答：同一份数据的两个通道。属性写点 SystemServer.java:868-870，事件写点 :872-873，事件参数与属性一一对应；要总量看属性，要时刻对齐看事件。

问：sys.system_server.start_count 为什么比 boot_progress_system_run 更适合判断反复重启？ 答：事件在每次进程启动时都会打一次，但只看单条事件看不出总量；start_count 是累计值，start_elapsed/start_uptime 提供同一次启动的两个基准，三者一起才能判断是否每次都在重来。
