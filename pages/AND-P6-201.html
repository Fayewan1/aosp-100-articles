1. TL;DR

SurfaceFlinger 是一个以 vsync 为节拍的循环进程：run() 把主循环交给 SurfaceFlinger::commit()，后者按 pacesetter 显示屏的帧目标判断这一帧是否触发 HWC 背压，再决定这次是走合成、走 GPU 合成回退还是「等下一个 vsync」。丢帧计数（didMissFrame()）只进 mTimeStats 统计，不参与这个控制流。vsync 不是硬件直接送到应用的，而是由 Scheduler 创建的 EventThread 按 VSyncPredictor 外推的时间点分发。合成路径最终落到 HWComposer，由它把层组合成 getDeviceCompositionChanges 请求的 HWC 接口形态；驱动能不能接、接多少层，决定这一帧是 GPU 合成还是硬件合成。抖动的根因通常不在合成代码本身，而在 pacesetter 帧目标、vsync 预测周期与刷新率切换三者对不齐。

3. 问题背景

一个动画在 120Hz 屏上偶尔卡一帧，dumpsys SurfaceFlinger 里却看不出谁慢。另一种现象：滑动列表时帧率忽高忽低，帧间隔呈锯齿状，而应用侧 Choreographer 回调时间看起来是均匀的。再一种：接上外接屏后，主屏的动画节奏跟着变了。

这三种现象指向同一个地方：SurfaceFlinger 进程内的帧节拍编排。它决定「这一帧什么时候被允许开始合成」「按哪个屏的 vsync 排队」「合成不成时是等还是丢」。本篇只讲 SurfaceFlinger 进程内的调度与合成编排，不展开队列内部实现，也不讲应用侧帧调度。

4. 核心机制

4.1 概念与关系

四个角色：pacesetter 显示屏给出帧目标；Scheduler 管理 vsync 周期与 EventThread；EventThread 把 vsync 分发给应用与 SurfaceFlinger 自己；HWComposer 把这次合成提交给显示硬件。它们围绕同一个时间轴对齐。

图 1：SurfaceFlinger 内 vsync 与合成的角色关系

  [ pacesetter 显示屏 ]
          |
          v
  [ Scheduler ] --> [ EventThread("app") ] --> 应用侧
      |                    |
      |                    v
      +-------------> [ SurfaceFlinger 主循环 commit() ]
                           |
                           v
                     [ HWComposer ] --> 显示硬件

Scheduler 持有 VSyncSchedule，EventThread 用它外推下一个 vsync 时刻。commit() 向 Scheduler 要 pacesetter 的帧目标，比对是否已经丢帧，再进入合成。合成结果经 HWComposer 提交。

4.2 关键内容

主循环的形状。 进程入口 main_surfaceflinger.cpp:71 调用 ProcessState::self()->setThreadPoolMaxThreadCount(4)，把 Binder 线程池显式设为 4；这对 SurfaceFlinger 有意义，因为 SurfaceComposerClient 的事务、createSurface、setDisplayPowerMode 等调用都要落到这个池里。SurfaceFlinger::run() 在 :626，init() 在 :938。主循环本身不含复杂逻辑，真正的编排在 commit()。

commit 的两段结构。 SurfaceFlinger::commit(PhysicalDisplayId pacesetterId, ...) 在 :2996。入口处 :2998 即 const scheduler::FrameTarget* pacesetterFrameTargetPtr = frameTargets.get(pacesetterId)->get()——从传入的 frameTargets 取节拍主屏的帧目标指针，此后贯穿使用；:3143 与 :3186 的 pacesetterFrameTargetPtr = mScheduler->pacesetterFrameTarget() 是两次防御性重取：前者在 updateLayerSnapshots（:3138-3140）之后，源码注释明示「A display transaction for hotplug reconnect may have just destroyed the original.」；后者在分辨率切换块之后（:3184-3187），注释为「A resolution change without refresh required may have just destroyed the original.」。三级判定都发生在入口取指之后、两次重取之前，用的都是 :2998 的入口指针：:3014 的 didMissFrame() 只把结果交给 mTimeStats->incrementMissedFrames()（:3015），是丢帧计数，不是控制门；:3026-3030 显示屏已移除时 return false 并 scheduleFrame()；:3036-3043 有 mode set 未完成时同样提前返回。真正的合成跳过门在 :3059-3066：pacesetterFrameTargetPtr->wouldBackpressureHwc() 为真，且（mBackpressureGpuComposition 或 pacesetterFrameTargetPtr->didMissHwcFrame()）时，:3064 scheduleCommit(FrameHint::kNone, slack) 后 return false。三个查询方法的语义差异见 FrameTargeter.h:64-66：wouldBackpressureHwc 是 mWouldBackpressureHwc（控制流门），didMissFrame 是 mFrameMissed（仅供统计），didMissHwcFrame 是 mHwcFrameMissed && !mGpuFrameMissed（驱动错帧门）。合成函数是 CompositeResultsPerDisplay SurfaceFlinger::composite(...)，在 :3330。于是「这一帧要不要做、做完算不算迟到」在进入合成之前就已经有结论。

Scheduler 的职责边界。 Scheduler.cpp 构造函数在 :59；Scheduler::createEventThread 在 :583，内部 :585-586 执行 std::make_unique<android::impl::EventThread>("app", getVsyncSchedule(), tokenManager, ...)——注意名字字面量是 "app"，即面向应用的连接线程由 Scheduler 创建。setVsyncConfig 在 :802，dispatchHotplug 在 :612。热插拔走的是 dispatchHotplug，不是简单的「重新读一遍显示列表」。

4.3 一个具体例子

假设主屏是 pacesetter。某个 120Hz 周期内，应用在 EventThreadConnection::requestNextVsync（EventThread.cpp:264）登记了需求。VSyncPredictor::nextAnticipatedVSyncTimeFrom（VSyncPredictor.cpp:380）按当前周期外推出下一个时刻，EventThread::onVsync（:472）在预测时刻触发。

应用完成一帧后提交缓冲区。SurfaceFlinger 主循环走到 SurfaceFlinger::commit(PhysicalDisplayId pacesetterId, ...)（SurfaceFlinger.cpp:2996），入口处 :2998 即从 frameTargets 取到 pacesetterFrameTargetPtr（frameTargets.get(pacesetterId)->get()）。下面三条路径的判定都使用这个入口指针——:3143 与 :3186 的 mScheduler->pacesetterFrameTarget() 是 updateLayerSnapshots 与分辨率切换之后的防御性重取，只影响其后的 VsyncTracker 回填与 trace，不参与下面的判定。

  • 正常路径：没有提前返回条件时继续到 composite(...)（:3330），由 HWComposer::getDeviceCompositionChanges（HWComposer.cpp:537）决定合成路径并提交。
  • 背压路径：入口指针的 :3059 wouldBackpressureHwc() 为真且 :3060（mBackpressureGpuComposition 或 didMissHwcFrame()）成立时，:3064 scheduleCommit(FrameHint::kNone, slack) 并 return false，这一帧不做合成，等下一个 vsync。
  • 丢帧计数：入口指针的 :3014 didMissFrame() 与上述两条路径都无关，只在 :3015 累加 mTimeStats 的 missed frames 统计。

如果此时 RefreshRateSelector（构造函数 :1422）刚好切了刷新率，或者 dispatchHotplug（:612）刚处理完一次热插拔，预测器的外推基线会变，下一次 requestNextVsync 到 onVsync 的间隔就与用户感知的动画周期不一致——这就是「帧间隔锯齿」的一种来源。

7. 常见问题与误区

7.1 误区

误区一：vsync 是硬件中断一到就立刻分发。 不是。分发时刻来自 VSyncPredictor::nextAnticipatedVSyncTimeFrom（VSyncPredictor.cpp:380）的外推，硬件上报只用于校正。预测基线在刷新率切换或热插拔后需要重新收敛。

误区二：只要应用在 Choreographer 里按时画完，就不会丢帧。 看起来对，其实错。SurfaceFlinger 侧的丢帧诊断来自 mTimeStats：commit() 在 SurfaceFlinger.cpp:3014 用 pacesetterFrameTargetPtr->didMissFrame() 判断，为真时在 :3015 累加 missed frames。应用画完但提交晚于 pacesetter 帧目标，仍然算错过。但要注意区分：这个查询只影响统计，决定这一帧走不走合成的是另一组门——:3059 的 wouldBackpressureHwc() 与 :3060 的 didMissHwcFrame()（语义见 FrameTargeter.h:64-66）。

误区三：`Scheduler` 只负责给应用发 vsync。 Scheduler::createEventThread（Scheduler.cpp:583）创建的是名为 "app" 的线程；Scheduler 同时通过 setVsyncConfig（:802）管周期，SurfaceFlinger 自己的合成节拍与这个周期同源。

误区四：composer 的实现形态是编译期固定的。 Composer::create（ComposerHal.cpp:26）按服务名在 AIDL 与 HIDL 两套实现间选择，运行期决定。

7.2 高频提问

问：setThreadPoolMaxThreadCount(4) 只有 4 个线程，事务多了会不会排队？ 答：它设的是 Binder 线程池上限，不是合成线程数；合成编排跑在 SurfaceFlinger 主循环与 Scheduler 的线程上。事务处理与合成不是同一批线程。 追问：那 commit() 阻塞会影响客户端调用吗？ 答：会改变时序。客户端调 SurfaceComposerClient 的接口最终落到 SurfaceFlinger 处理，主循环忙时这些调用得不到及时响应，表现为客户端侧的一次等待。

问：didMissFrame() 返回真之后，这一帧就扔掉了吗？ 答：不会。它只是帧目标对象上的状态查询（FrameTargeter.h:65，即 mFrameMissed），返回真时 commit() 只在 SurfaceFlinger.cpp:3015 累加一次 mTimeStats 的 missed frames 统计，既不扔内容也不改控制流。决定这一帧走不走合成的是另一组门：:3059 的 wouldBackpressureHwc() 与 :3060 的 didMissHwcFrame()。 追问：那我该看哪个数判断抖动？ 答：先看 pacesetter 是哪个显示屏，再看它的帧目标周期是否被 RefreshRateSelector 改过。周期在跳，帧间隔当然呈锯齿。
