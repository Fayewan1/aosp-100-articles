1. TL;DR

进程被杀的「凶手」在 Linux 4.12 之后不再是一个内核驱动。内核 lowmemorykiller 驱动已被移除，改由用户态守护进程低内存杀手守护进程（LMKD，二进制名 lmkd）承担监控与杀进程。lmkd 把 PSI 三档监视器挂在 epoll 上等唤醒——但叫醒之后杀不杀，判据是内存水位、swap 余量与抖动程度的组合，PSI 档位本身只在设备严重停顿（CRITICAL）时直接导出一档原因；挑牺牲者则按系统服务下发的 oomadj 值。你能观测的入口只有三条：/proc 面的取数路径、lmkd 的 seqpacket 控制套接字、以及内核模块兜底路径是否被启用。驱动内部实现不在本篇核验范围。

3. 问题背景

线上收到一条「后台应用被杀」的反馈，日志里没有任何 OOM 字样，dmesg 也干净。开发者去看 /proc/meminfo，空闲内存还剩不少，于是判断「不是内存问题」。这个判断在 4.12 之后就不成立了：杀进程的决定发生在用户态——PSI 事件负责把 lmkd 叫醒，水位与 swap 余量才决定它是否真的动手。要定位到底是谁杀的，必须知道 lmkd 读哪几个文件、按什么阈值、由谁告诉它该杀哪个进程。

4. 核心机制

4.1 概念与关系

四个概念串起整条链。触发面是 PSI 三档监视器——lmkd 把它挂在 epoll 上等唤醒；测量面是 /proc/zoneinfo、/proc/meminfo、/proc/vmstat 与 /proc/pressure/memory；决策面是 lmkd 内的水位档位表加上 swap 与抖动判据；输入面是系统服务通过控制套接字发来的进程优先级；输出面是 lmkd 直接对进程发信号。

触发面与决策面是两件事，最容易混：PSI 只回答「什么时候来看一眼」，杀不杀由后面的判据决定。mp_event_common()（lmkd.cpp:2795 起）被 PSI 事件唤走后，先取 wmark、swap_is_low、thrashing 三个量，再沿一条 if-else 链定 kill_reason：杀完一轮仍越 min 水位走 PRESSURE_AFTER_KILL（分支 :3025，赋值 :3032）；CRITICAL 档叠加 wmark <= WMARK_HIGH 走 NOT_RESPONDING（:3035，赋值 :3041）；低 swap 加抖动走 LOW_SWAP_AND_THRASHING（:3044）；swap 与水位双低走 LOW_MEM_AND_SWAP（:3055）；最后才是兜底的水位分支 LOW_MEM（:3119，赋值 :3120）。整条链里 PSI 档位只出现在前两个分支，其余分支看的是水位与 swap。

LMK_PROCPRIO 的包体是 struct lmk_procprio，字段为 pid、uid、oomadj、enum proc_type ptype、bool for_lmkd_only。enum proc_type 取 PROC_TYPE_APP 或 PROC_TYPE_SERVICE，两端夹 PROC_TYPE_FIRST 与 PROC_TYPE_COUNT。批量命令 LMK_PROCS_PRIO 受 MAX_PROCS_PRIO_RECORD_COUNT 3 约束，单条记录 LMK_PROCPRIO_FIELD_COUNT 5 个字段。

包体上限。CTRL_PACKET_MAX_SIZE 取 MAX_LMK_TARGET_SIZE 与 MAX_CTRL_PACKET_SIZE 的较大者；档位表本身受 MAX_TARGETS 6 限制，最多六档。这个 6 就是水位表能配出的最大档数，超出只能合并。

取数路径。lmkd 从三个 /proc 文件采集内存状态，常量定义在 lmkd.cpp：ZONEINFO_PATH "/proc/zoneinfo"（:75）、MEMINFO_PATH "/proc/meminfo"（:76）、VMSTAT_PATH "/proc/vmstat"（:77）。进程级字段名为 PROC_STATUS_TGID_FIELD "Tgid:"（:78）、PROC_STATUS_RSS_FIELD "VmRSS:"（:79）、PROC_STATUS_ANON_RSS_FIELD "RssAnon:"（:80）、PROC_STATUS_SWAP_FIELD "VmSwap:"（:81），另有 NODE_STATS_MARKER " per-node stats"（:82）用于切分 zone 段落。

PSI 档位。psi_thresholds[VMPRESS_LEVEL_COUNT]（:231-235）只有三行：{PSI_SOME, 70}、{PSI_SOME, 100}、{PSI_FULL, 70}，依次对应 enum vmpressure_level（:166-171）的 LOW／MEDIUM／CRITICAL。时间窗口默认 DEFAULT_PSI_WINDOW_SIZE_MS 1000（:122）；采样周期分快慢两档 PSI_POLL_PERIOD_SHORT_MS 10（:124）与 PSI_POLL_PERIOD_LONG_MS 100（:126）；失败上报限流 FAIL_REPORT_RLIMIT_MS 1000（:128）。

杀与不杀之间的默认值。DEF_LOW_SWAP 10（:134）定义低 swap 可用阈值。抖动（thrashing）三档为 DEF_THRASHING_LOWRAM 30（:136）、DEF_THRASHING 100（:137）、DEF_THRASHING_CRITICAL 300（:139）。停顿（stall）三档为 DEF_PARTIAL_STALL_LOWRAM 200（:144）、DEF_PARTIAL_STALL 70（:145）、DEF_COMPLETE_STALL 700（:147）。DEF_DIRECT_RECL_THRESH_MS 0（:149）、DEF_SWAP_COMP_RATIO 1（:151）分别是直接回收阈值与 swap 压缩比。最低可杀分界 DEF_LOWMEM_MIN_SCORE (PREVIOUS_APP_ADJ + 1)（:155）算出来是 701，对应属性 ro.lmk.lowmem_min_oom_score（README:107，默认值注释为「Default = 701 (all cached apps excluding the last active one)」）。

ADJ 空间。OOM_SCORE_ADJ_MIN (-1000)（:299）到 OOM_SCORE_ADJ_MAX 1000（:300），共 2001 个槽，即 ADJTOSLOT_COUNT（:552）＝ 2001。档位用到的锚点是 PERCEPTIBLE_APP_ADJ 200（:84）、PREVIOUS_APP_ADJ 700（:85）、SYSTEM_ADJ (-900)（:103）。SYSTEM_ADJ 在源码里的用途是识别 system_server：is_system_server = (oom_adj_score == SYSTEM_ADJ && ...)（:1199），随后决定 memcg soft_limit 的写入方式（:1201）。源码里并没有一条「排除 SYSTEM_ADJ 档」的显式候选过滤规则——该档事实上永远不可杀，是因为任何一档可杀分界阈值（最低的也是 201）都远高于 -900，数值上就被排除了。

内核模块兜底。lmkd 仍保留内核 lowmemorykiller 模块的兼容路径：INKERNEL_MINFREE_PATH "/sys/module/lowmemorykiller/parameters/minfree"（:91）与 INKERNEL_ADJ_PATH "/sys/module/lowmemorykiller/parameters/adj"（:92）。use_inkernel_interface 初值为 true（:162）。README §Background 写明了历史：Historically on Android systems memory monitoring and killing of non-essential processes was handled by a kernel lowmemorykiller driver. Since Linux Kernel 4.12 the lowmemorykiller driver has been removed and instead userspace lmkd daemon performs these tasks. 兜底路径存在，不等于它会被打开；上述 INKERNEL_*_PATH 指向的 sysfs 节点在无该模块的内核上根本不存在。

启动与重配。lmkd.rc:1 起定义服务；配置变更由属性触发：on property:lmkd.reinit=1 执行 exec_background /system/bin/lmkd --reinit，on property:sys.boot_completed=1 追加 --boot_completed，另一族 persist.device_config.lmkd_native.* 属性同样会触发 reinit。

4.3 一个具体例子

假设某进程的 oomadj 上报为 700。它等于 PREVIOUS_APP_ADJ 700（:85），低于 DEF_LOWMEM_MIN_SCORE（:155）算出的 701，所以在默认策略下它不在候选里。这里要把一件事说准：701 是全档共用的一个单值，不是逐档递进的线。属性 ro.lmk.lowmem_min_oom_score 默认 701（README:107），读进 static int lowmem_min_oom_score（:230），只在兜底的水位分支被消费——if (kill_reason == NONE && wmark < WMARK_HIGH && lowmem_min_oom_score <= OOM_SCORE_ADJ_MAX)（:3119），紧接着 min_score_adj = lowmem_min_oom_score（:3123）。LOW、MEDIUM、CRITICAL 三档走的是同一条判据链，用的是同一个 701；档位高低改变的是沿链落到哪个 kill_reason，而不是换一条分界线。

真正随档位变的是另两处。一是 NOT_RESPONDING 分支要求 level == VMPRESS_LEVEL_CRITICAL 且 wmark <= WMARK_HIGH（:3035），此时设备已处于完全停顿，critical_stall 会把 min_score_adj 压到 0（:3144-3146），连可感知应用都纳入候选；二是 LOW_SWAP_AND_THRASHING 分支把 min_score_adj 设为 PERCEPTIBLE_APP_ADJ + 1 即 201（:3051），但附加条件是 wmark > WMARK_MIN && thrashing < thrashing_critical_pct（:3050）——水位还没破 min 且抖动没到临界时才保护可感知应用。

逐档分界（ro.lmk.low／medium／critical，默认 1001／800／0，README:37-47）属于另一套策略：只有 ro.lmk.use_minfree_levels 打开后才生效（属性读取在 lmkd.cpp:4112-4113，分流在 :3372 与 :3383，用 level_oomadj[level] 取逐档值）。该开关默认 false，本篇按默认的新策略叙述。若这个进程是 PROC_TYPE_SERVICE，它的优先级语义与 PROC_TYPE_APP 不同，仍走同一条 2001 槽映射。整个判定只用 2001 个槽位索引，不需要遍历全表。

7. 常见问题与误区

7.1 误区

误区一：空闲内存还剩很多就不可能被杀。 错。叫醒 lmkd 的是 PSI 压力，不是 /proc/meminfo 的剩余量——可回收页多但回收慢时，压力可以很高而剩余量看起来正常。但要把另一层说清：被叫醒之后杀不杀，判据仍是水位（wmark）、swap 余量与抖动，PSI 档位只在 CRITICAL 且 wmark <= WMARK_HIGH 时直接导出一档（NOT_RESPONDING）。把「PSI 就是决策依据」当成结论，会漏掉真正那条全档共用的 701 分界，也会漏掉 ro.lmk.use_minfree_levels 打开后才会生效的逐档 1001／800／0。

误区二：`dmesg` 干净就说明不是内存问题。 错。杀进程发生在用户态，lmkd 直接发信号，不必然在内核日志留痕。要看 LMK_GETKILLCNT 与 LMK_STAT_KILL_OCCURRED 这条统计线。

误区三（看起来对其实是错的）：lmkd 现在的内核里仍有 lowmemorykiller 驱动在兜底。 错。README §Background 明确写了该驱动自 Linux 4.12 起被移除。lmkd.cpp 里的 INKERNEL_MINFREE_PATH 等常量只是历史兼容代码路径，use_inkernel_interface 初值 true 是变量初始化，不代表运行时会用到；目标内核上这些 sysfs 节点并不存在。

误区四：lmkd 自己算 oomadj。 错。lmkd 只接收 LMK_PROCPRIO／LMK_PROCS_PRIO 上报的数值，计算方在系统服务侧。

7.2 高频提问

问：为什么阈值表只有三档？答：psi_thresholds（:231-235）就是三行，对应 LOW／MEDIUM／CRITICAL 三个压力等级。水位表 MAX_TARGETS 6 是另一回事，那是 LMK_TARGET 下发的内存档位数。追问：那两个「档」数会不会互相限制？答：不会，一个约束 PSI 分级，一个约束水位表长度，各自独立。

问：为什么 DEF_LOWMEM_MIN_SCORE 要写成表达式而不是字面量？答：它是 PREVIOUS_APP_ADJ + 1（:155），即 701。这样 ADJ 锚点调整时自动跟随，避免两处硬编码不一致。

问：LMK_PROCS_PRIO 为什么限制 3 条记录？答：MAX_PROCS_PRIO_RECORD_COUNT 3 限制了单包批量发送的条数，包体总上限由 CTRL_PACKET_MAX_SIZE 兜住。

8. 边界与延伸

本篇不覆盖：Binder 内核驱动侧内存语义（AND-P5-201）；内核内存回收子系统本体（本卷对应篇）；oomadj 计算（P2／P9 进程管理篇）；进程被杀后的重建调度（ActivityManagerService 侧篇）。

本篇前置依赖：AND-P5-G01。

本篇后继：本卷讲内核内存回收子系统的篇，以及讲进程生命周期调度的篇。

数量级与边界值：

  • ADJ 槽位共 2001 个，由 OOM_SCORE_ADJ_MIN (-1000) 与 OOM_SCORE_ADJ_MAX 1000 推出，ADJTOSLOT_COUNT（:552）直接给出，来源：源码常量。
  • 水位表最多 6 档（MAX_TARGETS 6），来源：源码常量。
  • 批量优先级单包最多 3 条记录（MAX_PROCS_PRIO_RECORD_COUNT 3），来源：源码常量。
  • 低内存可杀分界 701（DEF_LOWMEM_MIN_SCORE，:155），来源：源码常量。
  • PSI 窗口 1000 ms、快慢采样 10/100 ms、失败限流 1000 ms，来源：源码常量。真实设备上的实际命中分布暂无实测，列为待补。
