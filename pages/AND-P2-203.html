1. TL;DR

system_server 把上百个系统服务分成三批拉起：startBootstrapServices、startCoreServices、startOtherServices，顺序本身就是依赖声明。安装链的核心在 PackageManagerService，实际安装动作落在 InstallPackageHelper.installPackagesTraced。输入链的 Java→native 对接发生在 InputManagerService 构造期（mNative 字段初始化，InputManagerService.java:569 → JNI cpp:657），start() 只负责随后启动 native 事件循环，窗口管理器的构造又反过来依赖输入管理器实例。三条线共同解释一件事：服务怎么起、怎么注册、怎么被 Binder 找到。

3. 问题背景

给系统加一个自定义服务，最常遇到的困惑是：代码写完了，ServiceManager.addService 也调了，可 getSystemService 拿到的还是 null。查日志又只看到一串服务名，看不出谁先谁后。另一头，改安装逻辑的开发者会发现：真正干活的不是 PackageManagerService 本体，而是一个 InstallPackageHelper，入口方法名里还带着 Traced。这两类困惑指向同一件事：系统服务不是平铺的，它有一张隐式的启动编排表。

4. 核心机制

4.1 概念与关系

三个概念串起本篇：

  • 系统服务（system service）：活在 system_server 进程里的单例对象，由 SystemServiceManager 按阶段拉起。
  • Binder 注册点：服务构造后经 ServiceManager.addService 把自身 Binder 挂到内核驱动，供其他进程按名字查找。
  • 阶段（boot phase）：服务之间用「阶段」表达先后依赖，比如 WMS 必须等到传感器服务就绪。

三者关系：编排决定构造顺序 → 构造完注册 Binder → 后启动的服务可通过阶段感知前者的存在。

4.2 关键内容

SystemServer 的三段式启动是全篇骨架。Bootstrap 段先起 AMS 与 PMS：ActivityManagerService.Lifecycle.startService 负责前者，PackageManagerService.main 负责后者——注意这里 main 是静态入口，真正的构造与方法定义在 PackageManagerService.java。

Other 段的次序更值得记：InputManagerService 先起，随后才是 WindowManagerService.main(...)。WMS 的构造实参里直接传入了 inputManager，所以输入管理器必须先于窗口管理器存在；在起 WMS 之前还有一次 startBootPhase(t, SystemService.PHASE_WAIT_FOR_SENSOR_SERVICE)，注释写明 WMS needs sensor service ready。

服务注册以 WMS 为例：

ServiceManager.addService(Context.WINDOW_SERVICE, wm,
    allowIsolated=false,
    DUMP_FLAG_PRIORITY_CRITICAL | DUMP_FLAG_PRIORITY_HIGH | DUMP_FLAG_PROTO);

（长代码块，建议到公众号/头条侧按截图策略处理）

addService 的四个实参（名字常量、Binder 对象、allowIsolated 布尔、一组 dump 优先级标志）中，后两类集中在一处，走的是同一套常量族：

名称含义出处
DUMP_FLAG_PRIORITY_CRITICAL最高 dump 优先级SystemServer.java 注册调用
DUMP_FLAG_PRIORITY_HIGH高 dump 优先级同上
DUMP_FLAG_PROTO输出 protobuf 格式 dump同上
allowIsolated=false不允许隔离进程访问同上

安装链的入口同样集中：InstallPackageHelper 承担真正的安装流程，installPackagesTraced(List<InstallRequest> requests, MoveInfo moveInfo) 是包内方法（无 public 修饰，调用方限于同包的 PackageManagerService，InstallPackageHelper.java:1081）。权限授予侧由 DefaultPermissionGrantPolicy 承担默认授权，运行期校验路径不属本篇。

输入链：先辨清三个名字——输入管理器（InputManager，glossary 标准名，指事件分发语义）由 Java 服务类 InputManagerService 承载，其 native 侧类型是 NativeInputManagerService（字段名 mNative）。Java 与 native 的构造对接发生在 InputManagerService 构造期：mNative 字段初始化（InputManagerService.java:569）经 JNI 落到 NativeInputManager 构造（com_android_server_input_InputManagerService.cpp:657），在那里 new InputManager(...)（位于 frameworks/native/services/inputflinger/InputManager.cpp）并 addService("inputflinger") 注册。start()（646 行）里的 mNative.start()（648 行）只是随后启动 native 事件循环，不是构造对接点——这个先后常被读反。

4.3 一个具体例子

想象一次开机：startBootstrapServices 在 1192 行进入，先走 AMS 的 Lifecycle.startService（1294），再走 PackageManagerService.main（1375）。到了 startOtherServices：1739–1741 行起 InputManagerService，并通过 .getService() 拿回实例；1754–1755 行推进到 PHASE_WAIT_FOR_SENSOR_SERVICE；1756 行调用 WindowManagerService.main(...)，把前面拿到的 inputManager 当实参传进去；1758–1760 行把 wm 注册进 ServiceManager。整个过程没有「服务列表注册中心」，顺序即约定。

7. 常见问题与误区

7.1 误区

  • 误区一：以为 SystemServer 里有一个服务清单表，加服务只需往表里登记。纠正：顺序是写死在三个 start*Services 方法里的语句，没有声明式的服务清单，先后关系靠代码位置与阶段表达。
  • 误区二：以为 PackageManagerService.main 就是安装逻辑的入口。纠正：main 是静态启动入口，方法定义在 1714 行；实际安装落在 InstallPackageHelper.installPackagesTraced。
  • 误区三（看起来对其实是错的）：以为 WMS 可以先于输入服务起，只要构造时传个占位对象即可。纠正：WindowManagerService.main 的实参就是前一步拿到的 inputManager，输入服务必须先完成启动。
  • 误区四：以为注册进 ServiceManager 就等于立刻可被所有进程访问。纠正：注册调用还带 allowIsolated、dump 优先级等参数，隔离进程的访问是被显式排除的。

7.2 高频提问

问：为什么 WMS 要等传感器服务就绪？ 答：startBootPhase(t, SystemService.PHASE_WAIT_FOR_SENSOR_SERVICE) 处的注释直接写了 WMS needs sensor service ready，说明窗口管理器的初始化依赖传感器数据通路。 追问：那输入服务和传感器是一个东西吗？ 答：不是。输入服务由 InputManagerService 承担，传感器服务是另一个阶段所等待的对象，两者在编排里是先后相邻但不同的节点。

问：两个服务都要注册，会不会互相覆盖？ 答：注册用的是 Context 里的名字常量，如 Context.WINDOW_SERVICE，重名会冲突，所以每个服务用各自的常量。 追问：怎么确认某个名字确实挂上了？ 答：静态核验时按 addService 实参配合 grep 定位；运行时用 adb shell dumpsys activity services 对照。
