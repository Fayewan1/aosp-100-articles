1. TL;DR

ART 的 Java 堆不是一整块，而是由若干空间（space）拼起来的；小对象住在按 kRegionSize = 256 * KB 切分的区域空间里，超过 12KB 的对象直接进大对象空间。堆的空闲水位上下限默认是 32MB 与 8MB，水位也是触发 GC 的主要依据之一。collector 的默认类型由编译期决定：本树 ART_DEFAULT_GC_TYPE 默认为 CMC（并发标记压缩，art/build/art.go:50），CMS/SS 等是可配置备选；启用读屏障走 CC（并发拷贝），启用 userfaultfd 走 CMC。移动式回收靠锁字（lock word）里的转发地址把旧对象指向新位置，应用线程通过读屏障（read barrier）在访问引用时顺便把自己引用的对象也「跟着搬」到新副本，所以上层看到的对象引用始终有效。

3. 问题背景

线上看到一个进程的 Java 堆只有 20MB 上下，GC 日志却一直在打，于是有人怀疑「堆没满为什么还回收」。另一个常见困惑是：在 MAT 里抓到的对象地址，和上一次抓的对不上，但应用里的引用明明没改过——对象到底被搬走没有？

这两个问题指向同一块知识：堆被切成什么形状、空闲水位怎么算、回收器在什么时候被选中、对象移动后引用又靠什么保持有效。不了解这些，看 logcat 里的 GC 行只能猜。

4. 核心机制

4.1 概念与关系

四个概念先立住：空间（space）是堆的物理分区；区域（region）是区域空间内部的分配粒度；collector 是被选中的回收算法实现；锁字（lock word）是每个对象头里的一段复用字段，转发时借它存新地址。

关系上：collector 负责决定哪些空间被扫、哪些对象被搬；搬家时把新地址写进锁字；应用线程（mutator）不主动查表，而是在每次读引用时由读屏障（read barrier）兜底修正。

4.2 关键内容

堆的空闲水位。 堆默认最大空闲 kDefaultMaxFree = 32 * MB，最小空闲 kDefaultMinFree = kDefaultMaxFree / 4，也就是 8MB。这两个值不是堆上限，而是「GC 之后希望剩下多少空闲」的目标区间；堆增长策略与 GC 触发判断都围绕这条区间展开。

区域粒度。 区域空间把映射区按固定粒度切开：kRegionSize = 256 * KB，区域数量 num_regions_ = mem_map_.Size() / kRegionSize。所以一个 4MB 的映射区就是 16 个区域。这个粒度决定了回收时「按区域腾挪」的最小单位。

大对象直通。 超过阈值的对象不进区域空间，直接进大对象空间。下限常量 kMinLargeObjectThreshold = 12 * KB，默认阈值 kDefaultLargeObjectThreshold = kMinLargeObjectThreshold，即默认 12KB。运行期可以通过 LargeObjectThreshold 选项调整。大对象空间有两种实现：kFreeList 与 kMap。

collector 选择。 枚举 art/runtime/gc/collector_type.h 里列了 kCollectorTypeMS、CMS、CMC、CMCBackground、SS、CC、CCBackground、HomogeneousSpaceCompact 等。默认 collector 由编译期常量 kCollectorTypeDefault 决定（collector_type.h:71-84，随 ART_DEFAULT_GC_TYPE 宏切换，本树为 CMC），运行期选项可以改选。heap.cc 构造流程里的两个分支（userfaultfd→CMC/CMCBackground，读屏障→CC/CCBackground）不是选型逻辑本身，而是对选型结果的一致性校验（CHECK_EQ，heap.cc:452-469）：先打一行日志 Using <generational> <foreground> GC.，再断言前台/后台类型与当前配置匹配；非 zygote 且是命令行运行的情况会关闭后台压缩（:478-484）。

对象移动的转发。 并发拷贝 collector 持有一个区域空间成员 region_space_，并对 to-space 维持不变式断言。对象被搬走后，旧副本的锁字被改写成转发状态：LockWord::kForwardingAddress 表示该锁字当前存的不是锁信息而是转发地址，LockWord::FromForwardingAddress 用来取出它，kForwardingAddressShift = kObjectAlignmentShift 说明地址是按对象对齐位数编码的。判断一个对象是否已被搬走，就看 old_lock_word.GetState() == LockWord::kForwardingAddress。

读屏障。 应用线程拿到一个引用时，ReadBarrier::Barrier 先查对象的读屏障状态：是灰对象才进慢路径 Mark(ref)（read_barrier-inl.h:51-63），Mark 内部再经锁字判断是否已转发（GetState() == LockWord::kForwardingAddress，concurrent_copying.cc:3458），是则取新副本地址；ReadBarrier::BarrierForRoot 负责根集里引用的同样处理。这是「移动式 GC 对上层透明」的全部秘密——引用值本身没变，变的是解引用路径。

堆大小相关的属性。 dalvik.vm.heapgrowthlimit、dalvik.vm.heapmaxfree、dalvik.vm.heapminfree、dalvik.vm.heapstartsize 这几个属性由 art/runtime/metrics/statsd.cc 读取（:498-502），用于把当前堆配置带进指标上报；它们本身不是调水位或堆增长行为的入口。

4.3 一个具体例子

假设进程的 region space 映射了 4MB。按 num_regions_ = mem_map_.Size() / kRegionSize，即 4MB / 256KB = 16 个区域。

一次 GC 后，堆里剩余空闲 8MB 以上、32MB 以下，落在 kDefaultMinFree 到 kDefaultMaxFree 的带子里，堆暂不扩张。此时应用分配一个 16KB 的数组：它超过 kDefaultLargeObjectThreshold（12KB），不走区域空间，直接进大对象空间，落在 kFreeList 或 kMap 实现之一上。随后应用分配一个 4KB 的小对象：走区域空间，占用 16 个区域中某一个区域的一段。

如果这轮选中的是 CC，小对象可能在下一轮被搬到 to-space。搬完之后，栈上那个引用还是老地址值，但读屏障一读，命中 LockWord::kForwardingAddress，取到新副本。应用代码零感知。

7. 常见问题与误区

7.1 误区

误区一：堆没满就不会 GC。 错。触发判断看的是空闲水位与分配速率，不是「堆用光」。一次 GC 后空闲量还没跌到 kDefaultMinFree 附近，也可能因为别的原因触发。

误区二：GC 后对象地址变了一定是应用出了问题。 错。移动式 collector 本来就会搬对象，搬到哪是它的事。应用看到的引用一直是有效的，因为读屏障在解引用时修正。

误区三（看起来对其实是错的）：引用值在对象移动后会同步改写成新地址。 不会。栈上和寄存器里的引用值保持原样，旧副本的锁字被写成转发地址。读屏障走一跳才拿到新副本。正因为如此，才不需要全量扫描并改写所有引用位置。

误区四：大对象和小对象走同一套回收逻辑。 不完全。超过 kDefaultLargeObjectThreshold 的对象进大对象空间，实现是 kFreeList 或 kMap，与区域空间的区域腾挪不是一回事。

7.2 高频提问

问：怎么确认当前进程用的是哪个 collector？ 答：看启动日志里 Using <generational> <foreground> GC. 那一行，它把代际与前台回收器都打出来了。 追问：那后台回收器呢？ 答：日志行只给前台；后台是从启用 userfaultfd 或读屏障的分支推出来的，分别是 CMCBackground 与 CCBackground。

问：把 dalvik.vm.heapmaxfree 调大能减少 GC 吗？ 答：这个属性和 dalvik.vm.heapminfree 一起影响 GC 后的目标空闲区间，从而影响堆增长与下一次触发的时机，但不保证「调大就不 GC」。 追问：那 dalvik.vm.heapstartsize 呢？ 答：它决定初始堆规模，影响的是早期分配要不要立刻扩张，属于起点而非上限。
