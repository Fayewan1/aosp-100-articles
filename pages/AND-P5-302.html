1. TL;DR

触摸和按键在内核侧统一成一种东西：/dev/input/event* 上按 8 字节时间戳加三个定长字段排列的事件流。用户态不「问」设备状态，而是 read 事件、用 EVIOCG* 系列 ioctl 查能力和常量、用 EVIOCS* 系列改配置。多点触控不是多个设备，而是同一设备上以 ABS_MT_SLOT 切换槽位、ABS_MT_TRACKING_ID 标记触点生死的协议。按键码不是内核规定的，内核只给 scancode，映射由 input_keymap_entry 描述、由上层查表翻译。一次手势的边界由 SYN_REPORT 划出：同一帧里槽位状态写全再报同步，上层才看到一个完整快照。

3. 问题背景

调试一次点击延迟，抓出 /dev/input/eventX 的原始字节，发现里面有一堆 type/code/value 三元组，却分不清哪几个属于同一根手指、哪几个属于同一个时间点。另一头，键盘上一个键按下去，KEY_HOME 这类常量在头文件里明明白白，可换个键盘型号行为就变了。这两个困惑指向同一件事：evdev 的 uapi 面到底约定了什么，哪些是内核给的、哪些是上层自己算的。

4. 核心机制

4.1 概念与关系

四个概念。事件是唯一的数据载体，定长、成流。能力查询告诉用户态这台设备会发哪些 type、哪些 code、绝对轴的取值范围。配置写入改变设备行为（重复率、时钟源、按键映射、独占）。多点触控协议是 EV_ABS 上的一组 ABS_MT_* 约定，把「多根手指」编码进单条事件流。

图 1：从设备到用户态的四个面

     /dev/input/eventN
            |
   +--------+--------+--------+
   |        |        |        |
 事件流   能力查询  配置写入  抓取/撤销
 read()  EVIOCG*  EVIOCS*  EVIOCGRAB
   |        |        |     EVIOCREVOKE
   +--------+--------+--------+
            |
      EventHub（epoll + inotify）

事件流和 ioctl 走的是同一个 fd，差别只在系统调用入口。EVIOCGRAB 与 EVIOCREVOKE 是互斥的一对：前者让本 fd 独占设备，后者让原持有者立刻失效。

4.2 关键内容

事件载体是 struct input_event（bionic/libc/kernel/uapi/linux/input.h:14）：time（timeval，32 位 time64 场景走 __sec/__usec 兼容分支）加 __u16 type、__u16 code、__s32 value。协议版本是 EV_VERSION 0x010001（同文件 :34），用户态拿它和内核比对，不匹配通常意味着头文件与内核不同代。

设备身份用 struct input_id（:35），四个字段 bustype／vendor／product／version。绝对轴参数用 struct input_absinfo（:41），六个字段 value／minimum／maximum／fuzz／flat／resolution——注意 fuzz 和 flat 不是精度描述，是给上层做去抖和判定阈值的参数。

按键映射用 struct input_keymap_entry（:49）：flags／len／index／keycode／scancode[32]，配合 INPUT_KEYMAP_BY_INDEX (1 << 0)（:50）决定是按索引还是按 scancode 查。事件过滤用 struct input_mask（:57）：type／codes_size／codes_ptr。

ioctl 面共 28 个宏，集中在 :62-:89。名字前缀已经把语义写死，G 读、S 写、REVOKE 撤销：

多点触控的 15 个常量全在 input-event-codes.h：ABS_MT_SLOT 0x2f（:730）、ABS_MT_TOUCH_MAJOR 0x30（:731）、ABS_MT_TOUCH_MINOR 0x31（:732）、ABS_MT_WIDTH_MAJOR 0x32（:733）、ABS_MT_WIDTH_MINOR 0x33（:734）、ABS_MT_ORIENTATION 0x34（:735）、ABS_MT_POSITION_X 0x35（:736）、ABS_MT_POSITION_Y 0x36（:737）、ABS_MT_TOOL_TYPE 0x37（:738）、ABS_MT_BLOB_ID 0x38（:739）、ABS_MT_TRACKING_ID 0x39（:740）、ABS_MT_PRESSURE 0x3a（:741）、ABS_MT_DISTANCE 0x3b（:742）、ABS_MT_TOOL_X 0x3c（:743）、ABS_MT_TOOL_Y 0x3d（:744）。协议的核心是两件事：用 ABS_MT_SLOT 声明「接下来写哪个槽」，用 ABS_MT_TRACKING_ID 的取值区分「新触点」（赋新 id）、「触点更新」（同一 id）、「触点抬起」（值 -1）。整个触点生命周期只靠这一个字段表达，位置字段随槽位写出。

常用键码：BTN_TOUCH 0x14a（:353）表示接触面按下，KEY_HOME 102（:140）、KEY_BACK 158（:199）、KEY_BACKSPACE 14（:53）、KEY_HOMEPAGE 172（:213）。注意 KEY_HOME 与 KEY_HOMEPAGE 是两个不同码，前者是传统 Home，后者是浏览器首页语义，映射到同一个行为是上层策略。

4.3 一个具体例子

以 EventHub 打开并挂载输入设备为例。它把设备目录写死为 DEVICE_INPUT_PATH = "/dev/input"（EventHub.cpp:84），父目录 DEVICE_PATH = "/dev"（:86）。epoll 实例来自 mEpollFd = epoll_create1(EPOLL_CLOEXEC)（:1020），目录监听来自 mINotifyFd = inotify_init1(IN_CLOEXEC)（:1023），注册 inotify_add_watch(mINotifyFd, DEVICE_INPUT_PATH, IN_DELETE | IN_CREATE)（:1087）。三个 fd 各司其职：inotify 管设备插拔，epoll 管已打开设备的可读，设备 fd 本身由 inotify 事件触发后打开。

设备一打开，能力查询立刻按 type 铺开：EVIOCGBIT（:881）拿能力位图，EVIOCGABS（:675）拿轴参数，EVIOCGKEY（:656）、EVIOCGSW（:659）、EVIOCGLED（:944）拿当前键／开关／LED 状态。多指槽位走 EVIOCGMTSLOTS（:917、:1294），按键重复走 EVIOCSREP（:633），时钟源走 EVIOCSCLOCKID（:648）。这套调用顺序说明上层不猜测设备形态，全部靠 ioctl 现查。

唤醒锁有个容易漏的点。EventHub.cpp:2190-2191 的注释点明：驱动释放内核唤醒锁之后，epoll 仍会持有唤醒锁，因为用了 EPOLLWAKEUP；唤醒锁由 epoll 在 epoll_wait（:2202）返回后释放。也就是说「设备没数据了但系统还不睡」在这个窗口内是预期行为，不是唤醒锁泄漏。驱动实现不在本树核验范围，这条结论以用户态可观测现象与注释口径为准。

4.4 与相邻篇的关系

本篇只到 evdev 的 uapi 与多点触控协议。事件进入 EventHub 之后的读取、去抖、槽位跟踪在 InputReader.cpp，策略判定（按键该不该拦、手势该不该给某个窗口）归 P2 的输入分发链路。显示侧一帧的节拍由 AND-P5-401 的 vsync 负责，和输入时间戳是两条独立时钟——比对两者要用 EVIOCSCLOCKID 选定的时钟源，本篇不展开合成逻辑。内核侧如何把驱动事件推到 /dev/input、调度与中断上下文的行为，属于 P5 卷其他内核篇的范围。

7. 常见问题与误区

7.1 误区

误区一：`/dev/input/eventX` 里每个触点是一条独立事件流。 纠正：只有一条流。多指靠 ABS_MT_SLOT 选槽、ABS_MT_TRACKING_ID 标记身份，所有手指的事件交错在同一个 fd 里，靠 SYN_REPORT 切帧。

误区二：收到 `EV_ABS` 的 `ABS_MT_POSITION_X` 就等于有一根手指按下。 纠正：位置字段只表示槽位当前坐标，没有 ABS_MT_TRACKING_ID 赋新值，这个槽位不算新触点。反过来 TRACKING_ID 置 -1 才是抬起，位置最后值不代表手指还在。

误区三：按键码是内核按物理键位固定分配的。 纠正：内核发的是 scancode，映射由 input_keymap_entry 描述、由上层查表翻译。同一个 KEY_HOME 与 KEY_HOMEPAGE 落到同一行为，是上层策略的结果。

误区四：`EVIOCGRAB` 之后原持有者只是收不到事件。 纠正：配合 EVIOCREVOKE 时原 fd 会失效。这是「看起来对其实是错的」那条：抓取不是静音，是转移访问权。

7.2 高频提问

问：为什么读到的 input_event 里 time 字段布局和我预期不一样？ 答：32 位 time64 场景走 __sec/__usec 兼容分支，结构体不是简单的 timeval 展开。跨架构移植时按宏分支读，别硬解偏移。 追问：那时间戳的时钟源怎么确定？ 答：由 EVIOCSCLOCKID 设定，EventHub 在 :648 就调它。不同时钟源下与其他子系统的时间戳不能直接相减。

问：epoll 明明没有新事件，为什么系统迟迟不睡？ 答：驱动释放唤醒锁后 epoll 仍持有唤醒锁（用了 EPOLLWAKEUP），要等 epoll_wait 返回才释放。见 EventHub.cpp:2190-2191 的注释与 :2202 的调用。 追问：这是缺陷吗？ 答：是设计上的窗口，不是泄漏。驱动实现不在本树核验范围，判断泄漏要看这段时间是否无限延长。

8. 边界与延伸

  • 本篇不覆盖：输入事件到窗口的分发与策略（P2 输入分发篇）；vsync 与帧节拍（AND-P5-401）；内核驱动内部实现与中断处理。
  • 本篇前置依赖：AND-P5-G01。
  • 本篇后继：P2 卷输入分发链路各篇；AND-P5-401（时间戳对齐语境）。
  • 数量级与边界值：
    • 事件载体固定 4 个字段，标量宽度为 __u16／__u16／__s32（源码常量，input.h:14）。
    • ioctl 面 28 个宏（源码计数，input.h:62-:89）。
    • 多点触控常量 15 个（源码计数，input-event-codes.h:730-:744）。
    • scancode[32] 是映射项的上限（源码常量，input.h:49）。
    • 单帧事件条数无固定上限，取决于驱动一次写入量——暂无实测，列为待补。
