1. TL;DR

setContentView 只是把布局塞进窗口的内容容器，真正让界面「挂到系统上」的是后面几步：Activity 在创建阶段就持有一个 PhoneWindow，窗口首次用到时安装 DecorView 并生成内容容器；随后根视图通过 WindowManagerImpl 进入 ViewRootImpl.setView，在那里携带该窗口的 Token 向系统的窗口会话申请加入显示。Token 是应用层与窗口管理服务之间的凭证，在 Activity.attach 阶段取得、随窗口属性一并送达系统，后续所有与显示相关的请求都靠它标识属于哪个窗口。

3. 问题背景

「我在 onCreate 里调了 setContentView，界面为什么还是黑的？」这类问题的答案往往不在布局 XML 本身，而在窗口还没走到注册那一步。反过来，排查「窗口泄漏」「Activity 销毁后 View 仍被持有」时，也必须知道是谁在什么时候持有窗口引用与 Token。把从布局到窗口会话这条线串起来，才能判断哪一环断在哪。

4. 核心机制

4.1 概念与关系

四个层级：Activity（组件）、Window（窗口抽象，实现为 PhoneWindow）、DecorView（窗口的根视图容器）、ViewRootImpl（根视图与系统的连接器）。

图 1：Activity 到 ViewRootImpl 的持有链

  Activity ──持有──▶ PhoneWindow ──根──▶ DecorView
                                            │
                        ViewRootImpl ◀──────┘
                              │
                       窗口会话（携带 Token 申请加入显示）

关键点：setContentView 只作用于 DecorView 内部的内容容器，不触发窗口注册；注册发生在 setView。

4.2 关键流程

四段式链路：

图 2：setContentView 到布局 inflate 的分解

  setContentView ─▶ Window.setContentView ─▶ installDecor
                        │
        DecorView ◀─────┴─▶ mContentParent ◀── inflate(应用布局)

第一段，窗口的诞生。Activity.attach 在创建实例时执行 mWindow = new PhoneWindow(...)，窗口对象此刻就存在，但根视图还没有。

第二段，内容的落位。setContentView 转发到窗口的 setContentView，后者在内容容器为空时先 installDecor：generateDecor 造出 DecorView，generateLayout 依主题生成布局并把内容容器 mContentParent 装到 DecorView 上，最后把应用布局 inflate 进内容容器。

第三段，窗口的注册。根视图经 WindowManagerImpl.addView 进入全局窗口管理，最终到达 ViewRootImpl.setView。这里把根视图挂为 mAttachInfo.mRootView，并通过窗口会话申请加入显示。

第四段，Token 的携带。窗口 Token 并非在加入显示时才生成：Activity.attach 取得的组件凭证先存进窗口（Activity.java 约 9247 行的 mToken → Window.java 约 933 行的 mAppToken）。窗口注册的入口是 WindowManagerGlobal.addView（约 409 行）；对顶层 Activity 窗口 parentWindow 非空，于是在约 423 行调用 Window.adjustLayoutParamsForSubWindow（约 947/995 行）把凭证填进窗口属性，随加入显示的请求一并送到系统——系统对它做的是校验与接纳，不是反向下发。此后它成为该窗口在系统侧的身份标识，ViewRootImpl 后续的显示请求都携带它。（装配点并非只有一处：WindowManagerImpl.applyTokens（约 199 行）会用 mDefaultToken 兜底，但条件是 mParentWindow == null——Activity 窗口不满足，故不适用。）

4.3 一个具体例子

在 onCreate 中调用 setContentView(R.layout.main) 时，实际发生的是：内容容器若为空，先补齐 DecorView 与内容容器，再把 main 的布局树加进容器。此时窗口对象与视图树都在，但尚未注册。

注册发生在主线程第一次触发遍历时：根视图被交给窗口管理，进入 ViewRootImpl.setView，向窗口会话申请加入显示。返回成功后窗口才算真正建立。这也解释了为什么在 onCreate 里读窗口尺寸常拿到零——注册与首次布局都还没发生。

7. 常见问题与误区

7.1 误区

误区一：以为 `setContentView` 会立刻显示界面。 它只填充内容容器；显示要等窗口注册与首次遍历。

误区二：以为 `onCreate` 里能拿到正确的视图宽高。 此刻尚未测量布局，读到的是零或占位值；可靠时机在首次布局之后。

误区三（看起来对其实是错的）：以为 Token 是在窗口加入显示时由系统下发的。 Token 确实不是应用自造的，但也不是等窗口注册时系统才发下来：它是 attach 阶段从系统取得的组件凭证，被应用在注册窗口时主动带进窗口属性（Window.java 约 933/995 行），随加入显示的请求送回系统；系统做的是校验与接纳，而不是授予。（其他窗口类型的装配点可能不同——WindowManagerImpl.applyTokens 的兜底只在无父窗口时生效。）

误区四：以为 `getWindow` 可能返回空。 窗口在 attach 阶段就创建，getWindow 总有对象；未注册不等于不存在。

7.2 高频提问

问：为什么 setContentView 之前调 requestWindowFeature 才有效？ 答：因为特性会影响 generateLayout 选用的布局，而该函数只在首次 installDecor 时跑一次；装饰装好后再改特性已不起作用。

追问：那重复调用 setContentView 会怎样？ 答：内容容器会被清空后重新填充，旧视图树被替换。

问：窗口什么时候真正「加入显示」？ 答：在 ViewRootImpl.setView 向窗口会话申请成功后。之前窗口对象与视图树都已存在，只是未注册。

追问：怎么验证注册已发生？ 答：静态看 setView 里的 addToDisplay 调用路径；运行时则看窗口是否出现在系统的窗口列表里（归 P6）。
