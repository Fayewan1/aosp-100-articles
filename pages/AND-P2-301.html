1. TL;DR

框架层有两套彼此独立、却又必须协同的并发机制。

一套在 native。每个进程一个 ProcessState（进程级单例），它拉起一个 Binder 线程池：startThreadPool 先起 1 个池线程，之后按需扩容，上限默认 15（DEFAULT_MAX_BINDER_THREADS，ProcessState.cpp:49）。线程的增减由内核按队列压力驱动，用户态只做登记（joinThreadPool，IPCThreadState.cpp:841）。

一套在 Java。每个线程一个 Looper（线程私有，ThreadLocal），主线程的 Looper 由 ActivityThread.main(ActivityThread.java:9465) 里的 Looper.prepareMainLooper()(9507) ＋ Looper.loop()(9523) 拉起，消息进 MessageQueue，由 Handler 分发。

关键结论有两条。 一是「Binder 线程」和「主线程」是两批完全不同的线程：系统服务在 Binder 线程上处理事务时，必须把要碰 UI/主线程状态的工作 post 到自己的 Handler 上——这正是框架里无处不在的 xxxHandler 的由来。二是两者叠加后，最典型的故障是跨进程同步调用造成的线程互相占满（双方的 Binder 线程与主线程全部阻塞在等 reply），表现为双方齐刷刷 ANR，而 logcat 只留一条 binder thread pool (16 threads) starved 告警——括号里的 16 是该进程通过 BINDER_SET_MAX_THREADS 设的池上限 mMaxThreads（默认 15），不是线程计数。

（长代码块，建议到公众号/头条侧按截图策略处理）

应用的主线程卡在等 reply，system_server 侧的 Binder 线程也全被占住（本例日志里的 16 表示该进程池上限被设为 16）。如果只看一侧，你会以为是「对方服务慢」；但真相常常是双方各自发了同步事务、又在等对方 reply——所有可用线程都拿去等了，没有任何一个线程能腾出来把 reply 送回去。这就是「跨进程同步调用」在高并发下的死锁形状。

要定位这类问题，脑子里得同时装着两套线程模型和它们之间的桥：Binder 线程是「外来请求的执行者」，Handler/Looper 是「本地任务的执行者」。什么时候该在哪一边干活、什么情况会把两边一起拖死，是本篇要讲清的。

4. 核心机制

4.1 数据结构与状态定义

图 2：进程级 Binder 状态与线程池

进程级（每个进程一份）
├─ ProcessState  （单例，ProcessState::self()）
│    ├─ mDriverFD               : /dev/binder 的 fd
│    ├─ mLock                  : 保护线程池登记

└─ Looper（ThreadLocal）
     ├─ mQueue : MessageQueue（消息队列）
     └─ mThread : 所属线程（主线程 = 进程主线程）

消息
└─ Message（target=Handler, callback, when）——由 Handler 入队/出队/分发

三条要点先把概念钉死：

  • Binder 线程池是进程级、跨语言层（Native 与 Java 侧）的：它由 ProcessState 管，Java 侧看不见这些线程对象，但 Java 的 Binder.onTransact 就跑在这些线程上。
  • `IPCThreadState` 是「当前线程」私有的：同线程发事务不会串，但一个线程同一时刻只能处理一个事务。
  • 主线程也是一个「有 Looper 的普通线程」：它在系统里之所以特殊，只因为 ActivityThread.main 给它建了主 Looper，且不允许 quit。

Handler 发送一方：sendMessage(Handler.java:705) → enqueueMessage(Handler.java:845) → queue.enqueueMessage(:699) 并唤醒 nativePollOnce。整条 Java 侧链路的核心事实：主线程是一个「走到 next() 就阻塞、被消息唤醒、执行、再阻塞」的循环，没有消息时它消耗 0 CPU。

失败路径（三类）：

  1. Binder 线程池耗尽（达到 `mMaxThreads` 上限）：所有池线程都在跑一个慢的 onTransact，新事务排队 → 调用方 waitForResponse 干等 → 主线程 ANR。日志即 §3 的 starved。
  2. 跨进程互相同步调用 → 死锁：A 主线程同步调 B，B 处理时又同步调 A；A 的池线程正被 B 占着、B 的池线程正被 A 占着，双方 reply 都送不回去。解除办法只有设计层：把至少一个方向改成 oneway，或跨进程绝不持锁/同步等待。
  3. `Looper.loop()` 退出即线程死亡：主线程 Looper 若被 quit（主 Looper 不允许），或非主线程 Looper 处理完 quit 后继续 sendMessage，会抛 IllegalStateException / 静默丢消息。用子线程 Handler 时必须保证 Looper 生命周期长于消息发送。

4.3 关键代码逐段剖析

第一段：拉起线程池（ProcessState.cpp:220–233）

void ProcessState::startThreadPool()
{
    std::unique_lock<std::mutex> _l(mLock);
    if (!mThreadPoolStarted) {
        if (mMaxThreads == 0) {
            ALOGW("Extra binder thread started, but 0 threads requested. Do not use "
                  "*startThreadPool when zero threads are requested.");
        }
        mThreadPoolStarted = true;
        spawnPooledThread(true);         // 只起 1 个新池线程（isMain=true）
    }
}

（长代码块，建议到公众号/头条侧按截图策略处理）

startThreadPool 只负责拉起 1 个新池线程（spawnPooledThread(true) 内部 sp<PoolThread>::make(isMain) ＋ t->run()，ProcessState.cpp:440–441），不是把调用者（通常是进程主线程）变成池成员；调用者主线程是否入池，由宿主代码在自己的 main 尾部另行调 joinThreadPool 决定。多出来的池线程由内核后续按需补——省线程、省内存，代价是「压力突然上来时，线程创建有延迟」，这也是为什么突发流量下会先看到 starved 告警而不是直接失败。

第二段：池线程的循环体（IPCThreadState.cpp:841–880，节选）

void IPCThreadState::joinThreadPool(bool isMain)
{
    mProcess->mCurrentThreads++;
    mOut.writeInt32(isMain ? BC_ENTER_LOOPER : BC_REGISTER_LOOPER);
    mIsLooper = true;
    status_t result;
    do {
        processPendingDerefs();
        result = getAndExecuteCommand();     // 取一条命令、执行；无事时阻塞在内核
        if (result == TIMED_OUT && !isMain) {
            break;                            // 非主线程空闲超时后退出池（内核按需再唤醒）
        }
    } while (result != -ECONNREFUSED && result != -EBADF);
    mOut.writeInt32(BC_EXIT_LOOPER);
    mIsLooper = false;
    talkWithDriver(false);
    mProcess->mCurrentThreads.fetch_sub(1);
}

（长代码块，建议到公众号/头条侧按截图策略处理）

BC_ENTER_LOOPER 和 BC_REGISTER_LOOPER 是给内核看的「我要/我加入池」命令；isMain 区分「主线程永不主动退出」与「池线程空闲可退出」。这实现的就是「线程池不是固定 15 个常驻线程，而是 1–15 之间动态伸缩」。

第三段：主线程循环与消息队列（Looper.java:373 与 MessageQueue.java:362–378，节选）

nativePollOnce 是主线程「睡觉」的地方：没有消息时它不空转，被 enqueueMessage 唤醒。推论：主线程卡顿有两种截然不同的形状——一是 dispatchMessage 里干了太久（你的代码慢），二是 nativePollOnce 里被无限期唤醒后消息海量（消息风暴）。二者堆栈完全不同，别混。

4.4 与相邻机制的关系

  • 与 Binder 事务（AND-P2-101）：本篇讲的是 101 那条事务链在「多个线程并发」下的行为。101 的单次时序图里，「服务端 Binder 线程」只是一个点；这里把它展开成一个会被占满的池。
  • 与线程池策略（AND-P2-102，承接篇）：oneway 的语义与死亡通知属 102；setThreadPoolMaxThreadCount 的取值权衡在本篇 §6 给出核验路径（默认上限与生命周期可静态定位）。
  • 与驱动（AND-P5-201/P5-202）：BR_SPAWN_LOOPER 的触发条件、内核如何决定「该给这个进程加线程」，属 P5。本篇止于 BC_REGISTER_LOOPER 的用户态侧。
  • 与应用层：HandlerThread、runOnUiThread、AsyncTask（已废弃）都是这套 Looper/Handler 模型的封装；Executor 系列则是另一套（Java 线程池），不要与 Binder 线程池混淆——它们互不隶属。

7. 常见问题与误区

Binder 回调跑在主线程上？ 不是。Binder.onTransact 跑在调用方的 Binder 线程（服务端进程的池线程），不是服务端主线程。在 onTransact 里直接动 UI 或主线程独占状态必然出事——post 到 Handler 才是正解。

Binder 线程池固定 16 个常驻？ 不是。它是 1–15 之间动态伸缩（startThreadPool 起第 1 个池线程，内核再按需补到 mMaxThreads，默认 15）。空闲池线程会退出，压力来时内核再「请」回来。

`Looper.loop()` 返回了就是正常结束？ 不是。主线程 Looper 不允许 quit；loop() 返回意味着收到 null 消息（quit），此后该线程再 sendMessage 会异常或丢消息。子线程 Handler 必须保证 Looper 活得比消息久。

Binder 线程池和 `ExecutorService` 是一回事？ 不是。前者由内核驱动、只服务 Binder 事务；后者是 Java 层线程池。把耗时任务丢进 Binder 线程（在 onTransact 里干重活）会占满池、拖垮整个进程收事务的能力。

面试高频：为什么 Binder 事务不要在服务端线程里做重活？ 答：onTransact 占用的是池线程，池上限只有 15。一个慢事务会把一个池线程钉死；并发几个慢事务就把池占满，进程再也接不了新请求，调用方全部排队——典型 ANR 成因。重活应移出 Binder 线程（post 到 Handler 或专用线程池），尽快 reply。

面试高频：主线程明明在"死循环"里 `loop()`，为什么手机不卡？ 答：loop() 大部分时间阻塞在 MessageQueue.next → nativePollOnce，由 epoll 等待，CPU 占用接近 0；只有消息到来才被唤醒执行。所以"主线程一直循环"不等于"一直跑"。

9. 版本差异

版本变化影响
早期 → 今Binder 线程池默认上限长期为 15（DEFAULT_MAX_BINDER_THREADS，ProcessState.cpp:49）该常量稳定，是理解池容量的基线
近期（本树）android.os.MessageQueue 采用变体源集布局：LegacyMessageQueue/、CombinedMessageQueue/、CombinedDeliMessageQueue/ 各存一份 MessageQueue.java，由构建按变体选源直接 find android/os/MessageQueue.java 会找不到；本篇按 LegacyMessageQueue/MessageQueue.java 取行号，换变体时行号可能不同
本树（android17-release）Looper.loop() 仍为阻塞式 for 循环 + nativePollOnce主线程模型未变
长期演进AsyncTask 已废弃（据官方文档，API 30），改用 Executor/协程理解 Looper 仍必要，但新代码别再用它做并发编排

★ 变体源集是本树的一个真实差异点：它不影响语义，但会让"按行号找代码"失效。定位时优先按符号名 grep，而非写死路径与行号。
