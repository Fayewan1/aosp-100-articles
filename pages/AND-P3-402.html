1. TL;DR

VNDK 版本号不是一句口头约定：check_vndk_version 以版本号为参数校验 prebuilts/vndk/v<版本> 目录的存在性，缺目录就报错，本树中它的调用点是 PRODUCT_EXTRA_VNDK_VERSIONS 的遍历（board_config.mk:1029）。VNDK 的运行时形态是一组 com.android.vndk.* APEX，linkerconfig 读得到这些 APEX 才启用 vndk 段；读不到也不致命，链接器按 apex 专属配置、/system/etc/ld.config.<abi>.txt → /linkerconfig/ld.config.txt → /system/etc/ld.config.<vndk 版本>.txt → /system/etc/ld.config.txt 的顺序逐级回落（五级，见 §8）。/system/etc/ld.config.vndk_lite.txt 是另一条通道：由 ro.vndk.lite 属性选择，服务的是 vndk-lite 旧设备，与「有没有 VNDK APEX」无关。稳定边界由两类东西承担：llndk_libraries_txt 生成的 llndk.libraries.txt 列表与 llndk 属性块（Symbol_file、Export_llndk_headers）声明的符号白名单，以及链接器为 vndk 段与 default 段生成的链接关系。判断一个 vendor 链接失败是配置问题还是符号问题，先看命名空间生成，再看符号表。

3. 问题背景

给 vendor 侧加一个依赖系统库的二进制，编译过了，刷机后启动即失败，日志只有一行找不到符号。另一类现象更难排查：同一份 vendor 代码，换一个系统版本重编就报缺少库，而库就在 /system/lib64 下。还有人在移植时把 VNDK 版本号配置写错，构建直接停在 board 配置阶段，报错只说某个路径不存在，看不出它要的是什么。

这三种现象背后是同一套东西：分区边界、VNDK 快照、链接器命名空间。它们分别在不同的阶段生效——构建配置期、soong 模块定义期、运行时链接期，所以报错形态完全不同。

4. 核心机制

4.1 概念与关系

四个概念构成一条链：

  • 系统分区提供实现，vendor 分区只看到被允许看到的接口。
  • VNDK 是系统库中「允许 vendor 依赖」的子集快照，以版本号区分。
  • LLNDK 是这份子集里更窄的一层，以列表产物与符号表形式显式声明。
  • 链接器命名空间是上面这些声明在运行时的落地物，决定谁可以链谁。

图 1：从构建配置到运行时链接的四段边界

这条链上任一环断开都会表现成「找不到库/符号」，但修法完全不同：配置环要在 board 配置里补，符号环要在模块定义里补声明。

4.2 关键内容

构建期的第一道闸在 board 配置。check_vndk_version（build/make/core/board_config.mk:1020 定义）把传入的版本号展开成 prebuilts/vndk/v<版本> 路径并检查存在性，缺目录即报错。本树中它的调用点只有一处：PRODUCT_EXTRA_VNDK_VERSIONS 非空时的逐版本遍历（同文件 :1029）。这一步发生在编译任何代码之前，所以版本号写错时看到的是路径不存在，不是链接错误。

BOARD_VNDK_VERSION 与 PLATFORM_VNDK_VERSION 这两个变量在 config.mk 里的命运是「被置空即终止」：config.mk:1331 与 :1334 在变量已定义时把它清空，build/make 全树再没有对它们的重新赋值，版本语义改由 soong config 承接——soong_config.mk:162 把 PRODUCT_EXTRA_VNDK_VERSIONS 汇总成 ExtraVndkVersions，落进 build/soong 的配置结构（android/variable.go:383）供构建期消费。留意这条链的终点不是 linkerconfig：它对 ExtraVndkVersions 全树零引用，版本号经 --vndk/--product_vndk 参数传入（system/linkerconfig/main.cc:87-88）。所以看到这两个变量在配置后期读不到值，是设计如此，不是变量没生效。

模块侧的声明由 soong 的 llndk 属性块与 llndk_libraries_txt 承担：Symbol_file（build/soong/cc/llndk_library.go:33）指定符号白名单文件，Export_llndk_headers（同文件 :43）导出 LLNDK 头文件，LLNDK 库产物统一带 .llndk 后缀（同文件 :26 的 llndkLibrarySuffix 常量），而 llndk_libraries_txt 模块类型（同文件 :111 注册）产出 llndk.libraries.txt 列表文件，把这一组库显式列出来。

运行时的第一判断是 VNDK APEX 在不在。context.cc 用 com.android.vndk. 前缀识别 APEX 名，是否找到这类 APEX 直接决定 vndk 段是否启用。即便没有生成配置，链接器也不会就此失败：get_ld_config_file_path（linker.cpp:3607 起）按顺序查找 apex 专属配置（get_ld_config_file_apex_path，:3617）、/system/etc/ld.config.<abi>.txt（:3626）、/linkerconfig/ld.config.txt（:3631）、vndk 版本配置（get_ld_config_file_vndk_path，:3640 起），最后兜底 /system/etc/ld.config.txt（:3645）。/system/etc/ld.config.vndk_lite.txt 不在这条回落链上——它只由 ro.vndk.lite 属性为 true 时选中（:3577-3579），对应 vndk-lite 旧设备。

命名空间之间的链接关系不是手写配置文件，而是 linkerconfig 算出来的。system_links.cc 计算 vndk 段与 default 段的链接关系，其中用到 VndkUserPartition 参数来区分发起方所在分区。

4.3 一个具体例子

设想 vendor 侧一个二进制需要链接某系统库：

  1. 构建期，board_config.mk 的 check_vndk_version 被 PRODUCT_EXTRA_VNDK_VERSIONS 遍历触发，核对 prebuilts/vndk/v<版本> 是否存在。不存在，构建停在这里。
  2. 配置阶段，BOARD_VNDK_VERSION/PLATFORM_VNDK_VERSION 在 config.mk 中被置空后不再重赋值，版本语义经 soong config 向下传递。
  3. 模块解析阶段，目标库若带 llndk 属性块，其 .llndk 产物与 Symbol_file 决定 vendor 可见的符号集合，llndk_libraries_txt 把集合列成 llndk.libraries.txt。
  4. 运行时，linkerconfig 扫到 com.android.vndk. 前缀的 APEX，启用 vndk 段，system_links.cc 生成 vndk 段与 default 段的链接边。
  5. 链接该二进制时，bionic 的链接器按生成的配置找库。找不到符号，问题在第 3 步的符号表；找不到库，问题在第 4、5 步的命名空间。

同一个「起不来」的现象，被拆成四个互不重叠的检查点，这就是排查顺序的来源。

4.4 与相邻篇的关系

AND-P3-401 讲进程守护与 ashmem 共享内存，是同一个进程内部的机制；本篇把尺度换成分区之间。HAL 契约、VINTF manifest 与 matrix 的内容归 AND-P4-101、AND-P4-102，本篇只说「边界存在」不说「边界上签什么协议」。vendor 镜像构建细节与产品变体归 P11，本篇只用到出口变量 TARGET_COPY_OUT_VENDOR 这一项。

7. 常见问题与误区

7.1 误区

「VNDK 版本号设了就能用」。设了只过第一关，而且过闸的方式是遍历：PRODUCT_EXTRA_VNDK_VERSIONS 里出现的每个版本号都会被 check_vndk_version 核对 prebuilts/vndk/v<版本>，缺一个就整体报错。该报错发生在编译之前，与链接无关。

「vendor 能链接系统库，是因为库在 `/system/lib64` 下」。位置不产生权限。可见性来自 llndk 属性块声明的符号白名单与 .llndk 产物，以及 linkerconfig 生成的命名空间链接关系。这条是「看起来对其实是错的」：路径存在和能链上是两件事。

「没有 VNDK APEX 就走 vndk_lite 配置」。两件事没有因果关系。ld.config.vndk_lite.txt 由 ro.vndk.lite 属性选中，服务 vndk-lite 旧设备；没有 VNDK APEX 时，链接器走的是 apex 专属配置前置、ld.config.<abi>.txt → /linkerconfig/ld.config.txt → vndk 版本配置 → ld.config.txt 的逐级回落（共五级），设备照样能起来。

7.2 高频提问

问：构建时提示 prebuilts/vndk/v<版本> 不存在，但我不想用 VNDK。答：校验由 check_vndk_version 触发，调用者是 PRODUCT_EXTRA_VNDK_VERSIONS 的遍历。先去核对版本号是从哪条配置带进来的，而不是往 prebuilts/vndk 下塞目录。追问：那我把版本号配置都删掉会不会绕过？答：可以，删掉后 PRODUCT_EXTRA_VNDK_VERSIONS 为空，这轮校验就不跑；但与此同时 BOARD_VNDK_VERSION/PLATFORM_VNDK_VERSION 在 config.mk 中本来就会被置空，版本语义改由 soong config 传递，要确认下游不依赖这两个变量。

问：vendor 二进制报找不到符号，库确实在。答：先分清是库不可见还是符号未导出。库不可见看命名空间生成，符号未导出看 Symbol_file 白名单。追问：怎么快速区分？答：换成链接一个确定在 LLNDK 集合里的库做对照，能链上说明命名空间没问题，问题在目标库的符号声明。

8. 边界与延伸

本篇不覆盖：HAL 契约与 VINTF manifest/matrix（AND-P4-101、AND-P4-102）；vendor 镜像构建与产品变体（P11）。

本篇前置依赖：AND-P3-401。

本篇后继：AND-P4-101、AND-P4-102。

数量级与边界值：

  • VNDK 版本路径只有一层版本号目录 prebuilts/vndk/v<版本>（口径：源码常量，build/make/core/board_config.mk:1021）。
  • LLNDK 产物后缀固定为 .llndk，符号文件属性名固定为 llndk.symbol_file（口径：源码常量，build/soong/cc/llndk_library.go:26、:33）。
  • APEX 名以前缀 com.android.vndk. 识别，无版本上限断言（口径：源码常量，context.cc）。
  • 运行时配置按 5 级顺序查找：apex 专属配置（get_ld_config_file_apex_path，linker.cpp:3617）→ ld.config.<abi>.txt（:3626）→ /linkerconfig/ld.config.txt（:3631）→ vndk 版本配置（:3640）→ 兜底 /system/etc/ld.config.txt（:3645）；兜底文件名唯一（口径：源码常量，bionic/linker/linker.cpp:3607-3646）。
  • ro.vndk.lite 为 true 时选中 /system/etc/ld.config.vndk_lite.txt，与 VNDK APEX 是否存在无关（口径：源码常量，bionic/linker/linker.cpp:3577-3579）。
  • 单个 VNDK 版本对应的具体库数量：暂无实测，列为待补。
