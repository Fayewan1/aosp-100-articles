1. TL;DR

Choreographer 不是一个计时器，而是应用进程侧的 vsync 消费端：它向 SurfaceFlinger 的 EventThread 预约下一次 vsync，收到回调后在同一个 doFrame 里按固定顺序跑输入、动画、插值动画、traversal、commit 五类回调。丢帧的本质不是 doFrame 慢，而是「上一帧的工作没在下一个 vsync 到来前做完」，导致 scheduleFrameLocked 预约的那一次 vsync 被浪费。判断丢帧要看的是预约时刻、回调触发时刻、FrameTimestamps 里各阶段 fence 的完成时刻三者的相对位置，而不是单看某一帧耗时。

3. 问题背景

线上帧率面板显示某个页面在动画期间每隔几帧就掉一帧，但抓 trace 看 doFrame 自身耗时只有 3–5 ms，远小于 16.6 ms 的预算。开发者因此困惑：既然每帧干的活都不多，帧率为什么还是不满。也有人发现 Choreographer 的 FrameCallback 时间戳「时快时慢」，怀疑是系统在抖动。这两类问题的答案都不在 doFrame 内部，而在 vsync 的预约、供给与回填这条链路上。

4. 核心机制

4.1 概念与关系

四个概念构成一条单向链：

  • vsync 供给端：SurfaceFlinger 的 EventThread，按 VSyncPredictor 预测的下一次 vsync 时刻投递事件。
  • 进程内接收端：DisplayEventReceiver 及其 native 侧 DisplayEventDispatcher，负责 fd 上的读事件与 requestNextVsync。
  • 调度器：Choreographer，持有两个 token，把回调按类型排进五个阶段。
  • 消费者：ViewRootImpl，通过 mChoreographer.postVsyncCallback 挂 traversal。

图 1：vsync 从 SurfaceFlinger 到应用 traversal 的消费链

EventThread --fd--> DisplayEventDispatcher --> onVsync

4.2 关键内容

回调类型是一组同前缀常量，取值与顺序决定了同一帧内的执行次序。CALLBACK_INPUT = 0、CALLBACK_ANIMATION = 1、CALLBACK_INSETS_ANIMATION = 2、CALLBACK_TRAVERSAL = 3、CALLBACK_COMMIT = 4，范围止于 CALLBACK_LAST = CALLBACK_COMMIT。注意 2 号位不是留白：CALLBACK_INSETS_ANIMATION（定义在 :344）服务窗口插值动画（InsetsAnimation）控制器回调，doFrame 在 :1206 真正调到它，位置在 CALLBACK_ANIMATION（:1205）之后、CALLBACK_TRAVERSAL（:1209）之前。

名称含义出处

Choreographer 用两个 token 区分回调来源：FRAME_CALLBACK_TOKEN 标记普通帧回调，VSYNC_CALLBACK_TOKEN 标记 vsync 回调。USE_VSYNC 是这套机制的总开关。mFrameIntervalNanos = (long)(1000000000 / getRefreshRate()) 给出的是按刷新率折算出的帧预算。注意口径：getRefreshRate()（:391）返回 float，1000000000 / getRefreshRate() 是浮点除法，结果经 (long) 强制转换截断——不是整数除法，也不是整数运算意义上的向下取整。计算式在 :379。

调度入口与执行点是 scheduleFrameLocked(long now) 与 doFrame(long frameTimeNanos, int frame, ...)。真正接 vsync 的是内部类 FrameDisplayEventReceiver，其 onVsync 是 vsync 到达应用进程后的第一个落点。

链路的 Java 侧对端是 DisplayEventReceiver：scheduleVsync 发起预约，nativeScheduleVsync 是 native 调用，onVsync 是回调。native 侧 DisplayEventDispatcher 的 scheduleVsync 在 :79，injectEvent 在 :105；内部通过 mReceiver.requestNextVsync() 向 SurfaceFlinger 要下一次 vsync，用 mReceiver.sendEvents(&event, 1) 把事件送上去。

SurfaceFlinger 侧的供给由 EventThread::onVsync(nsecs_t vsyncTime, nsecs_t wakeupTime, nsecs_t readyTime) 完成，EventThreadConnection::postEvent 负责投递到具体连接。时刻由 VSyncPredictor::nextAnticipatedVSyncTimeFrom 预测——所以应用看到的 vsync 时间是「预测值」，不是硬件回读值。

ViewRootImpl 一侧，mChoreographer 字段在 :692 声明、在 :1440 初始化；scheduleTraversals 在 :3307 里调 mChoreographer.postVsyncCallback（:3330），最终由 performTraversals（:3351）消费这一帧。注意 traversal 不是直接 postFrameCallback，而是 vsync 回调，语义更靠近「下一次 vsync 一定叫我」。

4.3 一个具体例子

假设一次 animator 推进导致需要重绘。应用侧走的是：scheduleTraversals → postVsyncCallback → scheduleFrameLocked(now) → native 侧 requestNextVsync。SurfaceFlinger 的 nextAnticipatedVSyncTimeFrom 给出下一次 vsync 时刻 T。T 到达时 FrameDisplayEventReceiver.onVsync 被调，doFrame 依次跑 CALLBACK_INPUT=0、CALLBACK_ANIMATION=1、CALLBACK_INSETS_ANIMATION=2、CALLBACK_TRAVERSAL=3、CALLBACK_COMMIT=4。

如果这次 CALLBACK_ANIMATION 里的动画计算把时间拖过了 T + mFrameIntervalNanos，那么下一次预约仍在，但 GPU 侧提交赶不上 T+1 的合成，表现为该帧被丢。trace 上看到的现象是 doFrame 时长正常，但两次 onVsync 之间的间隔变成两个帧周期——这就是「doFrame 不慢却掉帧」的典型形态。这里要把可锚定与推断的部分分开说：CPU 侧有源码级日志直接对应此机制——doFrame 在 Choreographer.java:1131 计算 skippedFrames = jitterNanos / frameIntervalNanos，超过阈值时（:1132-1136）打印 Skipped N frames! The application may be doing too much work on its main thread.；GPU→SurfaceFlinger 一段为黑盒，属设计语义推断，本树静态分析不可直接核验。

帧轨迹侧，FrameEventHistory::INITIAL_MAX_FRAME_HISTORY（:171）决定历史容量，getFrame（:179）取帧，checkFencesForCompletion（:201）检查 fence 是否已落地，ProducerFrameEventHistory::updateAcquireFence（:254）回填 acquire fence。渲染执行的回填点在 ThreadedRenderer.syncAndDrawFrame（ThreadedRenderer.java:848），属于渲染执行侧，本篇不展开。

7. 常见问题与误区

7.1 误区

误区一：`doFrame` 耗时小于帧周期就不会掉帧。 错。doFrame 只覆盖 CPU 侧的测量与录制，GPU 提交与合成还在后面。判断依据是这条管线整体是否在下一个 vsync 前闭环。

误区二：vsync 时间戳是硬件真实回读值。 错。应用侧拿到的时间来自 nextAnticipatedVSyncTimeFrom 的预测，它随刷新率与历史间隔变化，因此会看到「时快时慢」。

误区三：`Choreographer` 是一个 16 ms 定时器。 看起来对，其实是错的。它是事件驱动：只有在有回调登记时才 scheduleFrameLocked 去要 vsync，没有工作时不会空转。所谓「16 ms」只是 mFrameIntervalNanos 这个折算值。

误区四：traversal 和动画回调必然同一帧。 未必。两者虽然都在同一个 doFrame 里按 0/1/2/3/4 顺序执行，但如果在 CALLBACK_ANIMATION 里新登记了 traversal 回调，它进入的是下一次调度，而不是当前这一帧。

7.2 高频提问

问：为什么 postVsyncCallback 与 postFrameCallback 行为不同？ 答：两者用不同 token（VSYNC_CALLBACK_TOKEN 与 FRAME_CALLBACK_TOKEN）标识来源，前者语义是「下一次 vsync 一定通知我」，对齐的是 vsync 事件本身。 追问：那 traversal 为什么选后者？ 答：ViewRootImpl.scheduleTraversals 走 postVsyncCallback，因为它需要的是「被 vsync 准时叫醒」而不是「下一帧的回调槽位」。

问：onVsync 间隔突然变成两帧是怎么回事？ 答：上一次预约的 vsync 对应的帧没能在下一次合成前完成，SurfaceFlinger 侧没有可合成的新内容，于是应用侧看到的有效触发被推后。CPU 侧这一步有源码锚点：doFrame 在 Choreographer.java:1124 发现 jitterNanos >= frameIntervalNanos 后把 frameTimeNanos 修正为 startNanos 并回退 lastFrameOffset（:1129-1130），:1131 据此算出 skippedFrames，超过 SKIPPED_FRAME_WARNING_LIMIT 时打印 Skipped N frames!（:1132-1136）——「两次 onVsync 之间跨了两个帧周期」在应用进程内有直接日志可点；GPU 提交到 SurfaceFlinger 合成的那一段仍是黑盒。 追问：doFrame 里能直接看出吗？ 答：不一定，要结合 FrameTimestamps 里 checkFencesForCompletion 的结果看 fence 何时落地。
