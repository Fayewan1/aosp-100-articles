1. TL;DR

通用内核镜像（Generic Kernel Image，GKI）的关键不在「编译内核」，而在「配置片段的归属边界」：通用能力进 android-base.config，增强项进 android-recommended.config，供应商只能加模块。kernel/configs 用字母目录按内核版本分流，b/android-6.12/ 的产物叫 kernel_config_b_6.12，meta 指向 android-base-conditional.xml。KMI 冻结意味着配置与符号面在冻结窗口内不再随 vendor 需求变化，因此能进 base 的需求必须先在 kernel/configs 里落地。判断「能力能不能加」，实际就是判断它是 base 片段、recommended 片段，还是只能做模块。

3. 问题背景

同事要开一个网络特性，习惯性地往 defconfig 里加 CONFIG_XXX=y，结果 GKI 设备上启动没生效。另一头有人改了 fragment，check_fragments.sh 在 CI 报错，看不出是哪个架构失败。这类问题的共同点是：把「内核配置」当成一棵树的局部改动，而它其实是一套跨仓库的分层契约——片段在 Android 侧，defconfig 在内核侧，供应商侧只能挂模块。本篇按这三层拆开讲。

4. 核心机制

4.1 概念与关系

三个层次：内核树里的平台 defconfig（在 arch/*/configs/），Android 侧的 fragment（片段），以及供应商侧的内核模块。scripts/kconfig/merge_config.sh 负责把片段按顺序合并到 defconfig 上，最终产物就是该内核版本的配置。

图 1：三层配置的来源与合并关系

 内核树                      Android 侧                vendor 侧
 arch/*/configs/  --+      android-base.config  --+   vendor 模块 Kconfig
 (平台 defconfig)   |      android-recommended ... |   (只能 out-of-tree)
                    v                             v
              scripts/kconfig/merge_config.sh -> 最终 .config

片段的组织不是平铺，而是版本分目录。kernel/configs 顶层有 7 个字母目录：b、c、d、s、t、u、v，另有 build、tools、xsd 三个公共目录。字母是内核主版本序列（b 对应 6.12，v 对应 6.6，u 对应 6.1）。版本差异靠目录隔离，不用条件判断。

4.2 关键内容

基础要求与增强项的划分在 README 里写死：基础要求放 android-base.config，增强项放 android-recommended.config。P 及以前还有 android-base-<arch>.config 架构片段，P 之后这些被移除，条件要求改存 android-base-conditional.xml。自 Android R 起再按编译变体加片段，user 构建另有 non_debuggable.config。

Soong 侧的落点：kernel/configs/b/android-6.12/Android.bp 定义的模块名形如 kernel_config_b_6.12，meta 指向 kernel_meta_b_6.12，后者即 android-base-conditional.xml。TV 分支的两处二选一是同构的：配置侧在 android-base.config 与 android-tv-base.config 之间选，meta 侧在 android-base-conditional.xml 与 android-tv-base-conditional.xml 之间选，条件都是 select(soong_config_variable("google_tv","using_tv_gki"), ...)（kernel_meta_b_6.12 的 filegroup 见 Android.bp:45-51）；同时配 tv_kernel_base_config_b_6.12 genrule 做 cp 生成。

4.3 一个具体例子

以 b/android-6.12/ 为例走一遍：目录下 5 个文件，包含 Android.bp、android-base.config、android-base-conditional.xml。构建系统读 Android.bp 得到 kernel_config_b_6.12，meta 取 android-base-conditional.xml。若本次是 TV 配置，select(soong_config_variable("google_tv","using_tv_gki"), ...) 命中 android-tv-base.config，走 tv_kernel_base_config_b_6.12 的 genrule。内核侧拿到 base 片段后，与平台 defconfig 一起喂给 scripts/kconfig/merge_config.sh，合成最终配置。vendor 想加的项不在任何片段里，只能以外部模块形式存在。

7. 常见问题与误区

7.1 误区

误区一：改 defconfig 就能让所有设备生效。 平台 defconfig 在内核树的 arch/*/configs/，属于单内核树；GKI 设备吃的是合并后的公共配置，defconfig 改动不会自动进入。

误区二：vendor 想要的能力写进 `android-base.config` 就行。 看起来对其实是错的：base 片段是平台侧统一维护的，KMI 冻结后其配置面不随单个 vendor 需求变动。vendor 差异化只能走外部模块。

误区三：架构差异还用 `android-base-<arch>.config`。 P 之后架构片段已被移除，条件要求改存 android-base-conditional.xml。仍在找架构片段的，方向就错了。

误区四：片段文件顺序无所谓。 README 原句要求 keep them alphabetically (not randomly) sorted（README.md:138），顺序影响合并可读性与 diff 稳定性。

7.2 高频提问

问：kernel_config_b_6.12 和 kernel_meta_b_6.12 什么关系？ 答：前者是配置产物模块，后者是 meta 模块，指向 android-base-conditional.xml。 追问：那 TV 配置怎么进来？ 答：通过 select(soong_config_variable("google_tv","using_tv_gki"), ...) 在 base 与 TV 片段间二选一，并由 tv_kernel_base_config_b_6.12 genrule 生成。

问：kernel-lifetimes.xml 的 eol 能不能作为「我的分支还支持吗」的依据？ 答：它是分支生命周期的声明数据，android17-6.18 当前是 <no-releases reason="branch in pre-release phase"/>。追问：怎么核对某个具体 build 是否被批准？ 答：看 approved-ogki-builds.xml，按 <branch name=...> 找 <build id=... bug=.../>，schema 在 xsd/approvedBuild/approved_build.xsd。

8. 边界与延伸

本篇不覆盖：Binder 内核驱动内部行为归 AND-P5-201；启动镜像打包进 boot 归 P8-101。

本篇前置依赖：AND-P5-G01。

本篇后继：AND-P5-201、P8-101。

数量级与边界值：

  • 字母目录 7 个（b/c/d/s/t/u/v），另有 3 个公共目录（build/tools/xsd）。口径：kernel/configs 顶层目录实测。
  • 6.12 目录 5 个文件；6.6 与 6.1 目录各 3 个文件。口径：目录列目录实测。
  • check_fragments.sh 按 ARCHES="arm64 arm x86" 逐架构执行，需 ANDROID_BUILD_TOP 与内核树 -k。口径：脚本内置常量；该脚本需要 android common kernel 检出，本机树内无内核源码，不可执行，只作口径引用。
  • 驱动侧实现细节不在本篇核验范围，凡涉及驱动内部行为一律按内核契约与用户态可观测现象表述。
  • Soong 模块命名与 meta 指向的确切条目数：暂无实测，列为待补。
