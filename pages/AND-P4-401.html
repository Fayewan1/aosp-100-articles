1. TL;DR

相机 HAL 的接口被切成三段：ICameraProvider 枚举设备、ICameraDevice 拿到能力并打开、ICameraDeviceSession 做流配置与请求提交。三段都是 AIDL，流和请求都靠 metadata 描述，而 metadata 在请求与结果两个方向上各走一条 FMQ。接入失败的典型形态集中在一处：configureStreams 返回的 HalStream[] 与请求里假设的流对不上，后续 processCaptureRequest 就会长期无结果。判断「某件事能不能通过 HAL 做到」，先看它落在哪一段、对应符号是否在 ICameraDevice 或 ICameraDeviceSession 上。

3. 问题背景

相机起流失败时，日志常只有一句 configureStreams 返回错误，看不出是流组合不支持还是格式/尺寸不匹配。请求卡住时，表现为 processCaptureRequest 返回成功但结果队列一直空。结果对不上时，是回调里拿到的 metadata 与请求中设置的参数不是同一套字段。这三种现象对应三段接口上的三类契约破坏，需要分别定位。

4. 核心机制

4.1 概念与关系

三个概念：provider（设备枚举者，进程级单入口）、device（单台相机的能力查询与打开句柄）、session（一次开流后的会话，承载流配置、请求与结果）。关系是单向的：provider 产出 device，device 打开后产出 session，session 关闭后回到 device。

图 1：三段接口的调用链与 metadata 两条队列

ICameraProvider
  getCameraIdList / getCameraDeviceInterface
        |
        v
ICameraDevice
  getCameraCharacteristics / isStreamCombinationSupported
  open(ICameraDeviceCallback) -> ICameraDeviceSession
        |
        v
ICameraDeviceSession
  configureStreams -> HalStream[]
  getCaptureRequestMetadataQueue  <-- 请求 metadata (FMQ)
  getCaptureResultMetadataQueue   <-- 结果 metadata (FMQ)
  processCaptureRequest / flush / close

两条 FMQ 的方向相反：请求 metadata 由框架写入、HAL 读出；结果 metadata 由 HAL 写入、框架读出。二者都是 MQDescriptor<byte, SynchronizedReadWrite>。

4.2 关键内容

第一段：枚举。 interface ICameraProvider（ICameraProvider.aidl:58）只有少数几个方法。getCameraIdList()（:119）给出可用相机 id；getCameraDeviceInterface(String)（:147）按 id 取到该相机的 ICameraDevice；notifyDeviceStateChange（:186）把设备状态变化告知 provider。同目录还有 CameraIdAndStreamCombination.aidl 和 ConcurrentCameraIdCombination.aidl，描述多相机并发组合。

第二段：能力与打开。 ICameraDevice 上，getCameraCharacteristics()（:63）返回静态能力集；isStreamCombinationSupported(StreamConfiguration)（:158）用来在不打开会话的前提下提前确认「这套流组合是否可行」；open(ICameraDeviceCallback)（:188）返回 ICameraDeviceSession；constructDefaultRequestSettings（:362）给出某类请求的默认参数；setTorchMode（:273）控制闪光灯常亮。

第三段：流与请求。 ICameraDeviceSession 上，configureStreams 返回 HalStream[]（:162），这是流的实际配置结果；processCaptureRequest(CaptureRequest[], BufferCache[] cachesToRemove)（:486）提交请求，第二个参数是一批 (streamId, bufferId) 二元组，告知 HAL 这些缓冲可以从缓存表里删掉（BufferCache.aidl:35／:39）；flush()（:324）排空在途请求；close()（:50）结束会话；configureStreamsV2 返回 ConfigureStreamsRet（:616）。请求与结果的 metadata 各走一条队列：getCaptureRequestMetadataQueue()（:339）、getCaptureResultMetadataQueue()（:357）。

4.3 一个具体例子

一次典型的开流→出图过程，按符号走：

  1. getCameraIdList() 拿到 id，getCameraDeviceInterface(id) 得到 ICameraDevice。
  2. getCameraCharacteristics() 读能力，用 isStreamCombinationSupported(StreamConfiguration) 先验证预备的流组合。
  3. open(ICameraDeviceCallback) 得到 ICameraDeviceSession。
  4. 提交流配置。走哪个入口不是由调用方随便挑：框架按 ANDROID_INFO_SUPPORTED_BUFFER_MANAGEMENT_VERSION 二选一（ICameraDeviceSession.aidl:93-96 与 :603-607 两处文档都写明这条约束）——未声明该字段、或值为 ..._AIDL 时调 configureStreams（:162）拿 HalStream[]；值为 ..._SESSION_CONFIGURABLE 时改调 configureStreamsV2（:616）拿 ConfigureStreamsRet。返回的流是权威：后续请求里引用的流 id 必须以它为准，不能以提交时的假设为准。
  5. getCaptureRequestMetadataQueue() 与 getCaptureResultMetadataQueue() 各取一个 MQDescriptor<byte, SynchronizedReadWrite>。
  6. 每帧把 camera_metadata_t 序列化写入请求队列，再 processCaptureRequest(CaptureRequest[], BufferCache[] cachesToRemove) 提交（BufferCache 传空数组即可，只在要回收缓冲时才填）；结果从结果队列读出。
  7. 停止时 flush() 排空，再 close()。

失败点集中在第 4 步：如果 HalStream[] 里流 id 或格式与第 6 步写入的请求不一致，请求会被接受但永不出结果。

图 3：一帧的请求与结果两条队列

框架                                  HAL
  |-- 请求 metadata 写入 FMQ（:339）--->|
  |-- processCaptureRequest(:486) --->|
  |                                   |  采集 / 处理
  |<-- 结果 metadata FMQ（:357）-------|
  |<-- CaptureResult（含流 id、时间戳）--|

7. 常见问题与误区

7.1 误区

误区一：以为请求里的流 id 由自己决定。 实际以 configureStreams 返回的 HalStream[] 为准。返回的流顺序、id 与提交时的假设不同时，请求仍会被接受，但结果不会来。

误区二：以为 `isStreamCombinationSupported` 是必须的。 它是可选的前置问答，不调用也能 open 并 configureStreams。它的价值在于把失败提前到开流之前。

误区三：以为两条 metadata 队列是同一块内存。 这个判断看起来有理，其实是错的。getCaptureRequestMetadataQueue()（:339）与 getCaptureResultMetadataQueue()（:357）返回两个独立的 MQDescriptor<byte, SynchronizedReadWrite>，方向相反，容量各自独立，不能复用同一块缓冲读写。

误区四：以为 metadata 的 AIDL 化意味着旧版本目录已删。 hardware/interfaces/camera/metadata/ 下 3.2–3.7 与 aidl 并存，设备接口 AIDL 化不等于 metadata 的 HIDL 版本目录消失。

7.2 高频提问

问：configureStreams 返回成功，为什么还是不出帧？ 答：先看返回的 HalStream[] 与你请求里引用的流是否一致，再确认请求 metadata 是否真的写进了请求队列。 追问：如果流一致、队列也写了，还是不回结果呢？ 答：看 flush() 是否能正常返回；flush 卡住说明会话已在 HAL 侧失联，问题在更下层而不是请求参数。

问：constructDefaultRequestSettings 能不能完全替代自己组 metadata？ 答：它给的是某类请求的默认参数骨架，能用，但不包含你业务相关的控制字段。 追问：那能不能把它返回的 metadata 直接改几个字段再用？ 答：可以，但字段容量受 allocate_camera_metadata 申请的大小约束，加字段前要先确认容量够。
