1. TL;DR

JNI 不是"直接调用"——每个 JNI 函数都是 JNINativeInterface 结构里的一个函数指针，Java 侧调用 native、native 侧反查 Java 类与方法，全部经由这张表。方法查找失败最常见的原因不是名字写错，而是 FindClass 用错了类加载器：它取的是调用者 native 方法所属 library 的加载器，不是"当前线程上下文"的加载器。引用的生命周期由 indirect reference table 管理，局部引用不释放会撑满表；CheckJNI 只是把同一张表换成包装版本，先校验再转发。临界区（GetPrimitiveArrayCritical 等）换来的是不阻塞的访问窗口，代价是这段时间里几乎不能调用别的 JNI 函数。

3. 问题背景

典型现场：native 代码里 FindClass("com/example/Foo") 在某台设备上返回空，日志里还有一条 Call to JNI FindClass with dots in name。另一头，长时间跑循环的 native 线程在第几千次迭代后崩在 NewLocalRef 附近，栈里只有一串地址。还有人打开 -Xcheck:jni 复现失败，关掉就"好了"——那不是 bug 消失，是校验不做了。

这些现象分别落在三个点上：类加载器语义、引用表的容量与生命周期、校验层的开关。三者都在同一张 JNINativeInterface 函数表上，所以放在一起讲。

4. 核心机制

4.1 概念与关系

四个概念：函数表（JNINativeInterface，JNI 函数的唯一入口）、注册（把 Java 声明的 native 方法与 C++ 函数指针对上）、引用表（indirect reference table，管局部/全局/弱全局引用的槽位）、临界区（短暂挂起 GC 相关约束以换取裸指针）。

图 1：JNI 桥的三层结构

Java 侧 native 声明
      |
      v
[JNINativeInterface 函数表]  <- CheckJNI 时换成包装表
      |
      +--> RegisterNatives / FindClass / FindMethodID
      |
      +--> indirect reference table (局部/全局/弱全局)
      |
      +--> Get*Critical (临界区)

函数表是唯一入口，注册、查找、引用、临界区都是表里的不同槽位。CheckJNI 不改变调用方写法，只把表指针换成包装实现。

4.2 关键内容

函数表与实例选择。 基础实现在 art/runtime/jni/jni_internal.cc:3226 的 gJniNativeInterface，它是 JNINativeInterface 结构的一份静态实例。GetJniNativeInterface（同文件 :3463）按 JniIdType 选择返回哪一个实例——也就是说"JNI 函数表"在运行时可以有多个版本，调用方拿到的是哪一个由 ID 类型决定。虚拟机创建入口是 JNI_CreateJavaVM（art/runtime/jni/java_vm_ext.cc:1237，extern "C"），宿主进程启动时由此把运行时拉起来。

注册与查找。 注册走 RegisterNatives，但它的 CheckJNI 版本在 art/runtime/jni/check_jni.cc:1836，先校验方法签名与可见性，再转基础实现。查找侧的关键函数集中在下表：

GetClassLoader 是理解 FindClass 的钥匙。FindClass 的类加载器不是从线程上下文取的，而是从"当前正在执行的 native 方法属于哪个 library"推出来的。在系统启动阶段注册的 library 里调用 FindClass，拿到的就是那条加载链的视野，而不是应用自己的类。

命名还会触发告警：名字里带点会打 Call to JNI FindClass with dots in name（jni_internal.cc:356）。这条日志几乎总是"返回空"的伴生现象，不是独立故障。

引用表。 局部、全局、弱全局引用统一由 indirect reference table 管理（art/runtime/jni/indirect_reference_table.h）。弱全局另有清理路径 SweepJniWeakGlobals（同文件 :254）。局部引用不会因为函数返回"自动"回收——JNI 只保证在 native 方法返回 Java 侧时清理该帧内的局部引用；在 native 自己起的线程里，必须手动 DeleteLocalRef 或 PushLocalFrame/PopLocalFrame。

临界区与异常。 四个临界区函数在函数表里各占一个槽位：GetPrimitiveArrayCritical/ReleasePrimitiveArrayCritical（jni_internal.cc:3449-3450）、GetStringCritical/ReleaseStringCritical（:3451-3452）。名字里的 Critical 指的是"这段窗口内不要做别的事"：拿到裸指针后，任何可能触发 GC 或再次进入同一临界区的 JNI 调用都可能导致阻塞或未定义行为。异常方面，JNI 函数本身不抛 C++ 异常，异常挂起在运行时，native 侧必须显式检查并在返回 Java 前处理干净。

CheckJNI 的开关。 启动时用 -Xcheck:jni 选项（art/runtime/parsed_options.cc:128）。也支持迟启用：EnableDebugFeatures 处理 DEBUG_ENABLE_CHECKJNI 位，然后调 vm->SetCheckJniEnabled(true)（art/runtime/native/dalvik_system_ZygoteHooks.cc:164-176）。迟启用意味着一个已在运行的进程可以中途换成包装表——预算开销前一定要确认当前进程处于哪种状态。

4.3 一个具体例子

以系统进程注册 Binder 的 native 方法为样例：frameworks/base/core/jni/AndroidRuntime.cpp:657 的 AndroidRuntime::startVm 负责拼虚拟机参数，:1208 调 JNI_CreateJavaVM；之后 :1582 用 REG_JNI 宏把 register_android_os_Binder 登记进启动流程，批量 RegisterNatives 的实现在 frameworks/base/core/jni/android_util_Binder.cpp:1930（AndroidRuntime.cpp:60 只是它的 extern 声明）。

顺序很重要：startVm 先建虚拟机，之后才轮到各个 register_* 函数批量注册。在这些系统 library 里调 FindClass 时，GetClassLoader（jni_internal.cc:393）给出的是这条 library 所属的加载器。如果把一段系统侧 FindClass 代码复制进应用自己的 native library 里，逻辑看似一样，实际类加载器视野已经换了，于是同一个类名一边成功一边返回空。

7. 常见问题与误区

7.1 误区

"`FindClass` 找的是当前线程上下文的类加载器。" 不是。实现取的是当前正在执行的 native 方法其 declaring class 的类加载器（GetClassLoader，jni_internal.cc:393：经 GetCurrentMethod()->GetDeclaringClass()->GetClassLoader() 取到，Runtime.nativeLoad 场景用 override）。同一个类名在不同 declaring class 下结果可以不同。

"局部引用会随作用域结束自动释放。" 只在"native 方法返回到 Java 侧"这个边界上才清理该帧的局部引用。native 自建线程、长循环里必须显式删除，否则表持续增长直到溢出。

"开了 `-Xcheck:jni` 会更慢，所以上线版本一定没开。" 不一定。除了启动参数 -Xcheck:jni（art/runtime/parsed_options.cc:128），还有迟启用路径处理 DEBUG_ENABLE_CHECKJNI 位（dalvik_system_ZygoteHooks.cc:164-176）。看着"关掉就好了"的 bug，往往是被校验层抓住了。

"`GetPrimitiveArrayCritical` 拿到了裸指针，随便用。" 这段窗口内几乎不能调别的 JNI 函数，也不能长时间持有。它换的是访问窗口，不是使用自由度。

7.2 高频提问

问：日志里有 Call to JNI FindClass with dots in name，改成分号斜杠就一定能修好吗？

答：不一定。这条告警说明名字格式不对，但返回空也可能是加载器视野问题。改完格式后如果仍返回空，就去看这段代码属于哪个 library。

追问：怎么快速判断？

答：用 §6 的命令确认当前行号没漂，然后在调用点上方加一条 FindClass 前的类名与所属 library 记录，对照 GetClassLoader 的取法推断。

问：RegisterNatives 返回负数，但签名看着全对。

答：先确认签名字符串里的类型描述符（尤其引用类型的分号与斜杠）与 Java 声明逐字符一致；CheckJNI 版会在转发前校验，错误通常在返回值之外的日志里。

追问：CheckJNI 版本在哪？

答：art/runtime/jni/check_jni.cc:1836；整张包装表由 GetCheckJniNativeInterface（:4141）给出。
