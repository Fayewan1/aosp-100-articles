1. TL;DR

Zygote 的启动分三段：main 里做环境准备并打 BOOT_TIME 埋点，preload 里按六段 trace 预加载类、资源、HAL 与图形驱动，最后 fork 出 system_server 并进入命令循环（ZygoteServer.runSelectLoop）接收 App 请求。

预加载类来自 /system/etc/preloaded-classes，每读一行就开一个 trace，所以开机 trace 里能看到逐个类名。

fork system_server 的参数是硬编码的：uid 1000、gid 1000、一组 setgroups、一组 capabilities 和 --nice-name=system_server。

forkSystemServer 之前的父进程动作依次是：Zygote.initNativeState（:905，初始化 native 状态：接管 socket FD、初始化安全属性、按需卸载存储、加载性能 profile）、new ZygoteServer（:909）。fork 之后父进程只剩 ZygoteServer.runSelectLoop（:926）一件事。循环里的 fork 分两类：命令到达时 processCommand 里的 specialize fork，以及 USAP 池回填时 fillUsapPool → Zygote.forkUsap 的 USAP fork（ZygoteServer.java:648 与 :341），后者在常规路径下由池计数阈值与延迟计时器驱动；另有一条命令侧的例外——system_server 通过命令 socket 改 API deny list 状态时，ZygoteConnection.stateChangeWithUsapPoolReset（:370，调用点 :416/:452）会在状态切换后重置并再补一次池。

3. 问题背景

抓一段开机 boottrace，会看到几百条 trace 的名字是 Java 类名，一条挨一条，中间夹着 BeginPreload、PreloadClasses、PreloadResources。这些 trace 是谁打的？为什么打在每个类上？

另一个常见困惑：runSelectLoop 明明是个死循环，fork 到底在循环外还是循环里？system_server 是循环前 fork 的，那循环里又 fork 出什么？

还有一类现象：改了 preloaded-classes 之后，开机时间变了、内存变了，但 zygote 的代码一行没动。

这三个问题都指向同一段代码：ZygoteInit.main 从第一行到 runSelectLoop 之间做的事。本篇只走这一段，fork 之后 App 进程怎么长起来不在本篇。

4. 核心机制

4.1 概念与关系

四个角色：Zygote 进程本身（单一 JVM，后续所有 App 进程的母体）、预加载清单（一份类名文本文件，决定 fork 之后子进程省去重复劳动）、`ZygoteServer`（封装监听 socket 与 select 循环）、`ZygoteConnection`（一条命令连接的处理者，真正执行 fork 的地方）。

4.2 关键内容

main 的前半段是环境准备，顺序不可交换：

  1. ZygoteHooks.startZygoteNoThreadCreation()：声明本进程不再新建线程，为后面的单线程 fork 铺路。
  2. Os.setpgid(0, 0)：把自己设成进程组组长。
  3. 选 boot 计时标签：Process.is64Bit() 为真用 Zygote64Timing，否则 Zygote32Timing；随后 new TimingsTraceLog(bootTimeTag, Trace.TRACE_TAG_DALVIK)。

这里有个容易忽略的细节：main 到 runSelectLoop 这段启动路径上的 trace 都挂在 TRACE_TAG_DALVIK 下，而不是某个 zygote 专属 tag——new TimingsTraceLog(bootTimeTag, Trace.TRACE_TAG_DALVIK)（:847）指定了 tag，:142/:145/:338/:381/:389 各处 Trace.traceBegin 走的都是这条静态路径。检索 trace 时按 tag 过滤，会一并捞出全部预加载类名。范围要限定：ZygoteInit.java 内另有 zygoteInit() 的 :989 用 Trace.TRACE_TAG_ACTIVITY_MANAGER 打 "ZygoteInit"，那是 fork 之后的子进程初始化路径，不在本篇范围。

预加载分六段，每段一个 trace 区间（BeginPreload 是 preload 方法内的首段，与其余五段平级；整个预加载的外层区间另由 ZygotePreload :889-895 圈出），集中列在下面：

  • 对每一行类名，先 Trace.traceBegin(Trace.TRACE_TAG_DALVIK, line)（:338），再 Class.forName 触发类加载。

预加载完成后，main 依次往下走：traceBegin("PostZygoteInitGC")（:899）包住 gcAndFinalize()，把预加载产生的垃圾收掉；Zygote.initNativeState(isPrimaryZygote)（:905）；new ZygoteServer(isPrimaryZygote)（:909）；然后 forkSystemServer(abiList, zygoteSocketName, zygoteServer)（:912）；最后 zygoteServer.runSelectLoop(abiList)（:926）。

forkSystemServer 是硬编码参数的典型样本（String[] args = { 在 :729，收尾 }; 在 :739）：

  • --setuid=1000、--setgid=1000。
  • --setgroups= 后跟一长串 gid（:732-733）：1001 到 1010、1018、1021、1023、1024、1032、1065、3001、3002、3003、3005、3006、3007、3009、3010、3011、3012。
  • --capabilities= 后跟掩码（表达式在 :702-715），由下列常量按位或成：CAP_IPC_LOCK、CAP_KILL、CAP_NET_ADMIN、CAP_NET_BIND_SERVICE、CAP_NET_BROADCAST、CAP_NET_RAW、CAP_SYS_NICE、CAP_SYS_PTRACE、CAP_SYS_TIME、CAP_SYS_TTY_CONFIG、CAP_WAKE_ALARM、CAP_BLOCK_SUSPEND、CAP_MAC_ADMIN。
  • --nice-name=system_server、--runtime-args、--target-sdk-version=。
  • 末尾是入口类名 com.android.server.SystemServer。

这些参数走的是 zygote 自己解析的 argv，不是 shell 命令行，所以 ps 里看到的 system_server 进程名来自 --nice-name 而不是可执行文件名。这一点与 init.zygote64.rc 里 zygote 自己带的 --start-system-server 形成对照：后者是「要不要 fork」的开关，前者是「fork 出来长什么样」。两处写法不是同一个 token：rc 侧写的是带双横线的 --start-system-server，而 ZygoteInit.java:856 的解析匹配的是不带横线的 "start-system-server"。这不是「剥前缀」那么简单——app_main.cpp:266-281 是逐项识别开关（--zygote :266、--start-system-server :269、--nice-name= :273），遇到首个不以 -- 开头的参数就在 :275-277 当作类名并 break，其余带横线的参数在 :278-281 直接 --i; break; 不再消费；进入 zygote 模式后（:305 起），它只把识别结果以 String8("start-system-server")（:310，无横线）重新加入传给 AndroidRuntime 的参数表。所以 ZygoteInit 看到的是入口层重新组装的参数，字面自然不同，而 --setuid=1000、--setgroups=...、--capabilities=... 这些 fork 参数是 ZygoteInit 自己造的（:729-738），仍带横线。

循环侧的结构在 ZygoteServer.java（共 659 行）：runSelectLoop(String abiList)（:394）用 Os.poll（:486）等多路 FD 就绪——方法名里的 Select 是历史遗留，源码实际用 poll。挂进 poll 的不止命令 socket：USAP 池启用时，:440 把 mUsapPoolEventFD 也挂进 pollFDs，:446-453 再把 usapPipeFDs 里每个管道 FD 逐个挂上。所以「等命令」这个说法不完整，它同时在等池事件与池管道。

命令侧：命令 socket 可读时调 acceptCommandPeer(String abiList)（:199）拿到一个 ZygoteConnection，交给它的 processCommand（ZygoteConnection.java :120）。子进程处理完走 handleChildProc（:507），连接关闭走 closeSocket（ZygoteConnection.java :485 是方法定义，调用点见 :515）。

USAP 侧：:624 的 if (usapPoolFDRead) 是池管道的读事件，进来后按两条判据决定补池方式——:627 若 usapPoolCount < mUsapPoolSizeMin 判为 IMMEDIATE（:629，只补到下限），否则 :630 若 mUsapPoolSizeMax - usapPoolCount >= mUsapPoolRefillThreshold 就把 mUsapPoolRefillTriggerTimestamp 记成当前时刻（:632），等延迟窗到点。延迟窗的计时也在这层：:459-482 用 mUsapPoolRefillDelayMs 算出本次 poll 的 pollTimeoutMs，超时（:464-470）或 poll 返回 0（:491-498）都把动作置成 DELAYED。:637-648 是统一出口：动作不为 NONE 时取会话 socket 的裸 FD 列表，:648 调 fillUsapPool(sessionSocketRawFDs, isPriorityRefill)，返回值若不为 null 就 return command（:651）——USAP 子进程正是从这里离开循环、变成 App 进程。

fillUsapPool（:312）的补池量按类型分开算：优先级补 mUsapPoolSizeMin - usapPoolCount（:323），延迟补 mUsapPoolSizeMax - usapPoolCount（:329）；随后 :339-346 的 while (--numUsapsToSpawn >= 0) 逐个子进程调 Zygote.forkUsap(mUsapPoolSocket, sessionSocketRawFDs, isPriorityRefill)（:341）。父进程里 forkUsap 返回 null，循环继续；子进程里返回一个 Runnable，函数提前 return 把它交上去。这段代码就在 runSelectLoop 的循环体之内，不是 processCommand。

4.3 一个具体例子

拿一台 64 位设备的开机过程走一遍，只看 zygote 自己的日志：

  1. init 解析到 on zygote-start（init.rc :1091），执行段内的 start zygote（:1094），拉起 init.zygote64.rc 定义的服务，参数带 --start-system-server（该文件 :1）。
  2. zygote 进 ZygoteInit.main（:824），打 BOOT_TIME_EVENT_ELAPSED_TIME__EVENT__ZYGOTE_INIT_START。
  3. 打 LOG_BOOT_PROGRESS_PRELOAD_START，值 3020。
  4. 进 preload（:128），PreloadClasses 里逐行读 /system/etc/preloaded-classes，每行一个 trace。
  5. PreloadAppProcessHALs（:142）、PreloadGraphicsDriver（:145）依次跑完。
  6. 打 LOG_BOOT_PROGRESS_PRELOAD_END，值 3030。此刻到步骤 3 的差值就是纯预加载耗时。

步骤 3 到 6 整段都包在 if (!enableLazyPreload)（:888）里。enableLazyPreload 由 :859 的 --enable-lazy-preload 参数置真，本树 init.zygote64_32.rc:3 对 zygote_secondary 就是带这个参数的（init.rc:1095 会 start zygote_secondary）。在这条模式下，ZygotePreload 区间与 3020/3030 两个事件都不会出现，预加载被推到首次 fork 之前：ZygoteConnection.preload()（:461-462）调 ZygoteInit.lazyPreload()（:178），后者另起一个 tag 为 ZygoteInitTiming_lazy 的 TimingsTraceLog（:182）再跑同一份 preload。所以「3020 到 3030 的差值」这个测法只对主 zygote 有效。

  1. PostZygoteInitGC 区间包住 gcAndFinalize()。
  2. new ZygoteServer 建监听 socket；若 startSystemServer 为真，forkSystemServer 拉出 uid 1000 的 system_server。
  3. 自己进 runSelectLoop。此后 fork 有两条来源：App 启动时 processCommand 里的 specialize fork；USAP 池需要回填时，:648 调 fillUsapPool，:341 的 Zygote.forkUsap 在循环体内直接 fork。前一条由命令驱动；后一条常规由池计数与延迟计时器驱动，但 stateChangeWithUsapPoolReset（ZygoteConnection.java:370）在 API deny list 状态变更后会主动再补一次池，属命令侧例外。

第 6 步那个差值，是判断「开机慢在预加载还是在 system_server」的第一刀。

4.4 与相邻篇的关系

  • AND-P8-201 讲 init 与属性系统，本篇只从 on zygote-start 接住，不再展开 init 的服务模型。
  • AND-P3-201（ART 类加载与 DEX/OAT：从 ClassLoader 到 AOT 编译）讲类加载，preloadClasses 的 Class.forName 只作为调用点出现在本篇，加载器内部机制在该篇；AND-P2-401（进程模型：Zygote、fork、COW 与进程优先级 adj）提供进程侧背景。
  • USAP 与类共享的优化形态归 AND-P8-302；本篇描述的是一次性全量预加载这条基线。
  • fork 之后 App 进程如何 specialize、如何跑起 ActivityThread，归 AND-P1-101。
  • system_server 内各系统服务的启动顺序，归 AND-P8-401（SystemServer 启动序列与三阶段服务编排）；本篇的交付物只是「把 system_server 进程 fork 出来」。

7. 常见问题与误区

7.1 误区

误区一：预加载只在启动时跑一次，所以测不到。 纠正：它是启动时跑的，正常运行期间测不到。要么抓开机 trace，要么看 logcat -b events 里 3020 与 3030 两个事件的时间差。

误区二：`runSelectLoop` 只等命令，fork 全在 `processCommand` 里。 纠正：这个说法只覆盖了命令侧。循环里确有 fork，第二条来源是 USAP 池回填——fillUsapPool（ZygoteServer.java:312）在 :339-346 的 while 里调 Zygote.forkUsap（:341），调用点就在 runSelectLoop 的循环体内（:648），触发靠 :624-634 的池计数判定与 :459-498 的延迟计时器，与命令无关。命令侧那条才是 processCommand（ZygoteConnection.java :120）。system_server 那次更早——它在进循环之前就被 forkSystemServer（:912）拉走了。

误区三（看起来对其实是错的）：system_server 的进程名来自某个可执行文件。 纠正：它的名字来自传给 fork 的 --nice-name=system_server 参数，入口是 com.android.server.SystemServer 这个类。参数串在 :726-741 里硬编码，没有任何配置文件参与。

误区四：改了 `preloaded-classes` 就必须重编 zygote。 纠正：清单是运行时从 /system/etc/preloaded-classes 读的文本文件，zygote 只认路径不认内容。改动的影响体现为开机时间与内存，不体现为代码差异。

7.2 高频提问

问：为什么每个类加载要单独打一个 trace，不是整段打一个？

答：因为预加载的瓶颈通常集中在少数几个重类上，整段一个 trace 只给总时长，定位不到具体类。逐类 trace 的代价是 trace buffer 压力，但只在开机出现。

追问：那怎么从 trace 里快速找出最慢的那几个类？

答：按 TRACE_TAG_DALVIK 过滤后对同名区间的持续时间排序，取头部。名字就是清单里的类名原文，不用做映射。

问：forkSystemServer 和后续的 runSelectLoop 之间必须这个顺序吗？

答：是的。forkSystemServer（:912）之前已经完成 initNativeState（:905）与 new ZygoteServer（:909）；顺序反过来，system_server 就可能在监听 socket 尚未就绪时被拉起来。

追问：那如果 --start-system-server 没传呢？

答：forkSystemServer 那条路径不会执行，zygote 直接进 runSelectLoop，只作为纯 App 进程母体存在。是否传参由 init.zygote64.rc 决定。
