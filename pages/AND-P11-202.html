1. TL;DR

target files 是中间产物集合，OTA 包由它二次加工而来。ota_from_target_files.py 读 target files，产出全量包或增量包；包内 payload 由 update_engine 的 payload 生成器写出，update_metadata.proto 定义它的结构。设备侧两条入口：fastboot 直接写分区，sideload 把包交给 recovery 或 update_engine 消费。A/B 设备上，payload 的作用是往非活动槽写入并切槽；消费端落到 delta_performer.cc。本篇不给实测体积与耗时，凡是构建产物量级一律标「未在本树构建验证」。

3. 问题背景

一次 make dist 之后，out/dist/ 下会同时出现 *-img-*.zip、*-target_files-*.zip、*-ota-*.zip 三种文件。它们名字都带设备代号，内容却完全不同：有的能直接 fastboot flash，有的只能交给 recovery，有的必须交给 update_engine。搞错其中任意一步，现象是「刷完起不来」或「OTA 校验失败但看不出错在哪」。要理清这条链路，得先接受一个事实：镜像、target files、OTA 包是三段不同的产物，各有自己的消费方。本篇按这三段的顺序拆。

4. 核心机制

4.1 概念与关系

四个概念构成一条链：镜像（分区内容的原始字节）、target files（镜像 + 元数据的 zip 中间件）、payload（OTA 包内描述「怎么从旧状态变成新状态」的操作流）、槽位（A/B 设备上镜像落地的目标位置）。前三段在 host 侧完成，最后一段在设备侧。

图 1：三段产物的生成与消费链

  镜像(img)  ──►  target files  ──►  OTA 包(内含 payload)
   add_img_to_       ota_from_           update_engine
   target_files.py   target_files.py     或 fastboot/recovery

关键点：target files 不是终点。add_img_to_target_files.py 把 out/ 里的分区镜像重新组装进 target files zip；ota_from_target_files.py 再从 target files 出发，取两份 target files（旧、新）算差分，或只取新的做全量。镜像本身不携带差分信息，差分是 target files 阶段才算出来的。图里这条链是 A/B 路径；非 A/B 的包由 non_ab_ota.py 生成，块差分在 blockimgdiff.py，不产生 payload。

两侧共用同一份 update_metadata.proto，这是契约边界：host 侧写出的操作码，设备侧必须有对应执行器。新增操作码时两侧必须同步，否则失败形态是「install operation 未知」而不是校验和错误。

sideload 在 recovery 侧。bootable/recovery/recovery.cpp 共 912 行，长选项表里 sideload :632、sideload_auto_reboot :633，bool sideload :652 是开关。真正的实现落在 install/adb_install.cpp 共 395 行，其中 SetUsbConfig("sideload") :315 把 USB 配置切到 sideload 模式——这一步切换本身是链路上最容易出问题的点：主机侧 adb sideload 需要设备已进入该 USB 配置，否则命令挂住。

4.3 一个具体例子

假设要为一个 A/B 设备做增量 OTA，输入是旧、新两份 target files。按本树源码口径，流程是：

  1. 旧、新两份 target files 各解压一次，元信息读取分两条路：新包走 common.LoadInfoDict（ota_from_target_files.py :1327/:1329），旧包（增量源）才走 ParseInfoDict（:1360），随后 :1359 把新包结果复制成 target_info_dict；A/B 与否看 META/misc_info.txt 里的 ab_update 键（ota_from_target_files.py :1387 取该键判真假，common.py :421 同判据）；非 A/B 时走 non_ab_ota.py 的 GenerateNonAbOtaPackage（:285）与 WriteBlockIncrementalOTAPackage（:541）。
  2. 若是部分更新（partial update），GetTargetFilesZipForPartialUpdates :615 会裁剪 target files 只保留增量需要的部分。
  3. 调 payload 生成器。差分路径（旧镜像存在）由 ab_generator.cc 处理，无源镜像时走 full_update_generator.cc；文件系统后端按分区实际类型选 erofs_filesystem.cc 或 ext2_filesystem.cc。输出的操作流写进 update_metadata.proto 定义的结构。
  4. 若启用了 VABC，ModifyVABCCompressionParam :403 调整压缩参数，cow_size_estimator.cc 给出 COW 体积估算。
  5. 设备侧拿到包，delta_performer.cc 逐条执行；非活动槽由 boot_control_android.cc 共 180 行选出，动态分区由 dynamic_partition_control_android.cc 共 1494 行映射；update_attempter_android.cc 共 1789 行是 Android 侧调度外壳。

这条链上没有任何一步产出实测数值。包多大、耗时多久、COW 占多少空间，本树不做构建验证（本机 32GB 内存，V4 整包构建不可行），一律标「未在本树构建验证」。scripts/ 下的 brillo_update_payload 共 1028 行，是 bash 驱动的增量 payload 脚本（#!/bin/bash；:1004-1008 检查并转调 C++ 的 delta_generator 二进制，:338 的 python -c 只做文件截断）；paycheck.py、payload_info.py、blockdiff.py、cow_converter.py 是检查与转换工具，适合在拿到实际包之后再做量化。

7. 常见问题与误区

7.1 误区

误区一：`fastboot flash` 能刷 OTA 包。 不能。fastboot 写的是分区镜像，OTA 包是容器格式，内含 payload 和元数据。要在 fastboot 下用 OTA 包，得走 fastboot update 这类专门路径；普通 flash 只认镜像。

误区二：target files 就是镜像集合。 它是镜像加元数据的 zip。ota_from_target_files.py 需要从里面读 META/misc_info.txt（ParseInfoDict :569）才能决定怎么生成 payload。只拿镜像文件，增量更新无从算起。

误区三（看起来对其实是错的）：A/B 设备上 OTA 完成后重启就切换了。 重启只是让 bootloader 按已设置的槽启动。切槽动作在此之前由 IBootControl 完成，且新槽启动成功后必须调用 markBootSuccessful()（声明在 :108，其文档注释在 :104）；注释明确只有当前 slot 可标记成功。漏掉这一步，下次重启仍可能回到旧槽。

误区四：增量包的体积只取决于新旧镜像差多少。 VABC 场景下还要算 COW 体积；cow_size_estimator.cc 的存在说明这部分在 host 侧就要估出来，估不准的失败形态是设备侧合并中途空间不足。

7.2 高频提问

问：全量包和增量包用的是同一套 payload 工具吗？ 答：A/B 路径下是。generate_delta_main.cc 是共同入口，全量走 full_update_generator.cc，差分（有源镜像）走 ab_generator.cc，写出的都是 update_metadata.proto 定义的结构。非 A/B 是另一条路：包由 non_ab_ota.py 生成（GenerateNonAbOtaPackage :285、WriteBlockIncrementalOTAPackage :541），块差分算法落在 blockimgdiff.py（1632 行），不走 payload 这套工具。 追问：那设备侧要区分吗？ 答：设备侧不分。delta_performer.cc 只认操作流，不关心它是全量还是差分算出来的。

问：sideload 和 recovery 刷包是什么关系？ 答：sideload 是 recovery 的一种输入通道。recovery.cpp 的选项表里 sideload :632 是个开关，打开后 adb_install.cpp 用 SetUsbConfig("sideload") :315 切 USB 配置，主机侧再 adb sideload 推包。 追问：切不过去会怎样？ 答：主机命令会挂住，因为设备 USB 配置没到位。排查看 §7.3 第二行。
