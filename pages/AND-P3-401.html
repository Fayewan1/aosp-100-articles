1. TL;DR

init 是 native 服务的父进程：critical 服务在崩溃窗口内反复退出时，init 会主动重启整机而不是单服务。ashmem 与 memfd 在用户态被统一到 ashmem_create_region 一个入口，具体走哪条路由 use_memfd() 决定。memfd 路径用 __NR_memfd_create 加 F_ADD_SEALS 封住尺寸，ashmem 路径走 ASHMEM_SET_NAME/ASHMEM_SET_SIZE 两个 ioctl。libbinder 的 MemoryHeapBase 是这两条路径的第一个大用户：FORCE_MEMFD 打开就换 memfd，否则回退 ashmem。

3. 问题背景

你写了个 native daemon，挂在 rc 里 class core 启动。某次它因为一个 nullptr 崩了，你预期的行为是「init 把它拉起来，日志里留一行」；实际结果是设备直接重启，甚至进了 bootloader。另一头，你把一块 buffer 换成 memfd 传给别的进程，对方拿到的 fd 尺寸不可写，ftruncate 报错——因为创建方加过 seal。这两类问题都不是「写错代码」，而是因为你没弄清 init 的崩溃策略和共享内存的创建契约。

4. 核心机制

4.1 概念与关系

三个概念串起本篇：init 是服务守护者，ashmem 是传统匿名共享内存设备，memfd 是内核提供的无路径匿名文件。用户态通过 ashmem_create_region 统一入口，按 use_memfd() 分派到两套实现；MemoryHeapBase 再在其上做 binder 侧封装。

  |                -> ftruncate + F_ADD_SEALS
  `-- else        __ashmem_create_region -> open(/dev/ashmem)

4.2 关键内容

守护侧的关键在 flags 与策略分支。SVC_CRITICAL = 0x020（system/core/init/service.h）标记关键服务，注释写明持续崩溃会重启进 bootloader。service.cpp 的崩溃处理逻辑：在 fatal_crash_window_ 内统计退出次数，超过 4 次或系统尚未开机完成，就调用 SetFatalRebootTarget 并 LOG(FATAL) << "critical process '<name>' exited 4 times"。孤儿进程由 ReapAnyOutstandingChildren（system/core/init/init.cpp）在主循环中回收，再按每个服务的选项决定后续动作：oneshot_on/oneshot_off 控制一次性语义，restart 走 DoControlRestart。

__use_memfd（system/core/libcutils/ashmem-dev.cpp:58-106）是一条覆盖开关加三个并列条件的判定：先查 sys.use_memfd 属性，为 true 直接走 memfd（优先级最高，:61-66）；否则要求 memfd_class sepolicy capability、设备 vendor API level ≥ 202604、应用 target SDK ≥ 37 三项同时满足才走 memfd，任一不满足都回退 ashmem（:69-98）。ashmem 侧设备路径带 boot_id 后缀（/dev/ashmem 加 /proc/sys/kernel/random/boot_id 内容），用于隔离重启前后的 region。memfd 侧调用形式为 syscall(__NR_memfd_create, name, MFD_CLOEXEC | MFD_ALLOW_SEALING)，随后 ftruncate 定尺寸，再 F_ADD_SEALS(F_SEAL_GROW | F_SEAL_SHRINK) 封死增长与收缩。ashmem 侧常量 ASHMEM_SET_NAME/ASHMEM_SET_SIZE 定义在 bionic/libc/kernel/uapi/linux/ashmem.h。

bionic 对外声明的 memfd_create 在 bionic/libc/include/sys/mman.h，API 30 引入，也就是说直接用 libc 接口而非 syscall 时，低 API 目标要自己兜底。

4.3 一个具体例子

以 servicemanager 为例讲一圈。它的 rc 声明了 service servicemanager /system/bin/servicemanager、class core animation、user system、group system readproc、critical、shutdown critical、file /dev/kmsg w、onrestart restart audioserver、task_profiles ProcessCapacityHigh（frameworks/native/cmds/servicemanager/servicemanager.rc）。开机时 init.rc 的 on init 块（system/core/rootdir/init.rc:116）在 # Start essential services. 注释后依次 start servicemanager、start hwservicemanager、start vndservicemanager（同文件 :464-466）——这是块内的裸 start 命令，不是 class 触发。

因为它带 critical，如果它在窗口内连续退出 4 次，init 不会只重启它，而是设置 fatal reboot target 后 LOG(FATAL)。onrestart 里的 audioserver 只有在正常重启路径上才有意义——整机重启时这行不产生影响。

7. 常见问题与误区

7.1 误区

错误认知：带 critical 的服务崩了会被更频繁地拉起来，可用性更高。 纠正：正相反。它在崩溃窗口内超过 4 次就触发 LOG(FATAL) 与 fatal reboot target，代价是整机。critical 表达的是「它不可用整机就没意义」，不是「它更需要被守护」。

错误认知：onrestart restart audioserver 意味着 servicemanager 挂了 audioserver 一定跟着重启。 纠正：这行只在 init 走「重启该服务」的路径时生效；critical 服务触发整机重启时，该 rc 选项不参与决策。

错误认知：ashmem_create_region 一定创建 ashmem 设备节点。 纠正：它只是统一入口，实际分派看 use_memfd()。调用方最终拿到的可能是 /memfd: 开头的 fd，用 is_memfd_fd 才能判定。

错误认知：memfd 创建后还能 ftruncate 扩大尺寸。 纠正：创建路径加了 F_SEAL_GROW，扩大被拒；同理 F_SEAL_SHRINK 禁止收缩。尺寸必须在 seal 前一次定好。

7.2 高频提问

问：我的 native 服务老是让设备重启，怎么定位是谁触发的？ 答：先搜 logcat 里 critical process 与 exited 4 times 字样，再看该服务的 rc 里是否有 critical。 追问：去掉 critical 就正常了吗？ 答：行为从「整机重启」变成「单服务反复重启」，问题本身仍在，得修崩溃点。

问：新代码该直接用 memfd_create 还是 ashmem_create_region？ 答：跟随现有平台的封装更稳，ashmem_create_region 会替你处理分派，还与 libbinder 行为一致。 追问：直接调 libc 的 memfd_create 有什么坑？ 答：声明是 API 30 引入的，低 target SDK 的应用可能没有该符号，需要自己兜底。

  • 数量级与边界值：
    • critical 服务崩溃阈值 4 次，口径为源码日志字面量 exited 4 times（源码常量）。
    • SVC_CRITICAL 标志值 0x020，口径为 service.h 源码常量。
    • memfd_create 对外可用起点 API 30，口径为 sys/mman.h 声明处注释（官方头文件）。
    • F_ADD_SEALS 组合为 F_SEAL_GROW | F_SEAL_SHRINK，不含 F_SEAL_WRITE（源码常量）；具体 seal 组合的上层影响暂无实测，列为待补。
