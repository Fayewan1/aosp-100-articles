1. TL;DR

Android 的版本号不再靠「半年一个大版本」的手工排期，而是由一套 release config 旗标派生出来的。release_configs/trunk_staging.textproto 声明配置类型，flag_values/trunk_staging/ 下的旗标给出 LAST_STABLE、CODENAME、SDK 三个值，version_util.mk 再把它们派生成 PLATFORM_VERSION 等变量。trunk_staging 三个旗标的实测值是 17、Baklava、37；同一棵树上别名 aosp_current 指向的 cp2a 已定型，派生出的是数字 17。构建号前缀与版本一一对应：ap3a → 15，bp2a → 16，cp2a → 17。codename 屡经试改与回滚、SDK 定型后未再变动，这个时间差在本树可复现，并非笔误。

3. 问题背景

你看到构建号 CP2A.260605.016，想知道它对应哪个 Android 版本。翻 build_id.mk 只有一串数字，翻文档说是「Android 17」，但 PLATFORM_VERSION_CODENAME 里写着 Baklava，SDK 又写着 37。三个数字互不相同，谁是版本、谁是别名，没有一处集中说明。更麻烦的是 release_configs 下躺着 ap4a、bp4a、cp1a、mainline_2026_01 等一长串配置，看不出哪个是「当前」。这篇把这些散落的符号拉成一条链。

4. 核心机制

4.1 概念与关系

三个关键概念：release config（一套命名的版本参数集合）、旗标（flag，配置里的单个键值）、派生变量（构建系统读旗标后算出的变量）。

图 1：发布配置到派生变量的传导

release config  →  旗标键值  →  派生变量
trunk_staging      LAST_STABLE=17    PLATFORM_VERSION
                   CODENAME=Baklava  PLATFORM_VERSION_CODENAME
                   SDK_VERSION=37    PLATFORM_VERSION_SDK_VERSION

（长代码块，建议到公众号/头条侧按截图策略处理）

4.2 关键内容

build/release/release_configs/trunk_staging.textproto 是配置的入口，内容为 name "trunk_staging"、release_config_type RELEASE_CONFIG，并把 aconfig 值集指向 aconfig_value_set-platform_build_release-trunk_staging。取值按旗标拆成独立 textproto 文件。

build/make/core/version_util.mk 负责派生：当 codename 为 REL 时 PLATFORM_VERSION 取 PLATFORM_VERSION_LAST_STABLE，否则取 codename（约 148–154 行）。即开发中显示甜点名、已发布显示数字。

同族旗标集中如下：

名称含义出处
RELEASE_PLATFORM_VERSION_LAST_STABLE最近一个已定型的主版本号flag_values/trunk_staging/
RELEASE_PLATFORM_VERSION_CODENAME当前开发分支的甜点名flag_values/trunk_staging/
RELEASE_PLATFORM_SDK_VERSION该分支的 API 级别flag_values/trunk_staging/
RELEASE_PLATFORM_VERSION_KNOWN_CODENAMES历史 codename 清单flag_values/trunk_staging/

RELEASE_PLATFORM_VERSION_KNOWN_CODENAMES 的末位是 Baklava，前面依次是 UpsideDownCake、VanillaIceCream。想改动 codename 清单只能经这个 RELEASE_* 旗标传入，直接设置 PLATFORM_VERSION_KNOWN_CODENAMES 会报 error。

4.3 一个具体例子

读 build/release/flag_values/trunk_staging/ 三个文件，得到 LAST_STABLE="17"、CODENAME="Baklava"、SDK="37"。codename 不是 REL，PLATFORM_VERSION 取 Baklava。构建号由 build/make/core/build_id.mk 给出：BUILD_ID=CP2A.260605.016，前缀 cp2a 对应的旗标是 37 / 17 / REL，与 ap3a（35 / 15 / REL）、bp2a（36 / 16 / REL）同族。同一棵树上有两套取值：cp2a 已定型，PLATFORM_VERSION 显示数字 17；trunk_staging 仍在开发，显示 Baklava。build/release/release_config_map.textproto 的别名 aosp_current 本树指向 cp2a，而 lunch 不给 TARGET_RELEASE 时默认取 trunk_staging（build/make/envsetup.sh 用法说明）——故「本树版本」须带配置类型。

7. 常见问题与误区

7.1 误区

误区一：SDK 版本号就是平台主版本号。 本树里两者差 20：SDK 是 37，主版本是 17。两者由不同旗标控制，各走各的节奏。

误区二：codename 一变，SDK 就跟着跳。 事实相反。trunk_staging 的 codename 当前仍是 2024-10-22 设定的 Baklava，但期间两度试改又回滚：2025-12-08 改成 DEV、次日回滚，2026-03-04 改成 CinnamonBun、03-10 再回滚（git log 可证）。同期 SDK 在 2026-03-04 推到 37 后没再动过。codename 试改与回滚不带动 SDK。

误区三（看起来对其实是错的）：构建号前缀只是流水号，跟版本无关。 前缀是版本段。ap3a 对应 SDK 35 / LAST_STABLE 15，bp2a 对应 36 / 16，cp2a 对应 37 / 17，首字母与数字段都在编码版本信息。

7.2 高频提问

问：PLATFORM_VERSION 到底显示 17 还是 Baklava？ 答：看 codename 是否为 REL。是则取 PLATFORM_VERSION_LAST_STABLE，否则取 codename（约 148–154 行）。 追问：开发阶段用户看到的版本是什么？ 答：甜点名，本树是 Baklava；定型后翻成 REL，对外变回数字 17。

问：为什么 release_configs 下有这么多配置？ 答：目录里另有 ap2a/ap3a/ap4a/bp1a–bp4a/cp1a/cp2a/eng/userdebug/mainline_2026_01–04 等，是历史与变体并存。 追问：怎么确认本树用的是哪个配置？ 答：build/release/release_config_map.textproto 的别名 aosp_current 本树指向 cp2a；它与 manifest 的 android17-release 是两套坐标：前者选 release config，后者选同步分支。
