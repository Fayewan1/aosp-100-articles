1. TL;DR

APEX 不是普通文件，它的信任根挂在 vbmeta 上，不挂在 APK 签名块上。apexd 处理一个 APEX 时是读与验两条并行的线：ApexFile::Open（apex_file.cpp:80）一打开就把 apex_manifest.pb 提取并解析出来（:130 找条目、:158 解析），顺带取出内嵌公钥；校验则是另一条链——GetAvbFooter（:197）→ VerifyVbMeta（:263，内部调 VerifyVbMetaSignature:234，并在 :288 与传入公钥比对）→ VerifyApexVerity（:344），它是激活的前置门，不是「读 manifest 的前置门」。所以「文件在我手上就能被信任」不成立：能被信任的前提是验签这条链走得通，且包内公钥与预置副本一致。发布 APEX 就是发布一个可被系统独立验签的模块单元。

3. 问题背景

有人在设备上 adb push 了一个 APEX 到 /data/apex/active，重启后 apexd 拒绝激活，日志里是一串 AVB 相关的失败。他第一反应是「我没改文件，为什么不可信」。第二反应是「APK 签名能过，为什么这里不行」。这两问指向同一个结构：APEX 的可信性不来自文件自身携带的签名，而来自它与 vbmeta 的绑定关系，以及内嵌公钥能否打通这条绑定。本篇把这条链拆开。

4. 核心机制

4.1 概念与关系

五个概念：APEX 文件、AVB footer、vbmeta、apex_pubkey、apex_manifest.pb。

  • APEX 文件：一个打包单元，尾部挂 AVB footer 指向 vbmeta。
  • vbmeta：携带 hashtree 描述符与签名，是校验的数据源兼签名载体。
  • apex_pubkey：APEX 内嵌的公钥文件，用来验 vbmeta 的签名。
  • apex_manifest.pb：protobuf 形式的模块清单，ApexFile::Open 一打开就连同内嵌公钥一起读出解析，早于验签。

关系要分两条线看：读取线是 Open 一发生就解析 manifest（并取出内嵌公钥）；校验线是 footer 定位 vbmeta → 验 vbmeta 签名并与公钥比对 → 用 vbmeta 描述符验整包数据。两条线在「激活」这一步汇合——校验不过就不激活，但 manifest 早就被读出来了。

图 1：APEX 校验的信任链与读取顺序

APEX file
  |-- AVB footer        -> vbmeta 偏移
  |-- vbmeta            -> hashtree 描述符 + 签名
  |-- apex_pubkey       -> 验 vbmeta 签名
  `-- apex_manifest.pb  -> Open 即读，与验签并行

4.2 关键内容

apexd 的入口在 system/apex/apexd/apexd.cpp，全文件 3848 行；单文件校验逻辑收在 system/apex/apexd/apex_file.cpp，共 465 行。校验函数不是一锅炖，而是分层递进的四步：GetAvbFooter、VerifyVbMetaSignature、VerifyVbMeta、VerifyApexVerity。上层 VerifyApexVerity 依次调用下层，形成一条链：先取 footer（:358 调 GetAvbFooter），再验 vbmeta（:364 调 VerifyVbMeta，其内部 :283 调 VerifyVbMetaSignature），最后进入 verity 数据组装。函数级归属要分清：VerifyVbMetaSignature（:234）的签名是 (apex, data, length)，不接收公钥入参；与公钥的比对由 VerifyVbMeta 在 :288 用 CompareKeys 完成（不符即在 :290 报 public key doesn't match the pre-installed one）。这意味着「验签」和「验数据」是两个动作，签不过就不进入数据校验。

同族常量集中成一表：

名称含义出处

清单的解析时机值得单独说，而且和直觉相反：ApexFile::Open（apex_file.cpp:80）里 :130 先 FindEntry 找到 kManifestFilenamePb、:139-145 把它读到内存、:158 ParseManifest 解析——全程没有任何 verity 前置条件，紧随其后的 :146-156 取出内嵌公钥。验签与验数据是后面另一条链（GetAvbFooter:197 → VerifyVbMeta:263 → VerifyApexVerity:344）的事。代码里 manifest 被消费得比验签还早：apexd.cpp:283 刚 Open 完，:287 就用 GetManifest().name() 做删除决策。

那「改 manifest 骗过系统」靠什么挡？靠两处比对，都不是「不读 manifest」：其一，manifest 是包内数据的一部分，改了它 verity 的整包摘要就对不上；其二，挂载之后还有一道 VerifyMountedImage（apexd.cpp:328）——:333 读挂载镜像内的 apex_manifest.pb，:337 用 MessageDifferencer::Equals 与包内 manifest 比对，不一致就在 :339 报 Manifest inside filesystem does not match manifest outside it（调用点 apexd.cpp:599）。所以防篡改落在「验整包数据」与「挂载后再比一次」，而不是读取顺序。

对外接口由 AIDL 定义，system/apex/apexd/aidl/android/apex/IApexService.aidl 共 108 行。它是客户端（如 installd、系统组件）与 apexd 之间的契约面：谁能请求提交、激活、回滚，都从这 108 行的方法签名进入，而不是从文件系统直接操作。

信任的根在 vbmeta。APEX 镜像尾挂 AVB footer，签名验证由 vbmeta 的公钥完成。这与 APK 的签名块机制是两套独立通道——本篇不断言两者实现共享。因此 APEX 的信任模型可以概括为：文件不自证，绑定才自证。

rollback 保护在 TEE 侧由 Trusty 的 AVB 应用（trusty/user/app/avb）承担，本篇只按接口口径提及其存在，不展开内部实现。

4.3 一个具体例子

取本树里最普通的模块：packages/modules/adb/apex/apex_manifest.json。这是构建期的源清单；按本卷分工，构建期 json→pb 的转换与打包产出归 AND-P5-101／P11，本篇只把它当作「包内 manifest 的来源」提及，不把它当本篇可核验事实。

走一遍：设备侧拿到 APEX 文件 → ApexFile::Open 先解析出 apex_manifest.pb 与内嵌 apex_pubkey（:130/:158、:146-156）→ 校验链 GetAvbFooter(:197) 取 footer → VerifyVbMeta(:263) 读 vbmeta、VerifyVbMetaSignature(:234) 验签名、并在 :288 `CompareKeys` 与传入的公钥比对 → VerifyApexVerity(:344) 按 hashtree 描述符验整包数据 → 激活路径上还有 VerifyPackageBoot（apexd.cpp:834）：:841 先 CheckBundledPublicKeyMatchesPreinstalled（定义 :1142，:1147-1152 与预置副本比对），:843 才调 VerifyApexVerity → 挂载后再由 VerifyMountedImage（:328/:337）比对一次 manifest。

任何一步不通过，激活请求就被拒。这解释了第 3 节那个现象：文件没被改也可能失败——公钥与预置副本不一致（:1147-1152），或 footer/vbmeta 与公钥不配对（:288），第一步就过不了。注意失败在这里的表现是「不激活」，而不是「没读 manifest」：manifest 早就被读出来并参与过若干决策了。

7. 常见问题与误区

7.1 误区

误区一：APEX 用的是 APK 签名机制。 不是。APEX 的信任来自 vbmeta，签名验证由公钥完成，与 APK 签名块是两套独立通道。两者有无实现共享，本篇不断言。

误区二：把 APEX 文件拷进 `/data/apex/active` 就能生效。 看起来对，其实是错的。文件能不能生效取决于验签是否通过，与它放在哪个目录无关；目录只是 apexd 的扫描输入来源之一。

误区三：`apex_pubkey` 是信任根。 不是。它是被用来验 vbmeta 签名的那把公钥，本身要过两道比对：一是与系统预置副本一致（apexd.cpp:1142 CheckBundledPublicKeyMatchesPreinstalled，:1147-1152 逐字节比，不符即 public key doesn't match the pre-installed one），二是在 VerifyVbMeta 内与「签署 vbmeta 的那把公钥」比对（apex_file.cpp:288 CompareKeys）。两处任一不符即失败——所以它不是自证的信任根，而是被比对的对象。

误区四：manifest 解析和校验有先后、靠顺序挡住篡改。 不准确。manifest 在 ApexFile::Open 里就被解析了（:130/:158），比验签还早，apexd 也在验签前就用过它（apexd.cpp:283/:287）。真正挡住「改 manifest」的是另外两处：改了包内数据则 verity 摘要不符；挂载后 VerifyMountedImage（:328/:337/:339）再比对一次包内与镜像内的 manifest。把防篡改归给「读取顺序」会让人误判哪些环节能省。

7.2 高频提问

问：校验失败究竟是哪一步？ 答：按 GetAvbFooter → VerifyVbMeta → VerifyVbMetaSignature → verity 数据组装的顺序定位，先断在哪一步。 追问：断开点能区分「公钥不对」和「数据被改」吗？ 答：能。签名步失败指向公钥/签名层；签名过而数据步失败指向内容层。

问：为什么本树有 77 个 apex_manifest.json？ 答：packages/modules 与 system 下（不含测试数据）共 77 个，含 adb、AppSearch、ExtServices、IPsec、Permission、StatsD、ThreadNetwork、Uwb、Wifi、vndk 等模块，模块化以 APEX 为单元铺开。 追问：数量说明什么？ 答：说明 APEX 是 mainline 的默认交付粒度，单个模块的验签失败只影响该模块的激活，不牵动整包。
