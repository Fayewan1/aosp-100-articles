1. TL;DR

Android 上的 Java 代码常常被编译两次：先跑解释器与 JIT，把热点攒成 profile，再按 profile 做一次更"懂代码"的编译。JIT 的热度门槛默认被顶到 0xffff，也就是默认几乎不因为计数就触发优化编译——例外在 arm64：fast baseline 编译器生效时初始热度阈值为 4（jit.cc:1272-1280）。ProfileSaver::ProcessProfilingInfo 负责把内存里的采样落到 primary.prof 这类文件，强制保存时恒写。profile 文件头是 {'p','r','o','\0'} 加版本 015（boot image 用 016）。基线 profile（baseline profile）就是随 APK 分发的参考 profile，ART 侧读它的路径与本地 profile 完全相同。

3. 问题背景

你可能见过这种日志：应用冷启动慢，装上跑几天反而快了；或者 pm compile 出来的包，换台设备表现完全不同。有人于是拆 APK，发现里面躺着一个 baseline.prof，但不知道它和后端 /data/misc/profiles/ 下的文件是什么关系。更常见的困惑是：既然有 AOT，为什么还要 JIT？如果 JIT 已经编译过了，为什么还要再编译一次？这三个问题的答案都在同一个链条上：热度计数 → profile 落盘 → 按 profile 重编。

4. 核心机制

4.1 概念与关系

四个概念串成一条链。热度计数（hotness counter） 是入口点上的热度计数值，计数耗尽即视为方法变热。JIT 消费计数，把方法编成机器码放进 JIT code cache。profile 是运行中记录下来的"哪些方法热、哪些类被加载过"的采样集，由 ProfileSaver 落盘。编译档位（compiler filter） 决定第二次编译要用多少 profile 信息。

图 1：热度、JIT、profile 与重编的关系

  解释执行/JIT 计数
        |
        v
  热度耗尽（ResetCounter）
        |
        v
   Jit::CompileMethod --(入队)--> JIT 编译
        |
        v
   ProfileSaver::ProcessProfilingInfo
        |
        v
   primary.prof 等文件 --> profman/dex2oat 按档位重编

关键点：JIT 与 profile 采集不是同一件事。JIT 关心"现在要不要编"，profile 关心"以后怎么编得更好"。

4.2 关键内容

阈值默认值。 jit_options.cc 里三个常量：kJitDefaultWarmupThreshold = 0xffff、kJitDefaultOptimizeThreshold = 0xffff、kJitMaxThreshold 为 uint16 最大值。两个默认值都顶在上限附近，意味着默认配置下计数几乎不会自己触发优化编译——但 arm64 上 fast baseline 编译器生效（且非 debuggable）时例外：Jit::GetInitialHotnessThreshold（jit.cc:1268-1276）此时直接返回 kFastThreshold = 4。想改就传运行时选项 JITWarmupThreshold / JITOptimizeThreshold，声明在 runtime_options.def。

阈值在哪里被读。 热度计数在入口点递减，耗尽即视为热，Jit::CompileMethod（jit.h:207）把方法交给编译队列；初始阈值由 Jit::GetInitialHotnessThreshold（jit.cc:1268）给出。阈值的打印不在 Jit 构造函数里，而在 Jit::CreateJit 流程（jit.cc:115-120），走 VLOG(jit)，需要 -verbose:jit 才会出现在 logcat。

落盘细节。 ProfileSaver::ProcessProfilingInfo 是落盘入口。强制保存时恒写，不做"没变化就跳过"的优化，artd 依赖这个保证。写列表里 primary.prof 被放在末位，这个顺序本身是有意为之的（末位意味着前面若干项先写）。

文件格式。 profile_compilation_info.cc 定义 magic 为 {'p','r','o','\0'}，常规版本号 015，boot image 专用版本 016。所以拿到一个 .prof 先看头四个字节和紧随的版本串，就能判断是不是当前格式、是不是 boot image 用的。

profman。 这是 profile 的离线工具，--dump-only 只读不写，--reference-profile-file= 指定参考 profile。核对两个 .prof 的差异、把基线 profile 和本地 profile 对账，都走它。

档位与 profile 的耦合。 art/libartbase/base/compiler_filter.h 里 kSpeedProfile / kEverythingProfile / kSpaceProfile 都属于"依赖 profile"的档位，DependsOnProfile 给出判定。这就是"编译两次"的根因：第二次编译的质量取决于第一次跑出来的 profile 质量；profile 不匹配，档位退化成接近无 profile 的编译。

基线 profile。 baseline profile 是随 APK 分发的参考 profile，ART 侧消费路径与本地 profile 一样，走 profman/dex2oat 的 --profile-file 一族参数。它解决的问题是"首次安装时设备上还没有本地 profile"，让第二次编译一开始就有依据。

shell 入口。 ArtShellCommand 处理 compile 子命令并调用 setCompilerFilter；原来 pm force-dex-opt 的位置已给出废弃提示，改用 pm compile。手工验证档位与 profile 配合时，入口在这里。

4.3 一个具体例子

假设开发者在调试设备上确认 JIT 到底有没有按阈值编译。做法：查 jit_options.cc 拿到 0xffff，知道默认阈值接近 uint16 上限（arm64 fast 路径除外，初始阈值为 4）；在 jit.h:207 确认 Jit::CompileMethod 是编译入口，初始阈值看 Jit::GetInitialHotnessThreshold（jit.cc:1268）；运行时打印的值要走 -verbose:jit 才看得到。

接着查 profile：ProfileSaver::ProcessProfilingInfo 是落盘入口，强制保存恒写，primary.prof 在写列表末位。想让 profile 立即反映当前运行状态，就走强制保存路径，别指望常规保存会因为你"感觉没变"而触发。

最后核对文件：读 profile_compilation_info.cc 里的 magic {'p','r','o','\0'} 和版本 015，确认手上的 .prof 是常规 profile 而不是 boot image 的 016。再用 profman --dump-only 看内容，需要对比参考 profile 就加 --reference-profile-file=。

7. 常见问题与误区

7.1 误区

"JIT 阈值默认很小，跑几次就编译"。 事实相反，kJitDefaultWarmupThreshold 与 kJitDefaultOptimizeThreshold 都是 0xffff，接近 uint16 上限。不显式传 JITWarmupThreshold/JITOptimizeThreshold 时，计数本身几乎不会成为触发条件；唯一的例外是 arm64 上 fast baseline 编译器生效的场景，此时初始热度阈值为 4（jit.cc:1272-1280）。

"有 AOT 了就不需要 profile"。 kSpeedProfile/kEverythingProfile/kSpaceProfile 都依赖 profile，DependsOnProfile 明确给出判定。没有 profile，这些档位拿不到优化依据。

"profile 只在进程正常退出时才写"。 强制保存路径恒写，不看"有没有变化"，artd 正是依赖这条保证。看起来"没变化就不该写"的直觉在这里是错的。

"`baseline.prof` 和本地 profile 是两套机制"。 ART 侧消费路径相同，都走 profman/dex2oat 的 --profile-file 一族参数；区别只在来源和分发方式。

7.2 高频提问

问：为什么默认阈值要设到 0xffff？ 答：这是 ART 的默认配置选择，清单只给常量值，不给设计动机。 追问：那实际设备的有效阈值怎么确认？ 答：开 -verbose:jit 后看 Jit::CreateJit 里 VLOG(jit) 打印的 warmup/optimize 值，确认运行时选项有没有覆盖默认；fast 路径下注意初始阈值可能只有 4。

问：primary.prof 为什么排写列表末位？ 答：清单给的是顺序事实，primary.prof 位于写列表末位；顺序含义本篇不断言。 追问：想看当前 profile 内容怎么读？ 答：profman --dump-only 只读打印。需要和参考 profile 对比就加 --reference-profile-file=。

问：pm force-dex-opt 还能用吗？ 答：该入口已给出废弃提示，改用 pm compile。 追问：pm compile 背后是什么？ 答：ArtShellCommand 处理 compile 子命令并调用 setCompilerFilter。
