1. TL;DR

Native 侧的 Binder 由 libbinder 提供，核心是一对「本地实现 / 远程代理」：服务端继承 BBinder，客户端持 BpBinder。抽象接口由 IInterface 派生，DECLARE_META_INTERFACE 生成的 asInterface 决定返回本地实现还是代理。AIDL 生成代码在 Native 侧把这层对应固化为 BnInterface/BpInterface 模板。Java 的 Binder/BinderProxy 通过 android_util_Binder.cpp 的注册落到同一个 ProcessState/IPCThreadState，所以 Java 服务与 Native 服务共享同一套线程池与 mmap 区。跨进程传递时，强引用对象在 Parcel 中落为 flat_binder_object，按 BINDER_TYPE_BINDER 与 BINDER_TYPE_HANDLE 区分本地对象与远程句柄。

3. 问题背景

写一个 Native daemon，注册成系统服务，Java 侧 ServiceManager.getService() 能拿到代理并调通；但想反过来在 Java 里实现一个 Binder 子类、让 Native 客户端调，就会卡住：不知道该让 Native 侧持有什么类型，也不知道 asInterface 什么时候返回本地对象、什么时候返回代理。更常见的困惑是：AIDL 生成的 .cpp 里出现 BnFoo、BpFoo，而手写代码里只有 BBinder、BpBinder，这两组名字是什么关系，是否能互相替代。本篇把这些名字放回 libbinder 的类层次里逐一对应。

4. 核心机制

4.1 概念与关系

五个概念构成两条继承线与一个粘合点：

  • IBinder：事务能力的最小抽象，只关心 transact 一类操作。
  • BBinder：IBinder 的本地实现基类，服务端对象从这里派生。
  • BpBinder：IBinder 的远程代理，持有一个 handle，把调用转成对驱动的写入。
  • IInterface：业务接口抽象，提供 asBinder() 与 onAsBinder()（IInterface.h:28-37）；本地/代理的判定入口 queryLocalInterface 是 IBinder 上的虚函数，BnInterface 在 :72 重写它。
  • BnInterface/BpInterface：模板，把 IInterface 的某个具体接口与 BBinder/BpBinder 粘在一起。

图 1：Native 侧类族的两条继承线与粘合点

        IInterface            IBinder
            |                    |
     IFoo (业务接口)        +-----+------+
            |              |            |
   +--------+--------+   BBinder     BpBinder
   |                 |     |            |
 BnInterface<IFoo> BpInterface<IFoo>  (本地实现)  (远程代理)
   |                 |
 BnFoo             BpFoo     <- AIDL 生成

关键在 asInterface。判定入口 queryLocalInterface 是 IBinder 上的虚函数，服务端模板 BnInterface 在 frameworks/native/libs/binder/include/binder/IInterface.h:72 重写它；DECLARE_META_INTERFACE（同文件 :94）为每个接口生成 asInterface 声明；asInterface 的实现（:128-137）先调 queryLocalInterface(descriptor)，命中就返回本进程内的实现对象，否则回落构造 BpInterface 代理。这一条分支就是「同进程直调、跨进程走代理」在 Native 侧的全部开关。

4.2 关键内容

进程级上下文只有一份。 ProcessState 管 mmap 与线程池，IPCThreadState 管每线程的收发缓冲。BINDER_VM_SIZE = (1 * 1024 * 1024) - sysconf(_SC_PAGE_SIZE) * 2（frameworks/native/libs/binder/ProcessState.cpp:48），线程池上限 DEFAULT_MAX_BINDER_THREADS = 15（同文件 :49）。initWithDriver（:111）里执行 mmap(nullptr, BINDER_VM_SIZE, PROT_READ, MAP_PRIVATE | MAP_NORESERVE, ...)（:625）。线程进入循环的入口是 IPCThreadState::joinThreadPool（frameworks/native/libs/binder/IPCThreadState.cpp:841）。

强引用对象的线上形状。 Parcel 写入 Binder 对象时落为 flat_binder_object，本地对象标 BINDER_TYPE_BINDER，远程代理标 BINDER_TYPE_HANDLE。写侧两分支在 frameworks/native/libs/binder/Parcel.cpp 的 finishFlattenBinder：proxy 走 :303 的 BINDER_TYPE_HANDLE，local 走 :328 的 BINDER_TYPE_BINDER（另 :333 有一处兜底）；读侧对应 acquire_object 的两个 case（:160/:166）。这也是「同一个接口在不同进程里表现为不同类型」的物理原因：接收方看到 handle 就只能造代理。

服务注册表。 IServiceManager 的三个入口 getService/checkService/addService（frameworks/native/libs/binder/IServiceManager.cpp:97-99），客户端拿单例走 defaultServiceManager（同文件 :333）。服务端那一侧是 ServiceManager（frameworks/native/cmds/servicemanager/ServiceManager.cpp）与 main（main.cpp），访问控制放在 access.cpp。

Java 与 Native 的互转点。 ibinderForJavaObject（frameworks/base/core/jni/android_util_Binder.cpp:1051）把 Java 对象转成 Native 的 IBinder；反方向的调用路径是 android_os_BinderProxy_transact（同文件 :1644），它在 :1881 处经 transactNative 注册进 JNI 表。注册这件事本身就是证据：Java 的 Binder/BinderProxy 最终都落到同一 ProcessState/IPCThreadState，没有第二套 Native 栈。

AIDL 生成代码的父类。 服务端 BnFoo 继承 BnInterface<IFoo>，客户端 BpFoo 继承 BpInterface<IFoo>；BnInterface 模板落到 BBinder，BpInterface 则继承 BpRefBase（IInterface.h:82-84），由其 mRemote（Binder.h:231-248）持有 BpBinder——是组合，不是继承。手写 HAL/daemon 时若不跑 AIDL，就直接继承 BBinder 并自己实现 onTransact，语义等价，只是少了 asInterface 的样板。

4.3 一个具体例子

假设 Native 侧实现 IFoo，注册为系统服务。

服务端：BnFoo 对象由 addService 提交，defaultServiceManager（IServiceManager.cpp:333）返回 IServiceManager 代理，调用落到 servicemanager 进程。注册过程中该对象被写成 BINDER_TYPE_BINDER。

客户端 A（同进程内拿引用）：asInterface 走 queryLocalInterface(descriptor)（判定入口，BnInterface 在 IInterface.h:72 重写），命中本地对象，直接函数调用，不进驱动。

客户端 B（另一进程）：getService（IServiceManager.cpp:97-99）返回的 IBinder 是 BpBinder，asInterface 的 queryLocalInterface 落空，按 :128-137 回落 BpInterface，得到 BpFoo。它发起调用时，参数里的 Binder 对象在 Parcel 里记为 BINDER_TYPE_HANDLE。

服务进程要能收到这次调用，必须已有线程在 joinThreadPool（IPCThreadState.cpp:841）里循环；没有线程进池，调用会挂在驱动侧等不到处理者。这一层的入队与唤醒属驱动侧，本篇不断言细节。

7. 常见问题与误区

7.1 误区

误区一：`BnFoo` 和 `BBinder` 是两种东西。 其实是同一条继承线。BnFoo 继承 BnInterface<IFoo>，模板再落到 BBinder；手写代码直接继承 BBinder 与用 BnFoo 的差别只在是否复用 asInterface 样板。

误区二：`asInterface` 总是返回代理。 不一定。它先调 queryLocalInterface(descriptor)（BnInterface 在 IInterface.h:72 重写的判定入口），同进程内命中就返回本地对象，调用不经过驱动。只有落空才按 :128-137 回落 BpInterface。这一点的反面正是常见误解：很多人以为「拿到 IFoo 就一定是跨进程」。

误区三：Java 侧有一份独立的 Native Binder 栈。 没有。ibinderForJavaObject（android_util_Binder.cpp:1051）与 android_os_BinderProxy_transact（:1644，在 :1881 经 transactNative 注册）都汇入同一 ProcessState/IPCThreadState。进程的 mmap 区与线程池不会因为语言不同变两份。

误区四：注册了服务就等于能收到调用。 还要有线程进入 joinThreadPool（IPCThreadState.cpp:841）。线程池上限为 DEFAULT_MAX_BINDER_THREADS = 15（ProcessState.cpp:49），并发高了会排队而不是无限扩线程。

7.2 高频提问

问：Native 客户端拿到 IBinder 之后，怎么变成具体接口类型？ 答：调该接口的 asInterface。它先试 queryLocalInterface(descriptor)，命中返回本地实现，否则构造 BpInterface 代理。 追问：那我手写接口需要自己写这个方法吗？ 答：用 DECLARE_META_INTERFACE（IInterface.h:94）声明、按 :128-137 的形状实现即可；跑 AIDL 则由生成代码提供。

问：Java 里实现的 Binder 子类，Native 能直接当 BBinder 用吗？ 答：通过 ibinderForJavaObject（android_util_Binder.cpp:1051）转换得到 Native 的 IBinder，之后按正常 BBinder 语义参与事务。 追问：反方向呢？ 答：Java 侧调用代理走 android_os_BinderProxy_transact（:1644），与 Native 代理最终落到同一套收发路径。

问：addService 之后别的进程看到的是什么类型？ 答：看到 BpBinder，因为跨进程传递时对象被记为 BINDER_TYPE_HANDLE（读侧 case Parcel.cpp:166，写侧 proxy 分支 :303）。 追问：同进程内传呢？ 答：记为 BINDER_TYPE_BINDER（读侧 case :160，写侧 local 分支 :328），asInterface 能命中本地对象。
