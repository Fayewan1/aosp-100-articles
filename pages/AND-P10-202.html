1. TL;DR

一次「滑动掉帧」要分清三层：应用侧是否上报了 jank、渲染线程是否判出了慢帧类型、合成侧的时间戳是否对得上。应用侧入口是 android/app/jank/JankTracker.java，渲染侧判定在 libs/hwui/JankTracker.cpp，渲染侧的判定表围绕 FrameInfoIndex 的时间下标展开，应用侧只做采集与统计。要归因，先读 FrameInfo.h 里各下标的符号名，再拿 FrameMetrics.java 做应用侧对账。本篇只给度量口径与归因路径；阈值全部是源码常量口径，不含任何设备实测掉帧率。

3. 问题背景

滑动列表时肉眼看到一次顿挫，收集 trace 一看，主线程那条轨有一帧拉长，但渲染线程也有空闲，合成侧还有自己的时间戳。三处都能解释这次掉帧，你手里的数字却互相对不上。更麻烦的是，同一帧可能被应用侧判成 jank，被渲染侧判成另一种 JankType，两套命名并不一一对应。先把「什么算一帧慢」的口径统一，再谈「慢在哪一段」。

4. 核心机制

4.1 概念与关系

三个角色各自只看得见自己那一段。应用侧在 android/app/jank/JankTracker.java 里做采集与统计，开关是 KEY_JANK_METRIC_COLLECTION_ENABLED，取值走 DeviceConfig.getBoolean(NAMESPACE_SYSTEM_PERFORMANCE, ...)；数据落到 mJankDataProcessor，mergeJankStats 负责合并。渲染侧在 libs/hwui/JankTracker.cpp 里按判定表逐条比对帧的各时间下标，落到 JankType 枚举。两侧共同的底座是 FrameInfo.h：FrameInfoBuffer 就是 std::array<int64_t, NumIndexes>，一条时间戳数组，下标由 enum class FrameInfoIndex 定义，符号名由 FrameInfoNames 给出。

图 1：三层归因与共享的帧时间下标

应用侧            渲染侧            合成侧
JankTracker.java  JankTracker.cpp   SurfaceFlinger.cpp
      |                 |                 |
      +-------- FrameInfoIndex -----------+
              (FrameInfo.h 时间下标)

FrameInfoIndex 是唯一的对账锚点。只有 int 下标重载（:163）做完整上下界检查、越界返回 0，typed 重载（:197）仅在 index == NumIndexes 时返回 0——两者都可能让「下标写错」和「该阶段没有时间戳」在数值上长得一样，都是 0。判定表里 JankType::kMissedVsync 配的就是 FrameInfoIndex::IntendedVsync——比的是「我打算在哪次 vsync 出帧」与「实际出了没」。

4.2 关键内容

判定表是 static const std::array<Comparison, 4> COMPARISONS（JankTracker.cpp:46），共 4 条：kMissedVsync（:47）、kSlowUI（:50）、kSlowSync（:54）、kSlowRT（:58，区间 IssueDrawCommandsStart→FrameCompleted）。消费它的循环在 finishFrame 内（:235–:241），位于 :218 的 else 分支——只有错过 deadline 的帧（该分支先报 kMissedDeadline，:219/:220）才会进入：逐条独立比对，delta 落在门限与 IGNORE_EXCEEDING 之间即上报，循环体内无 `break`、无 `else if`、无 `return`。所以四条互不排斥，同一帧可以同时命中多个 JankType 并各自上报。kHighInputLatency 不在这个数组里，它的判定点在 :154/:155 与 :212/:213 两对上报。

4.3 一个具体例子

假设 trace 里一帧的 UI 线程段明显拉长，你想知道渲染侧会判成哪一类。

第一步，确认应用侧有没有开采集：KEY_JANK_METRIC_COLLECTION_ENABLED（JankTracker.java:48）经 DeviceConfig.getBoolean(NAMESPACE_SYSTEM_PERFORMANCE, ...)（:100-101）读取。没开，应用侧统计就是空的，别拿它当证据。但开关为真也不保证有数据：shouldTrack()（JankTracker.java:326，:332 返回）要求 mTrackingEnabled && mListenersRegistered && mComponentsReady（:85/:90/:332）三条件同时成立；此外 :93-95 的注释载明「Jank metric reporting is limited to 1% of devices controlled via server side configurations」——采样面本身只有 1% 的设备。开关已开却仍为空时，先查这三重门与设备是否被纳入采样，不要只盯着开关常量。

第二步，在渲染侧逐条比对四条 COMPARISONS（:47、:50、:54、:58）。它们是并列关系，不是先后关系：kMissedVsync（:47）看 FrameInfoIndex::IntendedVsync 有没有丢；kSlowUI（:50）、kSlowSync（:54）各自看自己那段的时长；kSlowRT（:58）看 IssueDrawCommandsStart→FrameCompleted。你观测到的「UI 段拉长」落在 kSlowUI 的判定区间上，但同一帧不排除同时命中别的类型。若延迟是输入引起的，还要看 kHighInputLatency（:154/:155、:212/:213）。

第三步，把下标翻成名字：FrameInfoNames（FrameInfo.h:76）给出每个下标对应的符号名，NumIndexes（:73）是上界。读到 0 先怀疑下标越界：int 重载（:163）越界返回 0，typed 重载（:197）仅在 index == NumIndexes 时返回 0，别急着说「这个阶段没耗时」。

第四步，用 FrameMetrics.java 做应用侧对账——它是应用侧读取帧各阶段耗时的公开入口，字段与 FrameInfoIndex 的分段对应。

7. 常见问题与误区

7.1 误区

误区一：主线程那条轨拉长就一定判 `kSlowUI`。 四条 COMPARISONS 是并列独立比对（循环体 :235–:241，无 break），一帧可同时上报 kMissedVsync（:47）、kSlowUI（:50）、kSlowSync（:54）、kSlowRT（:58）中的任意组合。看到 kSlowUI 不等于没有 kMissedVsync，反之亦然——要按四条分别核对。

误区二：`FrameInfoIndex` 某个下标读到 0，说明这一阶段不耗时。 int 下标重载（:163）越界返回 0，typed 重载（:197）只在 index == NumIndexes 时返回 0。0 是「没读到」的同义词，先查 NumIndexes（:73）上界。

误区三（看起来对其实是错的）：看到 `Skipped N frames!` 就知道掉了几帧。 这条日志的门限是 SKIPPED_FRAME_WARNING_LIMIT（Choreographer.java:178），只在该门限之上触发；低于门限的掉帧不会打这条日志。它是告警，不是全量计数。

7.2 高频提问

问：应用侧 jank 统计为什么在有的机器上是空的？ 答：先看 KEY_JANK_METRIC_COLLECTION_ENABLED（:48）是否被 DeviceConfig 置为真（读取在 :100-101）。开关关着，mJankDataProcessor（:59、:143）就收不到数据；开关开着却仍为空，则查 shouldTrack()（:326-333）的 mTrackingEnabled/mListenersRegistered/mComponentsReady 三重门，以及该设备是否在 :93-95 所述 1% 采样面内。 追问：开关开着就一定和渲染侧判得一样吗？ 答：不会。两侧是两套口径：应用侧走 mergeJankStats（:181）聚合，渲染侧按 JankType 枚举逐条独立判定、可同时命中多个，同一个慢帧可以两边结论不同名。

问：归因到底先看哪个字段？ 答：先看 FrameInfoIndex::IntendedVsync——它是 kMissedVsync（:47）的判定依据，也是四条里唯一回答「这帧到底出没出」的那条；其余三条都是时长比较。 追问：trace 里想抓渲染管线，开哪个类别？ 答：atrace 的 gfx 类别（frameworks/native/cmds/atrace/atrace.cpp:103，对应 ATRACE_TAG_GRAPHICS）。

8. 边界与延伸

本篇不覆盖：Choreographer 帧调度机制（AND-P6-301）、SurfaceFlinger 合成策略（AND-P6-201）、BufferQueue 机制（AND-P6-102）。

本篇前置依赖：AND-P6-301。

本篇后继：AND-P10-402（trace 采集工具链方向）、AND-P10-403（ANR 判定与 native 崩溃 tombstone 取证方向）。

数量级与边界值：

  • SKIPPED_FRAME_WARNING_LIMIT 的定义位置为 Choreographer.java:178，由 SystemProperties.getInt 读取——源码常量／属性口径，具体数值以树内默认为准。
  • FrameInfoBuffer 长度等于 NumIndexes（FrameInfo.h:73、:87）——源码常量口径。
  • COMPARISONS 条目数为 4（:46），即 kMissedVsync、kSlowUI、kSlowSync、kSlowRT；另 kHighInputLatency 在 :154/:155 与 :212/:213 两对上报——源码静态口径。
  • 四条判定在循环中逐一独立比对、无短路，单帧可上报多个 JankType——源码静态口径。
  • 各 JankType 的判定阈值：源码给的是相对 `frameInterval` 的比例而非固定毫秒——kMissedVsync 恒为 1ns（:47-48，只要 intended vsync 与 vsync 不等即命中）、kSlowUI 为 .5×（:51）、kSlowSync 为 .2×（:55）、kSlowRT 为 .75×（:59）；另有 IGNORE_EXCEEDING = seconds_to_nanoseconds(10)（:65）作上界，超过 10 秒的事件直接丢弃、按 ANR 处理。具体毫秒数随设备刷新率变化，故本篇不给出单一数值。
  • 设备实测掉帧率与各阶段耗时分布：暂无实测，列为待补。
