1. TL;DR

读源码树的顺序：先入口后细节，先数据流后控制流，一次只追一个符号。读补丁的顺序：先读 commit message 的一行主题，再看 diff 的文件列表，最后才进 hunk。git log --oneline -10 -- <file> 用来建立某个文件的提交节奏感，git show <sha> 再看单次补丁全文。判断改动性质，看它改了哪些文件比看改了多少行更有效：只改一个文件的一行，通常是值变更；跨多个目录，才可能是行为变更。但这只对纯值文件成立——makefile 里列表、标志位、配置的一行增删即行为变更。

3. 问题背景

在源码树里待久了会遇到这种局面：某个常量今天和昨天不一样，却不知道是谁改的、为什么改；或者 grep 一个符号，命中分布在十几个仓里，读完第一个文件就迷路。两种卡顿的解法在于把顺序固定下来。

4. 核心机制

4.1 概念与关系

三个层次：文件是阅读的最小单位，提交是变更的最小单位，符号是追踪的最小单位。三者互相定位：从符号查文件，从文件查提交，从提交的 diff 反查符号名。commit message 是提交的入口，主题行说明做了什么，正文与 Bug 引用说明为什么。

4.2 关键内容

阅读顺序四条：先入口后细节，从 main 与生命周期入口进；先数据流后控制流；按五条调用链走；一次只追一个符号。

读补丁的固定动作：先读主题行与 diff 文件列表，再进 hunk。commit message 的标准结构是一行主题（动词开头）＋ 正文 ＋ Bug 引用。

命令含义
git log --oneline -10 -- <file>看某个文件的最近历史
git show <sha>看单次补丁全文
git log -L :<funcname>:<file>跟一个函数的演进（函数名形式必须带前导冒号）
git blame <file>定位某一行的责任提交
git tag --points-at HEAD看当前提交上的发布标签

以上命令均在对应子仓内执行。

7. 常见问题与误区

7.1 误区

误区一：读补丁就是读 diff。 diff 只说明改了什么行；先读一行主题与文件列表，但「列表只有一项＝值变更」只对纯值文件成立。

误区二（看起来对其实是错的）：`git blame` 给出的是「谁写坏了」。 它只给出某一行的最后责任提交；改名与搬移后它可能只是搬运者，配合 git log --follow 看。

误区三：文件历史越长越要先读。 像 build_id.mk 这类随发布滚动的值文件历史噪音大，先读入口与数据流，不是最活跃的文件。

7.2 高频提问

问：符号在多个仓里同名怎么办？ 答：先按调用链确定它属于哪一层，再按仓名收窄。追问：收窄后仍有多个候选？ 答：用 git log -L :<funcname>:<file> 看函数演进，历史最短的通常不是主干实现。

问：git log -L 和 git blame 该先用哪个？ 答：理解逻辑来龙去脉用 git log -L，定位某一行由谁引入用 git blame。
