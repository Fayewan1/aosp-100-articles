1. TL;DR

Android 构建不是从 Make 直接跳到 Bazel，中间插着一层 kati：Make 的 Android.mk 由 kati 翻译成 ninja，才交给 ninja 执行。本树 build/envsetup.sh 是符号链接，入口 make() 先看树顶有没有 build/soong/soong_ui.bash：有、且参数不带 -C 前缀时走 --make-mode，否则（脚本缺失或带了 -C）回退到 command make（get_make_command :1016-1030）。m/mm/mmm 在 envsetup.sh 里没有定义（:1174-1180 还显式 unset），模块组构建只剩 tapas() 与 banchan()；另有三个脚本各定义了一个同名内部辅助 m()，与这两个入口不是一回事。ckati 是本树默认，rkati 是 Rust 重写版且 bool_value: false 默认关闭——这个默认不是靠 flag 语义推断的：config.KatiBin()（config.go :2035-2043）在 useRkati 为假时直接返回 prebuilts/build-tools/<host>/bin/ckati。平台构建规则仓 build/bazel 未收录进本树 manifest（1087 个项目），本篇不给该目录下任何路径与符号；但本树并非没有 Bazel 可核面——trusty/WORKSPACE.bazel 与 trusty/.bazelrc 是两条 linkfile 的落点（源在 trusty/host/common/bazel/，default.xml :1100-1101）、prebuilts/bazel/common（default.xml :883）含 bazel-complete.bash 与 release_bazel.py、external/ 下大量第三方仓自带 BUILD.bazel（顶层 32 个仓、递归上千个文件，此处仅举 abseil-cpp、antlr、brotli、cpu_features、cpuinfo、bazelbuild-remote-apis 六例）、build/pesto（default.xml :24）的 experiments/prepare_bazel_test_env/ 下是 data/templates/build/bazel/rules/*.template（含 BUILD.bazel.template）与 data/static/build/bazel/rules/*.sh 这类模板与静态数据，build/make/tools/rbcrun（Roboleaf）是另一处——三者都是测试/实验侧，同样不是可直接消费的平台构建规则。

3. 问题背景

你在树顶敲 make，以为它在跑 GNU make，其实大概率没跑——构建流程先被 get_make_command() 劫持到了 soong_ui.bash --make-mode。想看哪个模块被谁构建，Android.mk 里的依赖关系却查不到，因为 kati 已经把它转成了 ninja 文件。这时有人告诉你「以后要迁 Bazel」，你需要的不是口号，而是三条路线各自持有什么。本篇要回答的是：Make/kati、Soong、Bazel 在「谁持有构建逻辑、谁做依赖求解、谁生成执行图」这三层上分别占哪一格。

4. 核心机制

4.1 概念与关系

三条路线不是替代关系的三个时间点，而是构建流程上三个不同位置的分层：

图 1：三条路线在构建流程中的位置

  Android.mk ──kati──┐
                     ├─→ ninja 文件 ─→ ninja 执行 ─→ 镜像
  Android.bp ─Soong──┘
                      
  Bazel 目标（本树未收录）：自带依赖求解与执行图

Make 路线持有「构建逻辑」，Android.mk 用 make 语法写规则；kati 做的是翻译，把 make 语义转成 ninja 的显式图。Soong 路线持有「构建逻辑 + 依赖求解」，Android.bp 是声明式描述，求解在 Soong 内部完成，最终同样落到 ninja。Bazel 路线的定位是自带求解与执行图，理论上不需要经 kati 或 Soong 兜一层；本树未收录平台构建规则仓 build/bazel，这一句只能按官方文档口径说——Bazel 在本树的可核面是 trusty、prebuilts 与 external 三处，都不是平台构建规则本身。

4.2 关键内容

三条路线的对比按三层判据展开。前两层是本树可核的，第三层只有两侧可核。

名称含义出处

谁持有构建逻辑。 Make 侧持有方是 build/make/core/ 顶层的 113 个 .mk 文件（递归含子目录一共 148 个），主 Makefile 8229 行。Soong 侧持有方是 Android.bp 与 Go 侧配置代码，build/soong/Android.bp 359 行，build/soong/ui/build/config.go 2325 行。量级差异不说明优劣，只说明粒度：make 语法把规则与控制流混在一处，.bp 把规则拆成声明。

谁做依赖求解。 Make 侧的求解被切成两段：kati 负责 make 语义到 ninja 图的转换，ninja 负责按图执行。runKatiBuild（:239）就是这段的驱动。Soong 侧在自身内部完成模块依赖求解，产物仍是 ninja。Bazel 按官方文档口径把求解收在自己手里，不借道 kati。

谁生成执行图。 三条路线最终都产出执行图供 ninja 或自身执行器消费。区别在于图的来源：Make 侧靠 kati 转译，Soong 侧靠自身求解，Bazel 侧靠自身分析。

4.3 一个具体例子

在树顶执行 make，实际发生的是：

  1. build/envsetup.sh（1210 行，指向 make/envsetup.sh 的符号链接）被 source。
  2. make()（:1033）调用 get_make_command()（:1016）。
  3. 树顶检测到 build/soong/soong_ui.bash 且参数不带 -C 前缀，返回 --make-mode；带 -C 时仍返回 command make（:1021-1025）。
  4. 后续 Makefile 处理中，build/make/core/Makefile（8229 行）里 systemimage 在 :947 只是「为 all 目标占位」的空桩（:944-945 的注释即说明此意，无依赖无配方），真正的规则在 :3910 systemimage: $(INSTALLED_SYSTEMIMAGE_TARGET)；main.mk 1951 行、config.mk 1420 行、product.mk 683 行参与配置展开。
  5. 需要构建 Android.mk 描述的模块时，runKatiBuild（:239）驱动预编译的 ckati（prebuilts/build-tools/linux-x86/bin/ckati），因为它默认开启——RELEASE_USE_RKATI 的 bool_value: false。

这条链说明一件事：本树的 make 命令已经不再是「GNU make 跑 Makefile」，而是「Soong 的统一入口按需调 kati」。m/mm/mmm 消失、模块组构建改用 tapas()（:674）与 banchan()（:747），是同一件事的另一面。

7. 常见问题与误区

7.1 误区

误区一：敲 `make` 就是在跑 GNU make。 本树基本不是。get_make_command()（:1016-1030）先查树顶有没有 build/soong/soong_ui.bash：有、且参数不带 -C 前缀时返回带 --make-mode 的命令；command make 是回退分支（脚本缺失或带了 -C）。

误区二：`Android.mk` 由 GNU make 直接执行。 看起来对其实是错的。Android.mk 的语义由 kati 解析，runKatiBuild（:239）把它转成 ninja，执行的是 ninja 而非 make。kati 可执行文件是预编译二进制 prebuilts/build-tools/linux-x86/bin/ckati 与 rkati，build/make/kati 源码目录在本树未检出。

误区三：`m`/`mm`/`mmm` 只是换了名字还留着。 本树未检出这三个命令，envsetup.sh :1174-1180 还显式 unset m/mm/mma/mmm/mmma。模块组构建用 tapas()（:674）与 banchan()（:747）。写脚本时继续调 m 会直接失败。

误区四：rkati 已经取代 ckati。 RELEASE_USE_RKATI 的 bool_value: false、workflow: LAUNCH。描述是 Use rkati instead of ckati, a rust rewrite——重写版存在，默认关闭。

7.2 高频提问

问：三条路线里，Bazel 到底处在哪一层？答：按官方文档口径，它自带依赖求解与执行图生成，不依赖 kati 转译，也不依赖 Soong 求解。追问：那本树怎么看它的实现？答：平台构建规则仓 build/bazel 未收录进本树 manifest（本树工作区亦未检出该目录），本篇不给该目录下任何路径与符号。但 Bazel 在本树不是全无可核：trusty/WORKSPACE.bazel 的头两行注释就在讨论 ninja 的 toplevel_output_directories，是三条路线关系的一处现成旁证；build/pesto 那套则是测试侧的 Bazel 实验环境，里面是 data/templates/build/bazel/rules/*.template 与 data/static/build/bazel/rules/*.sh 这类模板与静态数据。

问：选型该看什么判据？答：看三层——谁持有构建逻辑、谁做依赖求解、谁生成执行图。三层归属一致的系统迁移成本最低。追问：为什么不用「哪个快」来选？答：本篇未做任何整包构建实测（本机 32GB 内存不可行），不给实测数字。
