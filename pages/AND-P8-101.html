1. TL;DR

bootloader 交棒时只保证一件事：把内核、ramdisk 和设备树（device tree，DT）放进内存并把控制权交给内核。接下来的一阶段 init 不再问 bootloader 要信息，它自己读 /proc/device-tree、自己选 fstab、自己触发校验。启动镜像里最容易被误解的一环是校验：avb_slot_verify 并不在一阶段 init 的 main 入口被调用，而是由 FirstStageMount 在挂载分区前经 libfs_avb 拉起来。设备树在运行时由 system/libufdt 的 ufdt_apply_overlay 打补丁，一阶段 init 只消费结果。二阶段 init 拿到的一阶段起始时刻靠环境变量传递，不是靠重新计时。

3. 问题背景

手机黑屏卡住，串口日志停在 First stage mount skipped，然后系统就没下文了。把 fstab 塞进 ramdisk 里再烧一次，日志变成 dm-verity 失败。同一个人还在问第三个问题：ro.boot.verifiedbootstate 明明是 bootloader 设的，为什么我在一阶段 init 里 getenv 拿不到、非得走属性服务？

这三个问题指向同一条链：内核起来之后的第一个用户态进程能看见什么、能读什么、什么时候校验。这条链上每一环的输入来源都不一样，混在一起就会判断错层。

4. 核心机制

4.1 概念与关系

一阶段 init 是 init 二进制的第一个执行分支。它的输入只有四类：kernel 命令行（含 bootconfig）、/proc/device-tree 下的 DT 节点、ramdisk 里的 fstab、以及分区本身的内容。四类输入经不同代码路径汇入，最后交出一个挂载好的 /system 并切到二阶段。

分区内容                     --> libfs_avb --> avb_slot_verify

DT 上的严格启动标记。 first_stage_mount.cpp:114-116 的静态函数 IsMicrodroidStrictBoot 用 access("/proc/device-tree/chosen/avf,strict-boot", F_OK) 探测该节点是否存在（探测语句在 :115）。它只有一个调用点：:135，在 InitDevices 内、且外层套着 IsMicrodroid() && IsOpenDiceChangesFlagEnabled() 的条件分支里，用来初始化 open-dice0 平台设备。也就是说，这条分支只服务虚拟化（microdroid）场景的平台设备准备，并不是一阶段挂载主干的「严格启动开关」。

4.3 一个具体例子

假设一台设备 fstab 里 system 分区带 avb 标志，bootloader 已把 androidboot.verifiedbootstate=green 写进命令行。

一阶段 main 进 FirstStageMain，先完成 /proc 挂载等最小环境准备，然后按三步走。这三步的边界要划清，尤其是「收集设备名单」和「建立 dm 设备」不在同一个函数里。

第一步，:539 调 CreateFirstStageMount(cmdline)——它转 FirstStageMount::Create，first_stage_mount_android.cpp:50 的 ReadDefaultFstab(&fstab) 在这里被调，实现在 fstab.cpp:765，fstab 在这一步读进对象。:539 是 if (!fsm) 守护下的常规入口；console_on_failure 模式下首次进入点更早，在 :479（want_console == CONSOLE_ON_FAILURE 分支内先建 fsm 并调 DoCreateDevices）。

第二步，:545 调 DoCreateDevices（定义在 first_stage_mount.cpp:97）：它转进 InitDevices（:118），:127 在 InitDevices 内调 GetDmVerityDevices（定义在 :415），把需要 dm-verity 的分区名收集成名单。这一步不是每次都会执行——first_stage_init.cpp:476 先置 created_devices = false，:479-481 在 console_on_failure 分支里已经建过一次并置真，所以 :545 写的是 if (!created_devices && !fsm->DoCreateDevices())，走 console 路径时这里会被短路，不会重复建设备。这一步到此为止——不建 dm 设备、也不做 AVB 校验。把 GetDmVerityDevices 与 SetUpDmVerity 焊成同一条链，是最常见的读法错误。

第三步，:551 调 DoFirstStageMount（定义在 :101）：先过 :102 的早返回条件 !IsDmLinearEnabled() && fstab_.empty()，二者不同时成立才继续；MountPartitions（:338）第一句是 TrySwitchSystemAsRoot（调用点 :339，定义在 :278）。这里要特别注意：MountPartition 在 MountPartitions 里有两个入口，不是只有一个。第一个在 TrySwitchSystemAsRoot 内部——:291 对 /system 单独调一次 MountPartition，所以 system-as-root 设备上 /system 的 dm-verity 建立与 AVB 校验就发生在这一步，早于后面的循环；这条入口是有条件的：:287 的 if (system_partition == fstab_.end()) return true; 先挡住「fstab 里没有 /system 条目」的情况。第二个才是常规循环——:371 逐分区调 MountPartition（定义在 :186），而循环体内 :349-352 会显式跳过 mount_point == "/system"（注释写明上方已挂过），所以两个入口不是重复劳动。两条路径都走 MountPartition 的 :205：调 SetUpDmVerity（定义在 :473）建 dm-verity 设备，建完才 fs_mgr_do_mount_one（:210）。

AVB 校验挂在这一步的 SetUpDmVerity 之下：它在内部 :479/:502/:508 调 InitAvbHandle（定义在 :538），后者经 AvbHandle::Open()（fs_avb.cpp:454）完成校验——Open() 的方法体从 :454 延伸到 :536（:537 是闭合花括号），:467-468 先调 avb_ops.AvbSlotVerify(...)，随后 :500-536 又按 verification_disabled／hashtree_disabled 两个标志定状态，其间还有 AvbVerifier::Create 与 VerifyVbmetaImages 的 vbmeta digest 二次校验。所以校验发生在 Open() 之内、且不止一次调用点，不是「打开句柄之后另起一步」。FsManagerAvbOps::AvbSlotVerify 定义在 avb_ops.cpp:255，它的实现里 :270 才是那句 avb_slot_verify(&avb_ops_, ...)（avb_slot_verify.c:1417）。ops 适配层的符号 FsManagerAvbOps::GetInstanceFromAvbOps 定义在 avb_ops.h:53，avb_ops.cpp:54 是它在 read_from_partition 里的首个使用点。返回 AVB_SLOT_VERIFY_RESULT_OK 后挂载成立。

main 结束前在 first_stage_init.cpp:568 用 setenv(kEnvFirstStageStartedAt, ...) 把一阶段起始时刻塞进环境变量，带进二阶段。

二阶段 init.cpp（1346 行）的次序要记准：:1126 的 PropertyInit()（property_service.cpp:1405 定义）先把 androidboot.* → ro.boot.* 的映射做完（其内部 :1423 调 ProcessKernelCmdline），:1155 才 StartPropertyService 起服务，所以 :1159 的 GetIntProperty("ro.boot.boot_timeout") 与 :1187 的 GetBoolProperty("ro.boot.wait_for_udc") 就已经能读到 ro.boot.*；:1208 的 LoadBootScripts（定义在 :347）只是又晚一步，它读的是 :350 的 GetProperty("ro.boot.init_rc") 来选 rc 路径。把「第一次读 ro.boot」记在 :1208 是常见的次序误判。:1166 调用 :904 的 RecordStageBoottimes，经环境变量设 ro.boottime.init、ro.boottime.init.first_stage、ro.boottime.init.selinux、ro.boottime.init.modules。

7. 常见问题与误区

7.1 误区

误区一：以为一阶段 init 会解析 fstab 里的每一行去判断分区合法性。 一阶段只做「取默认 fstab → 按标志挂载」两件事，合法性由 AVB 与 dm-verity 兜底。

误区二：以为 `ro.boot.verifiedbootstate` 在一阶段就能读。 它来自 kernel 命令行的 androidboot.* 前缀映射，映射发生在 property_service.cpp:1388，而属性服务要二阶段才起。一阶段该值只是命令行里的一个字符串。

误区三（看起来对其实是错的）：以为 `avb_slot_verify` 的调用者是一阶段 init 的 `main` 入口。 main 只负责环境与过渡；真正的校验在 DoFirstStageMount（:551）→ MountPartitions（:338）→ MountPartition（:371）→ :205 的 SetUpDmVerity 之下，经 InitAvbHandle 进 AvbHandle::Open()（fs_avb.cpp:454），Open() 内部 :467-468 直接调 FsManagerAvbOps::AvbSlotVerify（avb_ops.cpp:270）落到 avb_slot_verify。辨析要点：Open() 本身就做校验，不存在「先打开、后校验」两步；而收集分区名单的 GetDmVerityDevices 属建设备阶段，与校验不在同一条链上。

误区四：以为设备树必须由 bootloader 完整给出、init 不会改。 system/libufdt 的 ufdt_apply_overlay 在运行时对 DT 施加 overlay，init 读到的是补丁后的结果。

7.2 高频提问

问：日志里只有 First stage mount skipped，怎么判断是 fstab 缺失还是别的？ 答：先看日志后缀，这句话有两个出处。first_stage_mount.cpp:104 打的是 First stage mount skipped (missing/incompatible/empty fstab in device tree)，对应 DoFirstStageMount 在 :102 的早返回，条件是 !IsDmLinearEnabled() && fstab_.empty() 同时成立，直接原因通常是 ReadDefaultFstab 没拿到 fstab（或 fstab 为空）。first_stage_init.cpp:536 打的是 First stage mount skipped (recovery mode)，那是 recovery 模式下的分支——此时 fsm 根本不会被创建，DoFirstStageMount 也不执行。两条日志字面相同，排障方向完全相反。 追问：那 ramdisk 里有 fstab 但内容为空呢？ 答：同样走到早返回，因为判断的是 fstab 是否为空而不是文件是否存在；但若 fstab 里存在 dm-linear 逻辑分区条目，IsDmLinearEnabled() 为真，这条早返回就不会触发。

问：ro.boottime.init.first_stage 的值为什么和我从内核日志算出来的不一致？ 答：它是两个纳秒时刻的差值，起点是一阶段 setenv(kEnvFirstStageStartedAt, ...)（first_stage_init.cpp:568）携带的时刻，终点是 SELinux 起始时刻（init.cpp:922-923，selinux_start_time_ns - first_stage_start_time_ns）——两个端点都不是内核启动时刻，也不是二阶段 RecordStageBoottimes 被调用的时刻；后者定义在 init.cpp:904、调用点在 :1166，它只是把一阶段经环境变量传来的时刻读出来做差写进属性。 追问：那二阶段怎么不重新打点？ 答：一阶段已经打过点，二阶段经环境变量接续，避免重复计时。

问：/proc/device-tree/chosen/avf,strict-boot 存在代表什么？ 答：它只被 IsMicrodroidStrictBoot（first_stage_mount.cpp:114-116）探测，唯一调用点 :135 在 InitDevices 内、外层条件是 IsMicrodroid() && IsOpenDiceChangesFlagEnabled()，用途是初始化 open-dice0 平台设备——属虚拟化场景，与常规设备的「严格启动开关」不是一回事。 追问：谁写这个节点？ 答：本树不含写入方，按接口契约口径，这是虚拟化相关启动路径的标记。
