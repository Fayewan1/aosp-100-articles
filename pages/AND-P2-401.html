1. TL;DR

App 进程不是「启动」出来的，是 Zygote 进程（Zygote）预载完成后 fork 出来的；预载的类与资源靠 Linux 写时复制（copy-on-write，COW）在父子进程间共享，父子都不写就永不复制。fork 面向调用方的两个常规入口是 Zygote.forkAndSpecialize 与 Zygote.forkSystemServer，两侧都要过 ZygoteHooks.preFork() 与 ZygoteHooks.postForkCommon()。进程生下来之后，杀谁不杀谁由 adj 决定：常量从 SYSTEM_ADJ = -900 一路排到 CACHED_APP_MAX_ADJ = 999，值越大越先被杀。adj 由 OomAdjuster 算，经 ProcessList.setOomAdj 封装成 LMK_PROCPRIO 消息写进 Unix 域套接字 lmkd，由 LMKD（守护进程 lmkd）代写内核的 oom_score_adj。

3. 问题背景

同一个手机，微信在后台挂着没被杀，刚切走的一个小工具 App 一分钟后点回来已经冷启动了。开发者看着 dumpsys 里一堆进程，分不清哪个是「前台」哪个是「缓存」，更不知道系统按什么顺序挑人下手。还有一类困惑更底层：App 进程的 Java 堆里，为什么一开机就有一批类是可用的，这些类是每个进程各加载一遍，还是大家共用一份？把进程怎么被造出来、优先级怎么被定下来这两件事讲清，上面两类问题就有答案了。

4. 核心机制

4.1 概念与关系

四个概念。Zygote 是「预载完 Java 运行时的模板进程」，只等 fork。fork 是 Linux 系统调用，复制父进程地址空间并在写时复制。COW 是 kernel 侧的页共享策略，谁写谁复制。adj 是 Android 给每个进程贴的优先级数字，取值最终落到内核的 oom_score_adj，决定被杀顺序。

图 1：进程诞生与优先级落值两条链路

ZygoteInit.preload
   └─ fork ──> App 进程（COW 共享预载结果）
                   │
OomAdjuster 算 adj │
   └─ ProcessList.setOomAdj
          └─ writeLmkd ──> lmkd ──> oom_score_adj

注意这是两条链路，不是一条：fork 决定「进程怎么存在」，adj 决定「进程多容易被回收」，两者在时间上没有调用关系。

4.2 关键内容

fork 侧的关键是「先备料、后分裂」。ZygoteInit.preload（ZygoteInit.java:128）先跑 preloadClasses()（134 行），类清单固定读 /system/etc/preloaded-classes，路径常量 PRELOADED_CLASSES 在同一文件 112 行；再跑 Resources.preloadResources()（140 行）。预载完成后才进入 fork 循环。子进程拿到的是一份「已经加载好常用类和公共资源」的地址空间，靠 COW 与父进程共享物理页——注意这是 Linux fork 语义，不是 AOSP 自己发明的机制。

面向调用方的常规入口有两个，系统进程走一条，App 走另一条：

用途入口native 落点同族钩子
App 进程Zygote.forkAndSpecialize（Zygote.java:376）nativeForkAndSpecialize（407）ZygoteHooks.preFork() / postForkCommon()
系统进程Zygote.forkSystemServer（Zygote.java:510）nativeForkSystemServer（526）ZygoteHooks.preFork() / postForkCommon()

两侧都成对调用 ZygoteHooks.preFork() 与 ZygoteHooks.postForkCommon()，说明 fork 前后要做一致的运行时状态处理。此外还有 USAP（非专用进程池）路径的 forkUsap（Zygote.java:677），同样落到 native fork，归 USAP 专题展开，不属上面两个常规入口。

调度组管的是内核 CPU 调度倾向，adj 管的是内存回收倾向，两个维度不同，别混为一谈。

落值环节在 ProcessList.setOomAdj（ProcessList.java:1519）：组装 LMK_PROCPRIO 包，字段是 pid/uid/adj/PROC_TYPE_APP/forLmkdOnly（1529–1535 行），经 writeLmkd（ProcessList.java:1663）交给 LmkdConnection，走的是 LocalSocket——套接字名 "lmkd"、命名空间 RESERVED（LmkdConnection.java:273–274），建连方法 openSocket（LmkdConnection.java:267）。真正调内核写 oom_score_adj 的是 lmkd，不是 AMS 自己。若单次下发超过 250 ms，会打 "SLOW OOM ADJ" 警告（ProcessList.java:1537–1540）——这条日志就是 adj 慢的现场证据。

4.3 一个具体例子

一个 App 从后台被切到前台，走一遍：performUpdateOomAdjLSP 完成本次更新，updateAndTrimProcessLSP（1347 行）裁剪，结果经 mInjector.setOomAdj(...)（2325 行）下发。若该 App 成为顶层，同一文件 2372 行把它提到 processGroup = THREAD_GROUP_TOP_APP（值 5，见 android/os/Process.java 566–625）。adj 取值升到 FOREGROUND_APP_ADJ = 0 一档。ProcessList.setOomAdj（1519 行）把 pid/uid/adj 打成一个 LMK_PROCPRIO 包，writeLmkd（1663 行）经名为 "lmkd" 的 LocalSocket 送出，lmkd 落到 oom_score_adj。整条路径跑超 250 ms 就出 "SLOW OOM ADJ"。倒过来切回后台，值跌到 CACHED_APP_MIN_ADJ = 900 一档，被回收的位次就靠前了。

7. 常见问题与误区

7.1 误区

「每个 App 进程各自加载一遍常用类」——错。ZygoteInit.preload（128 行）在 fork 之前就把类和资源装好了，子进程靠 COW 共享父进程的物理页。只有子进程自己写过的页才会真的复制一份。

「adj 是 AMS 直接写进内核的」——错。AMS 算完 adj 后，ProcessList.setOomAdj（1519 行）只负责组包，经 writeLmkd（1663 行）走 LocalSocket 送到 lmkd，真正写 oom_score_adj 的是 lmkd。

「进程被创建的那一刻 adj 就定好了」——看起来对，其实是错的。fork 只决定进程存在，adj 是之后由 OomAdjuster 按前台/可见/服务/缓存等状态算出来的，还会随状态反复变；创建与定级是两条独立链路。

「adj 小就一定不会被杀」——错。负值只表示「优先级极高」，不构成豁免；具体回收策略由 lmkd 与内核共同决定，本篇不展开。

7.2 高频提问

问：预载类清单写在哪？答：常量 PRELOADED_CLASSES 在 ZygoteInit.java 112 行，运行时读的路径是 /system/etc/preloaded-classes。追问：能改吗？答：能，改清单即可，但清单变大会拉长 Zygote 启动时间，是拿启动换后续进程的加载速度。

问：forkAndSpecialize 和 forkSystemServer 为什么要分两个入口？答：两者要 specialize 的内容不同，system server 的 uid/gid 与 capability 处理和普通 App 不一样，所以各走一条 native 路径。追问：共同点是什么？答：两侧都成对调用 ZygoteHooks.preFork() 与 postForkCommon()，fork 前后的运行时状态处理是一致的。
