1. TL;DR

APK 签名从 v1 到 v4 是四套并行机制，不是新替代旧：v1 是 JAR 签名，v2 起改走 APK Signing Block，v3 在其中加密钥轮转，v4 则不写入 APK 本体，落在 APK 旁的 .idsig 文件里（fs-verity 元数据的载体）。验证链路的一条入口在 PackageParser 内调 ApkSignatureVerifier.verify，结果收敛到 SigningDetails。密钥轮转靠 v3 块内的 Proof-of-rotation 记录加 mergeLineageWith(...) 把血统合并，旧解析器忽略轮转字段，因此换钥能平滑过渡。后量子混合签名以 isPqcSigned() 形式进入同一套判定。

3. 问题背景

同一台设备上，一年前装的应用今天要做密钥轮转发布。新 APK 用新私钥签，旧版本用旧私钥签，系统怎么认得出这是同一个应用、而不是另一个冒名者？反过来，如果新 APK 同时带了 v2 和 v3 两种签名，旧系统读到哪一个？再看更常见的一幕：把一个 APK 解开、改一个字节、重新打包，为什么大多数情况下安装直接失败，而某些老格式的包却还能装进去？这三个问题指向同一件事：不同签名方案保护的范围不同，验证顺序与失败形态也不同。

4. 核心机制

4.1 概念与关系

四个概念构成一条链：APK Signing Block（v2 起的签名容器）→ 各方案专属 block id（定位具体方案的数据块）→ Proof-of-rotation 结构（v3 起承载换钥链）→ SigningDetails（框架侧统一收敛的签名详情，含签名方案枚举与血统）。

图 1：签名数据的四层关系

APK 文件
├─ 原始条目        ← v1 用 JAR 清单逐个摘要
├─ APK Signing Block ← v2/v3/v3.1/v3.2 的 block id 在此
│   ├─ 0x7109871a  v2
│   └─ 0xf05368c0  v3（内含轮转记录）
└─ APK 本体之外     ← v4 落在 APK 旁的 .idsig（fs-verity 元数据载体）

v1 保护的对象是 JAR 条目集合，v2 起保护的是整个 APK 的字节摘要，所以 v2 之后任何字节改动都会被拦住。v4 的验证对象是安装后的文件树，因此它天然允许在安装时补写。

验证链路的形状是：PackageParser 在 :1425 调 ApkSignatureVerifier.verify(input, apkPath, minSignatureScheme)（全仓共 6 个调用点，另见 ParsingPackageUtils.java:3476、PackageSessionVerifier.java:127、PackageInstallerSession.java:5359 等，PackageParser 是遗留解析路径之一）；skipVerify 分支（:1420-1424）改走 unsafeGetCertsWithoutVerification，绕过验证但仍给出证书——这是给系统内部重扫已装包用的口子。

v1 与 v4 的落点不同。v1 由 StrictJarVerifier.java（559 行）按 JAR 签名规则逐个条目校验。v4 的签名不进 APK 本体，而是落在 APK 文件旁边的独立 .idsig 文件里——V4Signature.EXT 就是 ".idsig"（frameworks/base/core/java/android/os/incremental/V4Signature.java:39）。取签名在 ApkSignatureSchemeV4Verifier.extractSignature（:76）：先问 IncFS（:85 IncrementalManager.unsafeGetFileSignature，命中则不再做一致性检查），拿不到再读 apk.getAbsolutePath() + V4Signature.EXT（:97），最后用 VerityUtils.getFsverityDigest（:115）核对「签名里记的摘要」与「实际文件的摘要」是否一致。

别把 VerityBuilder.java 当成 v4 的生成方：它的调用点共 4 处——ApkSignatureSchemeV2Verifier.java:416、ApkSignatureSchemeV3Verifier.java:1064、ApkSigningBlockUtils.java:380（apk-verity 树）加 ApkChecksums.java:587（fs-verity root hash），没有一处服务 v4。真正让 v4 区别于前三者的，是「签名与 APK 本体分离、靠 IncFS 或 fs-verity 的摘要自证」。

密钥轮转的全部信息在 v3 块的 Proof-of-rotation 结构里。ApkSignatureSchemeV3Verifier.java 的 verifyProofOfRotationStruct（import 在 :31）负责解析；VerifiedProofOfRotation por（:631）是解析产物。同一个 signer 的附加属性里出现第二条 Proof-of-rotation（PoR）就抛 SecurityException（:648 判 por != null、:650-652 记 metric、:654 抛出）。上限是「每个 signer 至多一条」，不是「一个包一条」——:898 明写 v3.2 支持 exactly two signers，双签名的包里可以各带一条。

rotationMinSdkVersion 不是「从哪个 SDK 起必须按轮转后的新钥验」的下限，而是一道防剥离比对。它写在 v3.0 块的附加属性里：ROTATION_MIN_SDK_VERSION_ATTR_ID = 0x559f8b02（定义 :622），在 verifyAdditionalAttributes 的 :699 case 中由 :706 attr.getInt() 读出。比对用的另一半是 v3.1 signer 块自身的 minSdkVersion——:358-363 把它存进 mOptionalRotationMinSdkVersion，而且只在该 signer 未被本平台选中（区间不覆盖当前 SDK_INT）时才存。两边在 :713-718 做相等性比对，不等就抛 SecurityException；若根本没有 v3.1 块，:708-711 直接报 Expected a v3.1 signing block targeting SDK version X, but a v3.1 block was not found。设计意图很清楚：不让「只认 v3.0 基本字段」的旧解析器靠看不见 v3.1 块来绕过轮转约束。

4.3 一个具体例子

假设某应用从钥 A 换到钥 B。

签名工具产出带 v3 块的新 APK，块内含一条 Proof-of-rotation 记录，链上依次是 A 和 B，rotationMinSdkVersion 指向支持轮转的那个 SDK。在只认 v3 基本字段的旧系统上，mOptionalRotationMinSdkVersion 不被解析，验证按块内旧证书路径走，应用照装。在 android17-release 上，verifyProofOfRotationStruct 解析出 VerifiedProofOfRotation por，mOptionalRotationMinSdkVersion 生效，系统知道"这个包的后继钥是 B"。

装完后，SigningDetails 通过 mergeLineageWith(...) 把祖先签名证书链并入当前签名详情。此后 PackageManagerService（PMS）比对升级时会拿血统判断同一应用，而不是只比单个证书——但「算不算同一应用」和「换钥后能继承什么」是两件事，后者由 PoR 上的能力位决定：SigningDetails.java:108-127 的 CertCapabilities 列出 INSTALLED_DATA(1)、SHARED_USER_ID(2)、PERMISSION(4)、ROLLBACK(8)、AUTH(16) 五档，查询侧 hasCertificateInternal（:933）在 :944 用 flags & mPastSigningCertificates[i].getFlags() 逐位比对；血统只在旧包单签名时才成立（hasAncestor :588 要求 oldDetails.mSignatures.length == 1，:938 注明 only single-signed apps can have pastSigningCertificates）。若某个 signer 的附加属性里出现第二条 PoR 记录，SecurityException（:648 判定、:654 抛出）终止验证。

7. 常见问题与误区

7.1 误区

误区一：v2 存在后 v1 就没用了。错。两者验证对象不同，老包与需要 JAR 语义的场景仍走 StrictJarVerifier；v1 到 v4 是并行机制。

误区二：v4 签名打在 APK 文件里。错。v4 落在 APK 旁独立的 .idsig 文件（V4Signature.EXT = ".idsig"），由 ApkSignatureSchemeV4Verifier.extractSignature 读取，并与 IncFS／fs-verity 的摘要做一致性检查；VerityBuilder.java 生成的是 v2/v3 的 verity 树，与 v4 无关。

误区三（看起来对其实是错的）：轮转后旧证书就作废了，且换钥后一律能继承原应用的数据与权限。前半错、后半也错。mergeLineageWith(...) 确实把祖先证书链并进 SigningDetails，旧证书作为血统成员保留；但继承什么由 CertCapabilities（SigningDetails.java:108-127）的五个能力位决定，查询侧按位比对（:944），能继承数据、共享 UID、签名级权限、回滚、鉴权是五件分开的事。另外血统只在旧包单签名时才成立（:588、:938）。

误区四：一个 APK 可以带多条轮转记录以便回退。错，且要分清口径：上限是每个 signer 的附加属性里至多一条 PoR（:650 判定、:654 抛出），不是「一个包一条」——v3.2 允许 exactly two signers（:898），双签名的包里可以各有一条。

7.2 高频提问

问：rotationMinSdkVersion 到底谁在读？答：两处、两个用途，别混。它作为 v3.0 块附加属性被读（ROTATION_MIN_SDK_VERSION_ATTR_ID = 0x559f8b02，:699 case、:706 取值）；比对对象是 v3.1 signer 块的 minSdkVersion（:358-363 存进 mOptionalRotationMinSdkVersion、:201 声明处），:713-718 做相等性比对，:708-711 在缺 v3.1 块时直接报错。追问：这机制防的是什么？答：防剥离——不让只认 v3.0 基本字段的旧解析器靠「看不见 v3.1 块」绕过轮转约束，而不是用来声明「从哪个 SDK 起换新钥」。

问：skipVerify 是不是等于不验签？答：它走 unsafeGetCertsWithoutVerification，确实不执行签名验证，但只用于已装包的内部重扫（:1420-1424）。追问：普通安装会走这条吗？答：不会，普通安装走 :1425 的 ApkSignatureVerifier.verify。

问：isPqcSigned() 与 isV32Hybrid() 什么关系？答：两者都在 SigningDetails.java，用于识别后量子混合签名形态；v3.2 的增量块 id 0x70e1c89f 是其载体。
