1. TL;DR

AudioTrack 与 AudioRecord 是应用播放与录制音频的唯一门面，但它们的 buffer 从不直达硬件：控制面经 Binder 让 audioserver 里的 AudioFlinger 建出一根 track，数据面则走共享内存环形缓冲——那块内存的句柄由 createTrack 的返回对象带来：AudioTrack.cpp:1906 调 audioFlinger->createTrack(aidlInput, response)，随后 :1946-1959 通过 output.audioTrack->getCblk(&sfr) 取出控制块与其背后的 sp<IMemory>。于是 write()/read() 只是在这块共享内存上搬运字节，不再经过 Binder 事务。混音、重采样在 AudioFlinger 里完成后，才交给 audio HAL。理解这条「控制走 Binder、数据走共享内存」的二分（以及 STATIC/STREAM 两种模式），是定位一切音频问题的起点。

3. 问题背景

「我 AudioTrack.write 写了数据却没声音」「录音读到全零」这类问题，根因常在链路中段而非两端：可能是 AudioFlinger 没把 track 接到正确的输出设备，可能是 HAL 没被打开，也可能是 buffer 模式选错导致数据被丢弃。本文把「应用写数据 → 混音 → 出声」这条链路在代码层面钉死，让定位有确定方向。

4. 核心机制

4.1 数据结构与状态定义

AudioTrack 在 Java 侧以两种模式运行：MODE_STATIC（一次性把全部数据写入，用于短音效，:147 定义 MODE_STATIC = 0）与 MODE_STREAM（流式持续写入，:152 定义 MODE_STREAM = 1）。无论哪种，track 成功初始化后状态为 STATE_INITIALIZED（:169）。AudioRecord 同样有 STATE_INITIALIZED（:113），是开始录制的前置条件。

4.2 关键流程（含失败路径）

播放侧：构造 AudioTrack（构造在 :746/:804）→ play()（:3171）→ 循环 write()（字节版 :3417、ByteBuffer 版 :3749）→ stop()（:3229）。write 的返回值表示本次消费/阻塞的字节数，负值代表错误。录制侧：startRecording()（:1501）→ 循环 read()（:1593）→ stop()（:1544）。

失败路径主要有：初始化未达 STATE_INITIALIZED（后续 write/read 直接报错）、AudioFlinger 连接失败（Binder 断连）、以及写速快于消费时的写侧行为（见下，这一点最常被写反）。

关于第三点，源码口径是明确的：write(...) 的默认重载走的是 `WRITE_BLOCKING`（AudioTrack.java:3418 把 WRITE_BLOCKING 传给内部 write；常量定义在 :438，WRITE_NON_BLOCKING = 1 在 :448）。也就是说：

  • 默认（阻塞）：写速超过消费时，write 会阻塞等待共享内存环形缓冲腾出位置，而不是把数据丢掉；数据只在 buffer 满到超时才可能报错，不会静默丢弃。
  • `WRITE_NON_BLOCKING`：写不动时立即返回 WOULD_BLOCK（或只写入一部分），由调用方决定重试还是跳帧。此时「丢弃」行为发生在应用自己选择丢弃，而不是框架替你丢。

反过来说，AudioTrack 侧常见的 `underrun` 才是「消费侧没跟上」的信号：buffer 被读空而没有新数据补上，由服务端/设备侧报告，方向与「生产者溢出」相反。把这两件事混为一谈，就会出现「write 卡住＝write 在丢数据」这种反向诊断。

图 2：STATIC 与 STREAM 两种模式的差异

STATIC : 应用一次写入全部数据 -> 框架按需播放（适合短音效）
STREAM : 应用边产边写 -> 框架边消费（适合音乐/实时）

4.3 关键代码逐段剖析

Java 门面只做封装与状态管理，play/stop/write 最终都走到 native。native 客户端 AudioTrack.cpp 是真正的传输层：start（:695）建立传输、stop（:835）结束、flush（:900）清空缓冲队列、setVolume（:1071/:1097）调增益、write（:2323）把用户 buffer 拷入共享内存环形队列。

跨进程的落点是 AudioFlinger.cpp 的 createTrack（:1048），它在 audioserver 进程里为本次播放创建一个服务端 track 对象，负责把多个客户端的 track 混音到同一输出。主音量由 setMasterVolume（:1311）统一管理。注意 AudioTrack 客户端库在 android17-release 已位于 frameworks/av/media/libaudioclient，与早期版本路径不同。

4.4 与相邻机制的关系

  • 与 audio HAL（AND-P4-301）的关系：AudioFlinger 通过 HAL 接口把混音结果写到硬件；HAL 篇讲契约，本篇讲框架侧如何驱动它。
  • 与 AudioPolicy（AND-P7-202）的关系：AudioFlinger 决定「怎么混」，AudioPolicy 决定「混完去哪个设备」，二者协作完成出声。
  • 与录制的关系：AudioRecord 是反向路径，数据从 HAL 经 AudioFlinger 的 record 分支回到应用（read）。

7. 常见问题与误区

7.1 误区

  • 「AudioTrack.write 返回就代表播出去了」。它只代表数据进了框架队列，AudioFlinger 何时混音、HAL 何时出声是后续步骤。
  • 「没声音一定是应用写错了」。更常见的是 AudioPolicy 把输出路由到了错误设备（见 202），或 AudioFlinger 未连接。
  • 「看起来对其实是错的」：以为 STATIC 模式适合长音频。STATIC 需一次性驻留全部数据，长音频应选 STREAM，否则内存与延迟都不可控。
  • 「录音读到零就是麦克风坏了」。更可能是权限、AudioRecord 未达 STATE_INITIALIZED，或 source 选错。

7.2 高频提问

问：如何判断声音卡在中段还是两端？ 答：dumpsys media.audio_flinger 看 track 是否已创建、buffer 是否流动；若 track 在但无输出，问题在 AudioFlinger→HAL 或路由（转 202）。 追问：STREAM 模式写入过快会怎样？ 答：默认走 WRITE_BLOCKING（AudioTrack.java:3418），写速超过消费时 write 会阻塞等待环形缓冲腾位；只有显式传 WRITE_NON_BLOCKING（:448）才会立刻返回 WOULD_BLOCK 或只写一部分。数据不会被框架静默丢弃——诊断到位见 §4.2。

问：为什么我的音量设置不生效？ 答：区分应用 setVolume（track 级增益）与 setMasterVolume（设备主音量），二者作用点不同。
