1. TL;DR

三套机制回答的是三个不同的问题：SELinux 判「这个域能不能对这个类型做这个操作」；seccomp 判「这个进程能不能发这个系统调用」；IMA 判「这个文件的内容和度量值对不对得上」。

拒绝发生时，avc: denied 一类审计来自 SELinux，进程被 SIGSYS 打死多半是 seccomp 过滤器命中 SECCOMP_RET_KILL_PROCESS，度量不匹配则会在打开或执行时失败，这三条线索互相不通约。

用户态的接口面都很薄：SELinux 侧是 libselinux 的 getcon()/setcon()/getfilecon() 与 Android 专用策略句柄入口；seccomp 侧是 linux/seccomp.h 的 SECCOMP_MODE_FILTER 与 BPF 动作位。

策略来源则是分层的：SELinux 的域映射解析 seapp_contexts 的五组候选路径；seccomp 的过滤器可以用 libminijail 编译并安装。

本篇只讲内核接口面与策略来源，不推断内核驱动的内部实现。

3. 问题背景

一条 open() 返回 EACCES，日志里躺着 avc: denied，但把这个文件在 shell 里 cat 一下又是通的——因为 shell 的域和应用的域不同。

另一条路径上，某个 native 进程刚启动就收到 SIGSYS，没有任何 Java 异常，tombstone 里只有一个信号和一条系统调用号，查半天不知道是谁拦的。

还有第三种：同样一份配置文件，改了内容之后进程起不来，报的是完整性错误而不是权限错误。

这三类现象被统称为「权限问题」，其实分属三套机制，排查手段完全不一样。

4. 核心机制

4.1 概念与关系

四个概念要放在一起看：安全上下文（security context） 是 SELinux 的标签串，形如用户:角色:类型:级别；域（domain） 是进程安全上下文里的类型字段；策略（policy） 是「域 × 类型 × 权限」的判定表；系统调用过滤器 与 完整性度量 是另外两套独立的判定层，不读写 SELinux 的策略库。

图 1：三套判定的先后与各自独立

进程发起一次操作
   ├─ seccomp 过滤器：系统调用号 + 参数 → 拦 / 放
   ├─ SELinux：域 + 目标类型 + 权限 → 拦 / 放
   └─ IMA：文件内容度量 / 签名 → 拦 / 放

三者可以任意一个先拒绝，拒绝的形态不同，所以第一步先认形态，而不是先翻策略。

4.3 一个具体例子

一个普通应用进程 fork 出来，要做域映射。libselinux 读 seapp_contexts 的五组候选路径，把每条规则解析成 struct seapp_context（:137），存进 seapp_contexts（:263）数组，nspec（:265）记条数。

匹配时逐个比选择器：进程是普通应用，user 命中 _app；再看 isPrivApp、seinfo、minTargetSdkVersion 等，一条规则里写了的都得对上——这是 AND 语义，任一不符就跳过。命中的那条给出该进程的域。

之后该进程发起 getfilecon()（:110）读目标文件的上下文，判定交给域对类型的权限表。若被拒，日志里是 avc: denied，而不是 SIGSYS。同一个进程如果另外装了 seccomp 过滤器，一个被禁的系统调用会在到达 SELinux 判定之前就被拦掉——两套机制的判定顺序由内核约定，用户态看到的只是「被拦了」。

7. 常见问题与误区

7.1 误区

误区一：所有权限拒绝都是 SELinux 干的。 错。seccomp 命中的表现是系统调用返回错误号（SECCOMP_RET_ERRNO）或进程直接死（SECCOMP_RET_KILL_PROCESS），根本不产生 avc: denied。先看有没有审计串，再决定翻哪套机制。

误区二：`seapp_contexts` 里某条规则只要有一个选择器对上就能命中。 恰好相反：一条规则里写的所有输入选择器都必须匹配，是逻辑与。少写一个选择器只是少一个约束，并非任选其一。

误区三：`security_context_t` 是推荐的写法。 它在头文件里已被显式标注 deprecated，带 __attribute__((deprecated))，只为兼容旧调用方保留。新代码用裸 char *。

误区四：`minijail_set_seccomp_filter_allow_speculation()` 名字里有 allow，就是放宽性能。 注释给的警告是：启用后可能对分支目标注入（Branch Target Injection）、推测存储绕过（Speculative Store Bypass）失去防护，只对不执行不可信代码的进程安全。

7.2 高频提问

问：进程被 SIGSYS 打死，怎么确认是 seccomp 而不是别的？ 答：SIGSYS 与过滤器命中 SECCOMP_RET_KILL_PROCESS 或 SECCOMP_RET_TRAP 的形态一致，同时不会有 avc: denied。确认过滤器来源要看该进程的启动方——它是否经 libminijail 加载了过滤器、策略文件里禁了哪些调用。 追问：那 SECCOMP_RET_ERRNO 呢？ 答：那种情况进程活着，只是某个系统调用返回特定错误号，容易被误读成普通权限失败，要看返回的错误号是否成规律地集中在少数几个调用上。

问：seapp_contexts 有 10 条候选路径，哪条生效？ 答：五组路径按分区分布，解析时把命中的规则汇成一张表，nspec 记下总条数，匹配时逐条按选择器与 AND 语义比较。分区各带一份的设计是为了让各分区独立演进，不代表只有一份被读。 追问：那多个分区都写规则会不会冲突？ 答：判定顺序由 android_seapp.c 的匹配过程决定，本篇不断言具体优先级；冲突排查时以实际命中的 struct seapp_context 为准，而不是猜想哪份文件赢。
