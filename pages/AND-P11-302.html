1. TL;DR

OEM/ODM 的定制代码至少落在四类位置：device/<oem>/<product>/ 的 product 配置、板级 BoardConfig.mk、overlay/rro_overlays/sepolicy/sysconfig 资源与策略叠加，以及设备侧原生代码与模块——goldfish 的 hals/ 有九个目录共 11 个 Android.bp，init/ 另有 init.ranchu.rc、init.system_ext.rc、ueventd.rc 与五个 init.*.sh。Treble 之后，framework 与 vendor 的分工由 hardware/interfaces/ 里的 AIDL/HIDL 接口和 VINTF 声明固定下来，不再靠头文件巧合。

libvndksupport 提供的是 llndk 面的 sphal namespace 加载 API。libvndksupport.map.txt 里三个符号的标注并不相同：:4-5 的两个加载符号标 llndk systemapi，:3 的 android_is_in_vendor_process 另标 llndk-deprecated=35 systemapi。它的调用方也分散在多处，不是某一条固定通道——libutils 用它做双载去重（system/core/libutils/misc.cpp :76）、libhidl 用它加载 Passthrough 服务实现（system/libhidl/transport/ServiceManagement.cpp :541）、binder 与 gralloc 用它取厂商实现（frameworks/native/libs/binder/IServiceManager.cpp :569、frameworks/native/libs/ui/Gralloc5.cpp :108）、多媒体侧 OMX 也走它（frameworks/av/media/libstagefright/omx/OMXStore.cpp :77）。

实现落点在 system/core/libvndksupport/linker.cpp（85 行）：android_load_sphal_library()（:64）先取 get_vendor_namespace()，再用 android_dlopen_ext 带上 ANDROID_DLEXT_USE_NAMESPACE 与 vendor namespace 句柄完成加载，取不到时才退回当前 namespace 并告警；android_is_in_vendor_process()（:52）靠 vndk namespace 的可见性反推当前是否在 vendor 进程，该函数在 linker.h :23-24 已标 deprecated。这是运行期动态加载，不是链接期行为。device/sample/ 是 AOSP 给出的定制化模板，device/generic/goldfish 是可读的参考机型实现，device/google_car/ 是 OEM 形态实例。本篇只讲落点与分工，构建产物未在本树验证。

3. 问题背景

接手一个新机型时，最常见的困惑是：厂商代码到底该放哪里。同一个「加一个开机服务」的需求，有人改 device/ 下的 .mk，有人动 BoardConfig.mk，有人只丢一个 overlay。第二层困惑在分工：Treble 之后，vendor 侧改一行代码为什么会影响 framework 侧的兼容性校验。第三层是 VNDK——很多人知道它存在，但说不清它在运行期到底替谁做了什么。这三层疑问指向同一件事：定制化的落点边界。

4. 核心机制

4.1 概念与关系

四个概念：product 配置定义「这台设备装什么」，板级配置定义「这台设备的硬件与分区参数」，资源与策略叠加定义「这台设备在运行时表现成什么样」，VINTF 与 hardware/interfaces/ 定义 framework 与 vendor 之间的契约。

图 1：定制化落点与 Treble 契约面的关系

  device/<oem>/<product>/          hardware/interfaces/
   ├─ AndroidProducts.mk           ├─ audio / bluetooth / camera
   ├─ product/*.mk  ─┐             ├─ boot / gnss / automotive
   │  （产品选择层）  │             └─ compatibility_matrices/
   └─ board/*.mk   ──┤                          │
      （板级参数层）  │                          │
                     ▼                          ▼
             构建出各分区镜像             VINTF 契约（AIDL/HIDL）
                     │                          │
   vendor/odm 分区 ◄──┴─────────────────────────►  system 分区 framework
                     │
        system/core/libvndksupport/linker.cpp（VNDK 运行期加载支撑）

（长代码块，建议到公众号/头条侧按截图策略处理）

关键关系：device/ 侧只做选择和参数，契约侧只做接口声明，两者通过 VINTF 对齐。vendor 分区里的实现只要满足 hardware/interfaces/ 的接口与 compatibility_matrices/ 的版本约束，就与 system 分区的 framework 解耦。

4.2 关键内容

本树 device/ 顶层有七类目录：amlogic、common、generic、google、google_car、linaro、sample。类别本身说明了分层意图：common 放跨机型共享片段，generic 放与具体厂商无关的参考实现，google/google_car 是实例，sample 是模板，amlogic/linaro 是平台方提供的参考。

device/sample/ 下分 apps、etc、frameworks、overlays、products、sdk_addon、skins 七个子目录。这七个名字就是 AOSP 对「定制化可以往哪放」的官方枚举：应用、预置配置、framework 补丁、覆盖层、产品配置、SDK 附加件、皮肤。

device/generic/goldfish 是可读的完整参考：product/ 有 11 项（base_phone.mk、phone.mk、tablet.mk、generic.mk、versions.mk 等 .mk 片段，另有一个 bluetooth.prop 属性文件），board/ 有 12 个条目（BoardConfigCommon.mk、emu64x、emu64a、fstab、kernel 等），AndroidProducts.mk 声明 12 个产品（sdk_phone64_x86_64、sdk_tablet_arm64、sdk_slim_x86_64 等）。这份结构可以直接对照三家 OEM 的实际树形。

OEM/ODM 实例看 device/google_car/：四个产品目录 cheetah_car、husky_car、panther_car、tangorpro_car，加一个 common/。common/ 内含 manifest.xml、sepolicy、overlay、rro_overlays、sysconfig、pre_google_car.mk、post_google_car.mk、unavailable_features.xml。AndroidProducts.mk 自第 17 行起声明 PRODUCT_MAKEFILES。这份清单就是 §4.1 四类落点的实物对照：manifest.xml 是 VINTF 侧，sepolicy/sysconfig/overlay/rro_overlays 是叠加侧，pre_/post_ 两个 .mk 是 product 配置的前后段注入。

Treble 契约面在树内可直接数：hardware/interfaces/ 下有 audio、bluetooth、camera、boot、gnss、dumpstate、gatekeeper、automotive、contexthub、compatibility_matrices 等。设备侧声明示例在 device/generic/goldfish/manifest.xml 首行：<manifest version="1.0" type="device" target-level="8">。

VNDK 侧，build/make/core/board_config.mk :1019 起是 check_vndk_version 的定义（:1020-1023，检查 prebuilts/vndk/v$(1) 下有无 Android.bp）；system/core/libvndksupport/linker.cpp 共 85 行，提供 sphal namespace 的库加载 API（android_load_sphal_library :64），符号按 llndk 面导出，供 vendor 侧进程按名加载 sphal 变体（本树实际调用方是 libutils 的双载去重）。这是 VNDK 最容易被忽略的一层：它不只管库集合，还管「进程怎么按 namespace 取到库的另一份副本」。

分区分工的直接证据：goldfish 的 AB_OTA_UPDATER := none 在 board/BoardConfigCommon.mk :39，是显式取反（该开关在 build/make/core/board_config.mk :973–:974 的默认值是 true）；而 PRODUCT_USE_DYNAMIC_PARTITIONS 开关在 build/make/core/board_config.mk :665。两个开关分属不同层、不同文件，改错位置就是典型的分工错误。

三类落点归纳：

4.3 一个具体例子

假设要在车载形态上加一个产品。路径是：在 AndroidProducts.mk 里加一条 PRODUCT_MAKEFILES 声明（对齐 device/google_car/AndroidProducts.mk :17 起的写法），在 common/ 里放共享片段，用 pre_google_car.mk/post_google_car.mk 的定位把本产品特有配置插在产品配置的前段与后段，硬件相关参数落 BoardConfig.mk，界面与能力差异落 overlay/rro_overlays/sysconfig，访问控制差异落 sepolicy。vendor 侧若要新增 HAL，只动 hardware/interfaces/ 的接口实现与设备侧 manifest.xml 的 VINTF 声明，不碰 framework。这条路径的每一段都能在本树找到对应文件，但实际构建产物未在本树构建验证。

4.4 与相邻篇的关系

AND-P11-201 讲 product 继承语法——inherit-product 的展开顺序、变量覆盖规则。本篇只讲「哪类内容该落在哪类文件」，语法细节归 201。AND-P11-301 讲 GMS 边界，决定无 GMS 机型在 overlay/sysconfig 上的定制自由度差异。签名与 OTA 信任归 AND-P11-202 与 AND-P9-301，本篇提到 AB_OTA_UPDATER 只用于说明分区分工，不展开更新流程。

7. 常见问题与误区

7.1 误区

误区一：定制就是把文件丢进 `device/` 就行。 纠正：device/ 只承载 product 配置与板级配置，运行时差异要靠 overlay/rro_overlays/sysconfig/sepolicy 叠加，这些在 device/google_car/common/ 里是分目录放的（内含 audio_effects.xml、manifest.xml、overlay、post_google_car.mk、pre_google_car.mk、rro_overlays、sepolicy、sysconfig 与两份 unavailable_features*.xml）。

误区二：VNDK 只是一份库清单。 纠正：system/core/libvndksupport/linker.cpp 存在说明它还有运行期加载职责——system 进程要取用 vendor 侧 SP-HAL 共享库，必须经 vendor namespace 的专门加载路径。

误区三（看起来对其实是错的）：`PRODUCT_USE_DYNAMIC_PARTITIONS` 与 `AB_OTA_UPDATER` 应该放一起。 纠正：前者在 build/make/core/board_config.mk 有引用（:665 是使用点，:672-675 才是两条 $(error)，含 BOARD_SUPER_PARTITION_SIZE 未定义校验；产品配置同样可以赋值，该文件只是校验点），后者在 board/BoardConfigCommon.mk :39。一个是构建系统的板级开关，一个是设备配置里的更新方式声明，层级不同。

7.2 高频提问

问：vendor 侧加一个 HAL，要不要动 frameworks/base？ 答：不动。接口在 hardware/interfaces/ 下，实现放 vendor 分区，设备侧在 manifest.xml 声明。 追问：那 framework 怎么知道 vendor 提供了什么？ 答：通过 VINTF 声明与 compatibility_matrices 的版本匹配，构建期与运行期各自校验。

问：device/generic/goldfish 能不能直接当 OEM 树模板？ 答：结构可以照抄，product/ 11 项与 board/ 12 个条目的分层方式就是模板（前者含 10 个 .mk 片段与 1 个 bluetooth.prop）。但它是模拟器参考实现，硬件参数与分区选择要换。 追问：device/sample/ 呢？ 答：该工程是 AOSP 提供的定制化模板，七个子目录对应七类可定制内容，适合看「能往哪放」，不适合看「完整机型长什么样」。

8. 边界与延伸

本篇不覆盖：product 继承语法细节（AND-P11-201）；签名与 OTA 信任链（AND-P11-202、AND-P9-301）；GMS 边界的具体条款（AND-P11-301）。

本篇前置依赖：AND-P11-301。另需注意产品入口在 device/generic/goldfish/64bitonly/product/（15 项中 12 个 .mk 由 AndroidProducts.mk 收录，另 3 个是 *.prop_template），同级的 product/ 是被 inherit-product 的共享片段——照后者抄入口会找不到自己的产品。

本篇后继：无严格后继；AND-P11-401 讲形态差异时可对照本篇的落点框架读。

数量级与边界值：

  • device/ 顶层七类目录：源码目录枚举，口径为 2026-10-23 于 android17-release 静态核。
  • goldfish product/ 11 项（10 个 .mk + 1 个 bluetooth.prop）、board/ 12 个条目、AndroidProducts.mk 12 个产品：同上口径。
  • system/core/libvndksupport/linker.cpp 85 行：同上口径。
  • manifest.xml 的 target-level="8"：VINTF 元数据，仅代表 goldfish 这一份声明，不代表其他设备的 level。
  • 构建耗时、镜像体积、OTA 包大小：暂无实测，列为待补。
