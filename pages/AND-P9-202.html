1. TL;DR

一个应用进程能碰什么，先由内核的 uid/gid 决定「物理上属于谁」，再由 SELinux 域决定「在 SELinux 策略上允许做什么」。uid 是固定的，域不是：同一个 u0_a123 在 targetSdk 不同时会落到 untrusted_app_34、untrusted_app 等不同域，权限面因此不同。域的选择查的是 seapp_contexts，输入是 uid、包名与 seinfo，外加 isSystemServer 标志（selinux_android_setcontext 四参签名，android_device.c:88-92），由 seapp_context_lookup 完成匹配。targetSdk 不是入参，而是 seinfo 串里的一个字段——SELinuxMMAC.java:460-472 把 seinfo 拼成「基础值 ＋ :privapp（特权时）＋ :targetSdkVersion=N ＋ :partition=X」的复合串，libselinux 侧再由 parse_seinfo（android_seapp.c:724）把它拆回来（:779 取出 targetSdkVersion），最后在 :903 与表里的 minTargetSdkVersion 比大小。安装期的签名白名单（mac_permissions.xml）把签名证书映射成 seinfo 的基础值，seinfo 再参与域匹配——这是「签名」与「域」的唯一连接点。数据目录的标签（如 app_data_file）从同一张表派生，文件隔离因此是 uid 隔离与 type 隔离两层叠加的结果。

3. 问题背景

有两个进程，ps -Z 看过去 uid 都是 u0_aXXX，但一个能读 /data/misc 下的某个文件，另一个不行。另一个常见困惑：同一个 App 只把 targetSdk 从 33 改到 34，什么代码都没动，却突然出现 avc: denied。还有一种：应用被声明为 isolatedProcess 后，open() 返回值全变成 EACCES，可它的 uid 看起来又不像普通应用。这三种现象的答案都落在同一处——进程身份到底由哪几样东西组成，各自在哪一步被确定。

4. 核心机制

4.1 概念与关系

四个概念：

  • uid/gid：内核 DAC 的主体标识，进程创建时由 Zygote fork 后 setuid/setgid 落下。
  • SELinux 域：进程的 SELinux 标签（如 untrusted_app），决定访问哪组 type。
  • seinfo：安装期由签名证书派生的复合字符串，是 seapp_contexts 的匹配输入之一，形如 platform:targetSdkVersion=34:partition=system。
  • type：文件的 SELinux 标签（如 app_data_file），由同一张表按进程属性派生。

图 2：从 fork 到标签落定

system_server ──指定 uid/gid/参数──> Zygote

两层顺序固定：DAC 先、SELinux 后。uid 一旦 setuid 就不可逆，所以 Zygote 必须在 fork 后、exec 前完成；域标签在这之后由 app 进程自己按 /proc/self/attr/current 写入。

uid 分段。Process.java 把 uid 空间切成互不重叠的几段，位于哪个段决定进程被当成什么：

普通应用段（10000–19999）里一个 uid 对应一个包（sharedUserId 显式共享的除外——共享 uid 的多个包必须落同一个 SELinux 域，SELinuxMMAC.java:360-373），是 DAC 隔离的粒度来源。SDK_SANDBOX_VIRTUAL_UID（Process.java:277，注释写明 "used to aggregate data related to SDK sandbox UIDs"）是给用量与电量统计用的聚合虚拟 uid，不参与 seapp_contexts 匹配——SDK 沙箱进程的匹配身份是 user=_sdksandbox，由 android_seapp.c:847-852 按 uid 落在 20000–29999 段推导（与 user=_app 同一条 if-else 链），对应条目在 seapp_contexts:185-187。PCC 段在应用段与隔离段之间单列，说明这几类主体在策略上被区别对待。

uid 的下发。ProcessList.java 负责为隔离进程挑 uid：IsolatedUidRange（:603）描述一段可分配的 uid 区间，IsolatedUidRangeAllocator（:648）负责挂包名与区间的对应，getIsolatedUidRangeLocked(String, int)（:671）是取用入口。分配至少涉及两个池：全局隔离池 mGlobalIsolatedUids（:712）用 99000–99999；挂在 app Zygote 下的隔离进程走 mAppIsolatedUidRangeAllocator（:723-724），区间是 90000–98999（Process.java:348/:362），并按 NUM_UIDS_PER_APP_ZYGOTE=100（:355）分片。此外还有第三条路径：开启 useSafesetidUidPolicy2 后，app Zygote 隔离 uid 改由 SafeSetID 侧统一管理，池是 mGlobalAppIsolatedUids（:733，:870 赋值）——getOrCreateIsolatedUidRangeLocked（:3454-3463）按「非 app Zygote／已开 SafeSetID 策略／其余」三分流，两池只是未开该策略时的主线。用完可回收——这是它与普通应用 uid 的本质差别：普通应用 uid 由安装决定并长期稳定，隔离进程 uid 是运行期临时资源。

参数怎么送到 Zygote。ZygoteProcess.java 的 :623 是注释，列出这一组 Zygote 参数；--setuid= 在 :626，--setgid= 在 :627。system_server 组装一串字符串参数，通过 Zygote 的 socket 发过去，Zygote fork 后解析参数并 setuid/setgid。这意味着 DAC 身份的授予点是 Zygote 子进程，而不是 system_server 自己——system_server 只有「指定」的权力，没有「代替执行」的能力。

域匹配表。seapp_contexts（222 行）是一张按属性匹配的表。targetSdk 阶梯在 209–216 行，从高到低匹配（:216 是「无门槛」的兜底行，不带 minTargetSdkVersion 键）：

minTargetSdkVersion=37untrusted_appseapp_contexts:209

注意两条细节。第一，:214 与 :215 都指向 untrusted_app_27，即 targetSdk 26 与 28 共用同一个域，阶梯不是一一映射。第二，最新一档（targetSdk ≥ 37）落回基线域 untrusted_app 本身，说明「新版本用主域、老版本用带后缀的兼容域」是整体设计方向：兼容域承载的是历史遗留的放行条目。

阶梯怎么比出来的，值得点明：表里写的是 minTargetSdkVersion=34 这样的门槛值，被比的是从 seinfo 里解析出的 targetSdkVersion——parse_seinfo（android_seapp.c:724）把 :targetSdkVersion=N 拆出来（:779），比对发生在 :903 的 cur->minTargetSdkVersion > info.targetSdkVersion。也就是说 targetSdk 这条线走的是「seinfo 子串 → 解析 → 与表内门槛比大小」，不是另开一个入参。

域阶梯的物理形态。system/sepolicy/private/ 下共 8 个相关文件：untrusted_app.te（23 行）、untrusted_app_25.te、_27、_29、_30、_32、_34 六份兼容域，再加公共文件 untrusted_app_all.te（public/untrusted_app.te 另有一份，声明哪些 app 会落进这个域）。主域文件只有 23 行，说明它主要靠引用公共文件组织规则，兼容域各自叠加删减。这种「一个基线 + 一列新旧域 + 一份公共尾部」的结构，让 targetSdk 的影响面可以被精确 diff。

app 域公共规则。app.te（903 行）是所有 app 类域共享的规则集合。它与 untrusted_app_all.te 的分工是：前者定义「凡是 app 就允许」的部分，后者定义「凡是 untrusted_app 家族就允许」的部分。域越往下（25/27/29…），叠加的额外放行越多。

文件侧 type。seapp_contexts 的 209–216 行每条都带 type=app_data_file，这一列决定的是进程数据目录的标签。同表还有 privapp_data_file 这类 type（:194-198，特权应用数据目录），以及 ephemeral_app 这类域（:193 user=_app isEphemeralApp=true domain=ephemeral_app type=app_data_file——临时应用换的是域，数据目录标签仍是 app_data_file）。:138 与 :139 是两条并列的 neverallow，分别针对 user=_app isPrivApp=false name=.* seinfo="" 与 seinfo=default 两种形态——即「基础 seinfo 为空」与「基础 seinfo 落到默认值」都不许触及相关标签，这是编译期就挡住越界的写法。

域间最小授权的形状。untrusted_app.te 里对 sdk_sandbox_data_file 放了两条、又用一条 neverallow 收口：:20 放行 fd 的 use，:21 追加放行 file 的 write，但 :23 用 neverallow ... :file { open create } 把「自己打开或新建」封死。合起来看是「能用别人递过来的 fd、也能往里写，但不能自己开文件」——只讲 :20 会漏掉 :21 的写权限，只讲放行又会漏掉 :23 的封口。这类条目是域阶梯差异的来源，也是「看起来 uid 相同、实际权限不同」的直接原因。

签名的接入点。mac_permissions.xml（77 行，10 个 <signer>）把签名证书映射成 seinfo；SELinuxMMAC.java（834 行）是这套映射的 Java 实现，安装期为包算出 seinfo。seinfo 一旦算出，就作为 seapp_contexts 的匹配输入参与域选择。这条链是签名在运行期产生实际效果的通道。

查表入口。android_seapp.c（982 行）是 libselinux 侧的匹配实现：seapp_context_lookup_internal 在 :810，对外入口 seapp_context_lookup 在 :972，:981 是转发。普通应用、SDK 沙箱与隔离进程（com_android_internal_os_Zygote.cpp:2174 是调用点）的域与数据目录标签都从这里取出，它是策略表与运行时标签之间的桥。system_server 是例外：Zygote 侧在 fork 后直接硬编码 selinux_android_setcon("u:r:system_server:s0")（com_android_internal_os_Zygote.cpp:2204-2208，TODO 明示待删），seapp_contexts:165 的 isSystemServer=true domain=system_server_startup 只覆盖 startup 路径，不是主进程的取域来源。

4.3 一个具体例子

一个 targetSdk 34 的第三方应用被拉起。system_server 通过 ZygoteProcess 的 --setuid=/--setgid= 参数把 u0_a123（落在 10000–19999 段）传给 Zygote；fork 后 setuid 完成，DAC 身份已定。接着 app 进程调 seapp_context_lookup，输入是 uid、包名与 seinfo——seinfo 此时形如 default:targetSdkVersion=34:partition=...，parse_seinfo 从中取出 34，在 seapp_contexts 里命中 :210 的 minTargetSdkVersion=34，得到 untrusted_app_34；同一行的 type=app_data_file 给出数据目录标签。

把 targetSdk 改成 32，重装后同样的 uid 和包名，命中的变成 :211，域变为 untrusted_app_32。DAC 侧一模一样，SELinux 侧换了一整套规则。

若这个包在 mac_permissions.xml 里没有对应的 <signer> 条目，seinfo 的基础值不是空字符串，而是落到默认值 default（SELinuxMMAC.java:80 DEFAULT_SEINFO、:461 赋值），随后的 :privapp/:targetSdkVersion=N/:partition=X 照旧拼上——seapp_contexts:139 那条 neverallow 针对的正是 seinfo=default 这种形态（:138 针对的是 seinfo=""）。所以「没有签名映射」不等于「没有 seinfo」，它只是拿不到由签名带来的基础值。

7. 常见问题与误区

7.1 误区

误区一：uid 相同就等于权限相同。 不对。uid 只决定 DAC 侧的「属于谁」。同一个 uid 完全可能落在不同 SELinux 域，域之间的 allow 规则由 mac_permissions.xml、targetSdk、是否特权应用等共同决定。

误区二：targetSdk 只影响行为兼容，不影响安全。 这是最「看起来对其实是错的」的一条。targetSdk 是域选择的直接输入（seapp_contexts:209-216），升到 34 就从 untrusted_app_32 切到 untrusted_app_34，可用规则集整块变化。只看代码是否兼容会漏掉 avc: denied。

误区三：隔离进程只是「uid 特殊」。 而且「特殊」还不止一段：隔离 uid 有两套池打底——全局池 99000–99999，app Zygote 池 90000–98999，都是运行期临时分配、用完回收复用（开 useSafesetidUidPolicy2 后 app Zygote 池还改由 SafeSetID 侧统一管理，见 §4.2）；普通应用 uid 则在安装后稳定。这个差别意味着它不能用「某 uid 一定对应某包」来做推理，也不能靠固定 uid 做文件授权。

误区四：`app.te` 和 `untrusted_app.te` 是同一套规则的粗细两版。 不是。app.te 是「所有 app 域都适用」的公共规则，untrusted_app_all.te 是「所有 untrusted_app 家族」的规则，两者是纵向上级关系；untrusted_app.te 只有 23 行，主要靠引用，不是 app.te 的裁剪副本。

7.2 高频提问

问：一个包在 mac_permissions.xml 里没有匹配的 <signer>，会怎样？

答：基础 seinfo 落到默认值 default（SELinuxMMAC.java:80 DEFAULT_SEINFO、:461 赋值），而不是空字符串。seapp_contexts 里两条 neverallow 各管一种形态：:138 管 seinfo=""、:139 管 seinfo=default；非特权应用落到后者时，策略层面不会被授予特权路径所需的标签。

追问：那它还能正常当普通应用跑吗？

答：能。default 不等于不能运行，它只是拿不到由签名映射带来的额外放行；最终域仍由 seinfo 里的 :targetSdkVersion=N 与表内门槛比对决定。

问：SDK_SANDBOX_VIRTUAL_UID = 1090 为什么不落在 20000–29999 段里？

答：它不是内核 DAC 上的实际 uid，是用量与电量统计的聚合身份（Process.java:273-277 注释），不参与 seapp_contexts 匹配。SDK 沙箱进程在 DAC 上落到 20000–29999 段，策略匹配走的是 user=_sdksandbox（android_seapp.c:847-852 按 uid 段推导），命中 seapp_contexts:185-187。把两套编号分开，是为了让统计聚合与策略匹配各走各的口径。

8. 边界与延伸

本篇不覆盖：内核 SELinux 的 AVC 判定与 type enforcement 语义（AND-P5-501）；运行时权限模型与 AppOps（AND-P9-201）；密钥存储分层（AND-P9-401）。

本篇前置依赖：AND-P5-501。

本篇后继：AND-P9-201（权限模型在本篇的域约束下工作）、AND-P9-401（密钥服务访问受本篇域规则限制）。

数量级与边界值：

  • 普通应用 uid 空间 10000–19999，共 10000 个槽位（口径：Process.java 常量，FIRST_APPLICATION_UID/LAST_APPLICATION_UID）。
  • 隔离进程 uid 有两套池打底，别只记一段：全局隔离段 99000–99999，共 1000 个槽位（FIRST_ISOLATED_UID/LAST_ISOLATED_UID，ProcessList.java:712 用它们建 mGlobalIsolatedUids）；app Zygote 隔离段 90000–98999，共 9000 个槽位（Process.java:348 FIRST_APP_ZYGOTE_ISOLATED_UID、:362 LAST_APP_ZYGOTE_ISOLATED_UID，ProcessList.java:723-724 用它们建 mAppIsolatedUidRangeAllocator）。挂在 app Zygote 下的隔离进程走后者；开 useSafesetidUidPolicy2 时后者改由 mGlobalAppIsolatedUids（ProcessList.java:733）承担。
  • seapp_contexts 的 targetSdk 阶梯共 8 档（含 :216 的无门槛兜底），其中两档共用 untrusted_app_27（口径：seapp_contexts:209-216）。
  • 签名白名单生效条目 6 个（口径：mac_permissions.xml，sed -n '48,$p' … | grep -c '<signer' 可复核；直接 grep -c '<signer' 得 10，含注释块 :4-47 里的 4 个示例）。
  • 单个设备上同时存在的隔离进程上限受 IsolatedUidRangeAllocator 的池大小约束，具体数值随分区配置变化；暂无实测，列为待补。
