1. TL;DR

Binder 内核驱动对用户态只暴露一层窄契约：14 个 ioctl 入口、22 条命令协议、24 条返回协议。线程池的"够不够用"由 BINDER_SET_MAX_THREADS 的上限和 BR_SPAWN_LOOPER 的扩线程请求共同决定，用户态 joinThreadPool 的第一件事是 BC_ENTER_LOOPER 或 BC_REGISTER_LOOPER。优先级继承的入口在 node 的 flat_binder_object 标志位里，只有 FLAT_BINDER_FLAG_INHERIT_RT 置位、且是同步事务时，调用方才把实时调度策略传进来。协议版本号在 64 位平台上为 8。驱动实现本身不在本树核验范围，本篇只写契约面。

3. 问题背景

跨进程调用偶发变慢，抓 trace 看到调用线程在等回复，服务端侧无线程可用。线程池明明设了上限，实际起来的线程数却对不上。另一头，音频链路的服务线程被普通优先级的调用方拉进长事务后，实时性突然掉了。这两类现象都不是用户态代码能单独解释的，答案在驱动那一侧的契约里：线程什么时候被叫起来、优先级什么时候被沿调用链传下去。

4. 核心机制

4.1 概念与关系

四个概念。节点（node）是驱动里一个可被跨进程引用的服务实体，它携带 flat_binder_object 里的标志位。线程池（thread pool）是每个进程在驱动侧挂着的线程集合，靠 BINDER_SET_MAX_THREADS 定上限、靠 BR_SPAWN_LOOPER 触发扩容。事务（transaction）是一次 BC_TRANSACTION 到 BR_TRANSACTION 的搬运，中间由 ioctl 的 BINDER_WRITE_READ 承载。调度策略位挂在 node 上，决定调用方优先级能否被继承。

图 1：契约面各层的对应关系

用户态 libbinder         驱动契约头            驱动侧实体
ProcessState.cpp   ->  binder.h ioctl 枚举  ->  线程池上限
IPCThreadState.cpp ->  BC_*/BR_* 协议       ->  事务与线程登记
flat_binder_object ->  flags 位             ->  node 调度策略

一个进程只有一条 BINDER_WRITE_READ 主干：写方向塞 BC_* 命令，读方向回 BR_* 返回。线程登记、事务投递、缓冲释放全在这条主干上来回。

4.2 关键内容

入口层：14 个 ioctl。 enum 起始于 binder.h:308，入口从 :309 排到 :322。其中和本篇直接相关的三个：

名称含义出处

同族还有 BINDER_SET_IDLE_TIMEOUT（:310）、BINDER_SET_IDLE_PRIORITY（:312）、BINDER_SET_CONTEXT_MGR（:313）、BINDER_THREAD_EXIT（:314）、BINDER_VERSION（:315）、BINDER_GET_NODE_DEBUG_INFO（:316）、BINDER_GET_NODE_INFO_FOR_REF（:317）、BINDER_FREEZE（:319）、BINDER_GET_FROZEN_INFO（:320）、BINDER_ENABLE_ONEWAY_SPAM_DETECTION（:321）、BINDER_GET_EXTENDED_ERROR（:322）。注意 BINDER_SET_IDLE_TIMEOUT 与 BINDER_SET_IDLE_PRIORITY 是历史入口，现代用户态不以此调度。

线程池：上限与扩容是两件事。 用户态侧 ProcessState.cpp:49 定义 DEFAULT_MAX_BINDER_THREADS 15；setThreadPoolMaxThreadCount(size_t maxThreads)（:451）经 ioctl(mDriverFD, BINDER_SET_MAX_THREADS, &maxThreads)（:455）把上限交给驱动。上限只约束数量，不负责唤醒。扩容请求由驱动在需要时说：返回协议里有一条 BR_SPAWN_LOOPER（:478）。用户态收到它就新起一个线程进 joinThreadPool，而 joinThreadPool 的首个动作是写 BC_ENTER_LOOPER（主线程）或 BC_REGISTER_LOOPER（新线程），见 IPCThreadState.cpp:847。也就是说，每个线程都必须向驱动登记，驱动才知道池里现在有几个可用线程。

图 2：线程从登记到扩容的契约往返

joinThreadPool -> BC_ENTER_LOOPER / BC_REGISTER_LOOPER  (登记)
驱动侧计数        (池内可用线程)
需要更多 -> BR_SPAWN_LOOPER  (请求扩容)
用户态新线程 -> joinThreadPool -> BC_REGISTER_LOOPER

上限是真约束：线程数到 BINDER_SET_MAX_THREADS 给的值后，驱动不再要求扩容。此时事务会排队，调用方表现为等回复变长。

命令与返回：22 与 24。 命令协议 enum binder_driver_command_protocol（:537-637）共 22 个，用户态写给驱动。返回协议 enum binder_driver_return_protocol（:415-535）共 24 个，驱动读给用户态。

优先级继承：位在 node 上，不在调用上。 flat_binder_object（:125）的结构是 hdr ＋ __u32 flags ＋ union（binder／handle）＋ cookie。flags 的语义在 enum flat_binder_object_flags（:53）里：

名称含义出处
FLAT_BINDER_FLAG_PRIORITY_MASK低 8 位，最低调度优先级掩码binder.h:65
FLAT_BINDER_FLAG_ACCEPTS_FDSnode 接受文件描述符binder.h:69
FLAT_BINDER_FLAG_INHERIT_RT允许继承实时调度策略binder.h:91
FLAT_BINDER_FLAG_TXN_SECURITY_CTX事务携带安全上下文binder.h:99

策略位本身占两个比特，起点是 FLAT_BINDER_FLAG_SCHED_POLICY_SHIFT = 9（:47），组合形式为 FLAT_BINDER_FLAG_SCHED_POLICY_MASK（:82-83，等于 3U << FLAT_BINDER_FLAG_SCHED_POLICY_SHIFT）。两比特编码四种（:76-81 注释）：00b 对应 SCHED_NORMAL，01b 对应 SCHED_FIFO，10b 对应 SCHED_RR，11b 对应 SCHED_BATCH。

关键在 FLAT_BINDER_FLAG_INHERIT_RT（:91）的注释：只有这一位置位，调用进入该 node 时才会从调用方继承实时调度策略，而且仅限同步事务（"for synchronous transactions"）。没置位，普通优先级调用方不会被抬高；置位但走 oneway，也不继承。

图 3：优先级继承的判定顺序

调用方发起同步事务
  -> 目标 node 的 flags 有 INHERIT_RT 吗
       否 -> 不继承，按 node 自身策略运行
       是 -> 调用方是实时策略吗
             是 -> 把策略传给服务线程
             否 -> 无可继承内容

注意这是契约描述，不是驱动内部实现描述。

4.3 一个具体例子

设服务进程启动时调 setThreadPoolMaxThreadCount(...)，上限落到 BINDER_SET_MAX_THREADS。主线程已写 BC_ENTER_LOOPER，另有两个线程写 BC_REGISTER_LOOPER，池内登记 3 个。三个并发同步事务各占一个，第四个调用方进来，驱动侧无空闲线程、上限又没到，于是回一个 BR_SPAWN_LOOPER；服务进程起新线程，joinThreadPool 写 BC_REGISTER_LOOPER，池内变 4 个，第四个事务被接走。这里线程池扩容是驱动请求、用户态响应的往返，用户态无法自主"多起几个线程"来提升处理能力。

再看优先级。音频服务把某个 node 的 flags 里两个策略位写成 01b、并置 FLAT_BINDER_FLAG_INHERIT_RT。此时一个 SCHED_FIFO 的调用方发起同步事务，服务线程按契约可继承实时策略。换成 oneway 传入，同一个 node 不继承——同步限定是硬条件，不是实现细节。

7. 常见问题与误区

7.1 误区

误区一：线程数上去了，处理能力就上去了。 上限只是天花板，扩容的动议在驱动侧。用户态能做的只有把上限抬高，以及收到 BR_SPAWN_LOOPER 后老实登记一个新线程。手工多起几个 joinThreadPool 线程当然有效，但那等于自己绕过驱动的扩容节奏，池内登记数与驱动预期就会不一致。

误区二：设置了优先级就一定被继承。 看起来对，其实错。策略位在 node 上，不在调用上。node 的 flags 里 FLAT_BINDER_FLAG_INHERIT_RT 不置位，调用方再高的实时优先级也不会传进去；置位了但事务是 oneway，同样不继承（"for synchronous transactions"）。

误区三：`BR_TRANSACTION_COMPLETE` 意味着对端处理完了。 它只表示本端这次写已交给驱动。同步事务要等 BR_REPLY；对端死掉等 BR_DEAD_REPLY；失败等 BR_FAILED_REPLY。把 complete 当 reply，会漏掉对端迟迟不回复的真实耗时。

误区四：bionic 里那份 `binder.h` 和 kernel-headers 那份可以混着用。 前者是自动生成拷贝，247 行，注释被裁掉，行号与权威头完全不可对账。查契约语义只认 external/kernel-headers 那份。

7.2 高频提问

问：BINDER_VM_SIZE 是给线程用的吗？ 答：不是。ProcessState.cpp:48 的 BINDER_VM_SIZE ((1 * 1024 * 1024) - sysconf(_SC_PAGE_SIZE) * 2) 是映射给驱动收发缓冲的地址空间大小，和线程池数量无关。 追问：那线程池大小靠什么决定？ 答：默认值 DEFAULT_MAX_BINDER_THREADS 15（:49），运行期可经 setThreadPoolMaxThreadCount 改；实际起多少线程由 BR_SPAWN_LOOPER 的到达节奏决定，两级都受约束。

问：BINDER_FREEZE 和线程池有关系吗？ 答：有边界关系。冻结进程时事务会挂起，BR_TRANSACTION_PENDING_FROZEN（:520）与 BR_FROZEN_REPLY（:507）是对外可见的两个返回码。但冻结主体机制不在本篇范围。 追问：那我现在能拿它判断什么？ 答：只判断"我这个事务是不是撞上了冻结"，不要在冻结场景下把挂起误读成线程池满。
