1. TL;DR

电源、震动、NFC、门锁四类小 HAL 都属硬件抽象层（HAL），接口都是 AIDL 包，规模落在 5 个方法（IOemLock）到 30 个（IVibrator）之间，共性是「方法不多、每个参数都带状态语义」。判断一个能力有没有 HAL 接口，先看 hardware/interfaces/<域>/aidl/android/hardware/<域>/ 下有没有 interface 声明，再看方法签名里的参数与回调。电源 HAL 的 hint session 面向调度器，震动 HAL 用 Effect＋EffectStrength 描述动作，NFC 的 open/close 成对且 close 要带关闭类型，门锁 HAL 用 getName 区分锁、用 byte[] 承载校验请求有效性的厂商签名。四者的通用契约（版本声明、接口查询、兼容性校验）不属于本篇，归 AND-P4-101。

3. 问题背景

你在写一个系统服务，需要「让设备短震一下」或「查设备是否允许 OEM 解锁」。翻 frameworks/base 找到某个 Manager 类，但不确定它底下到底有没有硬件侧接口、换一台机器还灵不灵。再往前一步：升版本后被 vendor 兼容性卡住，报错指向某个 HAL 版本，你分不清这是接口本身演进，还是厂商实现没跟上。这四类小 HAL 的共同问题是「接口窄、语义强」——方法少，但每个参数都带约定，读错一个布尔或漏掉一个回调就整条链路失效。本篇把它们的形状摊开，让你能定位「这件事该找哪个服务」。

4. 核心机制

4.1 概念与关系

四个概念：HAL 接口（interface 声明）、调用方 Manager/服务、能力或状态枚举、回调参数。关系是单向的：上层 Manager 绑定 HAL 接口，用枚举参数表达意图，需要异步结果时传回调。

图 1：四类小 HAL 的调用方向

上层 Manager / 系统服务
        |
        v
  HAL interface (AIDL)
        |
        v
  vendor 实现（HAL 服务进程）

四份接口的差异不在调用方向，而在参数承载的语义：电源用 hint 描述负载、震动用枚举描述动作、NFC 用回调会话描述连接、门锁用 byte[] 承载厂商自定义数据。

4.2 关键内容

通用形状是「方法不多＋状态语义明确」，但四者的量级并不齐：最小的 IOemLock 只有 5 个方法，最大的 IVibrator 有 30 个。下面按接口逐个看。电源 IPower（14 个方法）的核心方法：

名称含义出处
setMode(Mode, boolean)设置电源模式及是否启用IPower.aidl:45
createHintSession为线程组创建 hint sessionIPower.aidl:105
getHintSessionPreferredRate查询 hint session 首选频率IPower.aidl:115
createHintSessionWithConfig带配置 bundle 的 hint sessionIPower.aidl:131

createHintSession 与 createHintSessionWithConfig 成对存在：前者给线程组，后者额外带配置 bundle。hint session 面向调度器，不是让应用直接改频率，而是把负载意图告诉底层。

震动 IVibrator（30 个方法）：

名称含义出处
getCapabilities()返回能力位IVibrator.aidl:88
off()关闭震动IVibrator.aidl:98

getCapabilities 的能力位决定调用方能否用回调，注释落在 IVibrator.aidl:105/118。这意味着「能不能拿到异步完成通知」不是查文档问出来的，是读能力位读出来的。

NFC INfc（11 个方法）：open(INfcClientCallback)（INfc.aidl:41）成功后控制器才接受 NCI 命令；close(in NfcCloseType type)（INfc.aidl:55）要带关闭类型。关闭类型由 NfcCloseType 枚举表达，该枚举文件（NfcCloseType.aidl）与接口同目录。

门锁 IOemLock（5 个方法）：

名称含义出处
getName()返回锁名称IOemLock.aidl:40
setOemUnlockAllowedByCarrier(boolean, byte[])运营商维度设置IOemLock.aidl:72
setOemUnlockAllowedByDevice(boolean)设备维度设置IOemLock.aidl:80

门锁这条接口跨了两代机制，两处痕迹别混：hardware/interfaces/oemlock/1.0/ 里是 HIDL 时代的 IOemLock.hal 与 types.hal，与 aidl/ 同级；AIDL 这一代自己的版本推进记在 aidl/aidl_api/android.hardware.oemlock/ 下：1/ 是 v1 的冻结快照，current/ 是当前接口导出的快照，两者都由构建系统生成、不允许手改（文件头就写着 IMMUTABLE）。

4.3 一个具体例子

场景：系统服务要实现「短震一下并知道何时结束」。走 IVibrator：先调 getCapabilities()（IVibrator.aidl:88）读能力位，确认是否支持回调；支持则调 on(timeoutMs, callback)（IVibrator.aidl:113），把时长和回调一起传下去，回调返回即震动结束。若上层想要的是「按效果震」而非「按时长震」，改用 perform(Effect, EffectStrength, callback)（IVibrator.aidl:131），由 HAL 把效果映射成具体波形。两条路都不需要上层知道马达型号——这正是小 HAL 的价值。

7. 常见问题与误区

7.1 误区

  • 误区：小 HAL 方法少，所以可以硬编码版本。纠正：方法少不等于契约松散。门锁这一条在同一棵树里就摆着两代痕迹：上级目录的 1.0/ 是 HIDL 的 .hal，aidl/ 是 AIDL 版，而 AIDL 版内部还有 aidl_api 的冻结快照。硬编码版本会在换机时直接失败。
  • 误区：`on` 和 `perform` 只是语法糖二选一。纠正：on 按毫秒时长，perform 按 Effect＋EffectStrength；后者的效果映射由 HAL 负责，跨设备表现不同。选错会导致马达行为不可预期。
  • 误区：震动回调总是可用。纠正：这个判断看起来有理，其实是错的。能否用回调由 getCapabilities() 的能力位决定，注释明确落在 IVibrator.aidl:105/118。不读能力位就传回调，在不支持的实现上会拿不到完成通知。
  • 误区：`INfc.close` 无参数调用即可。纠正：close 要带关闭类型（INfc.aidl:55），类型由 NfcCloseType 枚举表达。漏掉类型等于跳过正常关闭会话的路径。

7.2 高频提问

问：我要「让设备别降频」，能不能直接调 IPower？ 答：IPower 暴露的是 setMode(Mode, boolean) 与 hint session 系列，hint session 是告诉调度器的负载提示，不是直接改频率的开关。真正怎么用这些提示是电源与功耗策略，见 AND-P10-301。 追问：那 createHintSession 和 createHintSessionWithConfig 我该用哪个？ 答：前者只给线程组，后者额外带配置 bundle；需要下发配置就用后者，两者成对存在（IPower.aidl:105/131）。

问：IOemLock 的 setOemUnlockAllowedByCarrier 带 byte[]，这个字节数组是什么？ 答：接口注释里写得很直白——@param signature to prove validity of this request or empty if not required（IOemLock.aidl:65），也就是用来校验这次设置请求有效性的厂商签名，不需要时可传空。哪种签名算对、走什么协议，由 vendor 实现决定。要看解锁流程本身怎么走，见 AND-P8-101 与 AND-P8-102；启动链如何验证见 AND-P9-102。
