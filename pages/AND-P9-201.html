1. TL;DR

权限分成两层：安装期决定「有没有」，运行期决定「此刻给不给」。normal 与 signature/signature|privileged 走安装期判定，只有 dangerous 需要运行期弹窗。权限组只影响弹窗如何归并与用户心智，不构成放行单位。特殊权限（如悬浮窗）没有 grant 授权状态，检查发生在调用时：checkPermission 遇 isAppOp 权限转交 app op 检查，窗口侧再以 noteOpNoThrow 现查一次——op 非 MODE_DEFAULT 时按 op 模式判定，只有 MODE_DEFAULT 才回退查 checkPermission。判定权在 system_server 进程，UI 与默认授予策略只是提案方。

3. 问题背景

应用声明了 SYSTEM_ALERT_WINDOW，用户在设置中找不到「悬浮窗权限」这一项，代码里 checkSelfPermission 却返回拒绝。另一个场景：用户给了一个权限组里的某个权限，同组另一个权限似乎「顺带」也被放行了。还有人发现 dangerous 权限被授予后，某个 API 调用仍然被拒。这三个现象指向同一个结构问题：权限不是一个布尔量，而是「安装期承诺 + 运行期状态 + 操作级管控」三层拼起来的判定链。

4. 核心机制

4.1 概念与关系

四个关键概念。权限条目（permission）是 AndroidManifest.xml 里的一条 <permission，带 protectionLevel。权限组（permission-group）是弹窗与设置页的归并单位。授权状态（grant）记录某包在某用户下是否已获某权限，由 PermissionManagerService 持有。应用操作（app op）是操作级开关，由 AppOpsService 按每次调用现查。

               app op 开关 ---- 每次敏感操作现查

三层不是串联放行，两层状态也不是各自独立演化。grant 存在 PermissionManagerService、app op 模式存在 AppOpsService，两处分开存；但 PermissionPolicyService 会把前者推导成后者并回写——synchronizeUidPermissionsAndAppOps(uid)（:623）与 synchronizePermissionsAndAppOpsForUser(userId)（:649）造一个内部类 PermissionToOpSynchroniser（:732），收齐包后调 syncPackages()（:819）逐个翻转。

同步的覆盖边界分三层，不是所有包、所有权限都参与：包级 addPackage 先挑包——拿不到包信息或 requestedPermissions 为空直接返回（:1013-1024），ROOT_UID/SYSTEM_UID 的包整体不同步（:1026-1030，注释说明这两个 uid 永远通过权限检查，动它们的 app op 只会破坏兼容性）；权限级 addAppOps 再查映射表，mRuntimeAndTheirBgPermissionInfos 缺项即返回（:874-877）；最后 addPermissionAppOp（:882）在三种情况下跳过——非 runtime 权限（:884）、带 FLAG_PERMISSION_REVIEW_REQUIRED 待复核（:893）、getSwitchOp() 返回 OP_NONE 即没有关联 op 的（:901，:902 的注释点明后台权限没有关联 op）。addAppOps 还经 addExtraAppOp（:879 调用、:971 定义）为 soft-restricted 权限另排 extra op，按 mayAllowExtraAppOp()/mayDenyExtraAppOpIfGranted() 分流（:993-997）；这里的 ignoreIfNotAllowed 不是 mode 常量（AppOpsManager 只定义 MODE_ALLOWED/MODE_IGNORED/MODE_ERRORED/MODE_DEFAULT/MODE_FOREGROUND 五种），而是队列 mOpsToIgnoreIfNotAllowed（:761）——setUidModeIgnoredIfNotAllowed（:1046）只在当前 op 模式非 MODE_ALLOWED 时把它落成 MODE_IGNORED（:1053）。推导出的模式按 MODE_ALLOWED/MODE_FOREGROUND/MODE_IGNORED 三档入队，syncPackages() 按 allow → foreground → ignore → ignoreIfNotAllowed 的顺序写，先写到的胜出（:820-823 的注释：两条变更撞同一个 op 时取最宽松的一档）。

所以「权限授予了但操作仍被拒」主要落在三类地方：不在同步覆盖范围里的权限（特殊权限走 app op 而非 runtime 权限）、没有关联 op 的权限、以及 grant 刚变、同步尚未跑完的窗口期。

4.2 关键内容

安装期与运行期的分界由 protectionLevel 决定。frameworks/base/core/res/AndroidManifest.xml 里有 1160 个 <permission> 元素（按行 grep -c '<permission ' 只得 1116，漏掉 44 个属性换行书写的标签）。其中 normal 87 条、dangerous 42 条、signature 298 条、signature|privileged 298 条，这四组是 protectionLevel 的完整串计数。若按首个 flag 分族，则是 signature 864、internal 133、normal 108、dangerous 51（余 4 条不以这四族开头：signatureOrSystem、system|signature|role、role|signature|privileged、module|signature|role 各 1），差额来自几十种带附加 flag 的组合（signature|role 48、signature|privileged|role 34、signature|privileged|development 24、dangerous|instant 8、dangerous|runtime 1、normal|instant 18 等）。

normal 安装即授；完整串为 dangerous 的 42 条构成运行时弹窗主体，连 dangerous|instant、dangerous|runtime 一起是 51 条；signature/signature|privileged 各 298 条按签名与特权门槛放行，用户界面不参与——但「596 条签名族」这个加法只在这两个完整串的口径下成立，不能当成签名类权限的全部（按首 flag 算是 864 条）。

同族 OP 常量集中在 AppOpsManager.java，该文件共 184 个 public static final int OP_ 常量。OP_SYSTEM_ALERT_WINDOW = AppOpEnums.APP_OP_SYSTEM_ALERT_WINDOW 位于 :1021。

4.3 一个具体例子

取 OP_SYSTEM_ALERT_WINDOW 走一遍。SYSTEM_ALERT_WINDOW 在 manifest 里的 protectionLevel 不在 dangerous 42 条之内，所以安装完成后用户不会看到运行期弹窗，GrantPermissionsActivity 不参与。应用调用悬浮窗 API 时，窗口侧 noteOpNoThrow 现查 OP_SYSTEM_ALERT_WINDOW（PhoneWindowManager.java:3200-3220）：MODE_ALLOWED 放行；MODE_IGNORED 也返回 ADD_OKAY，但窗口会在 WindowManagerService 里被隐藏（:3205-3208 注释）；MODE_ERRORED 对 targetSdkVersion < M 的应用放行、否则 ADD_PERMISSION_DENIED；只有 MODE_DEFAULT 才回退 checkPermission（ActivityTaskManagerService.java:1119-1128）。用户在设置页开关的其实是这个 app op，不是一条权限授权状态。

对比一个 dangerous 权限：安装时不授，第一次用到时 GrantPermissionsActivity 弹出会话。用户允许后 PermissionManagerService 写入授权状态，checkSelfPermission 从此返回已授予。若该权限同时绑定了 app op（例如相机类操作），AppOpsService 侧还需对应开关为允许，两层都过才真正可用。

7. 常见问题与误区

7.1 误区

误区一：每个权限都能在设置页里找到开关。 用户可交互的主体是 dangerous 那一族——完整串 42 条，连 dangerous|instant 8 条、dangerous|runtime 1 条一起是 51 条；signature/signature|privileged 与 normal 不出现在运行期界面，OP_SYSTEM_ALERT_WINDOW 这类走的是 app op 开关而非权限项——但 op 处于 MODE_DEFAULT 时，判定会回退到 checkPermission（见 §4.3），不是「永远不查权限」。

误区二：权限组是授权单位。 权限组只决定弹窗如何归并展示，授权状态仍按单条权限记录。同组放行是弹窗与默认策略的表现，不是判定规则本身。

误区三：权限授予了，敏感操作就一定成功。 这句话错在方向，不在结论。grant 与 app op 分两处存，但 PermissionPolicyService 会按 grant 推导 app op 并回写（见 §4.1），所以「授予了却仍被拒」不是常态，而是落在几类边界上：包级就被跳过（ROOT_UID/SYSTEM_UID、requestedPermissions 为空）、该权限不在同步覆盖范围（非 runtime 权限、getSwitchOp() 为 OP_NONE、映射表缺项）、待复核（review required 被跳过）、或同步还没跑完。排查要先分清是被哪一层拒的，再看它属不属于上述三类。

7.2 高频提问

问：为什么运行时权限的弹窗代码在 PermissionController 模块而不是 frameworks/base？ 答：弹窗是可独立更新的 UI 模块，GrantPermissionsActivity 只提交用户选择，最终状态仍写回 system_server 进程里的 PermissionManagerService。 追问：那弹窗被禁用或卸载会怎样？ 答：授权入口失效，但已写入的授权状态不受影响；默认授予与策略侧判定不依赖该 UI。

问：一次性权限到期由谁回收？

答：OneTimePermissionUserManager 管理时效并在到期时发起回收，回收动作仍落在 PermissionManagerService 授权状态上。

追问：回收后 app op 会同步变吗？

答：会联动。PermissionPolicyService 在构造时注册了 addOnPermissionsChangeListener（:232-233，回调 synchronizeUidPermissionsAndAppOpsAsync），grant 变更（含回收）即触发同步；未授权的 runtime 权限在 addPermissionAppOp 里把 appOpMode 判成 MODE_IGNORED（:919），再经 switch 入 mOpsToIgnore 队列（:931-932），对应 app op 被翻成忽略。只有不在同步覆盖范围内的——非 runtime、OP_NONE、待复核——才不联动。
