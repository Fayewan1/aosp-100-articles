1. TL;DR

一次 Binder 同步事务的完整路径是：BpBinder::transact() 把调用转交线程私有的 IPCThreadState::transact()，后者把 binder_transaction_data 写进 mOut 缓冲，由 talkWithDriver() 一次 ioctl(BINDER_WRITE_READ) 送进驱动；服务端进程的某个 Binder 线程被唤醒，驱动把同一份数据放进它的 mIn，BBinder::transact() 的 default 分支调 onTransact()，回复数据沿原路写回，调用方在 waitForResponse() 里收 BR_REPLY 后返回。oneway 调用与非 oneway 调用的唯一分叉点，在 `IPCThreadState::transact()` 里那个 `if ((flags & TF_ONE_WAY) == 0)`。 oneway 也要等 BR_TRANSACTION_COMPLETE（命令被驱动收下），但不等 reply。调用方看到 DEAD_OBJECT 时服务端进程已经死了，BpBinder::mAlive 会置 0 且永不复原。

3. 问题背景

先看一个具体故障。App 主线程经 ActivityManager 客户端类发起 Binder 调用、查运行中的服务列表，偶发 ANR，堆栈卡在 native 的 IPCThreadState::waitForResponse。同时 logcat 里躺着一条来自服务端进程的告警：

图 1：Binder 线程池饥饿告警日志

binder thread pool (16 threads) starved for 312 ms

这条告警出自 IPCThreadState::getAndExecuteCommand()（IPCThreadState.cpp:767–770）：服务端进程的 Binder 线程池满负荷超过 100 ms 时打印。调用方主线程发出的同步事务排进了驱动队列，但服务端没有空闲 Binder 线程去取——于是调用方阻塞、ANR。

要读懂这个故障，得把「一次事务」在用户空间的完整走位看清楚：数据在哪只缓冲里，在哪一行发生 oneway 分叉，reply 从哪个 case 返回，线程池又在哪个环节被消耗。这篇就把这条链路一次走通。它也是后续所有 Binder 篇目（oneway、死亡通知、线程池策略、驱动侧）的公共底座。

tr.flags        = binderFlags;          // 含 TF_ONE_WAY / TF_ACCEPT_FDS 等

tr.data.ptr.buffer  = data.ipcData();   // 净荷地址

两个容易忽略的点：其一，mOut/mIn 是每线程一个（IPCThreadState::self() 按 TLS 取），所以两个线程同时发事务互不干扰；其二，Parcel 里若嵌了 Binder 对象，offsets 表会告诉驱动哪些位置需要按进程改写——这是「Binder 引用跨进程传递」的机制基础，本篇只用不展开。

三条失败/分支路径（排查时最常踩）：

  1. 目标已死：BpBinder::transact 开头查 mAlive，为假直接返回 DEAD_OBJECT 不再下行（BpBinder.cpp:397–398, 445）；事务已发出后收到 BR_DEAD_REPLY 同样归 DEAD_OBJECT，并把 mAlive 置 0（BpBinder.cpp:440）——置 0 不可逆，此后该代理永久失效。
  2. 嵌套事务（重入）：服务端线程正在处理事务时，调用方又来一个以它为目标的同步事务，会以 BR_TRANSACTION 出现在 waitForResponse 的循环里（IPCThreadState.cpp:1489；waitForResponse 自 1153 行起），由同一线程递归执行。设计上允许，但实现服务时必须为这种重入留好并发边界。
  3. 线程池耗尽：驱动把事务排进目标队列，但目标进程没有空闲 Binder 线程执行 getAndExecuteCommand——就是 §3 那个 ANR 的形状。服务端可见 starvation 告警（:767–770），调用方线程只能持续阻塞等待。

4.3 关键代码逐段剖析

第一段：代理侧总入口（BpBinder.cpp:394–446，节选）

status_t BpBinder::transact(uint32_t code, const Parcel& data,
                            Parcel* reply, uint32_t flags) {
    if (mAlive) {
        bool privateVendor = flags & FLAG_PRIVATE_VENDOR;
        flags &= ~static_cast<uint32_t>(FLAG_PRIVATE_VENDOR);   // 用户态标志不进内核
        if (code >= FIRST_CALL_TRANSACTION && code <= LAST_CALL_TRANSACTION) {
            // Stability 校验：Vendor 稳定性等级不满足 → BAD_TYPE
            if (!Stability::check(stability, required)) return BAD_TYPE;
        }
        status_t status;
        if (isRpcBinder()) [[unlikely]] {
            status = rpcSession()->transact(...);               // RPC Binder 旁路
        } else {
            status = IPCThreadState::self()->transact(
                binderHandle(), code, data, reply, flags);      // 正统路径
        }
        if (status == DEAD_OBJECT) mAlive = 0;                  // 不可复活
        return status;
    }
    return DEAD_OBJECT;                                         // 已知已死，直接返回
}

（长代码块，建议到公众号/头条侧按截图策略处理）

三个要点：FLAG_PRIVATE_VENDOR 是纯用户态标志，进内核前必须剥掉；Stability::check 是 VINTF/AIDL stability 体系加的用户事务准入门槛（详见 §9）；IPCThreadState::self() 取的是当前线程的状态对象——Binder 调用走的是调用方自己的线程，不占用任何全局资源。

第二段：oneway 分叉（IPCThreadState.cpp:921–996，节选）

status_t IPCThreadState::transact(int32_t handle, uint32_t code,
                                  const Parcel& data, Parcel* reply, uint32_t flags) {
    flags |= TF_ACCEPT_FDS;                       // 默认允许传递 FD
    err = writeTransactionData(BC_TRANSACTION, flags, handle, code, data, nullptr);
    if (err != NO_ERROR) { if (reply) reply->setError(err); return err; }

    if ((flags & TF_ONE_WAY) == 0) {              // 同步：等 reply
        if (reply) err = waitForResponse(reply);
        else       err = waitForResponse(&fakeReply);
    } else {                                      // oneway：只等「命令被驱动收下」
        err = waitForResponse(nullptr, nullptr);
    }
    return err;
}

（长代码块，建议到公众号/头条侧按截图策略处理）

注意 oneway 分支并非「不等任何东西」：它仍要等 BR_TRANSACTION_COMPLETE，即驱动确认命令已入队。它的语义是不保证服务端已执行、不保证执行成功——把「已入队」误当「已完成」是 oneway 使用事故的头号来源（详见 §7）。

第三段：事务数据组装（IPCThreadState.cpp:1365–1398，节选）

status_t IPCThreadState::writeTransactionData(int32_t cmd, uint32_t binderFlags,
        int32_t handle, uint32_t code, const Parcel& data, status_t* statusBuffer) {
    binder_transaction_data tr;
    tr.target.ptr = 0;                 // 不把未初始化的栈数据传给远端进程
    tr.target.handle = handle;
    tr.code = code;
    tr.flags = binderFlags;
    ...
    tr.data_size = data.ipcDataSize();
    tr.data.ptr.buffer = data.ipcData();
    tr.offsets_size = data.ipcObjectsCount() * sizeof(binder_size_t);
    tr.data.ptr.offsets = data.ipcObjects();
    mOut.writeInt32(cmd);              // BC_TRANSACTION
    mOut.write(&tr, sizeof(tr));       // 随后是净荷（由 Parcel 布局承接）
    return NO_ERROR;
}

tr.target.ptr = 0 那行注释值得抄下来：「不要把未初始化的栈数据传给远端进程」——这是内核会读取的 UAPI 结构，栈上残留字节可能泄露到内核。

4.4 与相邻机制的关系

  • 与驱动侧（AND-P5-2 承接）：本篇到 ioctl 为止；驱动如何选目标进程、如何拷贝、binder 线程如何被唤醒，归 P5 内核卷。
  • 与 Java 层：android.os.Binder.java / IBinder.java 最终经 JNI 到 android_os_BinderProxy_transact → BpBinder::transact；Java 侧的 transact() 回调在服务端对应 BBinder::onTransact。本篇讲 native 主线，Java 侧只是薄封装。
  • 与 AIDL：BnInterface::onTransact（AIDL 生成）在 BBinder::transact 的 default 分支里被调，按 code 分发到具体方法。事务机制与接口描述语言无关。
  • 与 Native 侧服务（AND-P3-3 承接）：libbinder_ndk / AParcel 是同一机制的另一套 API 封装。

7. 常见问题与误区

误区一：oneway 就是「发完就不管」。 错。oneway 仍等 BR_TRANSACTION_COMPLETE（IPCThreadState.cpp:992）；且高频 oneway 会触发驱动的 spam 检测（BR_ONEWAY_SPAM_SUSPECT，IPCThreadState.cpp:1174）。它不保证的只有两件事：服务端是否已执行、是否执行成功。oneway 之后立刻读共享状态，是竞态 bug 的经典形状。

误区二：拿到 `DEAD_OBJECT` 重试一次就行。 错。BpBinder::mAlive 置 0 后该代理永久失效（BpBinder.cpp:440），重试同一个 BpBinder 毫无意义；正解是重新 getService 拿新代理，或走死亡通知重建。

误区三：Binder 调用会起新线程。 错。IPCThreadState::self() 是当前线程的 TLS 单例——同步事务占用调用方自己的线程。调用方是主线程，阻塞的就是主线程（§3 的 ANR 正是如此）。线程池是服务端的资源。

误区四：`transact` 返回 `OK` 等于业务成功。 错。status_t 只代表传输层结果；业务错误写在 reply Parcel 里（AIDL 的异常/状态码）。

面试高频：Binder 一次拷贝怎么做到的？ 答：调用方数据在 mOut，ioctl 时驱动直接把数据拷进目标进程 mIn（mmap 映射区），用户态不经过内核中转缓冲——数据从调用方缓冲到目标缓冲只有驱动内一次搬运。追问「为什么还是比管道慢」：事务有目标查找、线程唤醒、Stability 校验等固定开销，小数据下延迟主要取决于调度而非拷贝。

面试高频：同步事务里服务端又反向调用调用方，会发生什么？ 答：以 BR_TRANSACTION 出现在调用方 waitForResponse 循环里（IPCThreadState.cpp:1489），调用方线程递归处理。若双方互等对方 reply，死锁——所以「持锁跨进程同步调用」是明确的设计禁忌。
