1. TL;DR

同一份 AOSP 树，车载（AAOS）、IoT、可穿戴三种形态的差异不在「核心框架」，而在三类可核落点：多出的一组 HAL 接口、多出的系统服务族、多出的一套产品配置。车载的增量最重：hardware/interfaces/automotive/ 一整组接口、packages/services/Car/ 一整套 Car 服务与 native 组件、car_product/device/generic/car/device/google_car 三层产品声明。IoT 在本树只可核到 system/chre/ 与 device/google/contexthub/ 这条传感器管线，Android Things 已停止发行，本树未收录其组件。可穿戴（Wear）要分两层看：顶层未检出 wear 目录、packages/ 下未收录 Wear 包、device/ 下未收录 Wear 产品配置；但框架层有可核落点——frameworks/base/core/java/android/app/wearable/、frameworks/base/core/java/android/service/wearable/ 与 frameworks/base/services/core/java/com/android/server/wearable/ 构成穿戴感知的三层。发行形态本身仍按官方文档口径描述，本篇不断言其内部结构。TV 作对比形态，特征是 Leanback 应用族与 mDNS offload 服务。

3. 问题背景

移植工程师常见的困惑是：拿到一份通用 AOSP 树，想让它变成一个车机镜像，改动面看起来铺满整个仓库，实际要动的却只有固定的几处。反过来，想给一块带低功耗协处理器的板子接入传感器，会发现 device/ 下没有可抄的 IoT 产品样例，只有 device/google/contexthub/ 这一处名字对得上。再往上问「Wear 形态到底比手机少了什么」，顶层确实 grep 不到 Wear 专属系统目录，但 frameworks/base 下有 android.app.wearable、android.service.wearable 与 com.android.server.wearable 三层，是穿戴感知在框架侧的落点。三个问题指向同一个事实：AOSP 主干提供的是机制，形态是主干之外按层次叠加的增量，增量有多厚、落在哪一层，三种形态差别极大。

4. 核心机制

4.1 概念与关系

三种形态共用同一套框架层（frameworks/base、system/core），差异全部发生在框架层之外的三个位置：HAL 接口集合、系统服务与应用集合、产品与设备配置。车载三层齐备，IoT 只在 HAL 与低层运行时上有增量，可穿戴只在框架层的穿戴感知一处有可核增量，没有独立的 HAL 与产品配置。

图 1：形态差异的三个增量层

  形态          HAL 接口              服务/应用族与产品配置
  车载(AAOS)    automotive            Car 服务族 + car_product
  IoT           contexthub           CHRE（无产品配置样例）
  TV            tv（cec/hdmi/input/mediaquality/tuner）  Leanback 应用族 + device/google/atv
  Wear          -                    WearableSensing 三层（无 HAL/产品配置）

关键概念四条：车载形态的「车载 HAL 契约」是 hardware/interfaces/automotive/ 下的一整组 AIDL 接口；「Car 服务族」是 packages/services/Car/ 下由 service-builtin 构建进 system 的 Car 服务实现；「上下文中心（Context Hub）」是 system/chre/ 提供的低功耗运行时；「产品声明」是 *.mk 与 AndroidProducts.mk 组成的构建入口。四者的关系是：产品声明决定哪一组服务与 HAL 被装进镜像，HAL 契约决定上层服务能调什么，CHRE 是唯一不属于 Android 框架进程模型的运行环境。

4.2 关键内容

车载增量是三块，逐块可核。

第一块：HAL 接口。 hardware/interfaces/automotive/ 下多出一整组接口，名称包括 vehicle（VHAL 接口）、evs、audiocontrol、can、remoteaccess、occupant_awareness、ivn_android_device。这组接口与手机形态的 HAL 集合是并列追加关系，不替换任何既有接口。VHAL 是其中最关键的一条：上层 Car 服务通过它读车辆属性；packages/services/Car/cpp/vhal/ 下是 client 侧（client/ 的 libvhalclient），实现侧在 device/generic/car/emulator/vhal_aidl/（EmulatedVehicleService.cpp 与 VehicleEmulator/）。

第二块：Car 服务族。 packages/services/Car/ 顶层共 20 个目录，下表只列与形态增量直接相关的 8 项：

名称含义出处
car-lib供应用与系统服务调用的 Car API 层，351 个 Java 文件packages/services/Car/car-lib
car-lib-modulecar-lib 的模块化打包形态packages/services/Car/car-lib-module
serviceCar 服务实现，含 src/jni/proto/respackages/services/Car/service
service-builtin构建进 system 分区的服务入口，CarService.java 位于 service-builtin/src/com/android/car/packages/services/Car/service-builtin
apex_car_frameworkCar 框架的 APEX 打包packages/services/Car/apex_car_framework
cpp车载 native 组件族packages/services/Car/cpp
car_product产品配置声明packages/services/Car/car_product
experimental实验性组件packages/services/Car/experimental

cpp/ 下同族 native 组件集中列出：evs（Extended View System，后视/环视相机）、vhal（VHAL 的 client 库 libvhalclient）、computepipe、displayproxy、car_binder_lib、watchdog、telemetry、security、power、bugreport、libsysfsmonitor、packagemanagerproxy。这十二项构成车载形态的 native 侧增量，与 Java 侧服务族互补。

第三块：产品与设备配置。 三层落点：packages/services/Car/car_product/build/ 提供产品继承链，含 car.mk、car_base.mk、car_system.mk、car_system_ext.mk、car_vendor.mk、car_generic_system.mk、car_product.mk 以及 preinstalled-packages-product-car-base.xml；device/generic/car/ 提供 8 个 sdk_car*.mk、3 个 gsi_car_*.mk、4 个 emulator_car64_* 目录，common/ 另放公共片段（audio_effects.xml、manifest.xml、overlay、rro_overlays、sepolicy、sysconfig 等）；device/google_car/ 提供 cheetah_car、husky_car、panther_car、tangorpro_car 四套设备配置。三层的关系是产品族 → 通用设备 → 具体机型，继承方向见 AND-P11-201。

IoT 增量只有一条管线。Android Things 已停止发行，device/ 与 packages/ 下未检出 Things 目录，本树未收录 Things 组件。树内与 IoT 最近的可核形态是 device/google/contexthub/（含 contexthubhal、sensorhal、firmware、lib、util）与 system/chre/。CHRE 全称 Context Hub Runtime Environment，仓内顶层含 core、pal、platform、apps、chpp、zephyr 等目录。pal 是平台抽象层，负责把 CHRE 核心与具体协处理器平台隔开；contexthubhal 是设备侧 HAL 实现，把 CHRE 暴露给 Android 侧。两者共同构成「Android 主处理器 + 低功耗协处理器」的形态，但这不是一套完整产品配置——本树未收录配套的 IoT 产品 *.mk 样例。

TV 作对比形态可核：device/google/atv/ 下有 TvProvision、TvSampleLeanbackLauncher、LeanbackSampleApp、MdnsOffloadManagerService、products/、sdk/。TV 在 HAL 层同样有成组追加——hardware/interfaces/tv/ 下有 cec、hdmi、input、mediaquality、tuner 五个接口目录，与 automotive 并列；应用与服务层的增量是 Leanback 应用族与 mDNS offload，产品配置走 products/ 与 sdk/。

可穿戴要分两层看：顶层无 wear 目录、packages/ 下无 Wear 包、device/ 下无 Wear 产品配置；但框架层有可核落点——WearableSensingManager（frameworks/base/core/java/android/app/wearable/）、WearableSensingService（frameworks/base/core/java/android/service/wearable/）与 WearableSensingManagerService（frameworks/base/services/core/java/com/android/server/wearable/）三层。发行形态本身仍按官方文档口径（source.android.com 站内检索 wear）描述为「基于 Android 的可穿戴发行形态」，本篇不对其内部结构做断言。

4.3 一个具体例子

以车机镜像为例走一遍增量装载。构建入口是 device/generic/car/AndroidProducts.mk，它枚举该目录下 8 个 sdk_car*.mk；这些产品文件直接继承 car_generic_system.mk 与 car_system_ext.mk（以 sdk_car_arm64.mk 为例，分别在 :37 与 :46），同时 :51 与 :56 还继承 emulator/car_emulator_product.mk（转 car_product.mk）与 emulator/car_emulator_vendor.mk（转 car_vendor.mk），分区内容经这些文件装进镜像；car_base.mk 只被 car.mk :111 继承，不在 sdk_car 这条线上。产品侧同时带入 preinstalled-packages-product-car-base.xml，声明预装包清单。运行时，service-builtin 里的 CarService.java 作为系统服务启动，通过 car-lib 暴露 API，Car 服务经 android.hardware.automotive.vehicle 的 AIDL 直连 VHAL；cpp/vhal/client 的 libvhalclient 是给 cpp/power、cpp/watchdog、cpp/evs/apps/default、cpp/security/vehicle_binding_util 这些原生组件用的（cpp/car_binder_lib 下只有 largeParcelable，不是 VHAL 通道）。实现侧示例见 device/generic/car/emulator/vhal_aidl/。想换成具体机型，就把继承链末端换成 device/google_car/ 下的 cheetah_car 一类目录。整条路径上，框架层代码一行未改——这就是形态差异的定位。

7. 常见问题与误区

7.1 误区

误区一：车载形态需要改框架层。 实际不需要。packages/services/Car/ 与 hardware/interfaces/automotive/ 本身就是框架外的增量层，frameworks/base 对车载提供的是通用机制，Car 服务作为系统服务在其上运行。

误区二：IoT 形态就是 Android Things 的现行版本。 看起来像是改名或延续，实际 Android Things 已停止发行，本树未收录该组件。树内可核的 IoT 邻近形态只有 CHRE 与 contexthub 这条低功耗协处理器管线，它并非一套完整产品发行。

误区三：Wear 形态在树里有独立系统组件。 分两层看：顶层未检出 wear 目录、packages/ 下未收录 Wear 包、device/ 下未收录 Wear 产品配置，所以本树未检出独立的 HAL 与产品配置；但框架层有穿戴感知的三层（android.app.wearable、android.service.wearable、com.android.server.wearable）。发行形态本身仍按官方文档口径描述，本篇不对其内部结构做断言。

误区四：三种形态的差异总量相当。 实际差距很大：车载三层齐备（HAL + 服务族 + 产品配置），IoT 只有低层管线与设备侧 HAL，TV 在 HAL、应用与服务层各有增量，Wear 只在框架层的穿戴感知一处有增量。

7.2 高频提问

问：能不能只拿 device/generic/car/ 就能出车机镜像？ 答：不能。sdk_car*.mk 只是产品入口，真正的分区内容来自 packages/services/Car/car_product/build/ 下的 car_system.mk、car_system_ext.mk、car_vendor.mk，以及经 emulator 层转进来的 car_product.mk。 追问：那换机型要改哪些？ 答：换继承链末端，指向 device/google_car/ 下的 cheetah_car、husky_car、panther_car、tangorpro_car 之一；通用层不动。

问：CHRE 和 contexthubhal 是上下两层还是一件事？ 答：是两层。system/chre/ 是运行在协处理器上的运行时，contexthubhal 是设备侧的 HAL 实现，把 CHRE 能力暴露给 Android 侧。system/chre/pal 是 CHRE 内部的平台抽象层，与 HAL 不是同一层。 追问：那 IoT 形态是不是只靠这两者就够了？ 答：不够。本树未收录配套的 IoT 产品配置样例，形态只可核到这条管线。
