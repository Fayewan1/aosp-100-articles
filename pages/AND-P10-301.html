1. TL;DR

一格电被谁消耗，答案不在某个模块里，而在两条链路的交界处。统计侧由 BatteryStatsImpl 按 uid 记账，PowerProfile 把「时间与次数」乘成「电量」；控制侧由 ThermalManagerService 接收温度、把状态写进 trace，再由电源层与内核执行降频与限流。两侧的公共接口是 BatteryUsageStats 与 trace 的 power / thermal 类别。本篇只讲口径与链路，不给任何设备的实测功耗与温度阈值。

3. 问题背景

用户说「待机一晚上掉了 30%」，你要给出一个 uid 的名字。手机玩游戏十分钟烫手，帧率掉下去，你要说清降频指令是从哪一层下来的。这两件事看起来一个是统计、一个是控制，实际共用同一套「时间 → 电量 / 温度 → 状态」的换算口径。口径不通，你会拿到两个都对但彼此矛盾的数字：统计说某个 uid 只占 3%，用户体感却是它最耗电。

4. 核心机制

4.1 概念与关系

四个概念串成一条线：电量记账（按 uid 累计时间与次数）、功耗参数表（把时间乘成电流的系数）、聚合出口（对外一份 BatteryUsageStats）、温控状态（温度事件转成状态并进 trace）。

        |                    ^                   |
        |                    | IBatteryStats     |
  PowerManagerService ------+              ThermalManagerService
        |                                        |
        +------- trace: power / thermal ---------+
                                                 |
                                    降频、限流（策略端执行）

图 1 的关键点：ThermalManagerService 与 BatteryStatsImpl 之间没有任何直接调用，两者在 system_server 进程里共享状态；但电源侧不是纯旁观者——PowerManagerService 持有 IBatteryStats mBatteryStats（:362），经由 BatteryStatsService.getService()（:1461）直接调用统计侧的 computeBatteryTimeRemaining()（:7050）。所以「统计侧与控制侧互不调用」只在温控这一段成立，电源这一段有一根细线。对外暴露接缝的是 trace 的 power 与 thermal 两个类别。

从上一条往下看，「温度到达」与「counter 被写」不是同一件事，中间有三重门控：

4.3 一个具体例子

假设某 uid 在一段区间内持有唤醒锁、跑过 CPU，你想知道它的电量构成。

第一步，唤醒锁进入 noteStartWakeLocked（BatteryStatsImpl.java :4519），记到 Uid（:7496）名下。第二步，该 uid 的 CPU 运行时长按 getAveragePower("cpu.active")（:909 / :960）乘出运行态电量，（旧口径还会按 getAveragePower("cpu.suspend") 计一份恒加基底，但那是 :60–:71 注释描述的旧模型，本树实际生效路径见 §4.2 三的表下注。）第三步，各 uid 的 builder 汇总进 BatteryUsageStats.Builder（mUidBatteryConsumerBuilders：grep 首命中 :186 为构造内使用处，字段声明在 :925），构造出对外对象（:165）。

如果这段时间正好在省电模式，setLowPowerModeInternal（PowerManagerService.java :4416）已经在另一条路径上改过状态，统计口径不变，执行侧行为变了。两件事分开看，才不会把「统计没算准」和「策略没生效」混为一谈。

温控侧同时发生的是：onTemperatureChanged（ThermalManagerService.java :490 实现，:189 HAL 包装声明）收到温度，经 §4.2 第七条的门控链，在状态真的迁移时由 :415 写进 power 类别的 trace。你抓 trace 时看到 ThermalManagerService.status 的台阶变化，就对应一次状态迁移。

与 AND-P10-G01：G01 讲 trace 采集与工具链，本篇只用到 power / thermal 两个类别名，采集方法不重复。

7. 常见问题与误区

7.1 误区

误区一：温控状态在 `thermal` 类别里。 错。ThermalManagerService 写 ThermalManagerService.status 时用的 tag 是 TRACE_TAG_POWER（:415）。只开 thermal 抓不到这个计数器。

误区二：温度事件一到，counter 就会更新。 错。:415 在 setStatusLocked 里，被状态不等判断与 sendCallback、mIsStatusOverride、SKIN 传感器聚合三道门控拦住（见 §4.2 第七条）。看不到台阶先查门控，别急着怀疑传感器。

误区三：`cpu.suspend` 只在挂起时计费。 错——但要分清是哪一层的源码：按 PowerProfile.java :60–:71 注释的旧 cluster 模型口径它确实是恒加的基底项；可在本树实际生效的链路里，cpu.suspend 并没有消费方（默认 power_profile.xml 未定义该项，getAveragePowerOrDefault :892 返回 0），uid CPU 电量走 CpuPowerStatsProcessor.java :97/:102/:107、唤醒锁走 WakelockPowerStatsProcessor.java :29（POWER_CPU_IDLE）。所以「恒加」是注释口径，不是现行计费事实。

误区四：统计口径和降频策略失败是一件事。 看起来对，其实是两条独立链路。统计走 BatteryStatsImpl → BatteryUsageStats；降频走 ThermalManagerService 状态 → 策略端。统计正确不代表策略生效，反之亦然。

误区五：`getAveragePower(String)` 和带档位版本等价。 错。带第二参数的版本按档位取值（如频率档、信号档），Wi-Fi 的 _TX_LEVELS 就是个分级项。用单参数版估算分档场景会系统性偏低。

7.2 高频提问

问：为什么某 uid 唤醒锁时长为 0，电量却不为 0？ 答：唤醒锁只是账目之一。CPU 运行时长走 POWER_CPU_ACTIVE、基底项按注释口径记在 POWER_CPU_SUSPEND（本树实际链路见 §4.2 三的表下注），这两项与该 uid 是否持锁无必然关系。 追问：那唤醒锁账目什么时候才有区分度？ 答：在同一区间内比较多个 uid 时，持锁时长能把「长时间不让系统睡」的那一方放大出来；单看一个 uid 的绝对值没有意义。

问：省电模式改了 setLowPowerModeInternal，统计数字会变吗？ 答：统计口径不变，变量是执行侧允许的时间与频率。所以「开了省电模式但耗电没降」要先去查策略是否真的落到执行端，而不是怀疑统计。 追问：怎么区分这两种情况？ 答：抓 power 类别 trace，看 ThermalManagerService.status 与电源状态的台阶变化；台阶没动说明链路没走通（先按误区二排门控）。
