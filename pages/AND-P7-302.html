1. TL;DR

CaptureRequest 不是「一次拍照指令」，而是一个带类型的键值配置包：它用 Key<T> 把每一项拍摄参数（对焦模式、曝光、尺寸等）存进一个类型安全的 map，由 Builder 构造、build() 产出不可变请求；多摄场景下还用 mLogicalCameraId 区分逻辑相机与物理子摄。理解它的「键空间 + Builder + 逻辑/物理映射」三件事，才能正确配置相机而不踩类型与多摄的坑。

3. 问题背景

「设了 CONTROL_AF_MODE 为什么不生效」「多摄手机怎么指定用哪颗镜头」「为什么 get 出来的值和 set 的不一样」——这些问题的根因在 CaptureRequest 的语义：键是带类型的、请求是不可变的、build 之后改动无效，多摄下逻辑相机与物理相机是两套 id。本文把这套键空间与构造机制讲清。

4. 核心机制

4.1 数据结构与状态定义

CaptureRequest 继承自 CameraMetadata，其配置以 Key<T> 为键、以强类型值为内容；底层并不是一张 Map<Key, Object>——主配置由 CameraMetadataNative（CaptureRequest.java:239，一块 native metadata buffer，键经 getNativeKey() 映射后存取）承载，另有一个 HashMap<String, CameraMetadataNative> mPhysicalCameraSettings（:240）只在多摄场景按物理相机 id 分持各子摄设置。CameraMetadata 提供键空间的基底（构造 CameraMetadata.java:75、可用键枚举 getKeys() :148）。CaptureRequest 用 mLogicalCameraId（CaptureRequest.java:237）记录该请求属于哪个逻辑相机。

7. 常见问题与误区

7.1 误区

  • 「build 之后再改请求就能改配置」。请求不可变，build 后改动无效，必须重新 Builder.set 再 build。
  • 「所有键都能 set」。API 层面确实不校验——CameraMetadataNative.set 会把任何 Key 原样写进去（:532-542，查不到对应 SetCommand 就落到 setBase）；但值不生效的裁决权在设备能力一端：getKeys()（CameraMetadata.java:148）给出设备支持的键集合，不在此列的键会被下游按能力裁剪或忽略。所以准确说法是「都能写进去，但只有设备支持的才生效」。
  • 「看起来对其实是错的」：以为逻辑相机 id 等于物理镜头 id。多摄下二者不同，mLogicalCameraId（:237）是逻辑身份，物理子摄需另行指定。
  • 「get 出来一定等于 set 进去的」。默认值、设备能力裁剪都会让回读值不同于写入值。

7.2 高频提问

问：设了对焦模式不生效怎么办？ 答：先查该键是否在设备 getKeys() 支持列表里，并在合适的 CaptureRequest 模板上设置；build 后不要在旧对象上改。 追问：多摄怎么指定镜头？ 答：通过逻辑相机 id 与物理子摄的分别配置，确认 mLogicalCameraId 路由正确。

问：为什么读取参数和设置不一致？ 答：可能是设备不支持该值被裁剪为默认值，或读取的是不同请求实例。
