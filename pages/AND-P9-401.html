1. TL;DR

KeyMint 用四个安全等级值把「密钥由谁保证」写进接口契约：SOFTWARE=0 由 keystore2 进程自己保证，TRUSTED_ENVIRONMENT=1 与 STRONGBOX=2 落到硬件，KEYSTORE=100 是 Keystore 2 自己加的标签。Keystore 2 的服务端是 Rust 实现，system/security/keystore2 下 .rs 文件合计 51571 行，入口收敛在 keystore2_main.rs 的 fn main()。Gatekeeper 分两层：system/gatekeeper 是 HAL 实现入口，system/core/gatekeeperd 是系统侧守护进程。文件级加密（File-Based Encryption，FBE）的密钥派生入口在 system/vold/FsCrypt.cpp，元数据加密入口在 MetadataCrypt.cpp，两个文件共同决定「密钥从哪来」。

3. 问题背景

一个应用调用 KeyGenParameterSpec 生成密钥，只写「要求硬件支持」，然后拿不到密钥句柄，也没有明确的错误来源。另一种情况：设备开机第一帧就能读 /data，但没人能说清 /data 的密钥在开机脚本的哪一步被解开。还有人把 Gatekeeper 当成单纯的密码校验库，直到发现它和 KeyMint 在解锁链路上互相依赖。

这三类困惑指向同一个问题：密钥的「可信来源」在哪一层被确定，以及这一层失败时上层看到什么。本篇沿服务端代码走一遍这条链。

4. 核心机制

4.1 概念与关系

四个概念构成三层：

  • KeyMint：密钥操作的 HAL 接口层，通过 SecurityLevel 声明每次操作落在哪个安全等级。
  • Keystore 2：system/security/keystore2 的 Rust 服务，向上给应用提供密钥句柄，向下按 SecurityLevel 选择落点。
  • Gatekeeper：口令校验通道，HAL 实现与系统守护进程分离。
  • vold：块设备与加密卷的管理者，FBE 的密钥派生从这里进入内核。

图 1：密钥请求从应用到硬件的分层落点

应用 (uid)
   |  句柄/别名
keystore2 进程  --- SOFTWARE 级在此闭环
   |  KeyMint HAL (SecurityLevel)
TEE / StrongBox 硬件  --- TRUSTED_ENVIRONMENT / STRONGBOX
   ^  只有 KeyMint HAL 这一跳直连硬件
   |
   +-- vold (FsCrypt) --- FBE 密钥派生入口：包装密钥经 keystore2 进程
       |  请求（KeyStorage.cpp:117/:127），不直连硬件

4.2 关键内容

安全等级是本篇的核心契约。它不是一个实现细节，而是调用方可以观测的返回值。

名称含义出处
SOFTWARE值 0，密钥运算跑在 Android 进程内，由 keystore2 自身保证SecurityLevel.aidl
TRUSTED_ENVIRONMENT值 1，落在 TEE，满足 CDD 9.11.1 [C-1-2]SecurityLevel.aidl
STRONGBOX值 2，落在 StrongBox，满足 CDD 9.11.2SecurityLevel.aidl
KEYSTORE值 100，由 Keystore 2 自身强制的标签SecurityLevel.aidl

这张表的读法是：前三个值描述「谁的代码在算」，第四个值描述「Keystore 认为这个密钥属于自己管辖」。所以 KEYSTORE 不与前三个互斥，它是叠加标签。至于「请求不到硬件级会不会自动落到 SOFTWARE」——SecurityLevel.aidl（78 行全文）里没有任何降级条款，SOFTWARE 在其中只被描述为「runs in an Android process」；实际选路发生在 keystore2 侧（system/security/keystore2/src/security_level.rs 按实例取用），请求不到即失败，是否接受软件级取决于调用方请求的是哪个实例。本篇按这一口径表述，不把降级说成 aidl 的契约。

Keystore 2 服务端的形态可以直接从规模看出来。system/security/keystore2/src/keystore2_main.rs 共 165 行，fn main() 在 :38，说明入口层极薄，主体逻辑摊在其余 .rs 文件里。远端密钥配置（RKPD）路径单独成文件：system/security/keystore2/src/remote_provisioning.rs 共 159 行，负责经 Remote Provisioning HAL 生成密钥、以 CBOR 交配置服务器换回证书链并写入 SQLite——是「密钥的远端配置」，不是普通配置文件下发。

Gatekeeper 的两层分工按文件规模就能读出来。system/gatekeeper/gatekeeper.cpp 共 379 行，是 HAL 实现入口，跑在提供实现的进程一侧；system/core/gatekeeperd/gatekeeperd.cpp 共 530 行、system/core/gatekeeperd/main.cpp 共 50 行，是系统侧守护进程。前者偏「算法与存储怎么落」，后者偏「谁可以问、问几次」——系统侧只做 Binder 入口、SID 存储与 HAL 转发（含重试超时透传）。

数据加密在 vold 侧有两个入口：FsCrypt.cpp 共 1176 行，MetadataCrypt.cpp 共 501 行。前者是 FBE 卷的密钥获取与挂载流程，后者管元数据加密的设备映射。

这里最容易说反的是「密钥从哪来」：卷密钥由 vold 自己生成/取回（FsCrypt.cpp:546 的 retrieveOrGenerateKey(device_key_path, …, userdataKeyGen(), &device_key)），KeyMint 提供的那把是用来包装卷密钥的——KeyStorage.cpp:117 的 generateKeyStorageKey() 调 keystore.generateKey(...)（:127，先尝试带 TAG_ROLLBACK_RESISTANCE、不支持则回退）拿到的是 AES-GCM 的 key storage key，卷密钥被它加密后再落盘。所以 vold 不是单纯的消费者：它既是卷密钥的产出方，又是 KeyMint 的使用方。

SELinux 侧为这条链切了独立的域。system/sepolicy/private/ 下与这条链相关的有七项：keystore.te、keystore2_key_contexts、keystore_keys.te、gatekeeperd.te、hal_gatekeeper.te、vold.te、vold_prepare_subdirs.te。其中 keystore2_key_contexts 把 keystore2 的密钥 namespace 映射到 SELinux 类型标签，keystore_keys.te 声明这些 namespace 类型本身（type shell_key, keystore2_key_type; 一类，shell／vold／su／odsign／locksettings／keychain／resume_on_reboot 七行各一），两者把「哪个域的密钥对象」写成了策略而不是代码里的权限判断。

4.3 一个具体例子

一个请求要求 TRUSTED_ENVIRONMENT 级密钥。按 SecurityLevel.aidl，TRUSTED_ENVIRONMENT=1 意味着满足 CDD 9.11.1 [C-1-2]。keystore2 的选路只看实例名：globals.rs:204-211 把 TRUSTED_ENVIRONMENT 固定映射到 IKeyMintDevice/default，设备声明了 default 实例就用它，不校验 HAL 自报的安全等级与槽位是否一致（globals.rs:316-335 连上后只取 versionNumber）。软件变体（keymint-service.nonsecure）同样注册为 default（hardware/interfaces/security/keymint/aidl/default/service.cpp:38）——这类设备上请求会成功，「TEE 级」实际由软件实现背书；legacy compat 路径更直接：没有安全 Keymaster 时把软件实现填进 TRUSTED_ENVIRONMENT 槽位并打 WARNING（km_compat/km_compat.cpp:1468-1472）。反过来，调用方请求不到 SOFTWARE 级：get_security_level 只登记 TEE 与 StrongBox（service.rs:122-136），keymint_service_name 对 SOFTWARE 直接返回 HARDWARE_TYPE_UNAVAILABLE（globals.rs:219-224）。真正会失败的是另一种情况：设备没声明 default 实例，keystore2 启动即报错退出（service.rs:70-79，TEE 是 mandatory）——此时任何等级的请求都无从谈起。

对照规模数据：system/security/keystore2 下 .rs 合计 51571 行，其中 tests/test_utils 两目录占 16541 行，非测试部分 35030 行（find . -name '*.rs' -not -path './tests/*' -not -path './test_utils/*' 可复算）——选路逻辑摊在这 35030 行里，入口只占 165 行。这解释了为什么读 keystore2_main.rs 看不出安全等级逻辑——它不在入口。

7. 常见问题与误区

7.1 误区

误区一：`SOFTWARE` 是「不安全的兜底」，请求硬件级失败会自动落回它。 不是。SOFTWARE=0 是一个正式的等级值，代表由 keystore2 进程自身保证，它需要调用方明确接受才会被选中。把它当兜底会让调用方误判密钥的实际保护边界。

误区二：`KEYSTORE` 是比 `STRONGBOX` 更高的等级。 看起来像，其实是错的。STRONGBOX=2 和 KEYSTORE=100 描述的是不同维度：前者说运算在 StrongBox 硬件里，后者是 Keystore 2 强制的归属标签。数值大小不构成强弱排序。

误区三：Keystore 2 的入口文件会给出选路逻辑。 keystore2_main.rs 只有 165 行，fn main() 在 :38，是启动与装配。选路与等级判定分布在其余 .rs 文件里，全目录合计 51571 行（含 tests/test_utils 16541 行，非测试 35030 行）。

误区四：Gatekeeper 只是一个校验函数。 它被拆成 HAL 实现入口（gatekeeper.cpp，379 行）与系统守护进程（gatekeeperd.cpp，530 行加 main.cpp，50 行）两侧，失败计数与请求节流在 HAL 实现一侧（gatekeeper.cpp:68-88：GetFailureRecord :73、ThrottleRequest :78、IncrementFailureRecord :80、ComputeRetryTimeout :85，受 pw_handle->version >= HANDLE_VERSION_THROTTLE 门控）；gatekeeperd 只做系统侧 Binder 入口与 HAL 转发（全文无 throttle 相关命中）。

7.2 高频提问

问：一个密钥到底存在哪？

答：取决于 SecurityLevel。SOFTWARE 级的保护边界是 keystore2 进程；TRUSTED_ENVIRONMENT 与 STRONGBOX 级落在硬件侧，密钥材料不出 TEE 或 StrongBox。

追问：那 KEYSTORE 级呢？

答：它是 Keystore 2 自身强制的标签，与前三个等级不互斥，用来标记该对象由 Keystore 2 管辖，不单独决定存储位置。

问：FBE 的密钥从哪来？

答：分两把。卷密钥由 vold 自己生成或取回（FsCrypt.cpp:546 retrieveOrGenerateKey）；KeyMint 生成的是包装它用的 key storage key（KeyStorage.cpp:117/:127），卷密钥被加密后才落盘。

追问：密钥派生的数学细节在哪？

答：不在本篇范围，本篇只到 vold 的两个入口与这条调用链。
