1. TL;DR

模块名、目录名、安装路径是三套独立的命名空间，彼此没有推导关系。manifest 里 path 是工作区相对路径，name 是 Gerrit 上的项目名，两者经常不同。模块靠进 PRODUCT_PACKAGES 才进产品镜像，目录名与模块名相同只是巧合。安装路径来自构建系统约定，不在源码里硬编码每个模块的落点。

3. 问题背景

你 grep 到 logcat 这个模块名，想去改它的代码，于是打开 frameworks/base/ 逐层翻找，翻不到。换一条路：先在某目录看到 Android.bp 里写着 name: "logcat"，就以为目录名一定是模块名，下一次照着这个「规律」去找另一个模块，又错了。这类误判的根因是把几个命名空间当成一个。

4. 核心机制

4.1 概念与关系

三个命名空间：

命名空间举例谁定义
工作区路径system/logging/logcatmanifest 的 path
模块名logcat、services.coreAndroid.bp / Android.mk 的 name
安装路径/system/bin/logcat构建系统约定

图 1：从 manifest 路径到模块名的映射

manifest path ──► 工作区目录 ──► Android.bp
                                    │ name
                                    ▼
                              PRODUCT_PACKAGES
                                    │ 约定
                                    ▼
                              安装路径

目录名与模块名可相同也可无关；安装路径由模块类型加约定决定。

4.2 关键内容

构建描述文件有两套并存。Android.mk 用 Make 语法，属旧体系；Android.bp 用 Soong 语法，新代码用这套。找模块时两个文件名都要看。

模块要进产品镜像，通常得在产品配置的 PRODUCT_PACKAGES 里出现——除非它作为其它模块的 shared_libs/static_libs/required 被传递依赖带进去，libbase、libprocessgroup 就属此类。模块定义存在，不等于它会被装进某个产品——这是「找不到」的常见来源。

安装路径是构建系统的约定。native 可执行文件默认落 /system/bin，依据是 Soong 的安装器：build/soong/cc/binary.go:217 给 cc_binary 装 NewBaseInstaller("bin", "", InstallInSystem)，目录由 build/soong/cc/installer.go:73 的 installDir() 给出。binary.go:313 另有一处 /system/bin/linker，那是动态链接器路径（64 位为 linker64），与安装目录无因果，别拿它当依据。这是约定口径，本篇不冒充实测产物路径。

4.3 一个具体例子

先看 manifest 的双名：<project path="build/make" name="platform/build">，path 是工作区路径，name 是 Gerrit 项目名，两者分离，build/make 的项目名是 platform/build。

再看 logcat：模块定义在 system/logging/logcat/Android.bp，是 cc_binary，name 为 logcat，shared_libs 含 libbase、libutils、libprocessgroup、libprotobuf-cpp-lite，static_libs 含 liblog。目录名与模块名同名属巧合。

它出现在 base_system.mk 的 PRODUCT_PACKAGES 里，落点按约定是 /system/bin/logcat。

对照 services.core：定义在 frameworks/base/services/core/Android.bp，是 java_library，name 为 services.core；目录名 core 与模块名不同，落点是 framework jar。

7. 常见问题与误区

7.1 误区

错：模块名就是目录名。对：logcat 两者相同只是巧合，services.core 的目录是 frameworks/base/services/core，名不同。

错：定义了模块就会装进系统。对：还要进产品的 PRODUCT_PACKAGES，或被其它模块以 shared_libs/required 传递依赖带上。

错：安装路径写在模块定义里。对：落点由构建系统约定推导，源码里通常不写死每个模块的路径。

看起来对其实错：manifest 的 path 就是项目名。对：build/make 的 name 是 platform/build，两者经常不同。

7.2 高频提问

问：为什么我 grep 模块名找不到目录？答：模块名与目录名不同名是常态，改从 PRODUCT_PACKAGES 或全树 grep name: "xxx" 反查。追问：那怎么从目录找模块名？答：看该目录下的 Android.bp 或 Android.mk 的 name 字段。

问：只有一个 Android.mk 的目录是不是废弃了？答：不是，两套并存。追问：新写的用哪套？答：新代码用 Android.bp。
