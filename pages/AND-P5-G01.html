3. 问题背景

一个应用调 Binder 偶发超时，翻应用代码翻不出问题。一个后台进程莫名被杀，日志里没有异常退出，只有系统侧一条低内存记录。一条触摸事件从手指落到界面中间丢了，不知道断在驱动、输入子系统还是分发层。三种现象三套代码栈，落到内核层却共用同一条思路：找到请求穿过的那个接口，看契约怎么约定、失败形态长什么样。本篇是这本卷的地图，只告诉你每类现象该翻哪一篇。

4. 核心机制

4.1 概念与关系

入卷四个概念：

  • GKI（通用内核镜像，Generic Kernel Image）：内核二进制与配置的交付形态，决定哪些能力被编进去。
  • uapi 头：用户态与内核共享的接口声明，本卷反复出现的「唯一契约」就指它。
  • 用户态代理进程：把策略做在用户态的常驻进程，lmkd 是典型。
  • seccomp（安全计算模式，secure computing mode）：以系统调用为粒度的过滤机制。

图 1：请求从应用到内核的四条常见落点

应用/框架
  ├─ Binder 事务  -> Binder 内核驱动 -> binder.h 契约
  ├─ 内存压力     -> lmkd 策略进程
  ├─ 输入事件     -> input.h 契约 -> 输入子系统
  └─ 显示/电源/安全 -> DRM、autosuspend、SELinux

四者的关系：uapi 头管「能不能调、参数长什么样」；用户态代理管「什么时候做动作」；GKI 管「这些能力是否在场」。读任何一篇，先分清自己在看哪一层。

4.3 一个具体例子

以 Binder 为例走一遍读法。external/kernel-headers/original/uapi/linux/android/binder.h 共 640 行，是 Binder 内核驱动对用户态的唯一契约头。其 ioctl 枚举共 14 个入口，从 BINDER_WRITE_READ（:309）到 BINDER_GET_EXTENDED_ERROR（:322）。

读法三步：先在头文件里定位你要用的那个入口；再确认参数结构体里的字段边界；最后才去应用侧对号。反过来做——从应用代码猜驱动行为——就是 201 要纠正的第一类误区。驱动内部怎么实现，本树没有 kernel/common，不做核验。

7. 常见问题与误区

7.1 误区

误区一：读内核问题必须读内核 C 源码。 错。本树 kernel/ 下只有 configs、prebuilts、tests 三个仓，没有 kernel/common。本卷所有结论都建立在用户态可观测契约上，驱动实现不在核验范围。

误区二：uapi 头只是「声明」，随便看看就行。 恰好相反。binder.h 是 Binder 内核驱动对用户态的唯一契约头，640 行里 14 个 ioctl 入口就是全部对话面。参数边界、缓冲上限都从这几百行读出来。

误区三（看起来对其实是错的）：低内存杀进程的策略在内核里。 低内存策略的实际执行体是 system/memory/lmkd/lmkd.cpp，单文件 4100 余行，在用户态。内核提供压力信号，进程去或留由用户态决定。301 讲这件事。

7.2 高频提问

问：我只追一个现象，能不能不按顺序读？

答：可以，按 §4.1 的落点图对号入座就行。追 Binder 从 201 起，追进程被杀从 301 起，追触摸从 302 起。

追问：那为什么还建议 101 先读？

答：101 管「能力是否在场」。跳过它，后面可能把「配置没编进去」误诊成「机制有问题」。

问：本卷所有篇目都能在用户态核验吗？

答：是。每篇都给 uapi 头、用户态代理或内核约定的锚点，不依赖驱动 C 源码。

追问：那结论的可靠度会不会打折？

答：契约层面的结论是硬的——接口在不在、参数长什么样都可核验；驱动内部时序不做断言，避免越界。
