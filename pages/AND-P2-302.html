1. TL;DR

一次 checkPermission 从不直接等于一次权限查询。它在 uid 级短路、pid == MY_PID 直通、deniedPermissions 缓存、exported 与 owningUid 比较这些闸口上层层收敛，只有漏过所有闸口才落到 PermissionManagerService.checkUidPermission。判定结果只有两个取值：PERMISSION_GRANTED = 0、PERMISSION_DENIED = -1。系统服务内部预检走 AMS.checkPermission，服务端自保走 checkCallingPermission/enforceCallingPermission，组件访问走 checkComponentPermission，客户端自问走 ContextImpl.checkPermission，四条入口最终归到同一条 uid 级判定链。

3. 问题背景

应用里抛出一句 SecurityException: Permission Denial: ... requires android.permission.XXX，栈里只看到一个服务方法。你会以为调用方没有这个权限。可当你去 dumpsys package 查，权限明明授予了。

换个场景：同一个进程先查 checkPermission 返回 0，随后真正调用服务却抛异常。两次结果不同，因为你查的是 pid/uid 组合，服务用的是 Binder 上报的 callingPid/callingUid，中间可能还夹着 pid == MY_PID 的直通分支。

要把这些现象讲清，得先知道一次检查到底在哪几个位置可能提前返回。

4. 核心机制

4.1 概念与关系

四个关键概念：系统服务内部预检入口（AMS.checkPermission）、服务端自保入口（checkCallingPermission/enforceCallingPermission）、组件访问入口（AMS.checkComponentPermission）、客户端自问入口（ContextImpl.checkPermission）。前三个在系统服务进程内，第四个从应用进程发起。系统侧的三条入口最终收敛到 PermissionManagerService.checkUidPermission 的 uid 级判定；客户端自问那条经 permission_checker 服务，落到同一个 uid 级判定上。

4.2 关键内容

先看判定的两个取值，来自 PackageManager.java:1520/1526：

名称含义出处
PERMISSION_GRANTED = 0判定通过PackageManager.java:1520

系统服务内部入口是 ActivityManagerService.checkPermission(String permission, int pid, int uid)（ActivityManagerService.java:6946），它转到 checkPermissionForDevice（6962）。这里第一道闸口：permission == null 直接返回 PERMISSION_DENIED（6964–6966）。

服务端自保用另一个口子。checkCallingPermission（6976）自己取 Binder.getCallingPid()/getCallingUid() 再走上面的路径。enforceCallingPermission（6986）不返码，直接抛 SecurityException，消息形如 "Permission Denial: <func> from pid=…, uid=… requires <permission>"。组件场景用 AMS.checkComponentPermission（6885）：pid == MY_PID 直通（6900，位于 6 参重载 6898 内）；命中 deniedPermissions 缓存直拒（6909–6915）。

uid 级短路在 ActivityManager.checkComponentPermission（ActivityManager.java:5500）展开，按顺序：

条件结果行号
canAccessUnexportedComponents(uid)（appId 为 Process.ROOT_UID 或 Process.SYSTEM_UID）直通5503

owningUid >= 0 && UserHandle.isSameApp(uid, owningUid)直通5513

六条全部漏过才落点：AppGlobals.getPermissionManager().checkUidPermission(uid, permission, deviceId)（5558）→ PermissionManagerService.checkUidPermission（PermissionManagerService.java:247）。这里 permissionName == null 直拒（249–251）；CheckPermissionDelegate 非空时走旁路（257–264）。

客户端自问走另一条：ContextImpl.checkPermission（ContextImpl.java:2498）→ android.permission.PermissionManager.checkPermission（PermissionManager.java:1889，仅做 ROOT/SYSTEM 直通与本地 cache 短路）→ 跨进程路径经 checkPackageNamePermissionUncached（PermissionManager.java:2002）调 ActivityThread.getPermissionManager().checkPermission(...) → 服务侧 PermissionCheckerService，即 IPermissionChecker.Stub（PermissionManagerService.java:1001）。

4.3 一个具体例子

假设 uid 是普通应用 uid，permission 非 null，组件 exported=true，owningUid < 0，且不在 deniedPermissions 缓存里。路径这样走：

AMS.checkPermission（6946）只做转发 → checkPermissionForDevice（6962）先确认 permission != null（6964–6966，null 直接 PERMISSION_DENIED）→ 进入 checkComponentPermission（6898），在那里确认 caller 的 pid 不是 MY_PID（6900）→ 进入 ActivityManager.checkComponentPermission（5500）。canAccessUnexportedComponents 为假，isIsolated 为假，owningUid >= 0 不成立，exported=true 不触发 5546 直拒，permission != null 不触发 5554 直通。

走到 5558，调 checkUidPermission（247）。permissionName != null，CheckPermissionDelegate 为空，落到真正的 uid 级判定。返回 0 或 -1，一路原样上抛。任何一个前置闸口命中，都到不了这一行。

7. 常见问题与误区

7.1 误区

误区一：`checkPermission` 返回 -1 就一定没被授予权限。 错在只看落点。permission == null 会在 checkPermissionForDevice（6964–6966）直接返 PERMISSION_DENIED，此时根本没查过权限库。

误区二：`exported=false` 一定拒绝。 看起来对，其实要先看短路顺序。canAccessUnexportedComponents、isSameApp 在 5546 之前，pid == MY_PID 又在 AMS.checkComponentPermission（6900）更早生效，这些都会让 !exported 分支走不到。

误区三：客户端查的结果和服务端一致。 不一致。ContextImpl.checkPermission 走 PermissionCheckerService（1001），与 uid 级落点是两条路径，CheckPermissionDelegate 只影响后者。

7.2 高频提问

问：checkCallingPermission 和 checkPermission 有什么区别？ 答：前者自己取 Binder.getCallingPid()/getCallingUid()（6976），后者由调用方传入 pid/uid（6946）。 追问：那 enforceCallingPermission 呢？ 答：它复用调用检查但不返码，直接抛 SecurityException（6986）。

问：为什么我传的 permission 是 null 却成功？ 答：ActivityManager.checkComponentPermission 在 5554 对 permission == null 直通。 追问：那 AMS.checkPermission 里 null 为什么拒绝？ 答：那条路径在 6964–6966 先拒绝，入口不同，行为不同。
